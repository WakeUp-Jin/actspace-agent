No. 1

参考项目在做什么

你给的七个参考，排版策略其实分两个流派。它们的共性比差异更值得注意：前三屏全部交给「视觉 + 一句话定位 + 一条安装命令」，文字解释永远排在演示之后。

Kimi Code极简流
一张 GIF → 三行定义 → 一条安装命令。全文没有一个多余的 section，Docs 全部外链，README 只负责「让你跑起来」。
借用 → 最贴近你「精简干练」的口味，是 V0 的主要骨架来源。
Cherry Studio陈列流
badge 墙 + 三张大截图 + 五大类特性清单 + Roadmap + 社区。信息量大，适合已经有大量用户的成熟产品。
借用 → 截图先于特性文字出现；但 badge 墙和 Roadmap 对个人项目是噪音。
nanobot导航流
封面图 + 一段话定义 + 「Start Here」意图导航表（你想做 X → 去 Y），News 时间线展示项目活跃度。
借用 → 用一段话（而非列表）定义产品的写法；News 流维护成本太高，不学。
AFFiNE / browser-use品牌流
强视觉资产（wordmark、配图、统一色调），README 像一张海报。一句 slogan 就完成定位。
借用 → 你已有 wordmark，hero 区按海报思路拍一张「代表作」截图即可。

你说「大部分是 AI 火之前手写的，非常漂亮」——我认同，它们漂亮的根源是每一节都在回答读者的一个真实问题，而不是在展示作者写了多少东西。AI 生成的 README 常见病是对称工整但每节都半满；手写的好 README 是不对称的：该长的长（截图、特性），该短的极短（License 一行）。

No. 2

好 README 的五条规律

七秒法则
访客平均 7 秒决定去留。第一屏 = logo + 一句话 + 一张图，必须独立完成「这是什么、长什么样」的回答。任何需要滚动才能理解定位的 README 都失败了。
截图就是论点
对桌面应用而言，截图不是配图，是核心论据。「执行可视化」「上下文可控」这种卖点，一张带工具流和 context 面板的截图比三段文字更有说服力。
安装命令的字数 = 用户的信任度
Kimi Code 用一条 curl 赢得好感。你是源码构建路线，四行命令已是下限，不要再加注释和分支说明，例外情况放文档链接。
特性写差异，不写清单
「支持 Markdown 渲染」是清单；「Kairos 主动自治运行」是差异。README 只写后者，前者用户打开应用自然会发现。
个人项目的杀手锏是「人」
大厂 README 不敢写「想说的话」，这恰恰是个人项目最稀缺的差异化。你的第 7 节会是整个 README 记忆度最高的部分，值得认真打磨。
No. 3

V0 的结构与取舍

初稿按你的九节大纲落地，每节的角色和篇幅控制如下：

Hero 区wordmark + tagline + 锚点导航 + 主截图，独立完成定位核心
什么是 Actspace两段、三行以内；第二段直接亮三原则，这是全文的纲克制
核心特性7 条全部围绕差异：双模式、上下文控制、DeepSeek 适配、可视化、工具自构建、Agent 改造自己、本地优先核心
开始使用5 行命令 + 1 行打包，环境说明压缩进行内注释克制
截图2×2 网格，四张图各对应一个特性卖点核心
架构设计一行依赖图 + 设计文档链接清单，本体留在 docs/，README 只做入口克制
想说的话你的原文精修，结尾收在三件事 + 引文，居中排版制造仪式感打磨
致谢 / 许可致谢含 DeepSeek 与启发项目；许可一行克制

两个表达上的处理

「主动 / 被动」与「自构建 / 被添加」这两组对照是你独有的产品语言，我把它们直接做成了特性条目的标题句（「被动与主动，两种 Agent」「工具：被添加，也能自构建」），而不是藏在解释里——对照结构本身就有记忆点。

三原则（简约、上下文绝对控制、适配 DeepSeek）出现了两次：定义段一次、「想说的话」结尾一次（变体为 简约优雅 · 执行可视化 · 上下文可控）。两处措辞目前不一致，建议你统一成一套，全文只用一种说法。

⚠ 需要注意：「写在后面的话」那段引文
你贴的「感谢每一位用户的信任与支持……向实现 AGI 的目标不断靠近」是 DeepSeek 官方发布语，带有明显的团队/公司口吻（「我们」「AGI 目标」），照搬进个人项目会失真，也有抄录之嫌。V0 的处理是：只保留《荀子》引文「不诱于誉，不恐于诽，率道而行，端然正己」作为收尾——它本身是古文，气质相通且无归属问题；其余情绪由你自己的话承载。如果你想致敬那段话，更好的方式是在致谢里写明它来自 DeepSeek。
No. 4

截图：最重要的待办

V0 里有 5 个截图占位（1 张 hero + 4 张网格）。这是 README 成败的关键，建议按以下规范拍：

  • hero 图选「代表作」场景：一次完整的 Agent 任务——左侧会话、中间带工具执行流的消息、右侧文件 diff 同框，一张图同时证明「执行可视化 + 上下文可控」。
  • 统一窗口尺寸和主题：五张图同一分辨率（建议 1600×1000 左右窗口、2x retina 导出）、同一主题。GitHub 上浅色主题更通透，若想兼容深色页面可用 <picture> + prefers-color-scheme 出双版本。
  • 内容预演：截图里的会话标题、任务内容提前设计好，避免测试数据（「测试123」）和真实路径、API key、个人信息入镜。
  • 四张网格图各管一个卖点：Kairos 监控页（主动）、工具审批流（可视化）、Usage 缓存统计（DeepSeek 适配）、Review/文件预览（本地可追溯）。
  • 压缩后入库：PNG 过 oxipng/tinypng，单图控制在 300KB 内，统一放 docs/assets/readme/。
💡 进阶
hero 位如果换成 10–15 秒的 GIF/WebP 动图（发起任务 → 工具执行 → diff 出现），「执行可视化」的说服力会再上一个量级——这是 Kimi Code 和 browser-use 的共同选择。可以作为 V1 的目标，V0 先用静态图。
No. 5

留给你定夺的问题

问题我的建议
中文 or 双语？ 当前受众和「想说的话」的气质都是中文的，建议 V0 纯中文。等有海外用户再加 README.en.md，不要为不存在的读者写作。
tagline 定稿 V0 用了「为 DeepSeek 打造的本地 Agent 桌面工作台」。备选方向：「上下文绝对可控的本地 Agent 工作台」（卖差异）/「看得见每一步的 Agent 桌面应用」（卖可视化）。建议选一个最想被记住的点，只卖一个。
要不要 badge？ 最多三枚（License / Platform / DeepSeek Ready），或者一枚不放。个人项目阶段 badge 墙是负资产。
「工具自构建」的措辞 Lab 实验台目前是设计态、未实现。V0 的措辞（「依托 Lab 实验台」）略微超前，如果你介意，可以改成「正在通过 Lab 实验台落地」，README 不该承诺还不存在的能力。
三原则的最终措辞 「简约优雅 / 上下文的绝对控制 / 适配 DeepSeek」与「简约优雅 / 执行可视化 / 上下文可控」需要二选一并全文统一，我倾向前者（执行可视化可归入特性而非原则）。
当前 README.md 的去留 现 README 偏「仓库协作说明书」（运行边界、文档导航、仓库结构），这些对 Agent 协作有用但对访客是噪音。建议定稿后：面向访客的内容进新 README，协作向内容迁回 AGENTS.md / docs/REPO_COLLAB_GUIDE.md，避免两边重复。
