我们把**最终目标**和**第一阶段要完成的部分**分开看。

最终目标可以归纳为五项：

| 目标 | 完成后应该是什么样 |
|---|---|
| **以 Cordis 为基础，模块可独立替换** | 工具、提示词、上下文策略、Loop 等通过明确契约组合；优先解耦，再精简代码，不以包少为目标 |
| **为 Harness 自进化提供基础** | Agent 可以修改插件、验证并申请启用；同会话下一次 Run 使用新组合，当前 Run 继续使用旧组合 |
| **Agent Host 与客户端分离** | Host 拥有任务和生命周期；Desktop 可连接云端，断线不终止任务；手机 Web 前端以后单独实现 |
| **复用并理清现有职责** | Desktop、Headless 使用共同应用能力；会话、任务管理、Loop、策略各自负责自己的事情 |
| **代码、文档和目录一致清晰** | 合并重复实现，更新漂移文档，最后清理无用目录；保留必要模块边界 |

这里的“支持自进化”，本轮重点是**提供可修改、可验证、可启用、可回退的基础**。自动判断怎么改、评估改进效果等完整自进化策略，还不属于当前这份实施计划。

**第一阶段只完成前两项目标所依赖的运行基础。**

它要回答一个具体问题：

> 一个工具插件发生变化后，能否准备新组合，让新使用者采用它，同时保证旧使用者继续正常工作？

对应四块内容：

| 第一阶段内容 | 解决的问题 | 验收方式 |
|---|---|---|
| **固定运行产物** | 编辑源码会不会影响已经运行的实现？ | 修改原代码、依赖和资源文件，旧产物仍返回旧结果，新产物返回新结果 |
| **组合隔离** | 新旧插件会不会拿错服务、收到对方事件？ | 同名工具、服务和事件分别属于自己的组合，调用不串用 |
| **候选准备与选择切换** | 新组合失败，会不会把原来的可用组合弄坏？ | 候选成功才切换；失败保留旧选择；并发启用发现基线冲突 |
| **引用持有与回收** | 什么时候可以释放旧组合？ | 有使用者就保留；最后一个使用者结束后释放，不误伤新组合和共享 Host 服务 |

这四块是一条完整链路：

**生成固定产物 → 准备隔离的候选组合 → 成功后切换选择 → 旧使用者结束后回收旧组合。**

例如，把搜索工具从实现 A 改成 B：

1. 使用者甲已经持有 A。
2. 准备 B，检查它能否正常加载、依赖是否完整。
3. B 准备失败，后续使用者仍然取得 A。
4. B 准备成功并启用，使用者乙取得 B，甲继续使用 A。
5. 甲结束后，释放 A 的独占资源。

**第一阶段中的“使用者”先由测试模拟 Run 的持有行为，尚未接入真实任务流程。** 测试会使用真实文件产物和本项目实际 Cordis／Loader，不只是内存里的模拟对象。

因此，第一阶段完成后：

- 我们获得经过验证、后续能正式复用的加载与生命周期模块。
- Desktop 和 CLI 的现有默认行为保持可用。
- 还不能在产品里直接完成整套 Harness 自进化。
- 还没有完成真实 Loop 新旧共存、任务持久接纳、Desktop／Headless 迁移或远端 Host。

后续的分工是：**第二阶段把真实会话和 Run 接上这套基础；第三阶段把 Patch、审批和启用流程接成可使用的功能；第四阶段完成独立 Host 与 Desktop 远端连接；最后集中整理文档和目录。**

我认为第一阶段这个边界合适：先验证最容易影响整个架构的“实现固定、组合隔离和资源归属”，通过后再迁移真实业务，避免一边重构应用入口，一边才发现底层无法支撑新旧共存。
