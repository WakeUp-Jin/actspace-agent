# 发布记录说明

`feature-release-notes.md` 是官网更新日志的唯一事实来源，用来记录用户能够直接感知的新功能、改进和问题修复。

## 内容边界

- 公开更新只回答“这次发生了什么变化”，不复制实现路径、测试数量、内部协议和重构过程。
- 纯内部重构、未完成的实验和没有用户可见影响的维护工作不进入 release。
- 详细实现继续记录在 `docs/histories/`、设计文档和 execution plan 中。
- Release 日期不等于正式版本号、Git tag 或远程发布通道；没有真实版本号时不得伪造 `v0.x.y`。

## Markdown 格式

- 按月份使用 `## YYYY-MM` 分组，最新月份放在最上面。
- 每个日期只写一次发布，使用 `### YYYY-MM-DD — 发布标题`。
- 同月内按日期倒序排列。
- 发布内容只使用以下三个可选分类：
  - `#### 新功能`
  - `#### 改进`
  - `#### 问题修复`
- 没有内容的分类直接省略；每个已出现的分类至少包含一个无序列表项。
- 列表项可以使用 inline code、强调和安全链接，不使用嵌套列表、表格或大段实现说明。

示例：

```md
## 2026-07

### 2026-07-28 — 图片生成与更清晰的模型体验

#### 新功能

- 主 Agent 可以生成图片，并把结果保存为会话产物。

#### 改进

- 模型长时间没有返回内容时会显示运行提示。

#### 问题修复

- 修复生成图片无法在开发态预览的问题。
```

## 写作方法

1. 先检查当期 `docs/histories/YYYY-MM/` 和 Git Log，确认真实完成范围。
2. 把同一天的用户可见变化聚合成一个发布标题，不按 commit 或代码模块逐条复制。
3. 将全新能力放入“新功能”，现有体验与可靠性提升放入“改进”，可复现缺陷的修正放入“问题修复”。
4. 使用用户能观察到的结果描述变化；必要的技术名词可以保留，但不解释底层实现流水线。
5. 更新后运行站点 parser 测试、站点构建和文档检查。
