# 用 HTML 把系统设计讲清楚 — 原则与方法

这份文档回答一个问题：**怎样用一个网页，把一个软件系统的设计讲到让人真正学会？**

它不提供模板、不规定配色、不规定数据 Schema。形式完全自由——Tab、长卷滚动、泳道动画、分镜漫画、可点击的文件树，什么形式最能讲清你手上的主题，就用什么。它只约束那些**决定讲解质量的底层东西**：事实从哪来、叙事怎么搭、视觉语言怎么不骗人、读者的注意力怎么花。

> 背景：这份文档的前身是一份高度模板化的规范（固定三 Tab、固定渲染器、固定 Schema，"把创造题降为填空题"）。它能稳定产出合格品，但也把上限钉死在了模板上。这次重写把"什么不能变"和"什么随便变"彻底分开。

---

## 一、先想清楚：这个产物到底是什么

它是一篇**用 HTML 写的讲解文章**，不是一张图、不是一份 API 文档、也不是源码导览。

判断标准只有一条：**一个没读过这份源码的工程师，读完之后能不能向别人复述这个系统的设计——为什么这么设计、数据怎么流、自己想抄的话从哪下手。**

由此推出三个定位：

1. **讲解优先于展示**。每张图、每个动画都必须在回答一个明确的问题（"谁依赖谁？""这一步磁盘上发生了什么？"）。回答不了具体问题的图是装饰，删掉。
2. **读者是学习者，不是审计员**。他要的是心智模型，不是完备性。宁可深讲三个核心机制，不要平铺二十个模块。挑选本身就是讲解的一部分。
3. **HTML 是手段不是目的**。选 HTML 是因为它能做交互（渐进披露）、能做动画（表达时序）、能离线单文件交付。如果某段内容用一段文字讲得最清楚，就用文字。

## 二、五条底层原则（这些不能违反）

### 原则 1 · 事实必须有出处

任何**结构性断言**——依赖关系、字段名、时序、数字、文件路径——都必须来自源码本身：静态扫描、实际读代码、运行观察。禁止凭印象、凭文档、凭"通常都是这样"画图。

- 画依赖图之前先写脚本扫 import；写数据结构之前先翻到类型定义那一行。
- 错误的图比没有图更糟：读者会带着错误的心智模型走很远。
- 产物里标注数据来源和日期（"基于 2026-06-12 对 72 个文件的 import 扫描"），并提醒"代码变了请重新核对"。
- 展示数据结构时，**用真实字段名**。`{ from, text, timestamp, read }` 比 "消息包含发送者和内容" 的教学价值高一个数量级——读者可以拿着字段名直接去源码里搜。

### 原则 2 · 一种视觉元素 = 一种语义，全文一致

视觉语言是你和读者之间的契约，签了就不能变：

- 如果箭头表示"依赖方向"，全文所有箭头都得是依赖方向；数据流向要表达就换一种视觉元素（脉冲、泳道时序），或者分开成两张图。
- 颜色要么有固定语义（比如蓝=上游、橙=下游、绿=完成），要么不要用颜色区分。**禁止纯装饰性的彩色**。
- 每种用到的视觉约定（线型、粗细、虚实、色彩）都要有图例或在导语里说明。
- 动画只用来表达**时序和流动**这两件视觉天然擅长的事。让元素无意义地动起来的动画是噪音。

### 原则 3 · 用一个具体案例当叙事主轴

抽象机制挂在具体故事上才记得住。选**一条最有代表性的端到端链路**（一次请求、一次对话 turn、一个生命周期），从触发到结束讲完整：

- 案例要具体到有输入文本、有名字、有文件路径——"用户说『用一个团队重构 auth 模块』"远胜于"用户发起请求"。
- 每一步都讲清**此刻传递的数据是什么、它在哪里、发生了什么转换**。最好能直接展示那一刻的数据内容（JSON 片段、文件树状态）。
- 系统里最有意思的部分往往是循环、等待、协商、失败恢复——这些恰恰是静态架构图画不出来的，是动画/步进最该花力气的地方。

### 原则 4 · 渐进披露：先给骨架，细节藏在交互后面

读者的注意力是预算，首屏只花在骨架上：

- 默认状态安静（低对比、少色彩），交互之后才聚焦（高亮选中的上下游、显示详情侧栏）。
- 层次感优先于完整性：先全景（模块级），再局部（文件级），再细节（字段级）。读者自己选择走多深。
- 弱化而不隐藏：选中某个节点时，无关元素降低透明度而不是消失——保留空间感，读者知道"还有别的东西在那里"。
- 一屏只讲一个论点。讲不完就分节，不要堆。

### 原则 5 · 工程约束：单文件、零依赖、验证后交付

- 产物是**一个 HTML 文件**：纯 HTML + CSS + 原生 JS + 内联 SVG，双击可开、断网可用。不引入 d3 / mermaid / CDN 字体 / 任何网络请求。这保证它能被随手转发、长期存档。
- **交付前必须在浏览器里把每个交互都实际点一遍**。AI 生成的交互代码经常带 bug（典型：切换视图后侧栏残留旧内容、动画步进越界、点击区域偏移）。没点过不算完成。控制台必须无报错。

## 三、自由区（这些随便你）

下面这些在旧规范里都是硬性规定，现在明确归还给设计者。唯一的标准是"是否更有利于讲清当前主题"：

| 维度 | 自由度 |
|---|---|
| 页面结构 | Tab、长卷滚动叙事、分屏对照、目录跳转……任选。不必是"三个 Tab" |
| 图的种类 | 依赖图、泳道时序、状态机、文件树快照、数据结构卡片、对照表……按主题选 |
| 配色与字体 | 任何可读性好的方案。暖纸编辑风是一个被验证过的好选项，但不是要求 |
| 渲染实现 | 通用渲染器、手写 SVG、HTML+CSS 布局都行。数据与渲染分离是个好习惯（架构变更后好更新），但小图手写也没问题 |
| 内容章节 | 不必覆盖"所有模块"。按"理念 → 机制 → 案例 → 实现细节 → 可借鉴清单"组织往往比按目录结构组织好 |
| 交互形式 | 点击高亮、步进播放、hover 注释、可展开代码……为内容服务即可 |

**形式选择的判断题**（自查用）：

- 要表达"谁依赖谁" → 分层节点图，箭头单一语义
- 要表达"数据怎么流、什么顺序" → 泳道 + 步进/脉冲
- 要表达"磁盘/内存里此刻长什么样" → 文件树 + 内容快照，随步骤同步变化
- 要表达"一个东西有哪些字段、各干嘛" → 数据结构卡片 + 逐字段注释
- 要表达"几种实现方式的取舍" → 对照表
- 要表达"设计哲学" → 大字论点 + 一段正文 + 一个最小例子

## 四、工作流建议（顺序建议遵守，具体做法自由）

1. **读懂再动手**。把核心源码真读一遍，能回答"为什么这么设计"而不只是"它是什么"。讲解者比读者只多一样东西：消化过的理解。
2. **取证**。写脚本扫描依赖；摘录真实类型定义、常量（轮询间隔、路径、锁参数）；把证据留在笔记里随时回查。
3. **找到这个系统的"魂"**。每个值得讲的系统都有两三个反直觉的核心抉择（比如"不用消息队列而用文件"、"空闲不退出"）。整个讲解围绕它们组织，其余内容是支撑。
4. **选叙事主轴**（原则 3），列出步骤清单，每步标注：发生了什么、数据在哪、展示什么证据。
5. **选形式**（第三节判断题），搭页面骨架，再填内容。
6. **浏览器验证**（原则 5），逐交互点击 + 截图确认 + 控制台无报错。

## 五、反模式（见一个改一个）

- **凭印象画图**——任何没有出处的边、字段、数字。
- **箭头语义混用**——一张图里既有"依赖"箭头又有"数据流"箭头。
- **装饰性视觉**——没有语义的颜色、不表达时序的动画、为了好看的渐变。
- **首屏倾倒**——把所有节点、所有说明一次性铺满首屏，没有渐进披露。
- **平铺式完备**——二十个模块每个一段话，没有重点、没有"魂"。
- **抽象化教学**——通篇 "A 调用 B 处理数据"，没有真实名字、真实字段、真实路径。
- **伪交互**——能点但点了没增量信息；或交互坏了没发现（没验证）。
- **形式惯性**——不管讲什么主题都套同一套版式。上一份产物的形式是为上一个主题服务的。

## 六、给 Agent 的提示词（粘贴用）

```text
请为 <项目/子系统> 制作一份「讲解式」的单文件 HTML：目标是让没读过源码的工程师
读完后能复述它的设计——为什么这么设计、数据怎么流动、想借鉴的话从哪下手。

底线（必须遵守）：
1. 事实有出处：依赖关系先扫描、数据结构抄真实类型定义、数字常量回源码核对；
   页面标注数据来源与日期。禁止凭印象。
2. 视觉语义一致：一种视觉元素只表达一种含义，有图例；颜色和动画必须有语义。
3. 案例叙事：选一条最有代表性的端到端链路，具体到有输入文本和文件路径，
   每步讲清"此刻数据是什么、在哪、发生了什么转换"，最好直接展示数据内容。
   系统中的循环/等待/协商环节要重点表达。
4. 渐进披露：首屏只给骨架，细节放在点击/步进之后；无关元素弱化而非隐藏。
5. 工程约束:单 HTML、零外部依赖、离线可用;交付前在浏览器逐交互验证、
   控制台无报错。

自由（请自行设计）：页面结构、章节组织、图的种类、配色字体、渲染实现、交互形式。
先找出这个系统最核心的 2-3 个设计抉择（它的"魂"），围绕它们组织全文；
按"理念 → 核心机制 → 完整案例 → 实现细节 → 可借鉴清单"来讲，
比按目录结构平铺更好。
```
