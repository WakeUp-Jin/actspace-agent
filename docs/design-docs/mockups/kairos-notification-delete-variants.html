Kairos 通知删除 · 交互方案对比

三个方案不互斥：A 是单条删除的主交互，B 是它在展开态的补充位，C 解决批量清理。推荐 A + C 组合。

方案 A · 推荐（单条删除）

hover 行尾垃圾桶

鼠标悬停条目时右上角浮现垃圾桶图标，点击即删（无确认弹窗），列表底部出现 5 秒「已删除 · 撤销」提示。桌面端最常见的低摩擦删除模式（Gmail / macOS 通知中心同款）。图标点击不冒泡，不会误触展开。

通知
11:57:34 未读 消费记录 CSV 已分析：6/15-7/3 共 ¥4,652.70
11:21:26 消费记录分析 — 6/15~7/3 支出概要
09:02:11 检测到 3 个失败的定时任务
已删除「旧的巡检提醒」

↑ 第一条模拟 hover 态（垃圾桶悬停高亮），底部为删除后的撤销提示。

方案 B · 展开态补充

展开后显示操作区

点击条目展开正文后，底部出现「删除」小按钮。适合"读完再决定删不删"的流程，但删除必须先展开、多一步；单独使用时效率低，只作为 A 的补充位（触屏 / 无 hover 环境也可达）。

总览 | 12 笔交易，18 天跨度 - 必要支出：¥878.70（19%） - 非必要支出：¥3,774.00（81%）
11:21:26 消费记录分析 — 6/15~7/3 支出概要

↑ 展开正文后底部出现删除按钮。

方案 C · 推荐（批量清理）

头部「清理」下拉

头部「全部已读」旁增加「清理 ▾」下拉：清除已读 / 清空全部。清空全部因不可逆且影响面大，点击后按钮原地变为「确认清空？」二次确认（不弹对话框）。解决通知攒多之后一条条删的痛点。

11:21:26 消费记录分析 — 6/15~7/3 支出概要
09:02:11 检测到 3 个失败的定时任务

↑ 「清理 ▾」展开后的菜单：清除已读 / 清空全部（红色，需二次确认）。
