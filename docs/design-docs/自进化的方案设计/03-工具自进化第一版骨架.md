讨论顺序更新：先完整梳理 DSH 的运行时插件修改机制，再继续 ActSpace 方案。下文工具数量、生效时机、构建和启用流程均保留为待评估建议；尤其“下一个 Run 生效”尚未获得用户确认。新增调研已覆盖 Plugin Manager → HMR / Loader → Cordis Fiber → Agent 下一步工具组装，以及旧动态 Runner 的执行与恢复边界，见 [DSH 源码调研](../../references/dsh-self-modification-20261007.md)。

## 已确认的产品方向

- 先根据同类任务反复失败，让 Agent 主动修改工具；优先跑通简单骨架。
- 用户可以显式提出新增或修改 Harness 能力的需求，这是正式入口。
- 第一版从工具开始，执行机制与其他 Harness 组件后续扩展。
- 长期目标是形成适合不同领域的 Harness，保留演化分支，而非无限修改唯一全局版本。

此前讨论见 [架构对照](02-架构对照与讨论起点.md)，参考实现见 [DSH 源码调研](../../references/dsh-self-modification-20261007.md)。

## 核心建议

第一版做“Agent 能基于证据修改工具，并把修改持久启用”的闭环。完整的后台失败挖掘、基准评估平台与自动领域分化不作为前提。

```text
当前任务中的重复失败 ─┐
                     ├→ 修改意图和证据 → 查询工具契约 → 编写工具候选
用户显式能力需求 ─────┘                                  ↓
                                           检查与针对性试跑
                                                       ↓
                                       固定产物 → 候选 → Host 授权启用
                                                       ↓
                                         后续 Run 使用 → 验证或回退
```

这是能力闭环，不是已经具备自主优化效果保证的系统。

## 两个入口，共用一条修改链

**显式入口**：用户直接在对话中要求新增、修复或改进工具，例如“把每次手工拼的日志统计步骤做成一个工具”。无需先累计失败，也不必为第一版新增独立创建页面。

**主动入口**：Agent 在可见任务上下文中识别重复失败，说明共同原因和为什么工具修改能改善，再进入相同候选流程。第一版不建立后台扫描全部历史的服务；跨 Session 自动发现留作后续能力，不能宣称已经覆盖。

失败不等于工具应修改：网络不可用、输入有误、权限拒绝等先按原原因处理，不以改工具绕过限制。修改意图包含来源、用户目标或失败证据、目标工具、预期改善和父版本。

Agent 可以主动分析和生成候选；候选的实际启用仍经独立 Host 授权。用户提出目标不能被实现为 Agent 自填 `approved: true`。授权交互粒度仍需讨论。

## 第一版修改范围建议

| 支持方向 | 范围 |
|---|---|
| 新增工具 | 新增具体任务需要的工具，含描述、参数 schema、执行逻辑和输出 |
| 修改工具 | 为选定工具插件生成替代实现；保留旧产物，核对 schema、权限和输出兼容性 |
| 试用失败后恢复 | 放弃未启用候选，或通过已有历史组合准备回退 |
| 稳定 Host 能力 | 使用现有公开端口，不自动改 Host、凭据、权限服务或持久化 Codec |

“工具实现”不等于仓库中所有工具相关源码都可变。例如 [filesystem-read 插件](../../../packages/tools/filesystem-read/src/plugin.ts) 注册 schema 和 executor，但真正读取实现来自 `actspace.host.tools.filesystem-read`。替换 Harness behavior 可以改变参数处理、组合调用与结果加工；若需求必须改变 Host 底层能力，就超出这版热替换范围。

默认 Harness 将多个 behavior 打成同一内置产物。替换一个工具条目应使用独立候选插件身份和现有 Patch 替换槽位，不能让同一 pluginId 在同一组合中偷偷混用两版产物。一个条目可能拥有多个工具，候选必须保留未修改工具的行为与依赖服务。

## Agent 需要的最小接口

不机械照搬 DSH 的工具数量。建议提供两个模型工具入口，名称为讨论暂称：

| 入口 | 责任 |
|---|---|
| `harness_inspect` | 查询当前 digest、可修改工具与条目、公开契约、模板、源码入口和候选诊断；按需返回详情 |
| `harness_change` | 以明确 action 提交候选、查询检查结果、请求启用、丢弃或请求回退；这些操作仍有各自权限边界 |

编写代码继续使用已有文件工具。Host 侧负责根据已批准的格式构建/收集产物、固定身份并调用 `harness-control`；第一版限制为本地工具插件模板与允许的现有依赖，不做任意 npm 安装平台。

需要随应用提供可读契约与最小模板，不能假定安装版用户拥有 ActSpace 源码仓库。现有 [内置构建脚本](../../../packages/runtime/scripts/build-default-harness.mjs) 只处理明确的内置闭包，不是现成的通用候选打包器；开发期和安装版使用的构建方式需在实施计划前确定。

## 生效时机：推荐下一个 Run

ActSpace 已有 Run 固定租约。建议本轮完成修改和启用后，由下一次 Run 获取新版本；原 Run 不原位更换工具树。界面和回执必须明确“已启用，后续 Run 生效”，不能让 Agent 紧接着在旧 Run 调用新工具并误报成功。

如需要自动验证，可设计为原 Run 结束后发起新的验证 Run。第一版是否自动续跑尚未确认；最小路径允许用户下一条消息使用新工具。DSH 的同会话即时使用体验不能直接等同于 ActSpace 的同 Run 热切换。

## 验证与版本记录

第一版建议至少检查：语法/类型或构建结果、manifest 与依赖兼容、注册与释放、目标失败案例或用户要求的样例、相邻成功案例回归。新增工具没有旧实现时按需求断言验证；替换工具则比较基线与候选，不能只看加载成功。

检查由 Host 控制，候选不得自行伪造成绩。Agent 提供的样例可用于复现，但不等同于独立评估集。检查通过可支持人工启用，不能据此声称普遍能力提升。评估记录与候选内容身份绑定；修改候选后需重新检查。

记录至少包含来源、目标、证据引用、父版本、源文件快照、产物 digest、修改摘要、检查结果、启用决定。保留版本身份和父子关系，为后续领域谱系提供基础；第一版不创建角色、记忆归属或多智能体协作产品实体。

最小验收闭环：显式请求新增工具 → 后续 Run 可调用 → 再修改同一工具 → 重启可恢复 → 回退旧版本；另以重复失败场景验证 Agent 主动生成修改意图，并验证错误候选不改变当前选择。

## 必须在实施前收敛的边界

- **生效时机**：是否接受下一个 Run 生效，以及验证是否自动续跑。
- **授权**：一次候选启用如何展示变更、取得可信决定并绑定 digest；不能只接测试用 allow authorizer。
- **代码执行边界**：同进程插件与独立工作目录均不构成安全隔离；候选检查、初始化和执行的权限需明确。若首版采用受信代码授权模式，就必须如实描述，不能标成恶意代码沙箱。
- **可编辑样板**：选定一个真实工具案例，验证执行逻辑可在 Harness 边界内完成；确定安装版契约、模板和构建依赖交付方式。

以上是方向讨论，不是留有空项的已批准执行计划。当前未新增工具、服务或授权产品入口。
