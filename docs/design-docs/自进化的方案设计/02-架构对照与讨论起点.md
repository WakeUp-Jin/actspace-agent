## 当前基础

本轮仅检查文档与源码，未运行测试或进行界面验收。

| 已有基础 | 证据与边界 |
|---|---|
| Host 与 Harness 职责拆分 | [架构总览](../../ARCHITECTURE.md)；Host 保持稳定，Harness 通过组合与选择接入执行 |
| 固定产物与 Patch 准备候选 | [HarnessControl](../../../packages/harness-control/src/service.ts)中的 `prepare` 检查 revision、digest、产物和兼容性；这是可装配检查，不是效果评估 |
| 独立 Host 授权启用 | `activate` 未配置 authorizer 时拒绝；授权后重验基线并持久记录选择 |
| 历史版本回退 | `prepareRollback` 从历史完整组合准备候选，仍须经过启用流程 |
| Run 固定租约 | [P3 契约](../../exec-plans/completed/20261003-agent-harness-host-refactor/phase-3.md)明确新选择用于后续租约，旧 Run 不被中途替换 |
| 尚缺自进化闭环 | P3 明确不包括源码修改工作流、通用打包、效果评估、自动优化、自动回退及自进化审批产品入口 |

可以复用候选与启用底座，但不能把兼容检查当成效果评估。同进程插件不构成安全沙箱；候选准备可能执行插件初始化，“未启用”不等于“不会执行代码”。

## 建议的概念边界

- **Harness 版本**：固定的插件实现、配置和组合，追踪父版本与产物身份。
- **进化提案**：针对证据提出修改假设，说明预期改善、可能损害和适用任务范围。
- **实验**：基线与候选在固定模型配置、数据和环境条件下比较。
- **启用选择**：真实任务使用哪个版本，由可信 Host 控制。

这些概念不意味着立即新增四个服务或四个页面。长期记忆内容可影响实验，但其快照不能仅靠 Harness 代码版本来代表。

## 推荐方向：保留基线，在候选上实验

```text
任务证据 → 提案与预测 → 隔离构建候选 → 隔离对比评估
                                          ↓
                                  可追溯评估报告
                                          ↓
                              Host 授权并选择版本
                                          ↓
                              后续任务反馈 / 回退提案
```

异步评估不必阻塞用户继续使用稳定版本。候选能否提前进入真实任务，是另一个决策。建议默认后台评估后再改变日常选择；如果希望立即体验，可讨论明确授权的试用范围。该建议尚未获用户确认。

第一版方向已收敛为工具修改，支持用户主动发起以及 Agent 根据同类任务反复失败发起。先不加入周期调度、自动分化与自动晋级，证明闭环有价值。上下文策略和 Loop 留作后续扩展。

工作量主要在候选构建与隔离、可靠评估和证据追踪；现有控制服务可减少启用与回退部分的重复建设。首个对象和隔离等级未定，不作工期承诺。

## 如何证明“更好”

建议区分三类材料：目标失败案例检查原问题；已有成功案例检查退化；独立保留案例检查未见任务表现。保留案例由评估侧管理，限制候选生成者接触答案和评分细节。

分别记录质量、成本、耗时、稳定性和权限违规，避免单个总分掩盖退化。二十余条案例可以启动局部实验，但不足以自动推断全局提升。接受门槛与重复次数需按任务、预算和实测波动确定。

实验记录至少关联父版本、候选 digest、修改理由与预测、证据引用、模型及参数、数据集与评估器版本、环境快照、结果、资源消耗和接受或拒绝理由。证据可能包含敏感内容，只携带必要信息。

最脆弱的假设是：真实使用中能提取有判别力的评估案例。如果不成立，系统只能证明“可运行”，无法证明“更好”；此时保留人工审阅和试用结论，不自动晋级。

## 可信边界与回退限制

候选生成者可以修改授权范围内的 Harness，但不能改写该次实验的评分规则、保留集答案、最终成绩或启用授权。将评估器放到另一个目录、package 或进程不足以证明隔离，需结合文件访问、凭据、网络与执行权限设计。

Agent 可以建议新案例，但纳入案例和评分规则应经过独立审阅并形成新版本。候选应先隔离构建和执行，不能先加载进日常 Host 再检查可信性。

评估沙箱限制外部副作用；真实使用阶段的版本回退主要影响后续 Run，不会自动撤销已经发生的外部操作。首个闭环宜避免共享状态迁移，否则需另行设计数据恢复协议。

评估失败、超时或服务不可用时，候选保留为未验证或失败，稳定选择继续服务。评估完成时若基线改变，不能直接把旧报告与旧授权用于新基线。

## 建议的讨论顺序

1. 首要收益：解决同类任务反复失败、提升特定模型表现，还是形成长期领域专用版本？
2. 首个对象：工具实现、上下文策略或 Loop，哪一个有真实案例支撑？
3. 生效时机：后台评估后启用，还是允许限定范围先试用？
4. 评估与权限：谁提出候选、管理测试材料、批准启用，预算如何限制？
5. 版本与实体：先定义谱系、适用范围和状态归属，后续再接多智能体产品形态。

第 1、2 项已由 2026-10-07 用户反馈收敛：先解决反复失败，从工具开始，长期目标为领域专用版本；同时必须支持用户显式需求。其余设计继续讨论。当前只维护设计文档，不新增运行时代码、配置、命令、服务或产品入口。
