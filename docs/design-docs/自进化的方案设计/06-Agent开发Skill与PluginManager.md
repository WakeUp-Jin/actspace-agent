# Agent 开发 Skill 与 Plugin Manager

日期：2026-10-07。状态：保留接口职责设计，V1 实际 API 见 [10](10-V1实现与使用说明.md)；总体决策见 [05](05-总体架构与DSH借鉴边界.md)。

## 1. Skill 告诉 Agent 怎样开发

随安装包交付一份插件开发 Skill 及引用材料，名称为 `actspace-plugin-development`，已在 `packages/official-skills` 创建。下列清单保留总体职责；首版单文件工具契约见 10。

Skill 必须提供：

- 新增、修改、验证、请求应用、失败修复的标准顺序。
- ActSpace 插件 manifest、behavior 入口、工具 schema / output / permission 的最小可运行样板。
- 服务注入、Scope、注册 handle、ctx.effect 与异步资源清理示例。
- 固定产物、Patch replace/insert、会话局部选择的解释；不引导修改 artifact store、Profile 真值或授权记录。
- 当前支持的公开 Host 能力与不可修改范围的阅读入口。
- 按功能断言验证，不能把“构建通过”或“实例创建成功”当成效果提升。

V1 仅在用户明确提出新增或修改能力时进入开发流程。任务失败可以作为诊断材料，但不自动启动自进化；失败数据自动触发及评估门禁属于 V2，见 [09](09-交付阶段与验收边界.md)。

技能内容、模板和类型契约随 Host 版本发布。安装版无需本地源码 checkout；模板携带契约版本，发现不匹配时查询当前接口，不凭旧示例继续生成代码。

### 1.1 现有 Skill 能力与实际缺口

当前并非完全没有管理模块，也不要求所有 Skill 都手动安装：

- [discovery](../../../packages/prompt/src/skills/discovery.ts) 自动扫描项目的 `.actspace/skills`、`.agents/skills`、`.claude/skills`，以及用户数据和 home 下的约定目录；已有目录中的合法 Skill 可直接被发现。
- [桌面管理实现](../../../apps/desktop/src/main/runtime-v2/fixed-renderer-skills.ts) 支持列出、将本地所选目录复制到用户 Skill 目录、卸载受管目录。[Skills 界面](../../../apps/desktop/src/renderer/components/extensions/SkillsSection.tsx) 已提供安装及启停入口。
- 原默认扫描链缺少官方随包资源；本轮已通过 `@actspace/official-skills` 与 [Host prompt source](../../../packages/prompt/src/host-context.ts) 补齐。

因此新增的是官方内容模块与来源接线，发现、目录展示、正文读取和启停继续扩展已有模块。

### 1.2 官方 Skill 集合的推荐交付方式

已新增资源 package `@actspace/official-skills`，集中维护官方精选 Skill、引用材料和资源清单。它没有常驻任务，不要求成为第三个 Cordis 服务插件。若以后 Profile 需要按插件选装内容，只加薄的资源来源适配，不复制加载器。

| 部分 | V1 设计 |
|---|---|
| 内容 | 首个默认 Skill 为 `actspace-plugin-development`；同一集合可以加入用户挑选的官方 Skill，首版无需填满目录 |
| 交付 | 随应用构建发布只读资源和兼容版本清单；Host 解析实际资源路径，开发态、安装版和支持该功能的 CLI 共用相同内容 |
| 发现 | 扩展现有发现参数接受官方资源根；保留原有项目/用户来源优先级，官方作为默认补充来源，不复制覆盖用户安装目录 |
| 正文加载 | 默认可用指进入 catalog，正文仍按需读取或明确选择加载；不把全部官方 Skill 长文常驻注入每轮 prompt |
| UI 与启停 | 扩展原 Skills 列表显示官方来源、版本和遮蔽状态；可禁用，不允许当作用户目录删除；运行目录与 UI 使用一致的身份和优先级 |
| 更新 | 官方内容随应用版本更新；自定义修改先复制为用户 Skill，保留来源；已有用户内容不被升级覆盖 |
| 未来来源 | Actor 或其他扩展若携带 Skill，可接入同一来源机制；V1 不实现 Actor 安装器或在线市场 |

原运行 catalog 按 `id` 去重、桌面列表按 `name` 判断遮蔽；本轮已统一为 `id`，避免界面显示与模型实际读取的内容不一致。官方采用稳定的 `actspace-` 前缀，同 ID 被覆盖时明确显示实际来源，不能把用户副本标为官方原文。开发契约始终由 inspect/Manager 校验，Skill 文本不拥有授权能力。

默认启用沿用已有启停设置，不新增平行的官方开关系统；加载官方文件只授予所需的只读资源访问，不扩大普通文件工具的写权限。V1 验收必须包含无项目源码 checkout 的安装版读取正文、引用材料、模板和类型资源。

## 2. inspect 回答“当前有哪些准确接口”

建议提供一个只读模型工具 `harness_inspect`，按查询类别渐进返回。方法名为设计名，实施时遵循现有工具命名和 schema 规范。

| 查询对象 | 必要结果 |
|---|---|
| 当前选择 | sessionId 对应的绑定 revision、Harness 引用、当前 Run 的确定 digest；区分已选择和该 Run 实际使用 |
| 插件条目 | entryId、pluginId、manifestEntryId、artifactId、启停状态、提供/依赖的服务、可编辑原因或限制 |
| 工具 | 当前 Scope 可见的工具定义、参数与输出契约、权限声明、归属条目；不返回密钥和任意闭包源码 |
| 服务与事件 | 允许扩展访问的服务方法/类型、事件契约；不是通用 RPC 调用器 |
| 配置 | 指定条目的配置 schema 和可展示配置，敏感内容脱敏 |
| 开发资源 | 与确定版本对应的源码快照引用、模板与类型版本、构建能力；大文件使用引用并按需读取 |
| 变更状态 | 工作区、候选、检查、运行应用和验证的准确状态与诊断 |

工具 schema 从现有 ToolRuntime 获取，条目和版本从组合与 Control 获取。契约目录缺失的信息应明确返回不可用，不能让模型猜 API。只读查询需遵循 Scope 和数据访问边界，但不复用写操作的启用授权。该查询入口不形成第二套工具注册表。

## 3. Plugin Manager 的工具面与服务面

建议模型侧工具名 `plugin_manager`。工具仅解析请求、提供结构化回执并调用 Host 管理服务。所有可信身份、版本摘要、调用会话和权限从运行上下文取得，不能信任模型自报的授权或其他会话身份。

| 操作语义 | 输入重点 | 成功意味着什么 |
|---|---|---|
| 创建开发工作区 | 新增模板，或明确的基线版本与目标条目 | 返回受管工作区和原始来源；未改变运行版本 |
| 构建并检查 | workspaceId、预期源码摘要、验证样例引用 | 从固定源码快照构建，返回产物身份和各项检查结果 |
| 准备候选 | artifactIds、基线 digest/revision、目标条目 | Control 准备了可诊断候选；不代表用户已选用，也可能执行初始化 |
| 请求应用 | candidateId、目标会话绑定版本、changeId | 区分 queued、选择已提交、会话绑定完成；绑定完成后可供下一条用户消息使用，当前 Run 仍用旧版本 |
| 查询状态 | workspaceId / candidateId / changeId | 返回管理与运行时各阶段结果 |
| 丢弃 | 未启用候选或工作区标识 | 释放候选实例；不删除正在被会话或历史引用的产物 |
| 请求回退 | 明确历史版本、当前基线 | 重新验证并走相同授权、切换路径，不直接覆盖选择文件 |

工具可呈现逻辑独立的 actions，但不要以一个 action 绕过另一个 action 的权限。提交操作幂等：V1 的 apply 使用 Manager 持久化的 changeId；相同标识指向不同候选拒绝。create 每次创建独立工作区，build 每次固定当前源码，见 10。候选内容变动后重新检查、准备与授权。

Agent 使用原有文件工具编辑工作区；Manager 不生成业务代码。Manager 调用构建/产物发布能力，不让 HMR 安装依赖。首版使用本地模板与允许的依赖闭包，不自动执行未知包的安装脚本。

## 4. V1 用户需求进入开发路径

```text
用户在 Agent 模式明确提出新增或修改需求
  → Skill 指导 + inspect 查询
  → Manager 创建工作区
  → 已有文件工具编辑
  → Manager 固定源码、构建、检查、准备候选
  → HMR 接纳切换请求
  → Host 授权、提交局部选择与会话绑定
  → 当前 Run 仍用旧版本完成本次回复
  → 用户下一条消息的新 Run 获取新版本
```

源码修改不触发自动应用。即使编辑器产生很多次保存，也只有明确提交的源码快照参与构建。Manager 的回执应分别给出 build、prepare、selection、runtime、verification 的状态，不能用一个 `success: true` 混淆它们。

若未来提供创造模式，它复用此路径；V1 不增加自动续跑工具或任务。V2 在生产候选后、提交会话选择前插入独立评估门禁，不能只加一个失败监听后立即启用候选。

## 5. 执行权限与模板约束

版本目录、工作区和 Cordis Scope 都不是恶意代码沙箱。现有 Control 明确只接纳可信产物；候选准备会运行插件初始化，不能等到 activate 才第一次考虑代码执行许可。

推荐首版采用受信模板与 Host 授权的执行模式：静态检查后，执行构建脚本/初始化/试跑所需许可由 Host 策略判断；准入与最终启用分别有依据。已有授权可在其范围内复用，不要求每个步骤机械弹窗，Agent 不能自填 `approved: true`。

新工具继续经过正常权限与执行链；插件注册必须托管资源，初始化只注册能力，不启动共享独占任务。模板不以模块级可变全局变量存放会话状态。生成代码不能修改管理服务、Host 策略或该次检查结果。

## 6. 交付依赖

完整交付物包括 Skill、可读契约、模板源码、构建入口、版本对应关系和诊断说明。现有 [默认 Harness 构建脚本](../../../packages/runtime/scripts/build-default-harness.mjs) 处理内置闭包，不等于已具备任意工具候选构建服务。最终产物继续满足 [固定产物规则](../../../packages/cordis-adapter/src/plugin-artifact.ts)，不能把 DSH 的 package.json 模板原样作为 ActSpace 产物。

实施前应以一个可编辑工具模板跑通安装版构建，确认运行时、打包器与类型资源的分发方式。该工作无需新的云账号或第三方密钥；真实模型体验验证使用现有配置，测试不得记录凭据。
