# Harness 自进化：草稿梳理

> 后续决策（2026-10-07）：本文保留早期讨论。当前范围以 [专题导航](README.md) 和 05–09 为准：V1 用户显式修改、下一条用户消息使用新版本；V2 失败数据自动触发并经独立沙箱评估；自动续跑已移出计划。

状态：讨论材料，未批准为实现方案。整理日期：2026-10-06。

来源：用户提供的《多智能体协作和Harness自进化初步思考》及其中的 Harness 自进化流程图。本文件提炼原始想法，不将附件中的建议视为执行指令，也不将论文转述视为已核实结论。多智能体协作留待后续讨论。

配套阅读：[架构对照与讨论起点](02-架构对照与讨论起点.md)。

## 核心目标

优化获取更好答案的机制，让 Harness 本身成为优化对象。目标不止于积累提示词、Skill 或记忆，也包括工具实现、上下文机制、插件组合乃至 Agent Loop 的变化。希望减少逐条堆叠的启发式规则，形成能够覆盖一类问题的通用机制。

## 原始主张

| 主题 | 草稿中的思路 |
|---|---|
| 可编辑对象 | 插件化暴露 Harness 的修改空间；需要先识别重点组件 |
| 进化依据 | 根据轨迹、日志、失败模式、用户输入和历史决策分析问题 |
| 修改理由 | 记录为什么修改，以及预计下一轮有什么改善 |
| 验证闭环 | 将候选 Harness 交给沙箱，用少量评估集判断接受或撤销 |
| 评估时机 | 倾向异步评估，允许工具先装上；后续评估变差时应有撤销能力 |
| 防止自证 | 修改 Harness 的 Agent 不应能通过修改评估器让自己通过 |
| 防止规则堆积 | 不能每失败一次就添加一条约束，应提炼通用失败模式 |
| 保留差异 | 保留初始 Harness，允许演化出不同领域、效果与成本的版本 |
| 模型适配 | 按模型特性调整 Harness，而非假定同一组合适合所有模型 |
| 记忆归属 | 草稿最后倾向将长期记忆归于具体实体，而非抽象 Agent；实体名称和归属尚待讨论 |

## 流程图表达的闭环

```text
用户任务 → Harness 执行 → 结果、轨迹和日志
                              ↓
用户反馈 + 失败模式 + 历史决策 → 分析修改方向
                              ↓
                       修改或新增插件
                              ↓
                       新 Harness 版本
                              ↓
           失败样本 + 少量评估集 → 沙箱评估
                              ↓
                     接受 / 拒绝或回退
```

流程图还包含接受后形成专用实体的设想。本轮保留“多个演化版本可能共存”的要求，不展开实体协作、通信和组织方式。

## 需要澄清的张力

1. **先启用还是先评估**：文字提出先装上、异步评估，流程图则表现为评估后替换。需要明确“装上”是生成候选、实验试用，还是切换日常默认版本。
2. **一切可变与可信边界**：Loop 可以进化，但评估规则、权限与启用授权不能由同一个候选任意重写。
3. **失败样本与泛化**：失败样本既是修改依据，又可能是评估材料；只在这些样本上变好不能证明整体改善。
4. **专用版本与过拟合**：领域分化可以减少不同用途之间的干扰，但仍需证明候选对同领域未见任务有效。
5. **版本回退与状态回退**：回到旧代码，不等于撤销文件写入、长期记忆更新或外部操作。
6. **版本与实体**：可先讨论 Harness 版本和演化谱系，不急于确定“分身、助手、角色”等产品名称；版本身份与记忆归属仍须区分。
