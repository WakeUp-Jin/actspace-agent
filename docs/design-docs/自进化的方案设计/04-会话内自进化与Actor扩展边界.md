# 会话内自进化与 Actor 扩展边界

> 后续决策（2026-10-07）：本文保留早期讨论。当前范围以 [专题导航](README.md) 和 05–09 为准：V1 用户显式修改、下一条用户消息使用新版本；V2 失败数据自动触发并经独立沙箱评估；自动续跑已移出计划。

日期：2026-10-07。状态：结合用户最新产品方向和当前源码形成的建议稿，尚未批准实施。本文更新 [第一版骨架](03-工具自进化第一版骨架.md) 的作用域与生效体验讨论；不是执行计划。

## 用户已经明确的方向

- 首先支持工具新增与修改，既接受用户显式需求，也接受 Agent 根据同类任务反复失败提出改进。
- 希望在 Agent 模式直接提出需求，修改后就在当前会话使用，不让用户手动中断自进化过程。
- 创造模式可以是聚焦能力设计的入口；如果完整体验过于复杂，可以先实现这个入口。
- 默认成果只属于当前会话；不转换为 Actor 也能够使用。
- 未来可将成果转为 Actor，在新会话和多智能体协作中复用。Actor 本轮不实现，由其他工作负责，这里只提供清晰扩展边界。
- 旧 DynamicCordisRunner 不再作为方案候选；保留在外部调研中仅供理解历史。

产品语义依据：[ActSpace 产品概念思路初稿](../ActSpace产品概念思路初稿.md)。该文档中的 Actor 有场景、身份、能力和记忆，可以拥有多段对话。本轮只处理可交付给 Actor 的能力版本，不能把 Harness 版本直接当作完整 Actor。

## 推荐：Agent 模式直接发起，同会话自动衔接 Run

可以实现用户期待的连续体验。应区分三个边界：同一个 Session、用户感知的一次工作过程、内部一个固定 Harness 的 Run。用户无需切模式、另开会话或补一句“继续”，内部也不必在正在执行的函数栈上换代码。

建议默认流程：

```text
用户需求 / 重复失败证据
          ↓
当前会话中编写工具 → 构建固定产物 → 检查并准备候选
          ↓
Host 记录应用与续跑意图，按该会话的授权策略处理
          ↓
本轮全部工具调用及结果落盘 → 到达切换点 → 原 Run 结束并排空
          ↓
更新当前会话的 Harness 选择 → 新 Run 读取相同 Session 历史
          ↓
新工具完成针对性验证 → 继续尚未完成的原任务
```

切换可以有短暂等待，但无需用户操作。界面显示“正在应用能力 / 验证能力”，而不是中间弹出“任务完成”后等待新输入。内部 Run 与版本变化仍保留在 Trace 中。

当前机制约束一个 Run 的租约固定；推荐方案保留这个约束。真正的“同 Run 下一步原位换插件”会改变该契约，首版不推荐。若未来证明 Run 重建成本或持续状态迁移不可接受，再评估专门的步骤级切换协议。

## 创造模式解决交互聚焦，不自动降低运行时复杂度

| 体验 | 相对成本与取舍 |
|---|---|
| 创造模式构建，完成后用户下一条消息使用 | 最小可用选项；省掉自动续跑及其任务衔接，但仍必须实现局部选择、构建、验证、授权、恢复 |
| Agent 模式发起，完成后用户下一条消息使用 | 与上一项共享引擎；模式本身不是主要复杂度来源 |
| Agent 模式发起，同会话自动续跑 | 推荐产品目标；增加受控交接、队列/取消协调、崩溃恢复与连续 UI 投影，属于中等偏大的跨模块改动 |
| 同 Run 原位修改插件树 | 较高复杂度；涉及租约身份、工具请求快照、在途调用、依赖服务、状态迁移和回退，改变现有执行契约 |

因此首选在 Agent 模式开放能力，创造模式可后续作为相同引擎的专注入口。如果需要缩小首版，优先减少自动续跑范围，而不是以新增模式代替缺失的运行时机制。

当前模式契约只有 `chat / plan / agent`。若新增真正的 `create` 模式，需要同步共享协议、Journal、提示词/工具策略、Host 与 UI；不能把它当成仅增加一个按钮。也可先用 Agent 模式内的能力设计工作流验证价值。

## 会话局部选择与可复用版本

建议把“代码内容”“谁选用它”“未来属于哪个 Actor”分开：

| 概念 | 责任与保存内容 |
|---|---|
| Harness 版本 | 确定的 composition、artifactIds、executionDigest、兼容契约；版本来源另记父版本和修改证据 |
| 会话绑定 | 当前 sessionId 选择的 Harness 分支与绑定 revision；新 Run 在准入时确定版本 |
| 演化记录 | 来源需求/失败证据、源码快照或可恢复引用、检查结果、基线与目标版本、启用和交接状态 |
| Actor（未来） | 持久身份、场景、能力版本选择和记忆归属；消费上述版本接口，不进入本轮引擎 |

未发生局部修改的会话可沿用既有默认选择。首次修改时从当前 Run 的确定基线派生会话局部分支，成功应用后绑定到该分支；其他会话和默认 main 不变。未变代码产物可共享，运行时可变状态应由插件实例或会话 Scope 持有。

绑定必须持久化，恢复当前会话时继续选择已启用版本。“局部”表示使用范围，不表示仅保存在内存。第一版不自动跟随 main 后续变更，也不把局部成果自动推向其他会话。

当前同一 artifact 的模块级全局变量会跨实例共享，已有测试明确展示这一事实。工具模板应禁止用模块级可变变量承载会话私有状态，外部资源按会话或实例划分；否则即使选择不同，也不能宣称行为和状态完全隔离。

## 自动交接需要解决的工程问题

建议由 Host 调度侧拥有交接记录和提交次序，Agent 只提出候选、目标与续跑意图。避免在修改工具的执行函数里同步等待销毁自己所在的 Run；工具只登记请求并返回，Loop 在全部工具结果已记录的步骤边界让出执行权。

交接状态至少区分“候选就绪、应用待定、版本已选用、续跑已接纳、验证结果”，并以唯一 changeId 关联源任务、源 Run、基线和目标 digest。这些是设计语义，具体事件 Schema 在实施计划中确定。

必须处理：

- **安全切换点**：当前模型请求、并行工具批次和结果落盘完成后才交接；等待旧 Run 的工作停止，不在工具函数内部 dispose 自身。
- **实例与资源**：新 generation 准备时可能与旧 generation 共存；首版工具插件初始化只注册能力，不自动启动共享独占后台业务。不承诺迁移任意内存状态。
- **选择一致性**：会话绑定和 Harness 选择有不同的持久化位置。使用可恢复意图、幂等提交和准入闸门；不能声称跨文件天然原子。版本已提交而续跑未接纳时，恢复同一交接，不重复创建工作。
- **固定目标**：续跑必须核对预期绑定 revision / executionDigest，不能因为后来又有更新而静默使用第三个版本。
- **正常交接**：扩展正常交接的任务状态或关系，保留旧失败重试语义。系统续跑带可信来源，不伪造用户再次发言，不向模型重复整段原始需求并重做已完成的外部操作。
- **新输入与停止**：等待交接期间的新消息交由 Session 调度排序，不再吸收到即将结束的旧 Run；用户停止要阻止自动续跑，不能因换 Run 逃逸停止请求。
- **预算**：整次演化与续跑沿用总预算/截止时间，并限制自动修复次数，不能每次新 Run 都重新获取无限预算。
- **失败**：构建/准备失败保留原绑定；新版本验证失败时记录实际结果，可在相同授权范围内请求回退后重试；已提交版本、清理失败和任务失败分别报告。不得回滚已完成的外部业务操作。
- **清理**：旧 generation 无引用时释放；清理失败可诊断，不误报成功。结束或删除局部会话后的实例回收需补齐；固定产物与模块缓存不承诺即时卸载。

Host 授权仍绑定具体候选和 digest。Agent 模式可以自动推进已获授权范围内的操作；“创造模式”本身不等于权限升级。检查、准备和运行任意代码的执行边界仍须在实施前确定，第一版受信工具模板可缩小范围，但不是恶意代码沙箱。

## HMR 的借鉴范围

DSH 的 HMR 同时承担更新串行协调、配置监听/重组触发、受支持源码模块的缓存替换，并调用 Cordis 生命周期完成重新挂载。插件业务执行与资源释放归 Cordis，代码编写与效果判断归其他流程。

ActSpace 借用“准备 → 应用 → 生命周期收尾 → 后续模型可见”的链路。新代码已有不同 artifactId 路径，ESM 自然获得新模块身份；首版可加载新 generation 后切换会话选择，无需引入 Node 内部缓存清除或文件监听服务。实例释放不会清掉 ESM 缓存，长时间高频生成版本的内存占用属于后续需实测的限制。

本方案替换的物理单位是一个 Harness generation；产品第一版允许修改的逻辑范围仍限于工具。这样复用现有固定组合与租约机制，代价是重建一棵 Harness 子树，需测量准备和交接开销。不能描述为已经具备 DSH 那种逐条目的就地代码 HMR。

## Actor 扩展：可复用，不等于覆盖全局默认

将当前成果转为 Actor，建议理解为“获得可在新会话选择的持久身份”，不是覆盖所有会话的 main Harness。Actor 能力版本可被多个会话引用，每段对话仍有自己的 Session。

本轮准备的交付边界：

- 返回确定的 Harness 版本描述，包含组合、完整产物引用、Host 兼容约束和父版本来源；不能只导出依赖当前临时目录的 Patch。
- 版本引用与会话绑定解耦，使未来 Actor 模块可保留并选用已验证的能力版本。不能把 sessionId 永久写入能力本身。
- 为持久消费者保留产物引用/保留机制，防止会话删除导致未来 Actor 依赖的产物被回收；首版不实现自动产物 GC。
- 由将来的 Actor 模块建立身份、场景与记忆，并决定转化后原会话如何归属、新会话如何绑定；当前不新增 Actor 名册、数据库或协作逻辑。
- 不自动将整个 Session 历史、凭据、绝对工作区路径或临时权限纳入可复用版本。长期记忆如何归属由 Actor 方案决定。

产品稿中的“Actor 不能复制”指个体身份。复用固定代码产物、保留版本历史不等于复制 Actor；本轮不提供复制 Actor 的操作。

## 分段交付建议与验收依据

最小闭环：在 Agent 模式按显式需求构建工具，应用到当前会话局部分支，用户下一条消息可以调用；支持重启恢复与回退。这一段独立可用，既不依赖创造模式，也不依赖 Actor。

推荐完整体验在此之上增加：步骤边界交接、自动新 Run、针对性验证和原任务续跑；当前会话保持连续状态。之后再接入重复失败触发，复用同一修改与交接链。主动入口仍属于既定目标，不因分段交付取消。

验收需要覆盖：

1. A 会话新增/修改工具，A 能使用，B 与 main 不变；恢复 A 后版本一致。
2. 新产物代码实际被执行，Trace 中版本与 digest 正确；旧调用不混用新定义。
3. 自动切换不用用户补发消息，保留历史，原任务只继续未完成部分；系统交接不伪造成失败。
4. 并行工具、暂停/停止、插入新消息、总预算耗尽时交接行为确定。
5. 构建失败、激活失败、验证失败、旧资源清理失败分别有证据和恢复行为。
6. 在交接各持久化阶段中断并恢复，不重复启用、不重复续跑、不静默切到第三版。
7. 工具注册、事件、定时器和运行工作正确释放；模块全局变量与共享文件不会泄漏会话私有状态。
8. 版本描述完整、可由新会话绑定使用；不依赖 Actor 功能即可验证扩展契约。

这会涉及构建/产物、HarnessControl、Session 调度与持久化、Loop 边界、Host 接线、共享协议及前端状态，预计超过 8 个源码文件，不应包装成两个工具的小改动。具体 API、事件兼容和文件清单需要在方向确认后收敛成执行计划。
