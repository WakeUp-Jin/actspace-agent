## 1. 从官方 Projects 提炼出的模型

去掉云端特性后，这套设计真正承重的只有四个概念，其余都是它们的展开：

1. **一个常驻会话负责"派活"，而不是负责"干活"。** 项目会话不自己改代码，它把请求翻译成线程、追踪线程状态、汇总结果。用户在这里是「交代事情」，不是「写 prompt」。
2. **一个线程 = 一个独立上下文 + 一个独立分支。** 这是整件事的前提：只有上下文和分支都隔离，并行才成立；代价是它们互相看不见，重叠改动只能在合入时才暴露成冲突。
3. **状态显性化是可用性的全部。** 用户真正要回答的问题只有一个——「哪些线程现在需要我」。官方把它做成了概览面板的分组标题（待你处理 / 待审查 / 进行中 / 落地中 / 空闲 / 已解决）。
4. **项目级的长期记忆替代重复交代。** 指令（人写，每个线程都读）+ 记忆（模型自己记）把「为什么要这么做」沉淀下来，跨线程复用。

有一点值得单独拎出来：**官方项目会话里最抢眼的视觉元素不是消息气泡，而是随时间堆叠成层叠卡片的线程卡**。它用空间密度直接表达「一个项目跑了一周、开了很多线程」，这比任何状态列表都更好读。我们的概览面板应该保留这个表达能力。

## 3. 页面结构总览

RunSpace 沿用现有三栏底座，不新开一套布局。左栏多一个分区，右栏多一个模式：

```
┌────────────┬──────────────────────────────────┬──────────────────────────┐
│ 顶部窗口区  │  项目标题 / 目标 / 概览 齿轮       │ 概览面板                  │
├────────────┼──────────────────────────────────┼──────────────────────────┤
│ 新建会话    │                                  │ 线程 │ 库 │ PR │ 例行      │
│            │   项目会话（协调器）                │ ─────────────────────    │
│ 已置顶      │                                  │ ▾ 待你处理 (2)            │
│  · 会话      │   ┌── 你 ──────────────────┐      │   ⚠ 迁移 v1 调用方     │
│            │   │ 把checkout p75 降到200ms│      │ ▾ 进行中 (2)              │
│ RunSpaces ◂ │   └────────────────────────┘      │   ◐ profile 各端点      │
│  · 支付延迟  │                                  │ ▸ 待审查 (1)             │
│  · v1 下线  │   ┌── 建议线程 ────────────┐      │ ▸ 空闲 (3)               │
│            │   │ 建立基线跑分      [开始] │      │ ▸ 已解决 (5)            │
│ 工作区      │   │ 补齐 triage 样本   [开始] │      │                          │
│  · actspace │   └────────────────────────┘      │ ─────────────────────    │
│            │   [ 启动 2 个线程 ]               │ 项目记忆 ›               │
│ 设置        │                                  │ 🧠 发布推迟到周五        │
│            │   ┌── 项目会话 ────────────┐      │ 📌 改动计费需先问 @陈    │
│            │   │ 已按仓库拆成 2 个线程 ▸ │      │                          │
│            │   └────────────────────────┘      │ [输入框] 继续交代…        │
└────────────┴──────────────────────────────────┴──────────────────────────┘
```

**中栏底部输入框复用 Composer**，语义从「发消息」变成「交代事情」。**右栏复用对象浏览区底座**，概览只是它的一个新模式，和文件 / Review / 上下文 / 终端并列，可收起、宽度规则不变。

## 4. 页面逐块规格

### 4.1 左栏：RunSpaces 分区

- 位置在 `已置顶` 之下、`工作区` 之上，共享 `NavSectionHeader` 的分组标题规范（12px / 500 / faint）。
- 每个 RunSpace 一行，行内：[状态点 14px 槽位 | 名称 1fr | hover 操作]，与工作区行的三条意图正交化保持一致：
  - 左槽位：默认显示项目图标，hover 换成 chevron —— 点击折叠展开（与工作区行同构）。
  - 中间名称：单击进入该项目的工作台。
  - 右侧 hover：新建线程（起一次"单线程 RunSpace 会话"的快捷入口）。
- 行尾信息：线程计数（`3/5` 这样的「活跃/总数」或仅活跃数），有线程待你处理时显示琥珀色计数，而不是额外图标。
- 超过 8 个 RunSpace 用 `See more / See less`，与工作区一致。
- 每个 RunSpace 的名称是**数据**，不翻译。

### 4.2 中栏：项目会话

顶部 chrome 区（复用 `WindowChromeBar` 的中间列）：

- 左：RunSpace 名称，右上角一个**目标**行（灰色小字，如"把支付 API p95 压到 200ms 以下"）。没有目标时不占位。
- 右：`概览` 开关按钮，有待处理线程时按钮上带一个点；`齿轮` 打开 RunSpace 设置。

消息区需要三种卡片，都复用现有消息流排版与工具摘要规范：

| 卡片 | 出现时机 | 内容 |
| --- | --- | --- |
| **线程卡片** | 线程被创建后贴在你的那条消息下面 | 标题 + 状态点 + 状态文案；点击打开线程详情；有分支或改动时右下角带动作按钮 |
| **建议线程卡片** | 协调器认为该先确认再开工 | 一列建议项，每项标题 + 一句理由 + `开始` 按钮，可单条忽略（×）；底部 `启动 N 个线程` |
| **层叠卡** | 会话滚动到较早位置 | 历史线程收成层叠卡片，点击展开当时的线程组；表达"这个项目跑了一阵了" |

线程卡片的动作按钮直接复用现成语义：`解决冲突` / `修复 CI` / `处理评论` / `合并` / `查看 Review` / `创建 Review`。actspace 没有托管平台 PR 流程，按钮文案与是否保留「PR」概念见 [Q6](#11-待讨论问题)。

### 4.3 右栏：概览面板

四个页签，默认停在「线程」，与官方一致：

| 页签 | 内容 |
| --- | --- |
| **线程** | 按状态分组，可折叠；组标题带计数。组内每行：状态点 + 标题 + 分支名 + 最近活动时间 |
| **库** | 两段：`我添加的`（上传的文件/文件夹）与 `产出`（线程生成的产物）。支持从 `Add` 添加上下文 |
| **Review** | 线程开出的待合入分支，复用现有 Review 渲染，不新做 diff 视图 |
| **例行** | RunSpace 内的定时工作（当前产品无此能力，首版可整块隐藏，见 [Q7](#11-待讨论问题)） |

线程状态分组与配色映射（只用现有语义 token，不新增）：

| 分组 | 含义 | token |
| --- | --- | --- |
| **待你处理** | 需要你回复、审批，或已失败 | `warning`；失败项改用 `danger` |
| **待审查** | 已产出分支，等你过目 | `info` |
| **进行中** | 仍在跑 | `operational` |
| **落地中** | 已批准、排队合入 | `operational`（弱化一档） |
| **空闲** | 已结束且不需要你做什么 | `text-muted` |
| **已解决** | 你或协调器标记完成，或一周无活动自动收起 | `text-subtle` |

面板底部固定一块**项目记忆摘要**：显示最近 2–3 条记忆条目 + 一个 `全部` 入口。这是让「长期记忆」这件事可见的最低成本做法——如果记忆只藏在设置里，用户不会相信它真的记住了东西。

### 4.4 线程详情

点击线程行 → 在概览面板内打开该线程的完整记录（不是新窗口，也不跳走）：

- 顶部：标题 + 分支名 + 模型档位 + 本机/云端标记；运行中时 `停止` 按钮替换发送按钮，`Esc` 同样中断。
- 中部：完整 transcript，复用现有工具流渲染。
- 权限请求**原地弹出在线程里**，不在项目会话里——这一点官方专门强调，用户在项目会话说"去吧"是够不到线程的。这是必须做对的地方。
- 底部：该线程自己的输入框，消息直达线程，不经过协调器。

面板顶部提供返回项目会话的入口；同时保留「在左栏打开为独立会话」的逃生口，方便用已有会话能力深挖。

### 4.5 新建 RunSpace 对话框

只保留三个字段，与官方一致：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| 名称 | 是 | 显示在 RunSpaces 列表 |
| 目标 | 否 | 一行话；写进项目头部，协调器据此判断该不该开线程 |
| 上下文 | 否 | 工作区 / 仓库 + 文件、文件夹；点 `Add` 逐个添加 |

标准规则（分支策略、如何自检、什么要先问）**不放在这个对话框**，放到创建后的「项目指令」里。这样首版创建流程可以极短。

创建后的首轮：如果已有可读工作区，协调器可以主动开一个只读探查线程并给出**设置建议**（建议加入的工作区、建议的例行任务），每项默认开启、可逐项关掉——这是官方体验里很讨巧的一步，让空项目不空。

### 4.6 RunSpace 设置

三个分组，复用设置中心的内嵌分组规范：

- **通用**：线程模型 / 线程 Effort、协调器模型 / 协调器 Effort、通知开关。
- **记忆**：项目指令（纯文本，上限 16000 字符）、自动记忆条目列表（可读可改可删）。两者放同一页，因为在用户的心智里它们都是「我交代过的长期规则」。表头需要一行说明区分：指令是**我写的**，记忆是**它记的**。
- **环境**：工作区 / 仓库清单、允许的网络域名、环境变量与凭据、已安装工具。

## 5. 关键交互

### 5.1 消息路由

项目会话收到一条消息后有三种去向，用户必须能分辨：

1. 快捷提问 → 就地回答，不开线程。
2. 新工作 → 开新线程（或并入已有同领域线程），并在消息下方贴出线程卡片，明确写出「开了哪个线程」。
3. 多个不相关任务 → 拆成多个线程。

用户说不满意时，靠自然语言改（"这个线程继续跟进" / "在这直接回答"），协调器把这类偏好写进项目记忆。

### 5.2 调速旋钮

以下都是「跟协调器说一句」，不是设置项：同时最多跑几个线程、要不要先提建议再开工、更新频率、是否先给方案再开 Review。首版可以只在设置里放一个最常用的（线程并发上限），其余靠对话调，保持设置面收敛。

### 5.3 复用与边界

- 概览面板收起/展开、宽度、紧凑窗口降级，全部沿用[工作台布局与面板交互规范](front-工作台布局与面板交互规范.md)，不新增规则。
- 线程的 diff 一律走现有 Review，不新做 diff 视图。
- 线程的权限请求走线程，项目会话不代答。

## 6. 首版范围

**做**：左栏 RunSpaces 分区 → 新建对话框 → 项目会话（含线程卡片与建议线程）→ 概览面板（线程 / 库 / Review 三页签）→ 线程详情 → 项目指令与记忆。

**不做**：自动多线程路由（首版由用户或建议卡片显式发起）、例行任务、云端执行与远程控制、项目用量统计页面、跨项目记忆检索。

## 7. 待讨论问题

1. **线程跑在哪里？** 复用现有「新建工作树」在本机跑（与现有能力同构，实现成本最低），还是像官方那样跑云端，还是两者都要。我倾向首版本机工作树。
2. **RunSpace 与工作区的关系？** 是工作区之上的新顶层容器（一个 RunSpace 可挂多个仓库），还是某个工作区的属性。倾向前者，否则"一个目标跨多个仓库"这个主场景做不出来。
3. **概览面板放在哪？** 作为右栏对象区的一个新模式，还是独立面板。倾向前者，但需要决定它和文件 / Review 模式的切换优先级。
4. **首版要不要自动路由？** 即协调器自主决定开几个线程。这依赖模型能力且失败成本高，建议首版只做手动 + 建议卡片。
5. **术语中文化程度？** RunSpace / 线程 / 协调器 / 概览 哪些保留英文。
6. **保留「Pull request」概念吗？** actspace 本地优先，没有托管平台；可以考虑改叫「待合入分支」，动作按钮相应改成 `创建 Review` / `合并到 main`。
7. **例行任务整块隐藏还是占位？** 现有产品无定时能力，倾向整块隐藏而不是留灰条目。

## 8. 本草案的下一步

确认以上问题后，先出一个纯 HTML 的静态 demo（项目会话 + 建议线程卡片 + 概览面板三件套），把信息密度和层叠卡片的表现力定下来，再谈组件拆分。

视觉落点：demo 直接用 `tokens.css` 的 `--act-color-*`（浅深双主题）、`--act-radius-*`、`--act-shadow-*`，字号用 `text-act-xxs … text-act-title`，按钮用现有 `Button` / `IconButton` 的视觉语言，不引入新的灰阶或第二套强调色。
