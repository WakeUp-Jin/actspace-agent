# 资源监控规范（悬浮窗 + 设置「资源占用」）

本地排查性能问题用：一边聊天一边看 ActSpace 自己的 CPU、内存、主线程卡顿和子进程。取代原侧边栏底部的「性能面板」一行字。视觉按 2026-11-11 确认的 demo（悬浮窗样式 A）定稿，demo 已删，以本规范为准。

两条底线：

1. **数要准**。口径写清楚，和活动监视器对不上的地方在界面上写明。
2. **开着不拖累，关掉零成本**。监控自己的开销单独列一行、不算进合计；悬浮窗和资源页都关着时，采集器不存在：没有定时器、没有直方图、没有子进程。

只做桌面端；Web / PWA 不提供。

## 1. 两个入口

| 入口 | 作用 | 何时采集 |
| --- | --- | --- |
| 悬浮窗 | 常驻桌面一角，聊天时余光能看到 | 开关打开即采集，主窗口最小化也不停 |
| 设置 › 系统 ›「资源占用」 | 开关悬浮窗、看 5 分钟曲线和完整进程表、复制快照 | 页面打开期间采集，离开页面即停 |

两者共用主进程里同一个采集器，按订阅计数启停：计数从 0 到 1 时创建，回到 0 时销毁。

原侧边栏底部、设置导航底部、侧栏收起时工作台角落的 `PerformancePanel`，以及「通用」页的「性能监控」分组，全部删除。

## 2. 悬浮窗

### 2.1 收起（默认）

一行，约 340 × 34 px（读数变长到「CPU 123% · 内存 1.50 GB · 主线程 1.2 s」也不压到右侧按钮）：

```
⠿  CPU 12% · 内存 640 MB · 主线程 3 ms      ⌄  ×
```

- 三个数依次是：ActSpace 合计 CPU、合计内存、主线程延迟（见 §4）。
- 收起时不画图。
- `⌄` 展开，`×` 关闭悬浮窗。关闭等于把开关关掉，下次启动也不再出现。
- 整条可拖动（按钮除外）。

### 2.2 展开

宽 360 px，在一行摘要下面加三块：

1. CPU 曲线，5 分钟（150 个点）。
2. 内存曲线，5 分钟。
3. 分组进程表（与设置页同一张表，见 §3.2）。

曲线是一条折线加浅色填充，右上角写当前值。不画坐标轴、不画网格。

### 2.3 窗口行为

| 行为 | 规定 |
| --- | --- |
| 置顶 | 普通置顶（不压在全屏应用、系统菜单之上） |
| 桌面 | 所有桌面（Spaces）可见 |
| ⌘H 隐藏 ActSpace | 悬浮窗跟着隐藏（macOS 按应用隐藏全部窗口；实测 Electron 45 普通窗口和 panel 都会被藏，强行重新显示会把应用拉回前台，不做） |
| 焦点 | 显示时不抢焦点 |
| 关闭主窗口（macOS） | 悬浮窗保留；点 Dock 图标仍会重新打开主窗口 |
| 位置 | 拖动后记住，下次启动恢复；原位置所在屏幕不在了就放回主屏右上角 |
| 启动 | 上次开着就自动打开 |
| 外观 | 无动画、无半透明、无阴影动效，跟随系统浅色 / 深色 |

### 2.4 主进程卡住时

悬浮窗自己跑一个 1 秒的计时器（只比较时间，平时不改 DOM），超过 4 秒（两个采样周期）没收到新数据才变化，避免偶尔一次延迟就闪红条：

- 顶部出现红条「主进程无响应 N 秒」，N 每秒加一；
- 三个数变灰，主线程延迟写成「≥ N s」；
- 收到新数据后恢复。

这是悬浮窗最有用的场景之一：主进程卡住时它自己的渲染进程还活着，能把「卡了多久」显示出来。

## 3. 设置「资源占用」页

放在「系统」分组，排在「更新」上面。图标 `Activity`。

### 3.1 页面结构

1. **开关行**：「显示悬浮窗」`Toggle`。写 `general.performanceMonitoring`（沿用旧键，见 §6）。
2. **三张指标卡**一排（窄屏单列）：CPU、内存、主线程延迟。每张卡：标签、当前大数、5 分钟迷你折线。内存卡标签写「内存（含共享页）」。
3. **进程表**（§3.2）。
4. **「复制快照」按钮**：把当前一次完整读数复制成纯文本，见 §5.3。

页面只在打开期间订阅；切到别的设置页或关闭设置即退订。进入页面时，如果悬浮窗开着，曲线直接用采集器已有的历史，不从零开始。

### 3.2 分组进程表

列：名称、CPU、内存。分组固定按下面顺序，组内可展开看单个进程（pid、类型）：

| 分组 | 包含 |
| --- | --- |
| 主进程（含 Agent Runtime） | Electron Browser 进程；Agent Runtime 跑在主进程里 |
| 界面 | 主窗口的渲染进程 |
| GPU | GPU 进程 |
| 其他工具进程 | Electron 的 Utility 进程（网络服务、存储服务等） |
| Agent 子进程 | 主进程的后代里不属于 Electron 的进程（终端命令、MCP、Python 等），按命令名合并，名称后写个数，如 `node ×3`；没有时写 `0` |
| 监控自身 | 悬浮窗的渲染进程 + 采集器本身的耗时；**不计入合计**，行灰色 |

表格最后一行是合计（不含「监控自身」）。

### 3.3 颜色

只有两处会变色，其余一律中性色：

- 主进程 CPU ≥ 90%：警告色。主进程长时间吃满一个核，界面和 Agent 都会卡。
- 主线程延迟 ≥ 200 ms 警告色，≥ 1 s 危险色。

合计 CPU 不变色（多进程合计超过 100% 是正常的）。不弹通知、不发系统提醒。

## 4. 口径

| 指标 | 口径 | 来源 | 频率 |
| --- | --- | --- | --- |
| CPU | **100% = 一个核**。每个进程：两次采样间 CPU 累计秒数之差 ÷ 墙钟秒数 × 100 | Electron 进程：`app.getAppMetrics()` 的 `cpu.cumulativeCPUUsage`；Agent 子进程：`ps` 的 `time` 列 | Electron 进程 2 s；子进程 6 s |
| 内存 | 常驻内存（RSS / working set），**含共享页**，各进程直接相加 | `memory.workingSetSize`；子进程 `ps` 的 `rss` | 同上 |
| 主线程延迟 | 2 s 窗口内事件循环最大延迟 | `monitorEventLoopDelay({ resolution: 20 })` 的 `max − 20 ms` | 2 s |
| 精确内存 | macOS 的 footprint（活动监视器「内存」列的口径） | `/usr/bin/footprint` | 只在「复制快照」时取一次 |

实测依据（2026-11-11，Apple Silicon 10 核，Electron 主进程）：

- `percentCPUUsage` 在 macOS 上按核数归一：主进程单核跑满一半时它读 5%，用累计差值算出来是 50%。所以不用它，自己算差值；顺带避免和别的调用方抢同一个「上次采样」状态。
- `workingSetSize` 与 `ps` 的 RSS 完全一致。
- RSS 和活动监视器对不上：共享页会被多算（多进程相加偏大），被压缩 / 换出的部分又不算（偏小）。实测同一进程 RSS 66 MB、footprint 166 MB；另一组 working set 约 270 MB、footprint 79 MB。所以界面上写「含共享页」，精确值只在快照里给。
- `footprint` 一次查 4 个进程约 1.2 s CPU，`top -l 1` 约 1.1 s CPU，都不能周期性跑。
- 事件循环直方图在 Electron 主进程里准确：人为阻塞 150 / 400 / 1200 ms，读到 159.8 / 399.8 / 1201.7 ms。空闲时读数约等于分辨率，所以减去分辨率。
- 不另开 JS 定时器测卡顿：一个 100 ms 的空定时器在 Electron 主进程里 2 秒耗 15.6 ms CPU（约 0.8%），比整个采集器还贵。

## 5. 采集器

### 5.1 开销预算

| 项 | 实测单次成本 | 频率 | 折合 |
| --- | --- | --- | --- |
| `getAppMetrics()` | ≈ 0.06 ms | 2 s | 可忽略 |
| 事件循环直方图 | 原生实现，无 JS 回调 | 常开（订阅期间） | 可忽略 |
| `ps`（异步子进程） | ≈ 26 ms CPU（约 550 个进程的整机列表） | 6 s | ≈ 0.4% 单核 |
| 推送到悬浮窗 / 设置页 | 一条几百字节的消息 | 2 s | 可忽略 |
| 悬浮窗渲染进程 | 收起时只改三段文字 | 2 s | 常驻内存约几十 MB（独立渲染进程） |

合计目标：**采集 + 悬浮窗收起时 CPU < 1% 单核**。「监控自身」一行就是这个数的实时读数，超了在界面上能直接看到。

关闭时零成本：悬浮窗关、资源页没开时，没有采集器实例、没有定时器、直方图已 `disable()`、不会起 `ps`。有单测锁住。

### 5.2 Agent 子进程

- 每 6 s（每 3 次采样）异步执行一次 `ps -A -o pid=,ppid=,rss=,time=,comm=`（只取可执行文件路径，不取命令行参数，避免把参数里的路径、密钥带进界面和快照），在内存里从 `process.pid` 往下找后代。
- 去掉 `getAppMetrics()` 已经覆盖的 pid（Electron 自己的子进程），剩下的按命令名（可执行文件名）合并。
- CPU 用 `time` 列（累计 CPU 时间）两次之差算，口径与 §4 一致；第一次看到的进程 CPU 记「—」。
- 上一次 `ps` 还没返回时跳过这一轮，不排队。
- Windows 没有 `ps`：这一组显示「—」，不起子进程。

### 5.3 复制快照

纯文本，包含：时间、平台与核数、合计、每组与每个进程的 CPU / RSS、主线程延迟，以及（仅 macOS）每个 Electron 进程的 footprint。footprint 在点击时才取，取的过程中按钮显示加载态；取失败就在快照里写「footprint 读取失败」，其余照常复制。

## 6. 设置与状态

- 悬浮窗开关沿用 `general.performanceMonitoring: boolean`，默认关闭；语义从「显示性能面板」改为「显示悬浮窗」。不新增迁移。
- 悬浮窗位置和展开状态是本机窗口状态，不进设置文件，存在数据目录下的小 JSON 里（与设置文件分开，避免拖一下窗口就改设置 revision）。
- 主进程订阅设置变化：开关变了就开 / 关悬浮窗；悬浮窗上点 `×` 由主进程写回设置。

## 7. 不做

- 不做历史持久化、不导出曲线文件；曲线只保留内存里最近 5 分钟。
- 不做整机 CPU / 内存、不列别的应用。
- 不做告警通知、阈值设置。
- 不做 Web / PWA 版本、不显示远端 Host 的资源。
- 悬浮窗不复用主应用的 React 和样式（太重），是一个手写的极简页面。
