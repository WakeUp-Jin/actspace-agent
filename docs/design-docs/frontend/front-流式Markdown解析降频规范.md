# 流式 Markdown：尾部解析降频与解析器常驻

> 管流式回复时，聊天区 Markdown 多久重新解析一次尾部、两次解析之间怎样显示新到的字、解析器怎样复用。现行渲染规则见[聊天区 Markdown 渲染规范](front-聊天区Markdown渲染规范.md)，本文只改该规范的 §2「架构」和 §6「分块与性能」，§5 的流式视觉效果不变。

状态：已实现；实测效果见[性能待办](../../exec-plans/perf-backlog.md)「已完成」。

## 1. 为什么改

run7 渲染进程的分配采样（`tmp/heap/run7/renderer-*.heapprofile`，共 7 段，开发版）：

| 位置 | 分配 | 原因 |
|---|---|---|
| 每块的 `<Markdown>` 渲染 | 约 415 MB | 平滑输出每帧放几个字，最后一块每帧整块重新解析、转换、生成元素；react-markdown 每次渲染还要重新组装 unified 处理器（gfm 扩展合并约 70 MB） |
| `splitMarkdownBlocks` | 约 209 MB | 每帧为了切块，把最后两块用 `fromMarkdown` 解析一遍 |
| `hasVisibleText`（思考区、流式块、子 Agent 行） | 约 200 MB | 每帧对全文做一次 `replace` 来判断有没有可见字 |
| 代码高亮 | 约 17 MB | 不是问题 |

同一段尾部，每帧要被解析两遍：切块一遍，渲染一遍，频率约 60 次/秒。React 自身的分配在开发版里偏大，不计入。

## 2. 别家怎么做（2026-11-07 调研）

| 做法 | 谁在用 | 优点 | 缺点 |
|---|---|---|---|
| 冻结前缀，只重新解析尾部 | DSH、grok、我们 | 已完成的块不再算 | 尾部仍然每帧算 |
| 每帧解析尾部 | DSH 网页端、pi-mono 网页端 | 简单 | 就是我们现在的开销 |
| 遇到换行才重新解析，没写完的行先不显示或原样预览 | codex、kimi-cli | 解析次数降到每行一次 | kimi 不显示当前块；codex 要额外的预览通道 |
| 限频 | kimi-cli（100ms）、pi TUI（16ms） | 简单 | 只降频，不减少单次的量 |
| 尾部补全（给半截 `**` 补闭合） | opencode | 不闪 | 规则多、边界复杂 |
| 放到 worker 解析 | opencode | 主线程不卡 | 总量不降；React 渲染仍在主线程；要做看门狗和降级 |
| 解析器常驻，不每次重建 | 四家都是 | 没有副作用 | — |
| 结束时完整解析一次 | codex、grok、DSH | 纠正流式中的一切近似 | 块边界可能轻微跳一次 |

## 3. 改法

### 3.1 尾部最多每 100ms 解析一次

**名词：**
- **尾部**：`splitMarkdownBlocks` 里没冻结的那部分，也就是最后两块。
- **解析**：切块 + 渲染这一块的整条管线。

**规则：**
- `MarkdownProse` 维护「已解析的文字」`parsedText` 和上次推进的时间。
- 平滑输出每帧放出新字后，满足下面任意一条，就把已解析的文字推进到当前要显示的文字，重新切块并渲染尾部：
  1. 距上次推进已过 100ms；
  2. 新的一行：新放出的字里有换行，或者已解析部分停在一个还没定类型的行上（空行、只有块标记）。没闭合的代码块里新的一行还是代码，不算，只有出现围栏行（可能是收尾围栏）才算；
  3. 平滑输出追平了网络（网络停顿时不让原样尾巴一直挂着），或者回复写完；
  4. 内容不是追加（变短或被改写）；
  5. 还没有任何已解析内容（尾巴没有地方接）。
- 不满足时不重新解析。新放出的字作为一段**原样尾巴**，显示在最后一块的后面，见 §3.2。
- **还没定类型的行先不显示**：正文里，结尾的空行、只有块标记的行（`-`、`##`、`>`、`1.` 等）连同它前面的换行先不放出，等这一行出现内容再一起显示和解析。否则 `-`、`##` 会作为原样文字接在上一段末尾，或者每放出一个标记字符就要重新解析一次。最多晚一两帧，没闭合的代码块里不扣。
- 计时用 `performance.now()`，测试里用假时钟。

**模拟结果（`tmp/md-throttle-sim.mjs`，按 mock 的网络批次和现行平滑输出逐帧模拟）：**

| 回复 | 现在的解析次数 | 只按 100ms | 100ms + 遇换行 |
|---|---|---|---|
| Markdown 展示回复（3.8K 字，元素密集） | 889 | 135（约 1/6.6） | 197（约 1/4.5） |
| run7 最长一条真实回复（7.7K 字，60 行） | 1764 | 279（约 1/6.3） | 299（约 1/5.9） |

规则 2 让新的一行在第一时间按正确的块类型显示，代价是元素密集的回复少省一些。

### 3.2 两次解析之间的原样尾巴

原样尾巴是纯文本，不解析，接在最后一块已渲染内容的末尾，样式和正文一致。

- **最后一块是没闭合的代码块**（`isOpenFence`）：尾巴接进代码区的最后一行，也是纯文本，不高亮。下一次解析时这段才高亮，和现在每帧重算高亮的观感一样。
- **其他块**：尾巴接在最后一个文本节点后面。
  - 末尾渐显和光标：放在尾巴上（尾巴最末 36 个字按 §5 的三档透明度显示，光标跟在尾巴后面）。
  - 已解析部分只在尾巴不足 36 个字时承担剩下的渐显字数。
- **实现方式**：解析时不生成渐显和光标，`rehypeStreamTail` 只在 hast 上放两种占位元素，渲染时由 `markdown/StreamTail.tsx` 的组件从 `StreamTailContext` 读这一帧的尾巴。块本身按源码 memo，两次解析之间只有这几个小组件重新渲染。
  - `act-stream-tail`：尾巴的位置。沿最右边找最后一个块级容器（段落、列表项、标题、单元格），跳过隐藏的脚注区和脚注的「↩」，遇到行内元素（加粗、链接、行内代码）停在它后面；渲染成 `<span class="md-tail-raw">`，带渐显，光标在后面。块里没有可接的容器（最后是分隔线、独立公式）时不显示尾巴和光标，下次解析就归位。
  - `act-fade`：已解析部分最后 36 个字所在的文字片段，带上「后面还有几个已解析的字」。组件加上尾巴字数后决定每个字的渐显层级。
  - 没闭合的代码块：尾巴接在 `<code>` 里最后一行的行尾（`mdast-util-to-hast` 补的结尾换行之前）；块源码以换行结尾时尾巴另起一行；尾巴结尾的换行去掉，和下一次解析的行数一致。
  - 段落末尾的空格会被 Markdown 去掉，尾巴接上时补回来。
- **版面稳定**：§5 的稳定性硬约束仍然成立。
  - 光标不落在结尾换行后面：尾巴结尾的空白放在光标之后。
  - 代码块不回缩：尾巴不会让代码块变短。
  - 尾巴里有换行时，规则 2 会立即解析，所以尾巴里不会出现多行纯文本。

**会出现的近似**：100ms 内刚打出的行内语法，比如 `**加粗`、`` `代码 ``、`[链接](`，会先按原样显示，最多 100ms 后才变成格式化结果。现在逐帧解析时，这些半截语法本来也按 CommonMark 当字面量显示；平滑输出的 `snapCut` 也已经避免停在半截语法上。所以实际可见的差别是：格式生效最多晚 100ms。

### 3.3 解析器常驻

- 不再用 `<Markdown>` 组件（它每次渲染都执行 `unified().use(...)` 重新组装并冻结处理器）。管线对象由 `createPipelineCache` 按组合只建一次，`processor.ts` 用 WeakMap 按管线对象缓存处理器。
- 新增 `markdown/processor.ts`：按管线组合（`createPipelineCache` 的 key）缓存一个已经 `freeze()` 的 unified 处理器。
  - 渲染时只做 `processor.runSync(processor.parse(file), file)`，再执行 react-markdown 的 `post`：`visit` 处理 raw 节点和 URL 过滤，然后 `toJsxRuntime`。
  - 这一步约 40 行，对照 react-markdown 10.1.0 的 `lib/index.js` 实现。只用到我们传过的选项：`components`、`remarkRehypeOptions`、默认的 `urlTransform`。
- `splitMarkdownBlocks` 的 `fromMarkdown(markdown, { extensions: [gfm()], mdastExtensions: [gfmFromMarkdown()] })`：`gfm()` 和 `gfmFromMarkdown()` 的结果提到模块级，只建一次。
- 依赖：
  - `unified`、`remark-parse`、`remark-rehype`、`hast-util-to-jsx-runtime`、`html-url-attributes`、`vfile` 现在由 react-markdown 间接引入，改为在 `apps/desktop/package.json` 直接声明，版本与 react-markdown 10.1.0 锁定的一致；
  - react-markdown 保留：轨迹视图（`trajectory/shared.tsx`）仍在用；聊天区只用它导出的 `defaultUrlTransform` 和 `Components` 类型。

### 3.4 可见字判断不再整串替换

`@actspace/shared` 的 `hasVisibleText` 现在是 `text.replace(INVISIBLE, "").length > 0`，改为用一个非全局正则 `/[^\s​-‍⁠﻿]/` 做 `test`：遇到第一个可见字就返回，不分配新字符串。语义不变。

### 3.5 结束时完整解析

回复写完（不再有末尾效果）时立即推进到全文，最后一块按完整源码解析一次。冻结块不变。这一步保证最终显示和不经过流式、直接渲染整条回复完全一致。

## 4. 不做

- **增量解析器、自写 mdast 到 React 的渲染**（DSH 的做法）：现有插件（gfm、数学、callout、路径识别、脚注、HTML 净化、流式尾部）都基于 remark/rehype，换掉等于重写。
- **worker 解析**（opencode）：总量不降，React 渲染仍在主线程。
- **尾部补全**（opencode `heal.ts`）：`snapCut` 已经避免停在半截语法上，目前没有这类闪烁问题。
- **代码块增量高亮**（codex、grok、DSH）：run7 里高亮只有 17 MB；降频后整块重算的次数也随之下降。

## 5. 验收

- **等价**：同一条回复，按 mock 的网络批次逐帧回放到结束，最终 DOM 与一次性渲染完整内容的 DOM 相同（测试比较 `innerHTML`）。覆盖 `markdown-fixture.ts` 的全元素回复，以及 run7 最长回复。
- **降频**：同一回放下，最后一块管线的执行次数不超过现在的 1/4。用假时钟加计数器断言。
- **尾巴**：两次解析之间新放出的字立即出现在 DOM 里（逐帧可见），光标在尾巴后面。尾巴有换行时同一帧就解析。
- **代码块**：没闭合的代码块里，尾巴接在代码区内；代码块高度只增不减（沿用 `chat-markdown-stream.test.tsx` 的稳定性断言）。
- **解析器常驻**：连续 100 次渲染只创建一次处理器（计数 `unified()` 调用）。
- **`hasVisibleText`**：零宽字符、空白、普通文字三类用例的结果不变。
- **现有测试**：`chat-markdown-*`、`markdown-blocks`、`markdown-prose` 全部通过。
- **实机**：用 run7 的问法重跑 monitor，渲染进程里 `Markdown`、`splitMarkdownBlocks`、`hasVisibleText` 的分配合计降到改前的 1/4 以下。流式观感由用户在 Electron 里确认。

## 6. 实现结果（2026-11-07）

逐帧回放测试（`chat-markdown-throttle.test.tsx`，假时钟，mock 网络批次）里块的解析渲染次数：

| 回复 | 每帧解析 | 降频后 |
|---|---|---|
| Markdown 展示回复 | 835 | 203（约 1/4.1） |
| run7 最长一条真实回复 | 1670 | 345（约 1/4.8） |

两份回复回放结束后的 DOM 与一次性渲染完全相同。
