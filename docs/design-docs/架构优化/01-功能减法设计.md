# 01 功能减法设计

本文定义功能减法的取舍，已实现。判断依据见[专题 README](README.md) 的三条判断线。

## 1. 结论

| 处理 | 功能 |
|---|---|
| **删除** | 应用内渲染 HTML、代码、CSV；回复下方的「转成可视化 HTML」；内置终端；工作区文件树；Git Review 的暂存、取消暂存、还原，“已查看”标记，复制 apply 命令、创建 PR、初始化仓库，以及实时文件监听 |
| **外置为可选插件，默认不加载** | Agent 操控浏览器（Chrome 扩展 + browser-bridge + browser-tools）；英语学习（含朗读） |
| **保留并改进** | Markdown 配新的「文档」面板（预览、源码、编辑）；图片预览；Git Review 只留查看部分；输入框 +N/−M 改为每轮结束查一次 |
| **保留不变** | 顶部工作区菜单的提交、推送、新建分支；本轮改动卡 |
| **本轮不动** | 远程 Host 与 Web/手机端、沙箱、Space 演示，以及所有上下文和 Harness 功能 |

## 2. 文件怎么打开

应用里只渲染两种文件：**Markdown 和图片**。其余都交给系统。

| 文件 | 点击后 |
|---|---|
| `.md` / `.markdown` | 右侧「文档」面板打开 |
| 图片（png、jpg、jpeg、gif、webp、svg） | 应用内预览，保持现状 |
| `.html` / `.htm` | 系统默认浏览器打开（现有 `open-html-in-browser.ts` 的做法） |
| 其他所有文件 | 系统默认应用打开 |

**不写死 Chrome 或 VS Code。** 用系统默认应用：每台 Mac 至少有 Safari，用户把 Chrome 设为默认就用 Chrome，喜欢别的浏览器也不会被强迫。这也是“有分寸”：尊重用户已经选好的软件。

**打不开时的兜底。** 只有文件没有任何关联应用（常见于 `.ts`、`.go` 这类代码文件）时，才弹一个小对话框，提供三项：

1. 「选择应用打开」：复用交付卡现有的关联应用选择器；
2. 「在 Finder 中显示」；
3. 一行轻提示「推荐安装 VS Code」，附下载链接。

不在启动时检测软件，也不主动提醒，只在用户点了却打不开的那一刻出现。

## 3. 文档面板

取代工作区文件树。左右布局按用户在 demo 中选定的方案 A：**聊天 → 正文 → 文件树**，文件树在最右侧，大纲收在正文顶部的按钮里。

- 文件树保留原有目录结构，只列 Markdown 文件；不含 Markdown 的文件夹整个隐藏；按 `.gitignore` 排除。
- 绿点和「本会话改过」筛选：标出这次会话里 Agent 写过或改过的 Markdown。这一点把文档面板和上下文连起来，人和 Agent 都需要知道。
- 预览与源码可以切换，源码状态直接编辑，⌘S / Ctrl+S 保存；与 Agent 改同一文件时以人为准。Markdown 渲染做精以后单独立项。
- 标签页名称：文档面板叫「文档」，Review 叫「改动」。

完整交互和渲染要求见[文档面板规范](../frontend/front-文档面板规范.md)。

## 4. 终端

整块删除，包括 node-pty 原生模块、xterm 依赖、右侧终端标签页和它的 IPC。

终端只给人看，Agent 不需要读它；每台电脑都自带终端。Agent 的 Bash 工具和终端是两套独立代码，不受影响。删掉之后打包也少一个需要单独编译的原生模块。

## 5. Agent 操控浏览器：外置

它是 Agent 的一种能力，不是人的工具，所以不删，而是做成可选插件。第一步只做到：

1. **默认不加载**：从默认组合中移除 browser-tools。
2. **没有常驻开销**：现在应用启动后每 10 秒查一次 Chrome 连接状态，启动时还可能去安装或注册 Chrome 通信组件。改为只有启用这个能力后才开始。
3. **接线收拢**：桌面端的服务、连接面板、设置页和审批卡只在启用时出现，代码集中，方便第二步整体搬出。

代码暂时留在仓库里。打包成可安装的外部插件、从默认安装包里拿掉 Go 程序和 Chrome 扩展，等第二步定下插件格式后再做。

当时进行中的「Chrome 扩展连接、启动与使用体验闭环」计划与这个方向冲突，随本次减法暂停，后来连同计划归档一起删除；没有补完的实机验收登记在 `docs/exec-plans/tech-debt-tracker.md`「Browser Use 遗留」。

## 6. 英语学习：外置

和浏览器能力同样处理：默认不加载，没有常驻开销（启动时不再注册它的接口、不准备朗读），设置入口只在启用后出现。打包成外部插件放到第二步。

## 7. 「转成可视化 HTML」：删除

回复下方的按钮会让模型把回答生成为 HTML，再显示在右侧「Reply」视图里。既然 HTML 不在应用内渲染，这个功能整体删除，包括按钮、Reply 视图、生成逻辑和对应接口。

## 8. Git Review：只留查看

Review 的职责收窄为“看清改动”：Agent 动了哪些文件、改了什么。动手操作 git 的入口统一放在顶部工作区菜单。

| 功能 | 处理 | 理由 |
|---|---|---|
| 选择看哪一段改动（上一轮、全部未提交、未暂存、已暂存、某个提交、某个分支） | 保留 | 看清改动的核心 |
| 逐文件 diff（词级高亮、忽略空白、折叠上下文、加载全文、大改动上限） | 保留 | 同上 |
| 浏览分支、浏览提交 | 保留 | 用户需要看有多少分支、提交情况 |
| 暂存、取消暂存、还原（按段、文件、hunk） | 删除 | 暂存只有半个流程：Review 里不能提交，用户最后还得去别处提交。还原是没有撤销的 git 操作；撤销 Agent 本轮改动应当是 Harness 层面的能力，以后另做 |
| “已查看”标记 | 删除 | 没人用 |
| 复制 apply 命令、创建 PR、初始化仓库 | 删除 | 用户不会在这里手动操作 |
| 实时文件监听加刷新合并 | 删除 | 资源开销大、收益小，见第 10 节 |

**输入框 +N/−M 的新做法**：每轮 Agent 结束时查一次；打开 Review 面板或点刷新时查一次。两处都必须**强制刷新**：Review 协调器会缓存快照，去掉监听后没有东西让缓存失效，不强制刷新会一直显示旧数字（实测踩过这个坑）。

## 9. 顶部「提交、推送、新建分支」：保留

用户自己在用，而且它不是在重复电脑已有的工具，而是一件本来要找 Agent 去做的事的快捷方式：点一下就提交，省一轮对话和 token，也不会往 Agent 的上下文里塞一句“帮我提交”。

开销很小：界面约 660 行，后端约 990 行；没有后台进程、轮询或文件监听，只在点按钮或读取分支信息时跑一次 git。

第二步插件结构理好后，它适合成为一个默认开启、可以关掉的能力。

## 10. Review 实测数据

用应用里同一套 Review 模块（git 后台线程、git 查询、文件监听、刷新合并），在本仓库上模拟 Agent 工作一轮，共 60 秒：每 3 秒改一个源文件，中途一次构建写出 500 个被忽略的产物文件，穿插 3 次 `git status`。

| | 不开 Review（基线） | 现状：实时监听 | 减法后：每轮结束查一次 |
|---|---|---|---|
| 总 CPU（含 git 子进程） | 0.47 秒 | 3.58 秒 | 0.77 秒 |
| 比基线多出的 CPU | — | +3.1 秒 | +0.3 秒 |
| 启动 git 进程次数 | 0 | 125 次 | 10 次 |
| 重新计算改动快照 | 0 | 22 次 | 2 次 |
| 峰值内存 | 50 MB | 75 MB | 69 MB |

- Agent 工作期间，实时监听多花约 10 倍 CPU，git 进程启动次数多 12 倍；内存差别不大，问题在 CPU 和进程反复启停。
- 这是温和场景：仓库干净（6 个改动文件），只有一次构建。开着 dev server、跑 `pnpm install`，或仓库里未提交改动很多时会更重；应用里每次刷新还要经过进程间通信和界面重渲染，没有计入。每打开一个工作区就多挂一个监听，直到应用退出都不释放。

## 11. 排除的方案

- **保留应用内 HTML 渲染，只是做好一点。** 排除：渲染 HTML 是浏览器的本职，沙箱 iframe 既占资源又做不好。
- **固定用 Chrome / VS Code 打开，并在启动时检查是否安装。** 排除：会强迫用户换软件，也会打扰没用到这些功能的人。改为系统默认应用加打不开时兜底。
- **保留实时监听，只优化过滤规则。** 排除：之前已经做过一轮优化（`git check-ignore` 过滤加 500ms 合并），结构性开销仍在；+N/−M 的价值撑不起常驻监听。
- **把浏览器能力的代码直接删掉。** 排除：它是 Agent 的能力，按判断线应插件化，删掉会丢掉以后可选安装的基础。
- **只保留暂存、删掉还原。** 排除：没有提交入口，暂存就是半个流程。
