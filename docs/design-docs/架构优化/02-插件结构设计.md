# 02 插件结构设计

本文定义插件结构，已实现。当前包地图以 [packages/README.md](../../../packages/README.md) 为准，加载清单是 `packages/core/runtime/src/plugin-catalog.ts`；本文保留设计理由和规则，§1、§4 的「原位置」列、§6.2 的「原来手写的」列描述的是 2026-11-01 改造前的样子，只用于对照旧文档。执行计划：[20261101-plugin-structure](../../exec-plans/completed/20261101-plugin-structure/README.md)。

## 1. 要解决的问题

第一步做完减法之后，留下来的东西要能被看清楚。改造前看不清，原因有四个（下面的路径与数量是改造前的）：

1. **目录没有规则。** 62 个包里，有的平铺在 `packages/` 下（`boot`、`subagent`），有的按类型分组（`tools/`、`context/`、`session/`），有的按能力分组（`sandbox/`、`llm/`）。同一类东西放在不同深度，例如 `packages/background-tasks` 和 `packages/tools/background-tasks`。
2. **名字和位置对不上。** 目录 `sandbox/manager` 里放的是 `@actspace/sandbox`，`session/jsonl` 是 `@actspace/session-jsonl`，`tools/shell-tools` 是 `@actspace/tools-shell-tools`。看到包名找不到目录，看到目录也猜不出包名。
3. **一个插件要在六个地方登记。**
   - `packages/runtime/cordis.yml`；
   - 它的镜像 `TRUSTED_LOADER_ENTRIES`；
   - `DEFAULT_HARNESS_ENTRIES` 及其特殊映射 `defaultHarnessEntrySource`；
   - `TOOL_PLUGIN_TRANSPORT`；
   - `baseBundle` 的 manifest 列表；
   - Harness 打包脚本里的 `harness:todo` / `harness:factory` 别名。

   漏改一处，要么启动校验失败，要么插件悄悄没加载。
4. **用户看不到装了什么。** 设置里只有「能力」页的两张卡片，没有地方列出当前加载了哪些插件、哪些可以关。

## 2. 原则

照 DeepSeek Harness（DSH）的做法：**简单、清晰，不引入新概念层。**

- 一个能力一个目录，目录下放包，只有两级：`packages/<能力>/<包>`。
- 目录名就是包名去掉 `@actspace/`。
- 用户看到的只有「插件」一个词，分两类：**全局插件**和**会话插件**。
- 每个插件的中文名称和说明写在它自己的 manifest 里。
- 加载清单只在一个地方定义，其他地方从它生成或用它校验。

## 3. 目录规则

### 3.1 两级结构

```
packages/
  README.md              总地图
  <能力>/
    README.md            本能力有哪些包、各管什么、怎么连
    <包>/                目录名 = 包名去掉 @actspace/
      package.json
      src/
```

- 只有两级。不管一个能力有一个包还是十个包，都放在 `packages/<能力>/<包>`，例如 `packages/shell/tool-shell`。
- `pnpm-workspace.yaml` 只保留 `packages/*/*`，删掉 `packages/*`。
- `browser-bridge/`（Go 程序和 Chrome 扩展）留在仓库根目录，不进 `packages/`。

### 3.2 命名

| 角色 | 命名 | 例子 |
|---|---|---|
| 接口（定义一项能力的约定） | `<能力>` | `sandbox`、`approval`、`background-tasks` |
| 实现（某个接口的具体后端） | `<能力>-<实现>` | `sandbox-seatbelt`、`session-persistence-jsonl`、`llm-pi-ai` |
| 模型工具（给模型调用的工具） | `tool-<名>` | `tool-fs-read`、`tool-shell`、`tool-browser` |
| 其他 | 直接说它是什么 | `agent-loop`、`context-disclosure`、`harness-hmr` |

不再用 `tools-` 复数前缀和 `core-` 前缀。

### 3.3 归属规则

**`context/` 只管“东西怎么进入模型的上下文”，东西本身住在自己的能力目录里。**

- 后台任务本身在 `background-tasks/`，“把后台任务状态告诉模型”的 `context-background-tasks` 在 `context/`。
- Skill 本身（发现、注册、官方 Skill）在 `skill/`，“把 Skill 目录告诉模型”的 `context-skills` 在 `context/`。
- 上下文压缩改的是上下文本身，所以 `context-compaction` 留在 `context/`。

改的是**包名和目录**，不改运行时标识：Entry id（如 `filesystem-read`、`tools-approval`）、plugin id（如 `actspace.context-rules`）、service id（如 `tools.runtime`）、事件类型。这些标识写进了会话日志、Harness 代际记录和用户设置，改了要做数据迁移，对“看清楚”没有帮助。插件清单（§6）把 Entry id 和新包名对应起来，所以不再需要按名字拼路径的特殊映射。

## 5. 插件

### 5.1 两类

| 类别 | 何时加载 | 由谁加载 | 对用户的意思 |
|---|---|---|---|
| 全局插件 | ActSpace 启动时，整个应用一份 | Host 的 Cordis 加载器（`cordis.yml`） | 影响所有会话，例如会话存储、模型服务、英语学习 |
| 会话插件 | 每个会话的 Harness 里一份 | 默认 Harness | 决定这个会话里的 Agent 能做什么，例如读写文件、命令行、操控浏览器 |

底座（会话存储、Agent 注册表、运行时）也是全局插件，只是不能关。

“可选”是状态，不是类别。一个插件处于三种状态之一：

- **未安装**：本轮没有这种插件，留给以后的外部插件。
- **已安装、关闭**：在清单里，但这次启动没有加载，例如默认的操控浏览器、英语学习。
- **开启**：本次启动已加载。

### 5.2 展示信息

每个插件的 manifest 增加 `display` 字段，中文：

```ts
display: {
  title: "上下文披露",
  description: "按需把工作区路径和文件摘要告诉 Agent",
  scope: "session",        // "global" | "session"
  defaultEnabled: true,
  canDisable: true,
}
```

- `defineBuiltinPluginManifest` 增加必填参数 `display`。`PluginManifest` 增加可选字段 `display`（外部插件以后也用它），内置插件由检查脚本保证必须有。
- `validatePluginManifest` 校验：`title` 不超过 12 个字，`description` 不超过 40 个字，`scope` 取值合法。
- `@actspace/runtime` 里没有独立包的条目（运行时底座、会话运行时、Agent 运行时、Agent 循环）在 `core/runtime/src/manifests.ts` 里各写一份 manifest。

本轮可以关的只有两个：操控浏览器、英语学习。其他插件 `canDisable: false`，在插件页显示为「内置」。

### 5.3 一个包里有多个插件

- `@actspace/runtime` 提供四个：运行时底座（`actspace-runtime`）、会话运行时（`session-runtime`）、Agent 运行时（`agent-runtime`），这三个是全局插件；Agent 循环（`agent-factory`）是会话插件。
- `@actspace/tool-todo` 提供两个：待办工具（`todo-tools`，会话）和待办视图（`todo-projection`，全局）。待办视图从 `@actspace/runtime/todo-projection` 改为 `@actspace/tool-todo/projection`。
- `llm-service` 同时挂在 Host 和 Harness 里。插件清单里写成一行、`loaders: ["host", "harness"]`，插件页只在「全局」下显示一次。

| `browser-tools` | 操控浏览器 | 通过 Chrome 扩展操作网页 | 关 | 是 |

“默认”指 `defaultEnabled`。工具设置页里的单个工具开关（例如关掉网页搜索）不变，它控制的是工具可见性，不是插件加载。

## 6. 插件清单：唯一的登记处

### 6.1 位置与形状

新文件 `packages/core/runtime/src/plugin-catalog.ts`，导出 `PLUGIN_CATALOG`：

```ts
export type PluginCatalogEntry = {
  readonly id: string;                               // Entry id，不改
  readonly manifest: PluginManifest;                 // 从包的 ./manifest 导入
  readonly module: string;                           // 加载入口，如 "@actspace/tool-fs-read/plugin"
  readonly loaders: readonly ("host" | "harness")[];
  readonly codec?: string;                           // 有 Codec 的插件，如 "@actspace/tool-fs-read/codec"
};
```

每个插件只在这里写一行。顺序就是加载顺序。

同一文件导出 `PLUGIN_PACKAGES_OUTSIDE_DEFAULT`：带 `plugin.ts` 但不在默认组合里的包，每项写包名和一句原因（§4 开头列出的五个）。检查脚本据此区分“漏登记”和“有意不加载”。

### 6.2 从清单派生的东西

| 原来手写的 | 改成 |
|---|---|
| `packages/runtime/cordis.yml` | 由 `scripts/generate-plugin-loader.mjs` 从清单生成，`--check` 模式进 CI；文件头注明“生成文件，勿手改” |
| `TRUSTED_LOADER_ENTRIES` | 从清单的 `loaders` 含 `host` 的行计算，`inject` 取 manifest 的 `injects` |
| `DEFAULT_HARNESS_ENTRIES` | 从清单的 `loaders` 含 `harness` 的行计算，`provides` / `injects` / `optionalInjects` 取 manifest |
| `defaultHarnessEntrySource` | 删除，入口直接用清单的 `module` |
| `TOOL_PLUGIN_TRANSPORT` 与 `loadBuiltinToolCodec` 的特判 | 删除，Codec 用清单的 `codec` |
| `baseBundle` 的 manifest 列表 | 从清单中带 Codec 的行计算 |
| `composition.ts` 里内联的 `browserManifest` / `browserBundle` | 删除，用 `@actspace/tool-browser/manifest` |
| Harness 打包脚本的 `harness:todo` / `harness:factory` 别名 | 删除。`@actspace/tool-todo/plugin` 直接导出 `apply`，`@actspace/runtime/agent-factory` 导出 Agent 循环 |
| `boot.ts` 里“没有 `browser` 能力就禁用 `browser-tools`”的写死判断 | 改为通用规则：manifest `host.required` 里有 Host 不具备的能力，该条目就不加载 |

`DESKTOP_APP_BUNDLE`（桌面形态的应用 Bundle）和 `apps/cli/cordis.yml`（CLI 装配）各自保留，但其中出现的条目必须在清单里，由检查脚本校验。

### 6.3 依赖方向

- `@actspace/runtime` 的源码不再 import 或重导出 `@actspace/tool-browser`。桌面端需要的 `createNodeBrowserCapability` 等直接从 `@actspace/tool-browser` 导入。
- 默认 Harness 打包时要解析所有会话插件，所以 runtime 对这些包的依赖保留在 `package.json` 里，只用于打包，源码里除插件清单外不直接引用它们。

## 7. 开关与插件页

### 7.1 设置

设置 `tools` 下新增可选字段：

```ts
plugins?: Record<string, boolean>   // key 是 Entry id；缺省取 manifest 的 display.defaultEnabled
```

- 只有 `canDisable: true` 的插件读这个值，其余忽略。
- 不升 schema 版本，在 `migrations.ts` 的 tools 规范化里只保留布尔值，做法与现有 `tools.deepseekFetchEnabled?` 相同。
- 改动后重启生效，不做运行中热切换。

### 7.2 关闭时的行为

| 插件 | 关闭时 |
|---|---|
| 会话插件（操控浏览器） | 进入 `disabledHarnessEntries`，Harness 不加载。桌面端同时不创建 `BrowserBridgeService`、不轮询、不安装 Native Host、不上报 `browser` 能力；10 个浏览器 IPC 保留为桩，`getStatus` 返回“未启用”，其余返回错误“插件未开启” |
| 全局插件（英语学习） | 桌面端给 `createProfileComposition` 传 `invocationPatch`，对该条目做 `disable`。不创建 `DesktopSpeechPlayback`；英语学习 IPC 保留为桩 |

第一步计划 P6 的 `tools.optionalCapabilities` 字段和「能力」页开关不再做，由这里的通用开关取代。

### 7.3 插件页

扩展页的「能力」标签改为「插件」，与「Skills」「MCP」并列。采用「能关的插件在上」方案（原型见 git 历史）：每组里能关的插件放在最上面，其余收进「内置插件 N 个，不能关闭」折叠行；搜索时自动展开。

- 两组：「全局插件」「会话插件」，各自一句说明。
- 每行：名称、说明、所在目录（如 `context/`）、状态。状态有三种：「内置」（不能关）、开关（能关）、「重启后生效」（设置值与本次启动的加载状态不同）。
- 搜索框搜名称和说明。
- 操控浏览器、英语学习开启后，行下面展开原来的连接面板、英语学习设置；关闭时不渲染这些细节，也不请求浏览器状态和英语学习状态。
- 工具设置里的“浏览器”工具组、常规设置里的语音设置，在对应插件关闭时隐藏。

数据来自新 IPC `plugins.list`，main 从插件清单、本次启动的组合结果和设置算出：

```ts
type PluginListItem = {
  id: string; title: string; description: string;
  scope: "global" | "session"; directory: string;   // 能力目录名，如 "context"
  canDisable: boolean;
  loaded: boolean;        // 本次启动是否已加载
  enabled: boolean;       // 设置里的值（重启后生效的值）
};
```

“本次启动的值”由 main 记住，第一步 P6 里 renderer 模块级变量记启动值的办法不再需要。开关写设置走现有 `settingsApi.update`。

## 8. README 规范

### 8.1 总地图 `packages/README.md`

现有的 `packages/README.md` 和各目录下的 26 份 README 按下面的规范重写。

```md
---
description: "ActSpace 的包工作区：packages/ 下按能力分目录，每个目录放哪些包、谁依赖谁。"
kind: "package-map"
---
```

内容依次是：

1. 组织规则：两级结构、目录名即包名、命名约定（§3.2）、归属规则（§3.3）。
2. 能力目录表：目录、一句话职责、包数、全局 / 会话 / 库、链接到该目录 README。
3. 依赖方向：`util` ← `composition` ← `core` ← 各能力 ← `host`；能力目录之间只通过接口包依赖；应用（`apps/*`）不被包依赖。
4. 新增一个插件的步骤：选目录 → 建包（`manifest.ts` 含 `display`、`plugin.ts`、生命周期测试）→ 在插件清单加一行 → 跑 `pnpm generate:plugin-loader` → 在目录 README 的包表里加一行。
5. 检查命令：`pnpm check:packages`、`pnpm check:docs`。

### 8.2 能力目录 README `packages/<能力>/README.md`

```md
---
description: "一句话：这个能力做什么。"
kind: "package-group"
---
```

内容依次是：

1. 这个能力做什么、为什么要有它（两三句）。
2. 包表：包、角色（接口 / 实现 / 工具 / 库）、类别（全局 / 会话 / 库）、默认开关、一句话职责。
3. 包之间怎么连：谁 provides 什么服务、谁 inject 什么，用一张简图或一段流程。
4. 关键入口文件和测试。
5. 怎么扩展（例如新增一个沙箱后端要做什么）。

### 8.3 检查

新脚本 `scripts/check-package-readmes.mjs`，加进 `pnpm check:docs`：

- 每个能力目录都有 README，且 frontmatter 有 `description` 和 `kind`。
- 每个包都出现在所在目录 README 的包表里，包表里没有不存在的包。
- 每个能力目录都出现在总地图里。
- 包表里写的类别与插件清单一致：在清单里且 `loaders` 含 `host` 的是全局、含 `harness` 的是会话，不在清单里的是库。
- `packages/` 下不允许出现第三级包或第一级包。

另加 `scripts/check-plugin-catalog.mjs`（进 `pnpm check:packages`）：清单里每一行的 manifest 都有 `display`；`module` / `codec` 能解析；`cordis.yml` 与清单一致；`DESKTOP_APP_BUNDLE` 和 `apps/cli/cordis.yml` 的条目都在清单里；包里有 `src/plugin.ts`、却既不在清单里也不在 `PLUGIN_PACKAGES_OUTSIDE_DEFAULT` 里的报错。
