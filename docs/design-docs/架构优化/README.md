# 架构优化

更新：2026-11-01。状态：两步都已与用户逐项确认，待实施。

## 为什么做

ActSpace 是一个人在做的产品。如果大公司的 Agent 产品有什么功能就跟着做什么，既追不上，也会把精力耗光。这次架构优化只回答一个问题：**什么属于 ActSpace，什么不属于。**

## 判断线

定位来自 [ActSpace 产品概念思路（初稿）](../ActSpace产品概念思路初稿.md)：**会自我进化的 Agent 运行空间**。官网和 [roadmap](../../roadmap.md) 的三个方向是：上下文管理引擎、Harness 自进化、Actor 与 Space。

信念“唯变所适”要求空间“加上需要的，去掉多余的”。减法就是 ActSpace 践行自己的信念：一个主张去掉多余的产品，自己不能臃肿。气质“有分寸”也一样：知道自己的场景在哪，不越界，不硬做。

由此得到判断一个功能是否属于 ActSpace 的三条线：

1. **人和 Agent 都需要看到的，是上下文，属于 ActSpace。** 例如后台任务：用户要知道它在跑什么，Agent 也要知道。轨迹、上下文面板、压缩展示、用量、侧边对话、消息排队都在这一边。
2. **Agent 的能力，做成可选插件。** 某个空间或 Actor 需要时装上，不需要时就没有。例如操控浏览器、英语学习。
3. **只给人用、电脑上已有更好软件的工具，删掉。** 例如终端、文件树、PDF 和 Office 渲染。系统终端、Finder、VS Code、浏览器、Office 都比我们做得好。

格式上同样如此：PDF、Word 这类旧格式，Agent 要先转换才能读，交给原有软件；Markdown 和图片 Agent 可以直接读，是人和 Agent 共用的语言，所以保留并做精。

以上三条线覆盖了用户已经确认的部分。剩下拿不准的情况，逐项由用户判断，不另写成规则。
