# Harness 插件化与 Agent Host 分离：讨论与已确认决策

> 更新日期：2026-10-03。
> 状态：已确认设计与讨论记录；P1 已获批实施并完成自动化验收，其他阶段仍是目标设计。
> 本文描述目标，不代表当前实现。后续讨论持续更新本文件，避免另起多份相互漂移的方案。

## 1. 目标与讨论顺序

本轮重构有两条必须完成的架构主线：

1. 解耦 Agent 核心与扩展，贯彻“一切皆插件”，为即将增加的 Harness 自进化能力准备可组合、可替换的模块边界。
2. 完成 Agent Host 与客户端分离，明确 Agent 在哪里运行、谁拥有生命周期，以及 Desktop、CLI 如何使用它；不只是预留远程接口。

同时要减少冗余代码，使后端核心精简、目录职责清晰；后续再合并精简或删除冗余文档，核对文档与实现漂移，最后清理废弃目录。

2026-10-03 用户进一步明确优先级：模块化、解耦与可替换性优先，在此前提下精简。文件数、包数、层数和代码行数不是独立的优化目标；不得为了减少它们而合并本应独立演进的职责、引入隐式依赖或共享可变状态。重构前后统计用于观察变化，不作为架构优劣的单独判据。

推进方式：一步一次讨论，先确认边界，再形成实施计划；编写代码前描述方案并取得批准。当前只讨论插件边界与 Host/Client 分离。文档整体优化和目录删除暂不展开；本文件仅保存讨论，不属于开始文档迁移。

## 2. 已确认：一切皆插件，Loop 也可替换

- 插件底座只承担加载、依赖解析、作用域、生命周期和组合校验等基础职责，不固化 Agent 执行算法。
- Agent Loop、Session、LLM、Prompt、工具、上下文、压缩和子 Agent 等能力均可由插件提供。默认必装或业务重要，不等于必须属于不可替换的底座。
- 当前 Agent Loop 是默认实现，并非绝对不可替换；Harness 自进化可能修改或替换 Loop 本身。
- 稳定的是必要的插件协作契约，不是当前实现类及其全部内部细节。不能把现有 Loop 的所有实现细节复制到一个接口，就宣称完成解耦。
- 插件化不意味着每个函数、策略或职责都要新增一个包、一个服务或一层转发。判断标准是能否组合与替换行为，以及依赖、状态和资源释放的归属是否清楚。
- 模块边界与 package 边界分开判断；为实现可替换性而保留必要的接口、适配和装配代码是合理成本。精简优先消除重复实现、重复状态管理和无意义转发，不能以减少包数为由牺牲模块边界。

讨论中的概念划分：

| 层次 | 职责 |
|---|---|
| 插件底座 | 加载、依赖与作用域管理、生命周期、组合校验 |
| 能力与行为插件 | 提供实际 Agent 行为及支撑能力，可通过契约替换实现 |
| Harness 组合 | 选择插件实现、绑定依赖、配置策略，形成可识别的运行组合 |

“Harness 组合”目前是设计概念，不是批准新增框架或 package。优先检查现有 Profile / Bundle 能否承担该职责；具体映射尚未决定。

## 3. 已确认：运行边界替换，不做执行中热切换

- 一次运行开始时固定 Harness 插件组合、版本和配置。
- 运行期间允许正常的消息输入、审批和取消，但不替换该运行的 Loop 实现。
- 新 Harness 版本用于后续运行；旧运行使用原组合完成或终止。
- 记录每次运行使用的组合，用于实验比较、追溯和回退。选择规则见第 9 节；记录结构和评估接入尚待设计。
- 版本记录不等于承诺 Host 崩溃后自动续跑。

不做运行中热切换的原因：必须交接进行中的模型请求、工具副作用、审批和 Loop 内部状态；不同 Loop 未必兼容这些状态。该场景预期很少，首期不承担状态迁移、重复执行防护和热切换回滚的复杂度。

这里的“一次运行”已明确为一项任务从被接纳到完成、失败或取消，详见第 8 节。与仓库现有 Agent Run、Turn、Step 标识和事件的具体映射仍需在契约设计时核实，不能解释为整个 Session 永久固定，或任意 Step 都可切换。

## 4. 已确认：Host / Client 边界与服务合并

目标关系：

```text
Desktop / CLI / 后续 Web
          |
      Agent Client
          |
    Agent Service 插件
    应用操作 + 运行所有权
          |
    Harness 插件组合
    Loop / Session / Prompt / LLM / Tools 等

Agent Host 启动、持有并关闭上述服务端运行环境。
```

Host 拥有运行是生命周期意义上的所有权，不意味着把所有业务逻辑写进 Host 入口。应用服务和执行能力仍由插件承载。

| 部分 | 目标职责 |
|---|---|
| Agent Host | 提供运行环境与宿主能力，启动插件组合，管理进程侧启动和关闭 |
| Agent Service 插件 | 接受任务、持有运行实例、固定本次 Harness 组合，提供会话操作、查询、取消、审批和订阅 |
| Agent Client | 薄调用入口，适配进程内调用或远程连接，不再实现一套任务调度与会话业务状态机 |
| Desktop / CLI | 输入、展示与各自的本地交互能力 |

原讨论曾提出“应用服务插件 + 执行管理插件 + Agent Client”三部分。用户认为层次过多，已确认收敛为 Agent Service 与薄 Agent Client：

- 应用服务与执行管理合并，不新增独立的执行管理插件。
- Agent Service 内部可按职责分文件，也可复用已有运行控制对象；这不自动意味着新增服务层。
- 上述合并收敛的是对外应用入口与运行所有权，不授权将调度策略、审批、存储和 Loop 的实现耦合进同一个不可替换模块。内部仍应保留清晰的模块契约与依赖边界；若后续分析发现既定合并妨碍独立替换，应按解耦优先的原则重新讨论。
- 内嵌 Client 可以直接适配 Service，不要求每个调用经过多级转发。
- 不把 Client 与服务端完全合成一个跨端业务模块：远程形态确实存在两端，运行所有权必须留在服务端。
- 上述名称是职责名称；实际包名、类型名、目录名及迁移路径尚未决定。

提交与等待完成需要分开：客户端提交任务后获得运行标识，随后可观察、断开和再次查询。独立 Host 上的运行不能绑定于一次网络请求或连接。CLI 可以继续表现为“提交、等待结果、退出”，等待属于客户端使用方式。

## 5. 已确认：本机默认内嵌，远端独立运行

用户已批准的取舍：

- Desktop 本机默认保留内嵌 Host；本地一次性 CLI 可以内嵌运行。
- 本次实现可独立运行的 Agent Host，供远程运行使用，验证客户端断开后任务仍可继续。
- 两种形态复用相同应用契约、服务实现和插件组合机制，不复制另一套 Agent 内核。
- 内嵌形态通过类型化调用接入；进程外采用 JSON-RPC 2.0 over WebSocket，见第 13 节。Web 使用 WSS，Desktop 支持 WSS 或 SSH 隧道，见第 14 节；认证与具体部署配置尚待确定。
- 不在首期引入本机默认常驻 daemon 的安装、自动启动、发现和升级管理。未来是否提供本机独立 Host 产品入口另行讨论。

取舍依据：

| 内嵌 Host | 独立 Host |
|---|---|
| 启动、安装、调试与升级较直接 | 可独立于客户端进程持续运行 |
| Desktop 主进程退出，运行随之结束 | 需要连接、进程生命周期、版本匹配和故障处理 |
| 主进程故障会影响执行 | 客户端与 Host 的进程故障可以分开 |
| 不天然提供多个独立客户端的共享入口 | 可提供多个客户端连接同一 Host 的入口 |

关闭窗口不一定等于退出 Desktop 主进程；不能把窗口关闭与 Host 销毁混为一谈。内嵌模式不承诺主进程退出后继续运行。

远端持续运行的条件是远端 Host 仍健康且机器在线。客户端断开或客户端电脑关机，与 Host 崩溃、远端重启是不同故障；本轮尚未批准崩溃后自动续跑语义。

## 7. 已确认：复用现有服务，分离具体行为策略

2026-10-03 用户确认以下收敛方向；具体迁移文件与接口仍需后续设计：

- 以 `DesktopAppService` 的共同能力为基础形成 Agent Service，不在现有服务上面新增总门面，也不把原类全量改名后继续扩大。
- 创建、恢复、分叉会话，提交运行、取消、读取与订阅等作为共同应用入口。持久化、权限判断、压缩等具体能力仍由相应插件实现，Service 调用契约。
- 自动生成标题成为可选行为插件，可以默认启用，但不作为 Service 提交任务流程中的内置步骤。
- Chat / Plan / Agent 的具体策略交给相应行为插件或 Harness 组合；共同服务负责统一接纳、校验与调用，不各自在 Desktop 和 CLI 内实现策略。
- `HeadlessRunner` 收敛为使用共同服务的一次性工作流：解析输入、创建或恢复会话、提交、等待展示、导出和退出码。CLI 不再直接写 Journal；临时与持久化会话意图仍可保留。
- CLI 只关闭自己拥有的内嵌 Host，退出远端连接不能关闭远端 Host。
- 收敛 `DesktopAppService`、`RunController`、`AgentLoopService` 之间重叠的运行管理：共同 Service 内部有一个明确的运行管理者，复用现有排队、取消和释放逻辑；Loop 插件拥有具体执行状态。允许分文件，不增加独立执行管理服务层。
- Service 管理任务接纳、Harness 选择和执行所有权；Loop 管理本次执行如何进行及响应取消。
- Electron IPC、窗口、通知及终端展示留在相应客户端适配侧。

尚不能直接删除 `RunController` 的直接 Loop 执行分支：生产组装传入了 AgentLoopService，但测试和其他用途仍需核对。以上决定不授权删除现有能力或改变兼容行为。

## 8. 已确认：Session 跨运行保留，Loop 按 Run 创建与释放

2026-10-03 用户确认：

- Run 是一项任务从被接纳到完成、失败或取消的完整执行；期间多次模型调用、工具执行、等待审批和运行中插入指导均属于同一 Run，使用同一 Harness 组合。
- Session 长期保存会话事实，可以包含多次 Run，不永久绑定某个 Loop 对象。
- Loop 实例为本次 Run 创建，执行结束后释放其运行资源。
- 插件底座和声明为可共享的插件服务继续复用，不要求每次 Run 都重新加载所有插件。
- Session 不锁定 Harness；后续 Run 默认使用实际开始执行时已启用的对应组合，已在执行的 Run 保持原组合。新代码存在不等于新组合已启用，具体规则见第 9 节。
- 新 Harness 接手已有 Session 前必须满足历史事实的兼容要求；不兼容时明确拒绝或另开会话，不默认任意 Loop 能无损接手。

当前实现按 Session 缓存 Agent assembly，迁移时需要实际调整该生命周期。释放运行资源与继续保留 Session 事实必须分开；后台工具、子任务的归属及收尾边界仍需核实，不能简单销毁所有 Session 资源。

## 9. 已确认：会话连续，运行固定，新运行跟随已启用组合

2026-10-03 用户以两个场景明确了选择规则：同一会话内要求 Agent 修改 Harness 后，应能继续在该会话使用改进；主 Agent 后续创建的子 Agent，也可能使用最新 Harness。

“版本”在这里表示可识别的 Harness 插件实现与配置组合，不是项目既有 v1/v2 架构或模型版本。组合也可能是并行实验，不要求简单的新旧关系。

| 时点或场景 | 已确认行为 |
|---|---|
| 提交消息、进入队列 | 保存任务意图，默认不锁定具体 Harness 组合 |
| 任务实际开始执行 | 解析当时已启用的对应组合，固定到本次 Run |
| 执行期间启用新组合 | 当前 Run 继续使用原组合，不做运行中热切换 |
| 同一 Session 的后续 Run | 默认使用开始执行时已启用的对应组合，无需新建会话 |
| 创建子 Agent Run | 独立选择该子 Agent 所对应 Harness 的当前已启用组合，不强制继承父 Run 的组合 |
| 可重复的评估实验 | 可以显式指定组合，不跟随默认组合更新 |

例如当前 Run 用 A 修改 Harness，检查并启用 B 后仍用 A 收尾；同一 Session 的下一次 Run 用 B。主 Run 用 A 时，之后创建的 Explore 子 Run 可使用 Explore 当前启用的组合，而不是无条件套用主 Agent 组合。父子任务归属、权限约束和取消传播仍需保留。

修改成功与启用成功必须区分：“最新”指成功启用的组合，不是磁盘上最后修改的代码。加载失败或不兼容会话历史时明确报告，不能声称已切换；启用原则见第 10 节，具体校验契约仍待细化。

实现必须允许同一 Host 内旧 Run 使用 A、新 Run 使用 B 的过渡共存。不能覆盖所有运行共享的可变插件实例；发生变化的实现与配置需要隔离，无变化且兼容的基础服务才可共享。旧组合释放时机、模块加载和作用域机制尚未决定；本决策不授权假定现有 loader 已支持新旧组合共存。

此前提出的“Session 固定版本、显式升级”和“任务提交时锁定排队任务组合”已被本节取代，不作为实施依据。Run 可以在接纳后排队，但 Harness 在实际执行开始时才固定；接纳与启动的具体事件和标识映射仍待定义。

## 10. 已确认：显式启用与在线替换边界

2026-10-03 用户确认：

- 通过明确的“启用新组合”动作发布变更：修改插件或配置 → 准备并校验新组合 → 启用成功 → 后续运行使用新组合。
- 用户可以触发启用，Agent 也可以通过受控能力调用。2026-10-03 已确认：启用是独立权限操作，接入现有审批机制，首版默认明确批准；代码修改、准备与验证不等于启用授权，Bash/文件写入授权不自动包含启用权限，由 Host 启用入口执行检查。后续可支持明确授权范围内自动启用。具体工具字段在 P3 计划中定义。保存文件本身不触发自动启用，避免加载尚未完成的修改。
- 新组合加载、依赖和契约检查成功后，才切换后续运行的选择。失败时保留原有可用组合并明确报告失败，不声称新组合已启用。
- 已在运行的任务继续持有旧组合；相应运行资源释放后再清理旧实例，不能因启用新组合销毁旧运行依赖。
- 可隔离到运行组合中的能力（例如 Loop、Prompt 策略）支持在线启用与新旧共存，不要求为此新建会话或手动重启。
- 插件可替换不等于所有插件必须可在线替换。涉及 Host 监听端口、共享存储实现或数据格式迁移的变更，首期允许要求停止接纳任务、完成收尾后重启。
- 具体在线/重启分类依据插件依赖和资源所有权确定，不只按插件名称推断。尚未冻结分类清单、加载隔离机制和迁移方式。

## 11. 已确认：断线继续、审批等待、重连找回与提交去重

2026-10-03 用户确认以下独立 Host 行为：

- 客户端断线、退出或客户端电脑关机，不取消 Host 上已接纳的任务；前提是 Host 仍健康运行。
- 遇到需要审批的操作，保留审批请求并等待，不因客户端离线自动批准。等待暂停相关执行，不阻塞整个 Host 或其他会话。
- 首期不因客户端离线额外设置审批超时。2026-10-03 已确认：审批等待不消耗执行时长预算；用户明确指定的截止时间仍生效，到期停止推进并使待处理审批失效，旧审批不能重新启动任务。不撤销已发生的工具副作用。
- 客户端重连后找回同一任务的当前状态、结果和待审批事项，不重新创建任务。
- 用户明确取消任务时，由 Host 执行取消，并使该任务尚未处理的审批失效。
- 同一次提交携带稳定的请求标识。客户端未收到接纳回复时可以重试，Host 判断是否已接纳并返回原任务，不能意外启动第二次执行。
- Host 自身崩溃或重启与客户端断线分开处理；首期不承诺自动续跑。

上述提交去重不是对工具副作用 exactly-once 的承诺。去重记录与任务接纳如何持久化、标识作用域与保留期限、重连事件补齐及审批竞态的具体契约仍待设计。

## 12. 已确认：Host 关闭与崩溃恢复

2026-10-03 用户确认：

- 更新需要重启而仍有未完成任务时，暂缓更新，不自动中断任务。等待审批及排队任务也属于未完成任务。
- 用户明确停止 Host 时，停止接纳新任务，取消未完成任务，保存状态并释放资源后退出。
- 正常停止设置有限的收尾期限，避免永久挂起；超期明确报告未完成收尾，不能将所有任务标成已安全取消。具体期限与超期退出机制在实施计划中确定。
- Host 崩溃或机器断电后，重启恢复已持久保存的会话与任务记录；未结束的运行标记为已中断，首期不自动续跑。
- 工具可能已执行但结果未记录时，标记结果未知，不盲目重放工具副作用。
- 恢复会话不等于恢复旧 Loop 的内存执行状态。用户可以在原会话提交后续任务，但不能宣称旧运行已从中断点自动继续。

以上是行为决定，不是现有实现已通过恢复验收的声明。运行记录、未启动队列及工具检查点的持久化映射仍需在具体契约中定义。

## 13. 已确认：进程内直调，进程外 JSON-RPC over WebSocket

## 17. 已确认：多端均可操作，由 Host 统一排序和裁定

- 将 Cordis 的服务依赖、类型化事件、作用域和可撤销注册作为插件设计依据，不只在现有类外套一层插件入口。
- 将事件分发模式作为公开契约；纳入 `@mode` 声明及声明与调用点交叉检查的设计。检查实现尚未编写，不能声称已有保障。
- 具体能力如何分配给服务方法、事件和中间件，以及监听器顺序、错误与短路规则，仍需逐项设计。

本轮源码核对结果（不是运行验收）：

- Loop 和工具执行已有 `waterfall` 干预点，结束流程已有 `serial`；不是从零引入事件。
- `packages/cordis-adapter/src/event-contract.ts` 已有类型声明合并，但当前事件声明没有 `@mode`，部分分发接口仍接受宽泛字符串与 payload。
- `emitContained` 通过底层 `dispatch("emit", ...)` 取得回调后等待 `Promise.allSettled`；其等待行为不能等同于原生 `ctx.emit`。`requiredDispatch` 也手动调度回调；需要审查封装如何影响模式检查、错误传播与生命周期。
- 当前 adapter 的窄 `CordisContext` 没有暴露 `bail`。是否调整导出与封装，须结合事件契约设计，不因补齐模式而机械增加事件。

2026-10-03 用户认可上述协作方向并同意以工具执行继续细化：直接能力调用使用注入服务；策略干预使用具有明确模式的事件；观察通知与必须成功的业务操作分开。每个事件明确所属模块、参数与结果、模式、作用域、顺序、错误和短路语义。新旧 Harness 的监听器必须按运行组合隔离，避免新策略影响仍在执行的旧 Run；持久记录与远端协议不直接等同于进程内事件总线。

语义注意：`serial` 是按序等待直到返回 bail 值，并非保证执行全部监听器；`waterfall` 是 `next()` 环绕调用链，返回值可以是 Promise，不能把入门表格的“不 await”解释为异步链永远无需等待。具体事件须明确自己的返回与等待契约。

## 22. 已确认：工具服务完成调用，Cordis 中间件提供扩展点

2026-10-03 用户认可以下工具执行职责边界；具体接口尚未冻结：

## 23. 已确认：Host、Harness 组合与 Run 的生命周期归属

2026-10-03 用户认可以下资源归属；这是生命周期划分，不要求新增三层业务服务：

- Host 持有网络接入、认证、任务管理，以及明确兼容且未变化的共享能力。
- 某个 Harness 组合持有选定的插件实现、配置、策略监听器及组合依赖。
- 单次 Run 持有 Loop 实例、取消信号、执行临时状态及运行资源。
- 固定 Harness 包括固定该 Run 看到的服务实现、配置和策略链。不能只保留旧 Loop，却让它从全局读取新启用的策略。
- 启用新组合后，旧 Run 的后续工具调用仍使用旧策略，新 Run 使用新组合；兼容的存储等能力可共享。
- 策略默认归组合，执行状态归 Run，明确兼容的基础能力才共享。旧组合无运行或其他使用者后再撤销监听器、释放资源，不能销毁仍被其他组合使用的共享服务。
- 避免将新旧策略都注册为全局处理器，导致同一次调用重复处理。影响共享服务且无法并存的变更，按既定停止接纳、收尾和重启流程处理。

具体 Cordis 作用域、服务查找与监听器隔离机制尚未选择或验证，不将上述目标当成框架自动提供的保证。

## 24. 已确认：替代 Loop 与插件契约兼容性

2026-10-03 用户认可以下原则：

- 区分能力模块公共契约与特定 Loop 的扩展点。工具执行、模型请求、会话记录和审批等契约由相应能力模块提供；新 Loop 使用这些能力时遵守其契约，相关插件可继续参与。
- 某种思考步骤、规划阶段等扩展点可能只属于特定 Loop。替代 Loop 不必模拟原算法，也不能仅沿用事件名就宣称行为兼容；依赖这些扩展点的插件需要明确适配。
- 插件声明所需服务和扩展点，新组合启用前检查依赖。必需契约缺失或不兼容时拒绝启用，并指出受影响插件与缺失契约。
- 可选能力缺失时，按插件事先声明的降级行为处理；不能静默跳过必需插件并报告启用成功。
- 声明检查与行为验证分开：声明用于发现依赖和接口问题，契约测试用于验证实际行为；声明通过不等于行为已兼容。
- 优先复用已有插件声明与 Cordis 依赖机制，按缺口补充，不先建设独立的兼容性框架。

具体声明格式、契约兼容规则及检查实现仍待设计，尚未冻结接口或授权代码实施。

### HeadlessRunner 工作流边界（已确认）

2026-10-03 用户认可将其定位为共同服务的一次性工作流调用者，按下述边界迁移；未授权代码实施。

本轮读取 `packages/headless/src/runner.ts` 与 `apps/cli/src/runtime-v2/run.ts`。现有 Runner 直接持有 `SessionHandle`、写标题和模式事件、attach Agent、等待 followup 与 idle、flush；CLI 入口负责输入、导出与最终关闭自己启动的 Profile。以下细化第 6 节已确认方向：

- Runner 经共同服务创建/恢复会话、设置元数据、提交任务，使用返回的任务标识订阅或等待该任务结果；不等待整个 Host 空闲。
- Runner 不直接持有 SessionHandle、Agent 或 Loop，不直接写 Journal、执行模式规则或手动 flush。服务明确接纳与终态记录的持久化语义。
- 参数/stdin 解析、输出格式、文件导出和退出码归 CLI。导出内容通过读取/导出契约取得，写入客户端输出目录仍由 CLI 负责。
- 任务取消与停止等待分开；显式取消调用共同服务，连接断开不暗示取消。只关闭由本次命令拥有的内嵌 Host，不关闭独立 Host。
- 保留本机一次性执行的临时会话意图，但不承诺其在进程结束后可恢复。独立 Host 上正常接纳任务仍遵守持久接纳约定；临时模式不得无声削弱该保证。具体临时数据保存与清理方式待核对。
- 复用工作流不等于让 CLI 直接加载 Desktop Bundle。CLI 与 Desktop 通过各自组合使用同一应用契约。是否保留 Runner 独立包待职责与调用方核查后确定。

非交互 CLI 遇到审批时现有退出行为需在后续具体契约中与 Host 审批等待规则对齐，不能直接视为远端任务已取消；本节不增加远程 CLI 交付范围。

### RunController 与 AgentLoopService（已确认）

2026-10-03 用户同意下述划分：运行管理拥有统一的状态管理权，内部按职责模块化；Loop 承担单次执行，上层通过明确运行标识操作。此确认不授权代码实施。

本轮再次核对两者源码：`RunController` 缓存 assembly 并提供直调 Loop 与委托 AgentLoopService 两条路径；`AgentLoopService` 持有 Agent registry、followup Promise 链、接纳开关及 dispose 状态。它在排队 Promise 得到执行后才调用 inbox.enqueue，不能直接当成新的持久接纳实现。

- 将排队、运行实例登记、开始/终止状态与关闭协调收敛到运行管理模块，由 Agent Service 组合调用；不将两个类机械合成一个大类。
- 模块内部将任务记录/队列、活动运行句柄、Harness 解析与实例创建按职责组织，通过契约协作；持久状态与内存索引应明确主从关系，避免多个集合各自决定运行状态。
- Loop 插件提供单次运行执行实现及必要的控制契约，不持有跨 Run 的会话排队注册表；会话记录由会话/存储模块管理。
- 接纳时先持久保存，再进入可启动队列；启动时选择 Harness 并创建 Loop；收尾保存结果、释放该 Run 的资源与组合引用。失败和取消路径也需完整收尾。
- 上层取消和 steer 面向明确的运行标识，避免延迟命令误作用于同一会话的后续 Run；会话级取消队列等操作另行明确作用范围。
- 对外不暴露 assembly、loop 或 inbox。原有直调 fallback 与委托路径须核查所有调用方后统一迁移；不提前删除测试或兼容路径，也不保留第二套独立运行状态机。

具体任务/Run 标识映射、模块包名与类的保留/删除仍待实施设计，本节只确定职责收敛方向。

### Profile / Bundle / Patch 与 Harness 组合（方向已确认）

已核对 `packages/runtime/src/profiles/composition.ts`：当前 Profile 按 desktop/headless 区分，组合 kernel、base 和应用 Bundle，并由 `composeRuntime` 解析；现有启动组合同时包含宿主与执行相关能力。不能直接将整个已启动 Profile 当成可随 Run 替换的 Harness。

2026-10-03 用户认可复用已有 Profile/Bundle/Patch 的组合描述与解析能力，区分 Host 启动装配和可替换 Harness 执行组合，并补充：Profile 不应每次替换；合理组织 Bundle 后，通过 Patch 描述局部变更，例如仅替换一个工具插件。这是三者设计的关键用途，不应每次重建整个启动组合。

- Profile 提供稳定的组合基线，Bundle 组织可复用插件集合，Patch 表达相对于明确基线的插件或配置差异；不新增平行的组合框架。
- Patch 解析得到新的候选组合，经过校验和成功启用后供后续 Run 选择；不原地修改旧 Run 正在使用的实现、配置或监听器。继续遵守新旧共存与显式启用规则。
- 一次解析、校验并成功启用的 Harness 组合需具有可追溯身份，并在运行开始时绑定。客户端形态不决定唯一的执行算法，同一 Host 可支持主 Agent 与子 Agent 各自的组合。
- 局部描述变更不等于运行时只需重建单个实例；哪些依赖者需要重新装配、哪些兼容能力可共享，要依据依赖与资源归属判定，不能为复用而破坏新旧组合隔离。
- 当前 `PatchOperation` 支持 `insert`、`replace-config`、`disable`、`remove`，没有专门的插件替换操作；`applyPatch` 处理组合条目，不负责加载、实例切换或旧资源释放。现有机制能作为描述基础，不能据此声称在线替换已实现。

具体 Patch 基线标识、插件及 codec 准入、替换表达方式、影响范围计算、类型复用与装配隔离仍待设计和验证。

### 用 Patch 替换一个工具插件（启用流程已确认）

2026-10-03 用户认可先准备完整候选组合、成功后切换后续运行的选择、旧运行自然收尾的流程。下述为行为约定，尚未授权代码实施。

- Patch 指向明确的基线组合与目标实现，先解析完整候选描述，再判断依赖影响；若准备期间该 Harness 的当前组合已变化，启用时报告基线冲突，不静默覆盖他人变更。可重新基于当前组合解析和验证。
- 校验候选插件清单、能力契约、服务提供者、事件模式及顺序、配置与历史记录读取兼容性，形成需新建/可共享/需重启的范围。相关依赖者是否新建依据其绑定和生命周期判定，不机械重建全部依赖图。
- 在与旧运行隔离的范围内准备候选实例；准备不得将候选策略注册进旧运行，也不以真实工具副作用验证加载成功。无法隔离且需要修改共享状态的变更，转入既定重启流程。
- 必需服务与注册就绪、适用的契约检查通过后，才切换后续 Run 的组合选择；切换相对于 Run 启动具有明确顺序，每个 Run 绑定完整旧组合或新组合，不混用。此处“启用成功”不等于证明所有未来业务行为正确。
- 准备/校验失败时保留原组合选择，释放候选独占资源和取得的共享引用，不关闭共享服务。旧组合继续服务已绑定的 Run，待无使用者后再释放。
- 启用后若发现业务问题，可明确切回兼容的旧组合供后续 Run 使用；不自动切换正在运行的 Loop，不撤销已发生的工具副作用，也不将回退当作数据迁移的逆操作。

源码依据：`packages/composition/src/compose.ts` 已支持顺序应用 Patch、部分 Host 能力检查、重复服务提供者检查和组合 digest；codec 清单来自 manifest。因此单独插入行为条目不足以证明新插件及其历史事件 codec 已完整准入。完整事件/依赖兼容检查、在线候选装配与启用流程尚未实现或验证。
