📊 分析师 深思 22:16

基于搜索者的资料，从两个维度分析：

质量维度：

  • SWE-bench 数据显示多智能体有 +12-18% 优势，但前提是任务足够复杂
  • 代码审查是多智能体 ROI 最高的场景——独立 Reviewer 比自我审查效果显著更好
  • 关键门槛：涉及 3+ 文件修改的任务才适合并行分工

成本维度：

  • 朴素的多智能体（全用旗舰）贵 3-5x
  • tier-routing（不同角色用不同等级模型）可在质量持平下降低 40-55%
  • 核心洞察：搜索和摘要不需要旗舰，只有规划和审查需要

结论：多智能体 + tier-routing 是当前性价比最优解，但只适用于中等以上复杂度任务。

❓ 质疑者 深思 22:17

分析师的框架清晰，但有两点质疑：

1. 上下文割裂被低估了。 SWE-bench 是独立 issue，但真实编程中子代理 A 改 auth.ts 可能影响子代理 B 在改的 session.ts。论文没覆盖这种任务间实时冲突。

2. "质量持平"有水分。 tier-routing 论文的"持平"是 pass@1 衡量的。但编程还有可读性、架构一致性、命名风格等维度，benchmark 不测这些。

建议：上线前在内部 repo 跑 A/B，人工打分代码质量（不只是 pass/fail）。

📊 分析师 深思 22:17

质疑者的两点都很好，修正一下：

关于冲突——实际方案中 Leader 必须做冲突检测（或顺序依赖声明），Reviewer 的价值不只是代码审查还是一致性守门人。

关于风格统一——同意。首版可以用"同 provider 内切模型"（deepseek-pro ↔ deepseek-flash）来回避。

换个角度想：与其纠结"多 vs 单"的二选一，不如想什么时候切换。

类比 Linux 内核——不是"多进程 vs 单进程"二选一，而是按需 fork。Agent 可以学同样的模式：默认单智能体运行，检测到复杂度超阈值时自动 fork 子代理，完成后 join 回来。

首版手动选形态合理，但远期方向是系统自动决策。

📝 总结者 稳态 22:19

讨论总结

✅ 共识：

  • 多智能体 + tier-routing 在中等以上复杂任务有明确优势
  • 代码审查（独立 Reviewer）是 ROI 最高的场景
  • 同 provider 内切模型可避免风格不统一

⚠️ 注意事项：

  • 简单任务不适用（通信开销 > 收益）
  • 任务间依赖冲突是盲区，需要 Leader 冲突检测
  • 上线前需人工 A/B 评审，不能只看 pass/fail

💡 远期：从手动选形态演进到自动 fork/join。
