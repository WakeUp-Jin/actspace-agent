# Agent Team 产品设计

> 文档等级：future-product-design。当前 v2 尚未实现本产品形态；本文只保留产品意图和不变量，不作为当前 Runtime、存储或接口规范。
>
> 含旧实现细节的[完整 v1 稿](../../archive/v1/design-docs/agent-form-team.md)已归档。当前一次性委派见 [Subagent](agent-subagent-runtime.md)。

## 目标与角色

Team 面向结构化编程与执行任务，由一个 Leader 和扁平成员协作。Leader 拆解任务、分配职责并汇总结果；成员拥有独立上下文，围绕明确任务执行。Team 形态由用户选择，不由模型擅自切换。

成员预设描述角色和能力，运行中的成员承担具体任务，两者不混为一体。不引入无限嵌套团队或通用工作流引擎。

## 协作不变量

- 任务状态与结果形成统一、可追溯的工作记录，消息通知不另外充当结果事实源。
- 任务认领、分配、阻塞和完成应明确，避免同一任务被无意重复执行。
- 成员只获得任务 brief、必要约束和授权能力，不自动复制 Leader 或其他成员的完整上下文。
- 并行写入必须有明确的文件责任范围与冲突处理，通信消息不能扩大写权限。
- 用户可以向成员补充信息，Leader 能感知影响任务的变化；普通对话不隐式改写任务状态。
- 团队空闲只说明没有可执行工作，不等于用户目标完成；由 Leader 明确给出完成结论。
- 停止、失败与重启后的恢复不能制造无人持有的后台成员或未经确认的副作用重试。

## 产品交互与验收目标

通过 Leader、任务和成员视图查看总进度、任务依赖、各成员状态及结果。用户先看到协作进展，再按需查看成员细节；权限等待、失败和任务阻塞不能只表现为长期运行中。

验收关注任务分配与结果一致性、上下文隔离、并行写冲突、用户 steering、停止与失败恢复，以及“空闲”和“完成”的区别。
