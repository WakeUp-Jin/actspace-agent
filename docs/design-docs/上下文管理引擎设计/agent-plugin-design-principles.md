# 上下文引擎插件设计原则

状态：2026-10-06 第一版实现已接入；自动化与真实界面的验证范围见[执行摘要](../../exec-runs/20261006-context-management-engine/execution-summary.md)。本文维护设计契约，不承诺未执行的 Provider 验收。

## 模块化与低耦合

本专题及项目后续插件设计遵循：模块化、低耦合，通过统一接口协作。并非完全没有依赖，而是不依赖对方的内部实现。

- 按职责和变化原因划分插件；不把每一种信息标签机械拆成插件。
- 引擎消费公共接口，不导入具体来源或策略的内部实现。
- Cordis 管理服务依赖、插件注册和卸载；注册与清理跟随所属插件生命周期。
- 来源、策略可以复用统一上下文数据契约，但不强制每个插件实现无关方法。
- 会话状态隔离；插件卸载不删除历史事实。
- 先实现简单有效的第一版，再根据真实需要扩展。

## 已确认的来源边界

- 规则文件插件只考虑加载 `AGENTS.md`，不扩展为自动加载 `CLAUDE.md`。Agent/Plan 两处来源为用户数据目录及工作区根目录；Chat 保留只加载用户规则、不加载工作区 Skill 的现有边界；每个新用户 Turn 检查变化，用户规则优先，第一版不加载嵌套目录规则，不新增监听。
- 系统提示词插件后续实现按模型选择 Prompt。第一版准备按模型选择及扩展的接口，沿用已有 Agent/Chat 基础 Prompt；具体模型模板由后续单独接入。
- 规则文件、系统提示词和动态运行信息各自的职责应分开讨论。

## 数据结构与 LLM 转换的设计要求

具体契约见下方两份规范；本页仅保留共同约束：

- 以 Context 为统一交互对象，具名子类型仅用于清晰表达组成；直接复用 SessionSurfaceView，保留角色、工具调用和图片等原有结构。
- 明确一个转换方法，将组装结果转换为当前 LLM 服务接受的参数。插件不各自生成供应商请求体。
- 明确 `messages`、`tools`、请求选项、模型路由与管理状态的各自来源。
- 状态、来源归属和计数不自动发送给模型；路径由披露策略选择和呈现，转换器不能把完整 `pathlist` 再注入一次。
- 逻辑上下文转换与供应商协议适配分开；模型路由选择与系统 Prompt 使用的模型必须一致。
- 对外理解 Context 与 LlmInput 即可；不再引入 ContextEntry、ContextAssembly 等额外公共模型。现有请求快照保留，通过内部映射兼容。
- Session 既有结构保持；新增状态和动态补充使用插件事件持久化。补充不直接写成普通用户 Surface 消息，转换时按安全锚点插入。
