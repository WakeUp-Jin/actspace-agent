# 旧文档与源码漂移核对

状态：2026-10-11，记录初始源码/文档漂移，并补充 V2 实施后的对照结果。旧路径和旧语义只作为第一版历史证据保留。

## 1. 核对结论

当前第一版实现的核心边界仍然有效：Session 是事实来源，插件通过稳定契约贡献内容，压缩策略由引擎协调，LlmInput 会冻结，前端通过 request/context projection 展示，状态不直接发送给模型。

V2 需要改变的是 Context 的生命周期和所有权表述：源码中的 `Context` 仍是每次请求生成并冻结的对象；V2 要引入按 `Session + Agent 逻辑作用域` 管理的长期状态实例，并从该实例捕获本次请求视图。这是有意的架构升级，不是把现有 `readonly` 字段改成可写就完成。

## 2. 逐项对照

| 主题 | 当前源码或旧文档事实 | V2 判断 | 后续动作 |
| --- | --- | --- | --- |
| Context 语义 | 旧路径 `packages/context/src/types.ts` 曾把 Context 写成 request-scoped immutable view；当前实现位于 `packages/context/engine` | 初始架构漂移已完成迁移 | 长期 Context 由 engine 实例注册表维护；每次请求只生成冻结 `LlmInput` 和只读 Host Projection |
| 引擎实例寿命 | 旧 Loop 每个 Step 创建轻量 `ContextEngine`；当前 engine 插件在 Harness 提供共享 registry | 初始架构漂移已完成迁移 | registry 按 Session/Scope 管理实例；Loop facade 复用逻辑实例并按 durable watermark reconcile |
| Harness / Run / Session | Runtime 每次 Run 绑定 Scope，Run 结束释放；Session 可恢复/fork，默认 Loop 一个 Run 内多 Step | 约束仍有效，生命周期需要补充 | V2 明确逻辑 Context 身份与运行 Scope 分离，不把 Run 对象延长成 Session 全局对象 |
| Session 是事实源 | 第一版设计、Session persistence 规范和执行摘要均保持 Journal/Surface 为事实来源 | 继续有效 | 不让 Context 变成第二份可独立写入的 conversation store |
| append 与持久屏障 | Session 规范区分 acceptedSeq/durableSeq；Loop 在 dispatch、工具执行和下一 Step 前调用 awaited checkpoint | 继续有效且必须升级为 Context 发布前提 | reducer 只在明确水位后发布可用版本；故障恢复按水位重放 |
| 插件划分 | 初始实现曾把 registry、sources、disclosure 放在单一 Context 包，Prompt 承载多种 contributor | 物理拆包已完成 | `packages/context/engine`、`system`、`runtime`、`rules`、`skills`、`conversation`、`tools`、`disclosure`、`compaction` 各自是 workspace 包；Prompt 只保留 source-support；没有平行 contracts 包 |
| 插件状态 | 当前 `ContextStatus` 有 paths/facts/plugins，但 `plugins` 是 request Context 内的只读字典；披露 state reducer 已按 Session Journal 增量恢复 | 部分对齐，所有权还不完整 | 每插件拥有切片，engine 只路由事件和发布版本；拒绝任意 pluginId patch |
| 局部更新 | registry 通过 source callback 产生新 content，整体返回 immutable Context；supplement/state 通过 Session 事件保存 | 机制可复用，公共语义需要提高一层 | 保留 reducer/事件路径，增加 Context 实例的受控局部更新和一致 capture，不对外暴露整体替换 API |
| LlmInput | `engine.ts:54-74` 只转换并深冻结，第一版设计也把它定义为最终输入 | 继续有效 | LlmInput 保持请求快照；Context 不再承担它的生命周期语义 |
| 前端显示 | `packages/shared/src/context-projection.ts` 从最近 request/context 和 prepared/header 派生 `ContextState`；ContextPopup / 右侧 Context 面板（原 ContextRenderView）消费投影 | 部分对齐 | UI 继续消费只读 projection；V2 增加当前 Context projection 与请求 snapshot 的 basis/revision 区分，engine 是语义来源，Host/IPC 是传输边界 |
| Context capacity | 当前 UI 从真实 request 的 `contextWindow` 读取，缺失时为未知，不猜固定值；Provider usage 单独聚合 | 继续有效 | V2 不把“当前 Context 状态”误写成 Provider usage，也不使用设置文件实时值替代历史请求 facts |
| 压缩策略位置 | `packages/context/src/compaction.ts` 的 coordinator 负责提交；`packages/compaction` 提供 policy/summarizer 并注册策略 | 继续有效，是 V2 的目标关系 | 保留“策略服务引擎”方向，禁止策略直接改 Session 或 UI；拆包时保留 Codec/owner/恢复顺序 |
| 披露策略位置 | disclosure 已在 Context 下维护路径、计数、冷热状态和 index；压缩成功后由 coordinator 调用 | 继续有效 | 它是独立模块，可同时提供来源能力；不再向 compaction 暴露私有 state |
| 动态补充 | `surface: null` 事件、锚点、工具批次边界与请求转换已经实现 | 继续有效 | Context 长生命周期不改变补充的持久化和插入边界 |
| 模型切换 | 当前 request model 同时用于系统渲染与 LLM input；历史快照保存实际 model/facts | 继续有效 | 未来模型切换只影响下一次捕获，不修改已经冻结的 LlmInput |
| Codec 与包重命名 | manifest/codec 分开，旧事件必须可读；执行计划明确行为停用不删除 Codec | 继续有效且更重要 | 目标包拆分不能全局替换历史 owner；迁移计划单列 codec discovery 和默认 Harness 闭包检查 |

## 3. 需要标记为“当前实现”的旧表述

下面几类表述不应继续直接作为 V2 规范，但应保留在第一版文档或执行记录中：

1. `Context` 是“request-scoped, immutable view”。这是第一版代码/文档事实，已由 V2 长期实例模型替代。
2. `getContext(request)` 表示每次请求从来源重新取得完整 Context。V2 应改成取得或恢复 Session/Scope Context，再捕获当前组装视图；兼容适配器可以暂时继续使用旧方法名。
3. `packages/context` 现在是领域目录；`engine`、各类型插件和 `compaction` 已形成独立 workspace 包。engine 只依赖公共契约与基础服务，不 import 具体来源实现。
4. 前端只从最近一次 request/context 派生 ContextState。V2 还需要表达“当前 Context 尚未发送给模型”的状态，但历史请求投影仍保留。

## 4. 仍然有效、不要误判为漂移的内容

- Session Journal、Surface、append/flush/checkpoint、accepted/durable 水位和恢复/fork 边界。
- `LlmInput` 的深冻结、请求重试复用冻结输入、供应商协议由 LLM Adapter 处理。
- required/optional 来源、稳定排序、owner 校验、注册撤销与 Scope 隔离。
- 动态补充使用插件事件、`surface: null`、安全锚点、完整工具调用批次和生命周期。
- 压缩候选/core/applied 顺序、失败不清零、披露路径最多 100 条、睡眠读取只计数、成功压缩后整理。
- 真实 request 的 model/contextWindow/requestId、Context estimate 与 Provider usage 的显示边界。
- Codec 行为发现与行为启用分离；关闭插件不删除可读历史；未知 required 事件可以降级为 browse-only。

## 5. 旧文档更新顺序

V2 获得审阅后，按以下顺序更新仓库正式入口：

1. 先在现有 Context 设计入口加“第一版实现 / V2 设计”的状态分流，避免读者把目标当作当前代码。
2. 再更新 Context 数据契约：把长期 Context、ContextProjection 和 LlmInput 分开；保留 request snapshot 作为历史请求事实。
3. 更新插件拆分文档与 `packages/context/README.md`，记录已落地的物理子包、Prompt 边界和 Host/IPC Projection 接线。
4. 更新 Runtime/Session 相关文档，写清 Context 逻辑身份与 Run Scope、durable checkpoint 和释放重建。
5. 最后再写执行计划，计划中逐项处理 manifest、Codec、默认 Harness、Loop、Projection、前端 IPC 和测试。

执行计划不能通过改名或移动目录直接抹掉这些差异；每项迁移都需要明确兼容读取、双路径禁止条件和回滚边界。
