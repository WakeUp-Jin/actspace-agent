# 一个可执行文件存在，不代表应用缓存可用

macOS 的 app 是目录：主程序、Info.plist、Helper、动态库、符号链接与资源共同组成运行环境。只检查主程序是否存在，会漏掉“主程序还在、其余内容已丢失”的状态。于是缓存检查返回成功，而程序还没进入业务入口就退出，编译再多次也没有帮助。

可重建缓存应有三步：判定可用、在暂存位置构建、验证完成后替换。判断依据要覆盖真实依赖，而非随手挑一个标记文件。本例对照安装包检查结构、普通资源大小与链接，并单独检查被重命名的开发身份；发现异常会重新生成副本。

为什么不每次验证所有字节？大型运行库每次散列会增加启动成本，而且改名与签名会合法改变部分文件。结构检查能覆盖这次文件缺失的问题，但不能承诺检测同长度内容损坏或恶意篡改。缓存完整性检查和软件供应链安全验证是两种不同目标。

调试时先比较原始运行库与缓存副本执行同一个最小命令。原始能返回版本、缓存直接退出，就把问题缩到派生产物；若两者都失败，再检查更低层的环境。不要从业务日志为空直接推断业务初始化存在错误。
