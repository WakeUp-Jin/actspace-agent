# 服务包装层需要独立契约测试

一个内部类的方法测试全部通过，为什么真实应用仍会报“不是函数”？因为消费者拿到的可能不是那个类，而是依赖注入容器注册的包装层。

## 两层对象，两个合同

例如 `CompactionPlugin` 实现业务算法，`CompactionService` 管理 Cordis 生命周期并转发业务方法。给内部类增加 `withTriggerRatio()`，并不会自动给包装层增加该方法。类型断言 `ctx.get(id) as CompactionPlugin` 只影响编译检查，不会替换运行时对象，也不会生成方法。

修复应放在缺失的边界：沿用 Service 现有模式，增加委托。不要为躲开错误让消费者任意深入 `.runtime`、禁用功能或静默回退默认策略。

## 应测试哪一层

1. 算法单测：阈值计算与压缩行为是否正确。
2. 容器契约测试：真实注册插件，从消费者使用的 key 取服务，再调用新方法。
3. 应用验收：真实创建 Chat，确认 Host 装配路径和请求完成。

容器层只需替代外部 LLM，不要替代被测 Service。这样测试才能抓住“内部类有方法，注册对象没有方法”。先运行失败测试，再加入委托并观察通过，证明测试真正覆盖缺陷。

## 配置派生的另一个陷阱

Chat 动态阈值应派生独立实例，不能直接修改共享 Agent 的策略。还必须保留 resolver，而不是在创建时调用一次后缓存数值。测试先让同一个派生实例在高阈值下不触发，再改变 resolver 返回值使其触发，同时确认基础实例仍不触发。

## 自检

- 消费者从容器里真正拿到的是内部实现、包装层还是代理？
- 新方法是否在这个对象上可达？类型断言是否遮住了不匹配？
- 派生配置会不会污染其他消费者？动态值会不会被提前固化？
