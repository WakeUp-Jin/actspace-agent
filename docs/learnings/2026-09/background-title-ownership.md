# 后台生成结果不能抢走用户的修改权

自动标题、异步摘要和表单自动补全都有同一个问题：请求发出时字段为空，请求返回前用户已经输入了自己的内容。若返回时直接赋值，网络越慢，越容易覆盖用户操作。

首先分清展示值与业务值。`New chat` 是“尚未命名”的显示方式，业务状态应保留 `null`。把占位文案持久化以后，程序无法区分自动占位与用户主动输入的同名标题；这也是历史数据不能仅凭字符串就批量覆盖的原因。

其次给后台任务明确的失效条件。手动改名入口要在第一次 `await` 前取消命名任务，成功分支和失败兜底分支都检查取消状态。只比较标题字符串不够：用户可能刚好输入了与旧值相同的文字，但修改意图依然优先。

最后看写入顺序。这里所有标题写入走同一个 SessionHandle 的串行 append 队列：后台先入队、手动后入队，最终手动标题胜出；手动先取消，后台就不再入队。这个保证依赖单进程单写入入口；跨进程多写者应使用存储层版本号或条件更新，不能照搬内存中的 AbortController。

持久化也不等于界面已经刷新。Journal 提交后的通知必须让元数据消费者更新，合并事件时还要保留“本批含标题变化”这个事实，否则后续普通消息事件可能把标题更新信号挤掉。
