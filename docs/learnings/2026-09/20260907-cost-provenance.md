# 为什么费用 0 不能代替未知

一个接口返回 `cost: 0`，只说明有一个数值字段，不能证明服务免费。SDK 可能用缺省零单价乘 Token 算出零；代理可能根本没有返回账单字段。这两种情况与供应商明确报价为零，业务含义完全不同。

金额需要同时保存依据：谁给出的、用了什么价格、对应哪个实际模型、币种是什么、何时获取。Token 数可以是供应商精确返回的，金额却是客户端估算的，所以二者要有独立来源字段。

以 3,000 输入 Token、其中 2,000 缓存读取、500 输出为例，假设每百万输入 / 缓存 / 输出单价为 2 / 0.2 / 8 USD。先拆互斥桶：未缓存输入是 1,000，费用为 `(1000×2 + 2000×0.2 + 500×8) / 1000000 = 0.0064 USD`。若 500 输出中包含 400 推理 Token，不能再收一次推理费。若缓存已经发生却没有缓存价格，结果应为未知；缓存 Token 为零时不必因为缺缓存价而放弃其他桶的计算。

价格会更新，因此在请求开始时冻结这个模型的费率与来源，和结果一起保存。历史回放只读当时记录，不拿今天的目录重算。这个模式同样适用于税率、汇率、折扣和按量云服务：会变化的规则应进入交易依据，而非在展示时临时查找。

自检：没有价格依据的历史零值是不是免费？不是。现在目录降价能否改变旧请求金额？不能。来自供应商的 Token 数能否让客户端计算的金额变成真实账单？不能。

一个容易忽略的边界是 SDK 的归一化：原始响应即使有实际金额，SDK 也可能只留下自己计算的 cost。判断来源必须发生在丢失信息之前。对明确文档化的供应商字段，可以在协议适配层保留实际金额，计算层优先采用；不能因为字段叫 cost 就接受任意端点的数据。测试应穿过真实 SDK，用本地 stub 响应验证解析，避免只测试自建的理想对象。

展示层可以很简洁，保存层仍应完整：移除费用解释浮层不意味着删除价格快照。这样既能保持页面紧凑，也能在排障时核对历史依据。
