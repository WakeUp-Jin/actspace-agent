# 静态站图片优化：把下载成本放在正确的位置

页面已经设置高优先级，图片却仍然慢，先拆开首字节时间与下载总时间。如果约一秒就收到响应、之后仍要下载二十秒，优先降低图片字节数；继续增加 preload 不能解决低吞吐。

## 一份源图，多种交付尺寸

保留高清 PNG 作素材，构建时生成多个宽度的 WebP。`srcset` 列出真实文件及像素宽度，`sizes` 告诉浏览器图片在布局里多宽。浏览器结合屏幕像素密度选资源：显示宽度约 350 CSS 像素、DPR 为 2 的手机通常需要约 700 像素的图片，而不是默认下载 2880 像素原图。

首图保持 eager/high，后续图 lazy；放大查看再加载全尺寸 PNG。这样首屏节省流量，同时保留截图里的小字。静态生成只在构建时消耗图片处理资源，不需要访客请求时调用图片转换服务。

## 哈希与长期缓存是一对契约

一年 immutable 缓存只适合内容变化就更换 URL 的资源。给固定名称的 HTML 或 public 图片同样的缓存时间，会让用户看不到更新。内容哈希文件名把版本直接写入地址，新页面引用新地址，旧文件安全留在缓存。

## 三个容易误判的地方

- 使用 Astro `Image` 不代表已经压缩：passthrough 服务会跳过实际转换。
- 素材元数据里的原图 URL 不等于该文件一定出现在产物中；放大链接也要显式生成并检查文件存在。
- 字节数减少不等于已证明线上耗时改善。应分别报告构建产物大小、浏览器显示与发布后的网络复测结果。

自检：手机的 `currentSrc` 是否选中了较小文件？放大链接是否存在？长期缓存是否只覆盖带哈希的资源？
