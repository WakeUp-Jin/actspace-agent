# 大列表 mock 必须复制关系，不能只复制行

轨迹不是一组互不相干的文本。请求、消息、工具调用和结果通过 ID 相连；前端还用记录 ID 缓存行高、选中态和展开态。

把一段轨迹重复 24 次时，如果只改行号、不改 callId，归并器会认为 24 份结果属于同一次调用。即使页面能滚动，也不能证明虚拟化正确：重复 key 会让组件和行高缓存复用到错误记录。

正确做法是给每个批次添加统一 ID 前缀，并递归改写 turnId、stepId、requestId、messageId、callId 和 parentCallId。同一批次内的关联保持不变，批次之间完全独立。时间也要统一偏移，否则不同批次会重叠在同一段时间轴上。

验证应检查三个不变量：

1. 展示记录 ID 不重复。
2. 重复后调用数量按倍数增长，每次调用仍只关联自己的结果。
3. 偏移前后 duration 不变，只有绝对时间变化。

最后用浏览器确认挂载的行数远小于总行数，滚动到末尾后选中记录仍显示正确 Turn/Step。纯函数测试负责关联正确，真实布局检查负责虚拟化正确，两者不能相互代替。

相关实现：`apps/desktop/src/renderer/trajectory/fixtures.ts`。

## 点击关系与时间快照也需要身份

“工具属于前面最近一条 Assistant”只在最简单的线性日志里成立。同一步可以有多条消息，事件也可能分批到达。把工具绑定到消息，应优先使用消息里的 callId 引用，或工具明确携带的 assistantMessageId；位置只能决定排版，不能决定归属。找不到唯一归属时保留缺失，比跳到错误消息更可靠。

Schema 还包含时间维度：今天名为 bash 的工具可能已经更换参数，但昨天的调用仍应展示昨天请求中记录的定义。因此数据链应是 call → request snapshot → tool definition，而不是 call → 当前注册表。

一个关联功能至少有三层测试：纯函数验证 ID 配对，组件验证点击更换详情并展开目标，真实浏览器验证虚拟列表滚动与选中可见。测试数据可以故意在 Assistant 与工具之间插入另一条消息，或在调用之后更新同名工具定义；如果结果仍正确，才能证明没有靠“刚好相邻”通过测试。

## 接入真实数据：一致的版本，比字段齐全更重要

假设先读会话摘要得到版本 100，再读 Journal 时已经到了 103。如果把 103 的轨迹装进标记为 100 的响应，UI 可能同时显示“仍在执行”和“工具已完成”；客户端版本缓存还会错误拒绝后续更新。解决办法是把每个投影都固定到已读摘要的版本，拒绝缺失覆盖范围的数据，而不是取几个版本里的最大值。

分页还有另一个维度：用户加载了更早历史，即使 Journal revision 没有增长，数据窗口也发生了变化。因此不能只按 revision 去重历史请求；同 revision 可以接受更完整窗口，并让下一次实时刷新沿用该窗口起点。

最后，mock 的字段名字不能代替生产链路核对。本次 User 正文实际位于 surface.node.content，Tool 正文在 modelOutput，参数定义在 inputSchema。测试通过真实 Journal 准入再投影，能够暴露普通手写节点绕过的约束，例如 Inbox claim 必须引用 enqueue 并同时生成 Surface。
