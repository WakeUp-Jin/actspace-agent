# 模型发现、能力事实与费用快照为何要分开

`GET /models` 返回一个新 ID，只能证明该连接看到了这个模型。它不必包含图片支持、工具能力、上下文容量或价格。把“能发现”直接变成“能力齐全”，会让 UI 接受图片却在发送时失败，也可能错误估算费用。

可以把数据拆成三个生命周期：

1. **发现目录**随服务商刷新，缓存用于网络失败时继续浏览。缓存按服务商隔离，不能把一个连接的结果放到另一个连接下。
2. **能力与价格事实**来自官方资料或可信元数据。只有已知 ID 才补齐事实；未知值保留未知。别名归一到一个正式身份，避免同一模型出现多个条目。
3. **请求费用快照**在实际调用时冻结模型、单价、倍率与来源。账单展示读取这份快照；后续降价不应让上周的费用自动变化。

注意两个独立维度：模型发布后更换价目是一条版本边界；每天峰谷价是另一种计价策略。如果产品采用固定高峰估算，更新版本价目不意味着自动实现时段计费。

迁移也有冲突：旧 Pro 和旧 Flash 同时映射到新 Flash 时，依赖对象遍历顺序会随机保留配置。必须明确优先级，并在测试中反转输入顺序验证结果。当前策略是正式 Flash 优先，其次旧 Flash，最后退休 Pro；历史请求本身不参与配置迁移。

自检：远端目录没给价格时，能否仍诚实展示未知？刷新后历史账单会不会变化？两个别名同时存在时，保留哪一份凭据和启用状态？
