# 文档版本与事实来源是两个不同维度

一次版本迁移后，最容易误导开发的文档往往仍能正常打开：标题写着“总体架构”，顶部补了一句“已被替代”，正文却继续用旧接口解释当前系统。链接检查能证明文件存在，不能证明它说的是今天的系统。

## 先判断它回答什么问题

文档至少有三种用途：当前规范回答现在应如何工作，决策记录解释当时为什么选择某条路，历史快照保存已经退役的实现证据。它们都值得保留，但不应在默认阅读路线中拥有相同的优先级。

只改目录不能解决正文矛盾。仍承担当前规范职责的文件应原位更新正文、图示和示例；需要保留的旧推导进入明确的历史段落或决策记录。只有已退役的版本资料才按版本归档，避免每次内部演进都复制出一套新目录。

## 不要按名字里的版本号分类

产品版本、数据格式版本和文档修订版本可以独立变化。第二代产品完全可能继续使用第一版 Session 格式。判断应依据实际读写代码、schema 和使用方，而不是文件名中的 `v1`。

同样，“实现完成”与“人工验收完成”是不同状态。计划可以保存实现完成的结果，同时明确真实环境仍未验证；把这些计划永远留在 active 会掩盖真正需要继续实现的工作。

## 检查也要分层

- 所有需要导航的资料检查链接与资产存在性，包括归档。
- 当前入口额外检查已退役命令、API 示例和未标明用途的历史链接。
- 历史记录允许保留旧符号与源码路径；失效的源码位置应标成历史证据，不能机械指向今天的不同实现。
- 迁移映射记录旧位置和新位置，便于修复入链和回退；它本身不充当当前架构导航。

这次整理中，原有门禁全部通过却漏掉当前契约中的失效链接，说明“检查通过”的意义取决于覆盖范围。应同时记录检查了什么，以及它不能证明什么。
