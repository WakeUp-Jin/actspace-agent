# 缓存策略必须落到最终 Wire

当同一种模型协议既能直连 SDK，又能经过本地代理或另一套兼容 SDK 时，“设置里启用了缓存”不等于实际请求已经一致地发送缓存标记。

## 为什么上层开关不够

上层通常只知道策略，例如短缓存或关闭；真正的 JSON 结构却由最后一层序列化器决定。直连库可能接受 `cacheRetention`，代理路径可能要求手工给 system、tools 和 messages 内容块增加 `cache_control`。如果只在业务层传一个开关，其中一条路径很容易静默失效。

## 可复用的设计

1. 在连接配置中保存协议无关的策略语义，而不是保存某个 SDK 的参数名。
2. 在解析模型与连接时冻结本次请求的策略。
3. 在每条最终 wire adapter 中把策略翻译成该序列化器需要的字段。
4. 对最终 payload 做测试，而不只断言上层函数收到 `enabled: true`。
5. 关闭策略必须显式删除字段，不能依赖上游忽略未知值。

## Prompt Cache 断点

Anthropic 的短缓存适合放在稳定前缀边界。一个实用的首版是：

- system 的最后一个可缓存内容块；
- 最后一个工具定义；
- 最近 user 消息的最后一个可缓存内容块。

这些位置表达“前面的内容可以复用，后面的内容更容易变化”。不要把缓存命中当成配置成功的必然结果；只有 Provider 返回 cache read/write usage，才能作为运行时观测证据。

## 常见陷阱

- 连接测试也携带缓存标记，导致一次最小探测改变成本或兼容性。
- 代理路径和直连路径使用不同默认值，用户切换代理后行为改变。
- 文案写成“最近工具结果”，实现却标记工具定义，造成调试误判。
- Provider 拒绝缓存字段后静默重试同一个生成请求，可能产生重复输出和重复费用。

## 自检

- 测试能否看到最终请求中的缓存字段数量和位置？
- 关闭缓存后，所有 transport 是否都完全不发送相关字段？
- 缓存 usage 缺失时，产品是否仍诚实地显示“未观测到命中”？
