# 延迟加载详情时，保留可操作的摘要

详情尚未读取，不代表列表项本身不可展示。把这两种状态合并，会让原本可识别、可点击的工具卡片退化成一排相同的加载按钮。

可以把一条记录分成两部分：摘要负责名称、状态和导航，详情负责大量正文。列表首屏应保留摘要；只有用户需要正文时才读取详情。子任务尤其适合这种拆法：父会话里的卡片只需任务名、状态、简短结果和 child Session 引用，正文由子会话面板读取。

一个常见陷阱是在组件分发之前判断 `deferredToolDetail`，直接返回通用占位按钮。这样存储层的优化标记就覆盖了所有业务组件。更合适的做法是保留业务类型分发：已有独立详情入口的卡片继续使用原入口，普通工具显示摘要并保留按需加载操作。

另一个陷阱是递归渲染摘要时仍携带延迟标记，导致再次进入包装组件。渲染摘要副本时移除标记即可；保留原始记录上的引用用于读取完整详情，不修改事实源。

回归测试要同时验证“没读取详情也看得到名称”和“点击后才读取详情”。对子任务，还要验证点击直接打开 child Session，而不是先加载父工具全文。这能防止以后为了优化首屏体积，又把可用的导航入口一起隐藏。

自检：一个列表项的完整结果很大时，它的标题和状态也需要延迟吗？它是否已有独立详情入口？失败重试期间，用户还能认出是哪一项吗？

不要把“请求成功”当作“用户看见结果”：异步加载后若更换 React key，或重新挂载一个默认折叠的组件，用户仍看不到内容。让原有展开动作触发加载，保留组件身份与展开状态；测试应断言真实结果文本可见，而不是仅验证调用次数或摘要发生变化。
