# 工作耗时不能从提交时间推算

一个异步任务的事件可以在工作完成后一起落盘。此时“开始事件”和“完成事件”的时间只描述写入事务，不能回答任务耗费多久。网络摘要先花 35 秒，再用 68 毫秒追加四个事件，如果界面相减事件时间，重启后的耗时就变成 0 秒。

## 怎样区分两种时间

事件 time 回答“这个事实何时提交”；工作 durationMs 回答“从开始执行到产出结果经过多久”。它们都合理，但不能互换。把计时起点放在实际工作开始处，结果产生后把耗时放入成功完成事件，让实时界面与重放界面消费同一事实。旧事件没有新字段时可以回退旧口径，但不能恢复从未保存的信息。

## 为什么不直接提前写开始事件

提前写入开始事件能让时间差看似正确，却会改变失败语义：摘要失败后可能留下一条永久未完成的事务。原设计要求成功摘要与 Surface replacement 一起提交时，应把工作耗时作为事务数据保存，而不是为修指标破坏原子性。若业务需要持久化未完成任务，则需要完整的 started/succeeded/failed 恢复协议，是另一个设计任务。

## 怎样测试这类问题

让写入时间固定不动，在摘要函数中把测试时钟推进 1.5 秒：完成事件应保存 1500ms。再重放该事件，确认显示取工作耗时而不是 0ms。让摘要抛错，确认原始 journal 与 Surface 没变化。这样测的是时间边界与失败语义，而不是凑一个非零数字。

Date.now 是墙钟，本次实现与实时计时保持同口径并对负值钳制；有严格延迟测量需求时，可选择单调时钟，避免系统时间调整干扰。跨进程应保存已计算的 duration，不能把进程本地单调时钟起点直接持久化后跨进程相减。
