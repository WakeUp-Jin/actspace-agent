# 为什么运行中显示错，结束后却恢复正常？

同一段会话常有两个读取入口：运行时消费增量事件，完成后从持久化记录重建。如果它们采用不同的语义分类，最终状态正确并不能证明实时过程正确。

这次工具参数被流式收集器标成正文，前端自然把 JSON 交给 Markdown。完成后 Journal 中的 assistant/message 和 tool/result 是结构化的，重新投影就恢复正常。问题在事件分类和桥接，不在 Markdown 渲染器。

## 从哪里修

在最早知道类型的地方保留类型：text、reasoning、tool arguments 必须分开。不要在前端用正则删除看似工具参数的 JSON，因为合法正文也可以是 JSON。执行层发送事实，Host 把事实变成预览，React 只渲染预览。

运行中和历史共用一个预览构建器，但调用者提供不同阶段。生成参数不代表开始执行，审批通过也不代表完成；只有实际执行和结果提交才能产生对应事实。

## 两个容易忽略的排序

- **提交顺序**：并行工具后发先完成时，确定性的 Journal 可以仍按调用顺序提交。移除整批等待屏障能改善首个结果延迟，但不会消除前序提交等待。要区分 body 结束与可恢复的结果事实。
- **到达顺序**：前端可能先收到结果，再收到迟到的进度或审批。用稳定的 callId 更新同一条目，让终态优先；结果事件自身必须能创建条目。

## 怎样证明修好了

用真实执行循环、内存 Session 和假模型串起整个转换链。在工具函数、工具结果与下一段正文之间放可控停顿，分别检查：参数没有进入正文、工具已经出现、单个结果停止运行状态、最终重建没有重复条目。只手工发送 tool_started/tool_finished 给组件会绕过最容易出错的生产链路。

自检：如果模型只在 done 返回工具，会有工具行吗？如果进度晚于结果，会重新闪动吗？如果展示订阅者抛错，会不会让成功工具变成失败或重试？这三个问题能检查事件边界是否稳固。
