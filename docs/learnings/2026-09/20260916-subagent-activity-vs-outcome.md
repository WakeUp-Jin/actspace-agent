# 执行活动不是任务结论

“正在整理回复”描述模型当前在输出正文，但不保证它不会接着调用工具。“已完成”也可能只说明循环正常结束，并不说明找到了目标文件。这两类语义要分开，否则 UI 很容易替运行时做出并无证据的成功承诺。

实时活动适合从事件派生：请求开始 → 思考，推理增量 → 分析，工具生命周期 → 读取/搜索，正文增量 → 整理回复。这里只需保留工具 ID、少量安全参数和标签，不能把每个 token 当成一次需要重绘的活动变化。父子 Session/Call 的关联提供明确路由；父调用已经结束时，迟到的子事件不得把它变回运行中。

任务结论应由结构化终态给出。比如执行预算用尽，即使最后安排了一步总结，结束原因仍然是 step-limit。部分发现可以交回父任务，但必须同时带上未完成原因，父任务才有依据缩小目标或换工作区，而不是盲目再跑一遍。

另一个陷阱是将能力限制写进 prompt 就当作权限。prompt 解释边界，工具白名单决定模型可见能力，运行时准入决定实际允许执行什么，workspace guard 决定读取范围；这些层相互补充。暂不支持审批时，应缩小子任务能力，而不是把本应审批的动作默认放行。

自检：收到正文增量可以显示“已完成”吗？预算总结应标记成功吗？主任务可见 Bash，是否意味着只读子任务也能继承？这三个问题的答案都是否。

补充：状态刷新节流不能代替信息建模。若读取只持续几十毫秒，400ms 内“取最新值”会让文件名从未出现在屏幕上。应分别记录当前阶段和最近操作，组合成“正在分析 · 刚读取 a.ts”。这样即使 React 合并了短暂更新，对象仍然可见；不要通过延长“正在读取”来伪造执行时间。动画只负责呈现变化，不能决定哪些事实被保留。
