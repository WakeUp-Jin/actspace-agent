# 分页要限制哪一层的工作量？

页面只展示十条，并不代表系统只读取十条。若后端先扫描所有文件、解析完整历史，再在返回前 slice，传输和绘制可能减少，但磁盘与 CPU 成本依然存在。

真正的分页需要一个能定位数据的读取模型。例如日志系统可以维护可重建的摘要和回合字节偏移：列表读取摘要，正文读取指定范围。日志保留事实，索引只负责查询速度，因此索引损坏能重建，不能反过来把缓存当成恢复依据。

分页边界还必须符合业务关系。Agent 的用户输入可能在 turn/start 之前由 Inbox claim 写入；机械从 turn/start 截取会丢掉问题。工具调用和结果必须留在同一完整回合。一个回合特别大时，进一步延迟加载工具详情，比把回合拆断更可靠。

最后别忽略第二条读取链路：正文即使分页，其他组件若在挂载时请求完整轨迹，也会把成本重新带回来。验收应检查后端读取次数、传输体积与实际渲染，同时覆盖缓存失效和首次构建；单看 More 按钮不能证明优化有效。
