# 分页的边界：限制哪一层的工作量，以及“整轮统计”只属于完整轮

合并自：分页要限制哪一层的工作量、分页预算与“整轮统计”是两个不同承诺。

来源：[P4 远端 Host history](../../histories/2026-10/20261004-0108-p4-remote-host-in-progress.md)

## 1. 分页限制的是读取，不只是返回

页面只展示十条，不代表系统只读十条。后端先扫所有文件、解析完整历史、返回前 slice，传输与绘制减少了，磁盘与 CPU 成本依然在。真分页需要能定位数据的读取模型：可重建的摘要 + 回合字节偏移，列表读摘要、正文读指定范围。日志保留事实，索引只负责速度，损坏能重建，不能把缓存当恢复依据。

第二条读取链路别忽略：正文分页后，其他组件挂载时若请求完整轨迹，成本又带回来。验收检查后端读取次数、传输体积、实际渲染，覆盖缓存失效与首次构建；单看 More 按钮证明不了优化有效。

## 2. 分页边界要符合业务关系

- 用户输入可能在 `turn/start` 之前由 Inbox claim 写入，机械地从 `turn/start` 截取会丢掉问题。
- 工具调用与结果必须留在同一完整回合；一个回合特别大时，延迟加载工具详情比拆断回合可靠。

## 3. 预算裁剪、游标、整轮统计

远端历史要限制事件数和响应大小。直接保留最后 N 条，一页可能从某轮第二次工具调用开始——对这些片段累加 Token、从首个可见事件算耗时再标“本轮消耗”，就是错误的完整性暗示。需同时保证：响应有界、翻页不丢事实、整轮统计只用于完整轮。

- 裁剪后若后面还有完整轮的起点，把页面开头向后移到该起点；前翻游标必须使用这个新起点，略过的片段留给上一页，否则两页间出现空洞。
- 单轮本身大于预算：不能强行返回整轮，也不能返回空页；继续返回有界片段并推进游标，界面保留正文、工具等事实，暂不显示没有完整依据的整轮统计，加载更早历史拼接后再按完整数据展示。
- 增量同步语义不同：`afterSeq` 表示调用者已处理到哪个事件，不能为了页面边界跳过中间事件；整轮对齐只用于历史分页，不用于 delta。

测试：逐页读取并拼接证明事件没遗漏；超大单轮证明游标总能前进；统计同时写片段负例与完整轮正例（避免“全隐藏也能过”）。

## 自检

1. 分页限制了磁盘/CPU 的哪一层？有没有第二条链路读全量？
2. 页首是否可能落在某轮中间？此时统计和耗时还在显示吗？前翻游标有空洞吗？
3. delta 同步有没有被整轮对齐误伤？
