# 客户端队列 × 服务端收件箱：交接失败时问服务端，而不是猜

> 来源：`docs/histories/2026-09/20260930-1400-composer-message-queue.md`（Composer 消息队列与运行中插入）

## 场景

用户在 Agent 运行中排了几条消息（队列在渲染进程内存里），点「↳ 插入」把其中一条送进正在运行的回合。插入走的是服务端（main 进程）的 durable inbox：`enqueue` 之后，loop 在下一步开始时 `claim` 它，模型才看得到。

于是同一条消息在交接期间有两份「所有权」：

- 客户端：还在托盘里显示「下一步读取」，可以撤回。
- 服务端：inbox 里是 `pending`，随时可能被 `claim`，也可能在回合停止时被 `discardAll`。

## 陷阱：客户端按事件推断状态

直觉写法是「收到 `user_message_steered` 就算读到，回合结束还没收到就放回队列」。这会在三个时间窗里出错：

1. **插入请求还在路上**：用户点插入后立刻点停止。回合结束时客户端开始核对，服务端还没 `enqueue`，客户端判断「没读到」放回队列；随后请求到达服务端——如果此时下一条排队消息已经开跑，这条插入会被新回合读到，队列里又留着一份，**同一条消息发两次**。
2. **撤回与读取赛跑**：用户点撤回的同时 loop 正好 `claim`。客户端先删掉本地内容，事件到达时已经没法渲染那条用户消息。
3. **最后一步之后才到**：模型写完最终回复、loop 检查过 pending 之后才到的插入，会一直 pending 到下一回合，排在新用户消息之后。

## 做法：以服务端事实为准，并先等在途请求落定

- 服务端给每条 inbox 消息一个可查询状态：`status(messageId) → pending | claimed | discarded`（由 journal 里最后一次 inbox 操作决定）。
- 撤回 / 回合结束时，客户端调用 `cancelSteer`：服务端如果还是 `pending` 就丢弃并返回 `cancelled`，否则如实返回 `claimed` / `discarded` / `missing`。**只有 `claimed` 留在对话里，其余都放回队首。**
- 核对之前先 `await` 这个会话所有在途的插入请求，关掉窗口 1。
- 插入的正文单独存一份（`steerContentRef`），直到事件渲染或确认回队才删，关掉窗口 2。
- loop 在回合开始时把遗留的 `steer` 以 `stale-steer` 丢弃，客户端核对时看到 `discarded` 就放回队列，关掉窗口 3。

## 核心要点

- 跨进程交接的对象，客户端不要凭「收没收到事件」推断状态；给服务端一个幂等的「取消或告诉我结果」接口。
- 取消接口的返回值要区分「我取消了」和「来不及了，它已经被处理」，调用方据此决定回滚还是保留。
- 回滚前先等同一资源上的在途请求落定，否则回滚本身会和请求赛跑。
- 失败路径统一收敛为一种回滚动作（这里是「放回队首」），比为每种失败写分支更不容易漏。
