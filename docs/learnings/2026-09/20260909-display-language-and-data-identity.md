# 翻译界面时，为什么要区分文案和数据

界面里的英文可能来自按钮文案，也可能来自用户命名、模型输出或机器状态。同样显示为 Terminal，一个是终端入口，一个可能是用户为文件取的名字。仅凭文字相同，无法判断它们应不应该同时翻译。

## 用稳定身份决定展示

已知上下文分类有稳定 key，桌面层可以把 key 映射为中文标题，而不改变存储内容。未知 key 保留原文，既不会误译新类型，也方便定位问题。终端默认标题有宿主明确生成的格式，可以只映射这个格式；创建、恢复、重启都要走同一展示函数。

用户可自由编辑的名称没有这样的来源保证。把所有 New chat 替换成“新建会话”，可能会改掉用户刻意设置的名字。需要翻译历史默认名称时，应先具备区分系统默认值和用户输入的元数据，不能单靠文本猜测。

## 文案还可能参与搜索

斜杠菜单原本用名称和说明做搜索。说明翻译后，旧英文关键词会失效，即使命令本身没有改变。保留英文搜索别名，再让中文说明参与搜索，可以把“显示什么”和“用户如何找到它”分开。

验证时，应同时检查中文搜索、原英文关键词、命令前缀优先级和实际执行参数。只检查新文案出现，证明不了交互行为没有退化。

本次改动对应[中文界面设计](../../design-docs/frontend/front-desktop-chinese-ui.md)。这个经验同时具有可迁移性和容易误改数据、搜索行为的陷阱，因此单独记录。
