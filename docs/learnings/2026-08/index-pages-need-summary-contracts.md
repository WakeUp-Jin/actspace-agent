# 索引页需要自己的摘要契约

## 问题

详情页通常拥有最完整的数据结构，因此很容易顺手拿详情接口来拼索引页：先列出对象，再逐条读取完整内容并在前端计算标题、状态和统计。数据少时看不出问题；对象数量增长后，入口成本会从一次轻量查询退化为 N 次完整读取，任意一条损坏还可能拖垮整页。

会话分析就是典型例子。单个 Agent Run 的完整 Trace 可以很大，但首页只需要会话标题、更新时间、状态、模型和累计用量。为了这些字段读取所有 JSONL，既浪费 I/O，也把“选择分析对象”和“解释执行细节”耦合在一起。

## 处理模式

1. 为索引页定义独立、稳定的 summary contract，只包含排序、筛选、状态和概览真正需要的字段。
2. 在事实写入时同步维护 summary sidecar；索引接口批量读取元数据与 sidecar，不读取大对象正文。
3. 把索引与详情做成两级加载：先选择对象，选中后才读取详情；详情内部还可以继续按子对象懒加载。
4. 故障按列表项隔离。单条摘要损坏应降级该行或跳过该摘要，不能让整个索引失败。
5. 明确 summary 是派生索引，不是事实源。字段语义变化时需要版本化迁移，必要时再从有界原始事实重建。

## 为什么不能只做前端缓存

前端缓存只能避免同一运行周期内的重复读取，无法降低首次进入的 N 次大文件 I/O，也无法提供跨进程一致的安全校验。索引契约应由拥有文件系统和数据边界的 main/service 层聚合，Renderer 只消费一次返回的结构化结果。

## 常见陷阱

- 首页自动打开“当前对象”，导致索引存在但用户永远看不到，详情读取也在入口时立即发生。
- 为了追求字段齐全，把只有详情才需要的正文、工具参数或消息数组塞进 summary。
- 把空记录当错误过滤掉，使用户无法区分“没有对象”和“对象尚无分析数据”。
- 用一个全局 try/catch 包住批量读取，任意坏文件导致整页为空。
- 把索引常驻成详情页第三栏，信息层级和窄窗口成本一起上升。
