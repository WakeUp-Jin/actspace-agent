# 功能可用性不等于运行状态

## 问题

一个后台功能常同时有两类看似相近的开关：产品是否向用户开放，以及运行任务此刻是否启动。把两者塞进同一个 `enabled` 会产生反直觉行为：隐藏入口后后台仍可能运行，重新显示入口又可能自动恢复旧任务。

## 分层方法

把状态按职责拆开：

1. **功能门控**决定入口、对象与运行时资源是否存在，默认值应按产品发布策略选择。
2. **运行意图**决定已开放功能中的循环或任务是否运行，由功能自己的控制面维护。
3. **护栏状态**只约束预算、权限或速率，不能反向冒充前两层。

关闭功能时不能只隐藏 UI。可靠顺序是先持久化停止意图，再停止当前任务，最后释放 Controller 和运行态 IPC。重新开放功能时先确认停止意图已经落盘，再创建运行时资源，因此“显示功能”不会隐式变成“开始执行”。

## 控制面与运行面

设置页是功能关闭后的恢复入口，所以读取和修改配置的控制面必须常驻；依赖 Controller 的状态、事件和命令通道可以随运行面销毁。关闭状态下不要挂载会调用运行态通道的表单，否则用户只是进入设置页就会收到无意义错误。

## 常见陷阱

- 只在 renderer 隐藏按钮，main 仍按旧配置启动后台任务。
- Controller 不存在时跳过停止持久化，导致旧 `enabled=true` 在未来复活。
- 把“开启功能”直接连到 `start()`，让一次产品设置变成有成本的执行授权。
- 删除或重置整份配置来实现关闭，意外丢失用户任务和长期偏好。

## 自检

- 所有入口隐藏后，后台是否确定已经停止？
- 旧版本缺少功能门控字段时，默认行为是否明确？
- 重新开放功能是否仍需一次显式运行授权？
- Controller 不存在时，设置页是否仍能恢复功能？
