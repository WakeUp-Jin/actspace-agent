# 用目录分层隔离当前事实与历史设计

## 核心知识点

设计文档不只是给人看的说明文字，也是 Agent 的检索输入。当前架构和历史方案如果共享同一层级，旧文件名、旧包路径和已经删除的产品入口会被误认为仍然可用。

## 可迁移模式

把文档分成四个明确层级：

- 当前层：只放已经实现或仍约束当前实现的架构、公共契约和专题设计。
- 未来层：保留产品方向，但必须标记 `future-product-design`，不能附带看似可执行的旧代码路径。
- 研究层：固定证据快照和迁移判断，不能覆盖后续确认决策。
- 历史层：放已删除、被替代或只用于迁移复盘的设计，并在目录 README 中明确“不是当前事实来源”。

总索引只从当前层建立默认阅读路线；历史记录和执行计划可以链接历史层，但这些链接表达的是“当时依据”，不是“当前实现”。

## 机械门禁

目录分层仍然是软约束。更稳妥的做法是显式维护一组 current truth files，并在 CI/本地检查中拒绝：

- 已删除 package 或 Host 入口；
- 已归档设计仍以当前路径出现；
- 已丢弃计划重新进入 `active/`；
- 当前入口中的相对 Markdown 断链。

负向 fixture 很重要：它证明 checker 真的会在旧路径或断链出现时失败，而不只是对当前仓库永远输出绿色。

## 常见陷阱

- 只移动文件，不更新索引，Agent 仍会从旧链接进入历史设计。
- 只改标题，不改包路径和产品入口，读者会把删除的模块当成可实现模块。
- 为了“干净”删除历史资料，丢失迁移依据和决策上下文。
- 机械替换历史链接时改变原文叙述，导致 history 无法准确反映当时状态。
- 全仓库禁止某个旧词，误伤研究、迁移映射和明确的“已删除”说明；门禁应守卫默认事实区，而不是抹去历史证据。

## 自检问题

1. 新功能从 `docs/design-docs/index.md` 出发，是否会优先进入 v2 文档？
2. 历史文档是否有清晰的归档声明和当前替代入口？
3. 执行计划与 history 的旧链接是否仍能定位到真实文件？
4. 是否有负向测试证明旧路径和断链会让文档门禁失败？
