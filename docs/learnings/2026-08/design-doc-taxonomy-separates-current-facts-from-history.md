# 文档的分层与版本：当前事实、历史、版本号是三个不同的维度

合并自：用目录分层隔离当前事实与历史设计、文档版本与事实来源是两个不同维度。

设计文档不只是给人看，也是 Agent 的检索输入。当前架构与历史方案共享同一层级时，旧文件名、旧包路径、已删除的产品入口会被误认为仍然可用；一次版本迁移后最容易误导开发的文档往往仍能正常打开——标题写“总体架构”，顶部补一句“已被替代”，正文却继续用旧接口解释当前系统。链接检查能证明文件存在，不能证明它说的是今天的系统。

## 1. 先判断它回答什么问题

- **当前规范**：现在应如何工作；**决策记录**：当时为什么选这条路；**历史快照**：已退役实现的证据。都值得保留，但默认阅读路线里优先级不同。
- 只改目录解决不了正文矛盾：仍承担当前规范职责的文件原位更新正文、图示、示例；需要保留的旧推导进入明确的历史段落或决策记录；只有已退役的版本资料才按版本归档，避免每次内部演进都复制一套新目录。
- 不按名字里的版本号分类：产品版本、数据格式版本、文档修订版本可独立变化（第二代产品可能继续用第一版 Session 格式），依据实际读写代码、schema、使用方判断，不是文件名里的 `v1`。“实现完成”与“人工验收完成”也是不同状态，把真实环境仍未验证的计划永远留在 active 会掩盖真正需要继续的工作。

## 2. 四个层级

- 当前层：只放已实现或仍约束当前实现的架构、公共契约、专题设计。
- 未来层：保留产品方向，标记 `future-product-design`，不附带看似可执行的旧代码路径。
- 研究层：固定证据快照和迁移判断，不覆盖后续确认的决策。
- 历史层：已删除、被替代或仅供迁移复盘的设计，目录 README 明确“不是当前事实来源”。

总索引只从当前层建立默认阅读路线；历史记录和执行计划可以链接历史层，但这些链接表达“当时依据”，不是“当前实现”。

## 3. 机械门禁，且要分层、要有负向 fixture

目录分层是软约束。显式维护一组 current truth files，CI/本地检查拒绝：已删除 package 或 Host 入口；已归档设计仍以当前路径出现；已丢弃计划重新进入 `active/`；当前入口中的相对 Markdown 断链。

- 所有需要导航的资料检查链接与资产存在性（含归档）；当前入口额外检查已退役命令、API 示例、未标明用途的历史链接；历史记录允许保留旧符号与源码路径，失效的源码位置标成历史证据，不机械指向今天不同的实现；迁移映射记录旧→新位置便于修复入链与回退，本身不充当当前架构导航。
- 负向 fixture 很重要：证明 checker 在旧路径或断链出现时真会失败，而不是对当前仓库永远输出绿色。一次整理中原有门禁全部通过却漏掉当前契约中的失效链接——“检查通过”的意义取决于覆盖范围，要同时记录检查了什么、不能证明什么。
- 全仓库禁止某个旧词会误伤研究、迁移映射和“已删除”说明；门禁守卫默认事实区，而不是抹去历史证据。

## 常见陷阱

- 只移动文件不更新索引，Agent 仍从旧链接进入历史设计；只改标题不改包路径和产品入口。
- 为“干净”删除历史资料，丢失迁移依据和决策上下文；机械替换历史链接改变原文叙述，history 不再反映当时状态。

## 自检

1. 新功能从 `docs/design-docs/index.md` 出发，会优先进入当前层文档吗？
2. 历史文档有清晰的归档声明和当前替代入口吗？执行计划与 history 的旧链接还能定位到真实文件吗？
3. 是否有负向测试证明旧路径和断链会让文档门禁失败？
