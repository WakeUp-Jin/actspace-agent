# 诊断界面需要按决策顺序渐进披露

开发者工具拥有大量真实数据，不代表应该把所有数据同时放到首屏。诊断界面的信息顺序应当跟随人的判断过程：先确认发生了什么，再定位为什么发生，最后才检查原始证据。

## 一个实用的三层模型

1. **结果层**：状态、响应、错误、耗时与关键用量。它回答“这次调用发生了什么”。
2. **上下文层**：消息、系统提示词、工具定义与相邻调用差异。它回答“模型为什么这样响应”。
3. **证据层**：规范化 Trace、请求 JSON、脱敏 cURL。它回答“需要逐字段核对时，事实是什么”。

首屏默认展示结果层；上下文层按分组折叠；证据层保持可达但默认收起。这不是隐藏能力，而是降低开始诊断时的认知成本。

## 为什么 Schema 不适合成为首屏

工具 Schema 通常同时具备三个特征：数量多、文本长、重复结构明显。一次展开十几个工具会让低频参考信息占据主要视觉面积，并把真正的异常响应推到滚动区之外。

更合适的结构是两级披露：

- 第一级只展示工具名、一行描述和参数数量。
- 第二级在用户选择单个工具后展示完整描述与参数。

原始 Schema 仍应保留在 Trace 中，避免可读视图为了简洁而丢失证据。

## 视觉层级不能由颜色代替

输入、输出、缓存和耗时如果分别使用不同颜色，界面会像数据图表，但这些字段并没有需要图例区分的序列关系。普通数值应使用中性文字、等宽数字和分隔线；颜色只承担选中、运行、成功、警告和失败等语义状态。

同样地，诊断工作台应尽量使用一个主 Surface 加平面分区。为标题、每个 Accordion 和内部工具条目重复增加圆角、描边与阴影，会制造虚假的多层层级。

## 页面切换也要渐进披露

渐进披露不只作用于字段和折叠区，也作用于导航空间。用户只是浏览对象列表时，仍处于低承诺的定位阶段；如果点击一个导航项就立即隐藏原导航、接管整页，会让“看看有哪些记录”产生不必要的上下文切换。

可以按任务强度划分两级空间：

- **来源空间内浏览**：列表、汇总、搜索和筛选保留在用户进入它的导航空间内。
- **独立工作区诊断**：只有选择具体对象、进入高密度操作后，才用完整页面承载复杂内容。

独立工作区返回时必须恢复来源空间的搜索、筛选和滚动位置。否则视觉层级虽然正确，交互上仍然相当于重新打开了一次列表。

## 自检问题

- 用户打开页面后，第一屏能否回答“发生了什么”？
- 折叠低频内容后，所有原始证据是否仍然可达？
- 用户是否在真正需要空间之前就被迫离开来源导航？
- 去掉彩色点和阴影后，页面层级是否仍然清楚？如果不能，说明信息架构还依赖装饰补救。
