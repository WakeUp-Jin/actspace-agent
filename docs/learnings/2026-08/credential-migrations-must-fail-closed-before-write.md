# 凭据存储安全：先读后写、三态编辑与靠近出站的脱敏

合并自三篇：凭据迁移必须先完整读取再允许写入、脱敏编辑表单需要三态 PATCH、错误脱敏要靠近实际出站请求。共同主题：**秘密只能单向流动，且任何“读不到/看不到”都不能被解释成“没有”**。

## 1. 缺失与不可读是不同状态（fail closed）

凭据读取失败时最危险的是把它当“尚未配置”：用户随后保存别的设置，内存里的空凭据覆盖磁盘上真实 Key，把可恢复的读取问题变成数据丢失。

```ts
type CredentialLoadResult =
  | { status: "missing"; credentials: EmptyCredentials }
  | { status: "ready"; credentials: Credentials }
  | { status: "unavailable"; code: string };
```

只有 `missing` 可从空对象开始写；`unavailable` 要阻止所有会改写凭据文件的操作（新增、替换、清除、级联删除）。

全量迁移而非逐字段：先在内存完成所有字段解析/解密/校验，再一次原子提交（读原文件 → 校验整体结构 → 转换全部 → 任一失败保留原文件进入 unavailable → 全部成功写临时文件、设权限、rename 替换）。边读边写会产生半迁移状态，任何中断都让后续版本难判断真实来源。

文件权限不是加密：`0600` 隔离同机其他账号，不能阻止当前账号下的恶意进程、备份或同步工具读取。明文凭据文件还需：只允许可信主进程读；renderer/IPC/日志/session/错误消息不返回明文；原子写临时文件**创建时**就设严格权限（不能 rename 后补）；启动时检查并收紧已有文件权限。回归：文件不存在允许首次保存；有效旧格式全转换且新文件内容与权限正确；任一旧字段转换失败原文件逐字节不变；JSON 损坏/未知版本/字段类型错误时新增与删除都被阻止；已有 `0644` 加载后收紧为 `0600`；不同应用身份或加密实现仍能读新格式。

## 2. 脱敏编辑表单的三态 PATCH

Renderer 读不到密钥时，编辑表单里的空输入不等于“当前没有值”。若保存把空串当无效或清除，用户无法只改其他字段，或一次无关保存意外覆盖已有配置。

```ts
type SecretPatch = undefined /* 保持 */ | string /* 替换 */ | null /* 清除 */;
// 保持代理 {}；替换/首启 { proxy: { enabled: true, url } }；明确关闭 { proxy: { enabled: false, url: null } }
```

表单校验也要知道当前状态：“代理开启且输入为空”不能一律禁用保存，只有当前没有已存地址且首次开启时空输入才是错误；已有地址被脱敏时提示“已配置；留空保持不变”，提交时省略字段。不要把脱敏值（`http://127.0.0.1:••••`、`sk-••••`）填回输入框——它们只是展示值，会让用户以为可直接编辑并把遮罩文本写回持久层；Renderer 只需“是否存在”与必要脱敏摘要。测试：已有值+空输入省略字段原值不变；+新输入替换；明确关闭提交 `null`；首次启用+空输入阻止保存；失败回滚时普通设置与密钥文件两边恢复同一旧状态。适用于 API Key、Webhook secret、数据库密码等任何只写不读的配置。

## 3. 错误脱敏要靠近最终出站请求

请求经过 resolver、模型路由、适配器、SDK 才发出；resolver 返回的凭据不一定是最终凭据（Host 可能在选择 Provider 后才绑定 Key）。早期凭据为空时，脱敏函数再正确也只能靠格式猜测，漏掉自定义格式 Key。

- 沿请求链标两件事：凭据在哪一步成为最终值、错误在哪一步可能进入业务事件或持久化；脱敏器位于两者之间，且要接住创建流时的异常、迭代时的异常、流中的 error/aborted 终止事件（只在 `await dispatch()` 外 catch 接不到稍后迭代的错误）。当前实现：PreparedLlmCall 保留早期防护，共用 PiAiAdapter 再用实际出站 credential 包裹直接 SDK 与 legacy 引擎；两层职责取决于各自掌握的事实，不能用“已脱敏过”代替检查凭据是否完整。
- 请求作用域优于全局密钥表：不长期保留已轮换密钥，请求 A 不会改写请求 B 的诊断。错误采用白名单复制字段（换了 message 但仍挂着原 cause/stack/headers 会旁路泄露）；正常回复保持原样，不把用户内容当错误诊断处理。
- 证明边界生效：用随机无效凭据，回环服务先确认实际鉴权，再故意在错误中回显原值和 URL 编码值；同时证明诊断与 HTTP 状态保留、两种值消失、正常回复不变；最后检查真实进程的实时事件、读取投影、Journal、输出文件。这次 CLI 全过而 Host 仍泄露，说明不同入口绑定时间不同，验收矩阵要按真实入口划分，再复用公共组件测试。

## 自检

1. 读取失败时，后续保存会不会把空凭据写回磁盘？半迁移被中断后旧文件还完整吗？
2. 用户只改其他字段时，Key 输入留空会保持原值吗？表单是否把遮罩值当作可提交值？
3. 凭据是否还会在下游被替换？流迭代异常是否被捕获？错误对象是否仍保留原始 Provider 属性？
