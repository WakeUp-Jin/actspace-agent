# 凭据迁移必须先完整读取，再允许写入

凭据存储读取失败时，最危险的处理不是直接报错，而是把失败解释为“尚未配置”。一旦用户随后保存其他设置，内存中的空凭据就可能覆盖磁盘上的真实 Key，把一次可恢复的读取问题变成不可恢复的数据丢失。

## 把缺失和不可读建模为不同状态

凭据加载至少需要三类结果：

```ts
type CredentialLoadResult =
  | { status: "missing"; credentials: EmptyCredentials }
  | { status: "ready"; credentials: Credentials }
  | { status: "unavailable"; code: string };
```

只有 `missing` 可以安全地从空对象开始写。`unavailable` 代表磁盘上可能存在无法读取的数据，必须阻止所有会改写凭据文件的操作，包括新增、替换、清除和级联删除。

## 全量迁移而不是逐字段迁移

从旧格式迁移时，应先在内存完成所有字段的解析、解密和校验，再一次原子提交新格式：

```text
读取原文件
  -> 校验整体结构
  -> 转换全部凭据
  -> 任一失败：保留原文件并进入 unavailable
  -> 全部成功：写临时文件，设置权限，rename 替换
```

逐字段边读边写会产生半迁移状态：一部分 Key 已换格式，另一部分仍是旧格式，任何中断都会让后续版本难以判断真实来源。全量迁移让旧文件或新文件始终至少有一份完整副本。

## 文件权限不是加密

Unix 权限 `0600` 表示所有者可读写、group 和 other 无权限；`0644` 则允许 group 和 other 读取。它能隔离同机其他账号，但不能阻止当前账号下的恶意进程、备份工具或同步工具读取。因此使用明文凭据文件时，还要保持以下边界：

- 只允许可信主进程读取文件。
- renderer、IPC、日志、session 和错误消息不返回明文。
- 原子写的临时文件在创建时就设置严格权限，不能等 rename 后再补。
- 启动时检查并收紧已有文件权限。

## 回归测试重点

- 文件不存在时允许首次保存。
- 有效旧格式全部转换成功，且新文件内容和权限正确。
- 任一旧字段转换失败时原文件逐字节不变。
- JSON 损坏、未知版本或字段类型错误时，新增与删除都被阻止。
- 已有 `0644` 文件加载后收紧为 `0600`。
- 不同应用身份或不同加密实现仍能读取新格式。
