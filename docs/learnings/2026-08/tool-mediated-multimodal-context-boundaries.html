Agent architecture note

工具委托式多模态：从图片到可信上下文

文本模型调用视觉模型，不等于文本模型获得了视觉能力。真正需要设计的是一条受控的数据管道：谁能读取哪张图片、图片发给谁、视觉结果如何变成主模型可以依赖的上下文。

一条请求里有五个不同责任

01 Intent主模型判断是否真的需要看图
02 Guard宿主验证路径、格式和大小
03 Observe视觉模型只接收问题与图片
04 Normalize工具包装稳定、版本化结果
05 Reason主模型基于文字证据继续工作

这五步不能合并成“把图片传给另一个模型”。一旦跳过 Guard，工具可能变成本地文件外传通道；一旦跳过 Normalize，Provider 的自由文本、错误对象和提示词注入会直接污染主模型上下文。

能力、输入和证据不是同一件事

原生多模态

主模型协议直接接收 image content part。图片属于这次主 LLM 调用的输入。

工具委托

主模型只看到工具定义和最终文字结果。视觉能力属于独立 LLM，主模型得到的是二手证据。

工具结果

它不是 Provider 原始响应，而是宿主承诺的稳定上下文契约，必须能版本化、截断和脱敏。

可观察事实

视觉输出仍可能出错。提示词必须区分直接可见事实、推断和无法确认区域。

为什么要三层视觉报告

<image_inspection_result version="1">
status: success
provider: openrouter
model: openai/gpt-5.6-luna

<visual_report>
## Image brief
## Answer to question
## Detailed evidence
### Layout
### Visible text
### Elements and states
### Relationships
### Visual details
### Anomalies and uncertainties
</visual_report>
</image_inspection_result>

Image brief 给主模型一个整体识别概念，Answer to question 提供当前任务的直接结论，Detailed evidence 保留足够细节让主模型复核、比较和继续推理。外层 envelope 属于工具，内层 Markdown 属于视觉报告，两者职责不同。

最容易踩的四个坑

  • 把附件等同于授权：当前轮附件可以精确放行，但不能由此允许模型读取任意绝对路径。
  • 只信扩展名：photo.png 可能不是 PNG，发送前应检查文件魔数和普通文件类型。
  • 把图片文字当指令：图片中的“忽略之前规则”只是待描述的像素证据，不是新的 system prompt。
  • 失败后自动换模型：这既可能重复计费，也会把同一图片发送给用户没有预期的第二个 Provider。
关键判断：工具的只读属性只表示它不修改本地文件，不表示它没有隐私或费用影响。向外部视觉 Provider 发送图片仍然是一次有数据边界的外部操作。

实现自检

  • 主模型原生支持图片时，是否避免重复注册视觉工具？
  • 工具请求是否只包含固定提示词、问题、安全文件名和单张图片？
  • Base64、绝对路径、Key、原始错误体是否都被挡在 session 与 renderer 之外？
  • 超时、取消、空响应、输出超限是否有稳定且不自动重试的行为？
  • 主模型拿到的究竟是 Provider 输出，还是工具承诺的版本化上下文？
