# 退役供应商时保留独立能力配置

## 核心知识点

一个产品供应商名称可能出现在多条能力链路中，但“文字模型供应商”和“图片生成服务”并不因此共享同一个生命周期。退役文字供应商时，应该沿着 Provider Registry、模型注册表、任务模型引用和文字密钥逐层清理；图片生成则通过自己的 secret id、端点和模型配置继续运行。

## 为什么容易出错

按供应商字符串做全局删除会误删图片生成配置，导致设置页看起来干净，但运行时在真正生成图片时才失败。反过来，只隐藏 UI 而不迁移持久化数据，会让旧模型继续被任务模型选择器或 runtime 解析。

## 可复用做法

1. 先列出能力边界，而不是列出供应商名称：确认每条链路的配置键、模型键、密钥 id 和 runtime 入口。
2. 迁移时只接受旧字段作为“待清理输入”，清理后重写规范格式；保留不属于退役链路的字段。
3. 为迁移写一个包含“旧文字配置 + 独立图片配置”的回归测试，断言两者分别被清理和保留。

## 自检问题

- 删除一个 Provider Registry 条目时，是否还有其他能力使用同一 base URL 或品牌名？
- 旧任务模型引用被清理后，历史 session 和 usage 是否仍然可读？
- 测试是否验证了独立能力的 key、端点和模型都没有变化？
