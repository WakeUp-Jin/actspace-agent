# 派生索引字段变义时，必须显式迁移

## 问题

Trace summary 中的 `toolNames` 原本从请求的 `tools` 数组生成。这个数组表达“模型可以调用哪些工具”，并不表达“模型实际调用了哪些工具”。当 UI 把它当作调用筛选索引后，所有能力声明都会显示成非零活动。

这类问题不能只在 UI 用条件隐藏，因为错误已经写进持久化 sidecar，旧记录也会继续携带错误语义。

## 处理模式

1. 先找到真正的事实事件。本例以 `llm_response.message.content[].type === "toolCall"` 作为实际调用来源。
2. 给派生数据增加独立语义版本，例如 `toolSummaryVersion: 2`。不要仅依赖整个文件的 schema 版本，因为文件结构并没有整体变化。
3. 新写入路径直接生成新语义。
4. 读取旧 sidecar 时，从有边界的原始日志重建目标字段，并原子回写。
5. 合并时只替换发生变义的派生字段，保留旧 sidecar 中 JSONL 截断后仍可能存在的终态和累计值。
6. 原始日志缺失时选择“不声称发生过调用”，而不是继续展示无法证明的旧索引。

## 为什么保留原始日志

Sidecar 是为了快速列表查询而存在的缓存，不是事实源。只要原始事件仍然可读，派生字段就可以修正、重建和升级。反过来，如果只存聚合结果，字段一旦变义就无法区分历史事实。

## 常见陷阱

- 把 capability、configuration、attempt 和 activity 混成同一个字段。
- 升级整个 schema，却没有定义旧记录何时迁移。
- 重建全部 summary，覆盖原 sidecar 中比截断 JSONL 更完整的终态。
- 迁移写盘失败时让读取也失败；派生缓存回写应尽量是 best effort。
