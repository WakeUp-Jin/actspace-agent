# 排序 UI 测试必须使用确定性时间 Fixture

当产品会按 `updatedAt`、`createdAt` 或优先级排序时，测试数据里的时间不仅是“必填字段”，而是决定展示顺序的输入。使用实时 `new Date()` 批量创建 fixture，可能让单测独跑稳定、全量并发却偶发失败。

## 为什么会只在全量测试中失败

假设组件先按时间降序排序，再只显示前 8 条：

```ts
const visible = sessions
  .sort((a, b) => b.updatedAt.localeCompare(a.updatedAt))
  .slice(0, 8);
```

测试快速独跑时，连续创建的记录可能共享同一毫秒时间戳。稳定排序会保留输入顺序，于是测试看起来可靠。全量并发增加 CPU 压力后，创建过程跨越多个毫秒，后创建的记录获得更新的时间并被排到前面，原本假定“第 9 条不可见”的断言就会失败。

问题不在排序算法，也不一定是测试间状态污染，而是 fixture 没有表达自己依赖的顺序。

## 正确做法

如果测试关心顺序，就直接编码顺序：

```ts
const sessions = Array.from({ length: 12 }, (_, index) => ({
  id: `session-${index}`,
  title: `Item ${index}`,
  updatedAt: new Date(Date.UTC(2026, 7, 26, 0, 0, 12 - index)).toISOString(),
}));
```

这样 `Item 0` 明确比 `Item 9` 更新，断言不依赖机器速度、并发度或毫秒碰撞。

如果测试并不关心顺序，则应该断言“只渲染 8 条”和“展开后渲染 12 条”，不要借某个名称的位置间接表达数量契约。

## 排查这类失败的顺序

1. 单独运行失败用例；若通过，说明需要寻找环境、并发或共享状态差异。
2. 运行整个测试文件；若仍通过，检查跨文件并发和实时输入。
3. 从产品路径反查所有排序、截断和分组条件。
4. 检查 fixture 是否使用当前时间、随机数、locale、时区或不稳定对象顺序。
5. 修复输入确定性，而不是给断言加等待、重试或放宽条件。

## 核心原则

- 时间和随机数只要参与业务决策，就必须由测试显式控制。
- “单测独跑通过”不能排除 fixture 不确定性。
- UI 截断测试应同时固定排序输入与可见数量契约。
- 不要用重试掩盖不确定测试；先找出哪个输入随运行环境变化。
