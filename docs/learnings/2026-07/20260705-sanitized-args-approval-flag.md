# 用 sanitizedArgs 内部标记实现「审批后放行」且防模型伪造

关联 history：`docs/histories/2026-07/20260705-1522-user-message-clamp-diff-preview-write-approval.md`

## 是什么

当权限检查器和 executor 各自独立做边界校验时，会出现一个结构问题：检查器判定"越界但用户已批准"，executor 却再跑一次硬守卫把它拒掉。需要一个通道把"这次调用已被人批准"从检查阶段传递到执行阶段。

做法：权限检查器返回 `ask` 时，在 `sanitizedArgs` 里塞一个内部标记（如 `APPROVED_OUTSIDE_BOUNDARY_ARG: true`）；调度器在用户批准后**用 sanitizedArgs 而不是原始 args 执行**；executor 看到标记就跳过边界守卫。

## 为什么需要，以及关键的防伪造约束

天真的替代方案都有问题：

- **全局状态/会话白名单**：批准的是"这一次调用"，全局状态会泄漏到后续调用，粒度错了。
- **executor 直接放开边界**：等于删掉守卫，模型可以不经审批写任意路径。

标记方案的安全性完全依赖一条不变式：**标记只能由权限检查器写入，模型传入的同名参数必须被剥除**。实现上检查器对每条路径都先解构剔除模型自带的标记（`const { [FLAG]: _, ...cleanArgs } = args`），工作区内路径返回的 sanitizedArgs 不含标记，越界路径的标记由检查器自己加回。这样模型伪造 `{ path: "/etc/passwd", approved_outside_boundary: true }` 会在检查阶段被清洗，仍然走 ask。

这个模式成立的前提是调度器契约：**批准后必须以 sanitizedArgs 执行**。如果调度器批准后用原始 args 执行，整条链路失效——接入前要先确认这条契约存在。

## 核心要点

1. 一次性审批的授权信息应该随"这次调用的参数"流动，而不是放进全局/会话状态。
2. 任何"参数里的特权标记"都必须由可信层写入、且对不可信输入做剥除，否则就是后门。
3. 必须为"模型自行传入标记"写一条测试锁死剥除行为，这是该模式最容易被后续重构悄悄破坏的点。

## 常见陷阱

- 只在越界分支剥除标记、允许分支忘了剥——工作区内路径带着模型伪造的标记通过 `allow`，下游如果还有别的消费者就被污染了。剥除要在检查器入口统一做。
- 硬拒绝看似更安全，实际会诱导模型绕道（本例中模型被拒后立刻尝试用 bash 写文件）。把"用户能理解并授权"的风险从 deny 挪到 ask，反而收窄了绕过面。

## 自检问题

- 你的 executor 信任 args 里的哪些字段？它们都只能由可信层写入吗？
- 用户批准的授权范围是"这一次调用"还是"以后类似的都行"？你的实现粒度和意图一致吗？
