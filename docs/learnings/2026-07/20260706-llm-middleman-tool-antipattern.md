# 反模式：用 LLM 中间层包装确定性能力

> 提炼自 history `2026-07/20260706-2350-split-web-tools-multi-provider-search.md`。

## 是什么

给 Agent 提供「读网页」「搜索」这类工具时，一个诱人的捷径是让另一个 LLM 代劳——比如用 Kimi 的 builtin `$web_search` 同时承担关键词搜索和 URL 爬取，由 Kimi 总结后返回自然语言。看起来一个接口解决两件事，实际上是把**确定性任务交给了概率性系统**。

## 踩到的坑

1. **能力错配**：`$web_search` 本质是搜索引擎入口，不是爬虫。给它一个具体 URL，它做的是「搜索这个 URL」，经常搜不到原文。
2. **幻觉不可分辨**：页面不可达时，中间层 LLM 会基于 URL 字面编造内容，主模型（和用户）完全无法区分真读到的和编的。确定性工具失败会报 HTTP 404；LLM 中间层失败会「成功」返回假货——**后者的失败模式危险得多**。
3. **成本与时延不可审计**：一次工具调用内部可能触发多轮 LLM 往返（搜索回填循环），token 消耗和耗时黑盒化。
4. **依赖耦合**：搜索能力被绑死在特定 LLM 供应商的 key 上，供应商细节泄漏进工具层。

## 怎么想

判断标准：**这个任务的正确输出是否唯一确定？**

- 「抓取 URL 并转 Markdown」——输出确定 → 用纯代码实现（fetch + charset 探测 + Turndown），失败就是明确的 HTTP 错误。
- 「搜索关键词返回候选」——由专业搜索 API 返回结构化结果（title/url/snippet），同样不需要 LLM 加工。
- 只有「理解图片内容」这类本质上需要模型能力的任务，才值得保留 LLM 辅助层。

配套模式：外部 API 依赖用**多供应商 + 错误分类降级**兜底——把 HTTP 状态码分类成 `quota / auth / rate_limit`（可降级）与其他错误，同一次调用内按优先级 failover 到下一家，部分成功也返回。这比单供应商 + 重试的可用性好得多，且各家是薄适配器（query → 结构化结果），互相替换零成本。

## 自检

- 你的工具链里有没有「LLM 调 LLM」的环节？它处理的任务输出是确定的吗？
- 如果中间层失败，上层能分辨「失败」和「幻觉的成功」吗？
