# 布局状态需要稳定的测量基准

来源：`docs/histories/2026-07/20260712-1453-composer-stable-inline-measurement.md`

## 问题模式

自适应 UI 常会根据内容的渲染尺寸选择布局。危险情况是：**布局选择本身也会改变被测量的尺寸**。

例如 Composer 有两种形态：

```text
inline:  + | 较窄的 textarea | model | send
stacked: |       全宽 textarea       |
         + | model                 | send
```

如果使用当前 `scrollHeight` 选择布局，就可能得到：

```text
inline 较窄 -> 文本折行 -> 切 stacked
stacked 较宽 -> 文本不折行 -> 切 inline
inline 较窄 -> 再次折行
```

最后一次宽度变化如果没有触发重测，UI 会停在“状态说是单行，实际已经折行”的矛盾状态；即使持续重测，也可能变成无限振荡。

## 核心原则

将“判定尺寸”和“展示尺寸”分开：

1. 选定一个稳定的候选布局作为判定基准。
2. 每次都在这个基准宽度下测量是否需要升级布局。
3. 得到布局状态后，再按当前实际宽度测量展示高度。

对 Composer 而言，问题是“内容在 inline 中是否放得下”，因此无论当前显示 inline 还是 stacked，判定都应使用 inline 的可用宽度。

## 实现注意

- 在 React 中宜用 `useLayoutEffect` 在浏览器绘制前完成尺寸校正，避免用户看到中间布局。
- 测量宽度应包含实际 padding、column gap 和相邻控件宽度，不要用字符数估算折行。
- 容器宽度、字体、模型按钮文案等变化都可能使原测量失效。宽度变化可用 `ResizeObserver` 补测，但要忽略纯高度变化，防止 observer 回调自我触发。
- CSS 数值解析必须处理空字符串和 `NaN`；测试 DOM 不一定像真实浏览器一样返回完整 computed style。

## 测试方法

只测“`scrollHeight` 从 34 变 74”不够，因为这把宽度与高度的关系人为切断了。回归测试至少要表达两个事实：

- 同一段文本在 inline 宽度下是多行。
- 同一段文本在 stacked 宽度下可能是单行。

然后再模拟文本二次变化，确认稳定判定不会被当前 stacked 宽度覆盖。

## 自检

1. 当前布局是否会改变用于选择布局的测量值？
2. 判定使用的宽度是否在所有状态下都一致？
3. 布局切换、窗口缩放和相邻控件宽度变化后是否会重测？
4. 测试是否真正模拟了“不同宽度下同一内容的不同高度”？
