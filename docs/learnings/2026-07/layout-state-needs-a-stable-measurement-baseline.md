# 布局测量不能依赖自己的判定结果：稳定基准 + 隔离的测量节点

合并自：布局状态需要稳定的测量基准、布局测量不能依赖自己的判定结果。

来源：`docs/histories/2026-07/20260712-1453-composer-stable-inline-measurement.md`

## 问题模式：布局选择本身改变被测量的尺寸

Composer 有两种形态：`inline`（`+ | 较窄的 textarea | model | send`）与 `stacked`（全宽 textarea 独占一行，按钮在下一行）。若用当前 `scrollHeight` 选布局：

```text
inline 较窄 -> 文本折行 -> 切 stacked
stacked 较宽 -> 文本不折行 -> 切 inline
inline 较窄 -> 再次折行 ...
```

最后一次宽度变化若没触发重测，UI 停在“状态说单行、实际已折行”的矛盾状态；持续重测则无限振荡——layout effect 每次更新状态，抛 `Maximum update depth exceeded`，没有错误边界时整个页面消失。两种布局里按钮宽度也可能不同，先读当前按钮宽度再推算“单行输入框能有多宽”，测量值就依赖刚选定的布局。

## 原则：判定尺寸与展示尺寸分开

1. 选定一个稳定的候选布局作为判定基准（Composer 的问题是“内容在 inline 中放不放得下”，无论当前显示 inline 还是 stacked，判定都用 inline 的可用宽度）。
2. 每次在这个基准宽度下测量是否需要升级布局。
3. 得到布局状态后，再按当前实际宽度测量展示高度。

实现：Composer 复制当前输入网格，在不可见、不可交互、脱离布局的**副本**上应用 inline 网格，读取 textarea 的 `scrollHeight`，再切回实际网格规则测量目标高度；副本沿用控件内容、字体继承、gap 和响应式断点，不用 JavaScript 重新推算按钮宽度；真实输入框只在目标高度变化时更新一次。

**不要在真实元素上同步切换网格再 `finally` 恢复**：它消除了状态反馈循环，却没消除浏览器内部副作用——输入框暂时变窄变矮时 `scrollTop` 也会变，即使同一帧恢复尺寸，输入法提交后光标可见区域也未必恢复。“用户看不到临时布局”不等于“临时布局没有副作用”。独立测量节点必须同步内容和 CSS 并及时移除，不能成为第二套手算布局。

## 实现注意

- 用 `useLayoutEffect` 在绘制前完成尺寸校正；测量宽度含实际 padding、column gap、相邻控件宽度，不用字符数估算折行。
- 容器宽度、字体、模型按钮文案变化都会使原测量失效；宽度变化可用 `ResizeObserver` 补测，但忽略纯高度变化，防止回调自我触发。
- CSS 数值解析处理空字符串和 `NaN`（测试 DOM 不一定返回完整 computed style）。

## 测试

只把 `scrollHeight` 从 34 固定变 74 不够，这人为切断了宽度与高度的关系。回归测试要表达：同一段文本在 inline 宽度下是多行、在 stacked 宽度下可能单行；再模拟文本二次变化，确认稳定判定不被当前 stacked 宽度覆盖；旧代码应实际失败、新代码稳定收敛。jsdom 没有布局引擎，仍需浏览器跨断点检查。
