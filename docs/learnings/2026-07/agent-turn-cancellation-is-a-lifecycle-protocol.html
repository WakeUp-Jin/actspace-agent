Agent Turn 取消是一份生命周期协议

一次 Stop 会跨过 UI、IPC、审批等待、工具进程、Agent loop 和持久化。只在某一层设置一个 boolean，通常只能“看起来停止”，不能真正收敛。

问题的本质

Renderer恢复输入框
Main找到当前 turn
Approval结束等待
Executor停止前台进程
Storage记录终态

任何一环没有观察取消，用户都会感知为“卡住”；任何终态没有落盘，用户都会在重进会话时感知为“历史丢失”。

三个关键不变量

  1. 取消作用域一致：同一个 turn 的 Agent、pending approval 和前台 executor 必须观察同一个取消事实。
  2. 终态独立建模：aborted 是 turn 的状态，不是最后一条 assistant message 的属性。
  3. UI 从事实恢复：streaming state 只用于运行中展示；完成、失败和中止都应回到持久化 SessionRecord。

Before / After

脆弱做法

abortButton.onclick = () => agent.abort()

status = lastAssistant.stopReason
ui.push({ text: "Stopped" })

审批 Promise 仍可能等待到超时；最后一条消息可能还是 toolUse；Stopped 只在当前 renderer 内存里。

可恢复做法

abortTurn(turnKey) {
  agent.abort()
  approvals.abortTurn(turnKey)
}

result.status = "aborted"
append({ type: "turn_aborted" })
ui.reloadSession()

等待立即结束，executor 有明确门禁，终态成为 append-only 会话事实。

最容易忽略的竞态

用户点击 Allow 的同时也可能点击 Stop。registry 需要让 pending entry 只被第一次有效 decision 消费；scheduler 即使拿到了 Allow，也要在启动 executor 前再检查一次 signal。这个“入口检查 + 等待后复检”模式适用于锁、队列、网络授权和任何异步门禁。

另一个陷阱是后台任务：一旦 Bash 已经转为 background task，它的生命周期就不应继续绑定原 turn，否则用户停止下一轮 Agent 时可能误杀长期任务。

自检问题

  • 如果 abort 发生在第一条模型回复之前，系统能否返回合法终态而不是抛“没有 assistant message”？
  • 如果 approval 刚返回 Allow，abort 是否仍能阻止 executor 启动？
  • 应用重启后，Stopped 是从事件事实恢复，还是靠上一次页面内存？
