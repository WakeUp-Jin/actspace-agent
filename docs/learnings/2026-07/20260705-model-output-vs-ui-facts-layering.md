# 工具结果的「模型回填」与「UI 事实」必须分层

关联 history：`docs/histories/2026-07/20260705-1522-user-message-clamp-diff-preview-write-approval.md`

## 是什么

一次工具执行产出两类消费者完全不同的数据：

- **模型回填（modelOutput）**：塞进 LLM 上下文的文本，允许被摘要、截断、压缩——它的目标是"够模型继续推理就行"。
- **UI 事实（structured）**：前端展示需要的原始结构化结果（diff 全文、additions/deletions、后台 taskId 等）——它必须精确、完整、不可被改写。

两者必须从工具结果产生的那一刻起就走不同字段，不能让 UI 从 modelOutput 反解析。

## 为什么需要

这次踩的坑：edit 工具的 diff 一旦超过截断阈值，`modelOutput` 会被上下文压缩改写成摘要文本。前端此前从回填文本里数 `+`/`-` 行来算统计，压缩后统计直接归零、展开看到的是摘要而不是 diff——用户报告"编辑工具不显示行数和 diff"。

根因不是压缩策略写错了，而是**UI 把一个"允许失真"的字段当成了事实来源**。只要 UI 依赖 modelOutput，任何压缩/截断策略的调整都会随机破坏前端展示，这类 bug 还只在"输出恰好超过阈值"时出现，很难在小用例里复现。

## 怎么做

- scheduler 后处理在**所有返回路径**（成功、失败、无输出、被压缩）都把原始结果保留到 `ToolResult.structured`。容易漏的是失败分支和"renderResult 覆盖 data"的分支。
- bridge 构建 `ToolUiPreview` 时优先读 structured，modelOutput 只做兜底（兼容旧事件）。
- 压缩/截断只作用于回填给模型的字符串，永远不碰 structured。

## 核心要点

1. 判断一个字段能不能当 UI 事实来源，看它是否可能被中间层改写——modelOutput 天生"允许失真"，不合格。
2. 保留原始数据的代码要覆盖全部返回路径，分支遗漏是这类修复最常见的回归点。
3. 这类 bug 有阈值触发特征（小 diff 正常、大 diff 坏掉），测试要专门构造超过截断阈值的用例锁行为。

## 自检问题

- 你的前端展示字段，中间经过了几层可能改写它的处理？每一层都确认过不碰它吗？
- 如果明天把截断阈值从 2000 改成 200，前端展示会变化吗？会的话说明分层没做干净。
