# Electron 的 minWidth 不是响应式布局

## 核心结论

Electron `BrowserWindow.minWidth` 只决定用户能不能继续拖窄窗口，不会替 renderer 处理侧栏、工具栏、表格和设置页的空间竞争。把 `minWidth` 从 `1120` 直接改成 `480`，可能让窗口尺寸达标，却让关键入口不可达。

## 为什么容易误判

桌面应用常在一个窗口里同时存在三类宽度约束：

1. Electron 原生窗口下限。
2. renderer 布局区域的业务下限，例如 sidebar `260px`、主聊天区 `560px`。
3. 组件内部下限，例如 Select、表格、Composer 工具栏。

第一层放开以后，后两层仍然存在。更隐蔽的情况是布局代码已经会“空间不足时自动隐藏侧栏”，但用户在窄窗中点击展开后，下一次尺寸校正又会立即把它隐藏。界面没有明显报错，入口却实际上不可用。

## 可复用的处理模式

### 1. 用业务宽度推导 breakpoint

不要随意选择一个常见断点。若桌面布局要求：

```text
默认 sidebar 260px + 主区保护宽度 560px = 820px
```

那么 `820px` 就是自然的模式切换边界。低于它继续使用分栏，只会产生反复隐藏或内容挤压。

### 2. 窄窗改变面板参与布局的方式

宽窗中，左右面板是 SplitView 的 grid columns；窄窗中，主区维持单列，面板改成临时 overlay：

```text
宽窗：sidebar | main | preview
窄窗：main + overlay(sidebar 或 preview)
```

这比不断降低各区域 `min-width` 更稳定，因为导航和预览本来就是临时任务，主聊天区才是持续工作区。

### 3. 不覆盖用户的桌面偏好

响应式降级状态不应写回桌面 `leftMode / leftWidth / rightWidth`。否则用户只是暂时缩窄窗口，却会永久丢失此前调整好的面板宽度。紧凑模式应持有独立、非持久化的 overlay open 状态。

### 4. 页面级视图也必须降级

工作台能缩小不代表整个应用能缩小。设置页、统计页和监控台往往拥有自己的固定两栏或宽表格，需要分别选择：

- 两栏变单栏；
- 固定侧栏变顶部横向导航；
- 宽表格保留语义宽度，通过局部横向滚动查看；
- Composer 从 inline 强制切 stacked，保护输入和发送按钮。

## 常见陷阱

- 只在 CSS 加媒体查询，却让 React 状态机继续按桌面分栏规则自动开关面板。
- breakpoint 小于“侧栏 + 主区保护宽度”，留下一个侧栏无法稳定打开的死区。
- 窄窗自动隐藏面板时顺手写入 localStorage，破坏宽窗偏好。
- 为了塞进 480px 把表格所有列强行压缩，结果数值和标题都不可读；这种内容更适合局部横向滚动。
- 只测试静态 DOM，没有覆盖“打开侧栏 → 打开右栏 → Escape 关闭”的状态转换。
