Architecture learning · Observability

观测 ID 必须跟随真实生命周期

一个页面标签可以随时改名，但关联键必须表达实体何时创建、何时结束、何时重试。否则日志看似完整，实际上无法回答“这次请求属于哪一步”。

agentRunId一次用户输入触发的完整 Agent 运行agent_start → agent_end
↓ 包含多个
turnId一次内部推理及其后续工具执行步骤turn_start → turn_end
↓ 正常一次，重试多次
llmCallId一次真实 provider API 请求llm_call_start → llm_call_end

问题从哪里来

最常见的错误是把“用户看到的一轮对话”直接命名为 Turn，再把后端真实的内部 Turn 忽略掉。此时 Abort、usage、重试和持久化都会共享一个含义模糊的 ID。

// 含义漂移：同一个 turnId 同时表示两种生命周期
runTurn({ turnId })
emit({ type: "turn_started", turnId })
persist({ turnId, usage })

正确的建模顺序

先找生产事件的代码，再画生命周期，最后命名 ID。不要从现有按钮文字或数据库字段名倒推领域模型。

agentRunId = user submission boundary
turnId     = engine step boundary
llmCallId  = network attempt boundary
attempt    = retry ordinal

重试是最好的验尸刀

如果无法确定两个 ID 是否应该分开，问一句：失败后自动重试时，哪个实体继续存在，哪个实体重新创建？

  • Agent Run 不变：用户没有重新提交。
  • Turn 不变：仍在完成同一个内部步骤。
  • LLM Call 改变：发生了新的真实网络请求。

恢复事实与分析证据分开

完整请求快照很适合分析，却会放大会话文件并引入敏感信息风险。事件存储应只保留恢复所需的稳定事实；深度 Trace 独立、脱敏、可删除。

session.jsonl  → 恢复消息与状态
traces/*.jsonl → 请求、响应、差异与耗时

删除 Trace ≠ 破坏会话恢复

长 Trace 的三件套

append-only JSONL 适合保存证据，却不适合每次打开列表时全量扫描。生产读取应拆成事实、索引和护栏三层。

trace.jsonl        → append-only evidence
trace.summary.json → atomic navigation index
bounded reader     → byte/event/symlink limits
  • 列表只读 sidecar，选中对象后才懒加载完整 Trace。
  • sidecar 损坏时只回退重建该对象，不能拖垮整个会话。
  • 达到体积上限时停止记录分析证据，但主业务继续运行。

常见陷阱

  • 只重命名 TypeScript 字段，却不修改事件生产位置。
  • 用数组索引充当长期 ID，过滤或排序后关联失效。
  • 失败重试覆盖前一次 usage，导致成本与耗时少算。
  • 把 Authorization、data URL 或上游错误体原样写入 Trace。
  • 让 renderer 直接拼文件路径读取本地分析数据。

自检问题

同一内部步骤重试三次时，应该有几个 Turn、几个 LLM Call？
删除分析 Trace 后，历史会话还能否完整恢复？
一个字段的名称来自 UI 文案，还是来自事件生命周期？
