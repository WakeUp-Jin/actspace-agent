# 原子 rename 不等于并发安全的 JSON Registry

关联变更：`docs/histories/2026-07/20260729-1515-workspace-git-worktree-context.md`

## 问题是什么

本地 JSON registry 常见的安全写法是：先写临时文件，再把临时文件 rename 到正式路径。它能避免进程崩溃时留下半截 JSON，但不能自动保证多个异步调用并发执行时的数据正确性。

如果所有调用共用同一个临时路径：

1. A 写入 `registry.json.tmp`。
2. B 覆盖写入同一个 `registry.json.tmp`。
3. A rename 临时文件到正式文件。
4. B 再 rename 时，临时文件已经不存在，得到 `ENOENT`。

即使给每次写入换成唯一临时文件，也只解决了 rename 冲突。两个调用仍可能同时读取旧快照，各自追加不同条目，最后完成的写入会覆盖另一个调用的结果。

## 正确的思考单位

真正需要串行化的不是单独的 `writeFile`，而是完整的 read-modify-write 事务：

```text
读取当前 registry
  -> 校验 / 修复
  -> 合并新条目
  -> 写唯一临时文件
  -> 原子 rename
```

进程内可以用 Promise queue 或 mutex 按 registry 路径串行执行事务。每次落盘仍应使用唯一临时文件，以防未来存在绕过队列的写入者，也便于失败后只清理本次生成物。

## 实现要点

- 读操作如果可能修复并写回文件，它就不是纯读，也必须进入同一队列。
- 被锁住的内部函数不要再次调用公开的加锁函数，否则可能形成等待自己的死锁。
- 临时文件名至少包含进程标识与随机标识。
- rename 后在 `finally` 中尝试清理本次临时文件；清理失败不能覆盖原始错误。
- 并发测试不能只断言“没有报错”，还要并行注册多个不同条目，再确认最终文件保留了全部结果。

## 边界

进程内 Promise queue 只能协调同一进程中的调用。如果未来允许多个独立进程同时修改同一个 registry，需要升级为文件锁、单一写入服务或数据库事务，而不是继续扩大进程内 mutex。

## 自检问题

2. 哪些看起来是“读取”的函数实际上也必须进入写事务队列？
3. 如果 registry 开始被多个进程修改，当前方案还缺少什么？
