Agent Harness Pattern · 2026-07-25

渐进式工具披露，不是动态装卸执行器

当一个能力域拥有大量工具时，最稳定的做法是让执行器保持注册，只动态改变本次模型请求能看到的 definitions，并把授权继续留在独立的安全层。

Registered

系统能不能执行

executor、permission checker、Socket client 和 disposer 是否已经装配。

Visible

模型这次看见什么

当前 LLM 请求携带哪些工具 schema。渐进披露只改变这一层。

Authorized

用户是否允许执行

审批租约、能力 hard deny 和风险策略；不能被“已披露”替代。

为什么不动态 register / unregister？

注册通常带着资源和生命周期：连接池、Socket、清理函数、权限检查器、输出渲染器。为了省模型 token 而反复重建这些对象，会把上下文优化变成运行时稳定性问题。

ToolManager
  ├─ registered tools: gateway + deferred executors
  ├─ visible definitions: filtered per LLM call
  ├─ active disclosure groups
  └─ pending disclosure groups

正确时序：pending 到下一次调用才 commit

LLM call #1

只看到 gateway。

→

Gateway success

记录 pending group，不立即放行。

→

LLM call #2

commit 后看到完整工具包。

关键陷阱：如果 gateway 成功后立刻激活，模型在同一条 assistant message 中幻觉生成的隐藏工具，可能因顺序执行而被意外放行。披露必须绑定到下一次模型请求边界。

实现骨架

// 工具注册时记录披露元数据
gateway.progressiveDisclosure = { group: "browser", role: "gateway" }
deferred.progressiveDisclosure = { group: "browser", role: "deferred" }

// gateway 成功：只写 pending
pendingDisclosureGroups.add("browser")

// 下一次 LLM 调用前
commitProgressiveDisclosure()
context.tools = toolManager.getToolDefinitions()

隐藏工具不仅不能出现在 definitions 中，执行入口也必须检查可见性。否则模型或不可信历史仍可能绕过“UI 隐藏”。

不要漏掉这些消费者

主 Agent 初始 Context
每次 LLM 调用前的刷新
Context token bucket / 完整视图
手动与自动上下文压缩
自治 Agent 的下一次 tick
设置总开关与 system prompt

只改一个 producer 很容易产生“双口径”：模型看见一组工具，Context 面板却统计另一组；或者用户关闭总开关后，system prompt 仍宣称能力可用。

自检问题

  • 同一批 tool calls 中，gateway 后面的隐藏工具会不会被顺序放行？
  • 下一条用户消息是否恢复为 gateway-only，而不是永久膨胀？
  • 关闭工具组后，definitions、prompt、运行时依赖和 Context 统计是否同时消失？
  • 工具披露是否被错误地当成用户授权？
