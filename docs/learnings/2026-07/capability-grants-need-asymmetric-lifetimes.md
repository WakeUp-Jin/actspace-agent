# 能力授权与拒绝需要不对称的生命周期

来源：`docs/histories/2026-07/20260711-2315-browser-session-authorization.md`

## 问题

一组工具共享同一种外部能力时，如果每次叶子调用都审批，用户会被连续弹窗打断；如果一次拒绝永久封禁，又会让用户无法在下一次明确指令中改变决定。

Browser Use 是典型例子：`tabs`、`navigation`、`locator`、`cua` 等命令虽然名字不同，但都在使用同一个真实 Chrome 控制能力。

## 建模方式

把审批结果拆成两个生命周期不同的状态：

```text
允许 -> Session capability grant
拒绝 -> Turn-scoped denial
```

- Session grant：当前应用运行期间，只要 Session 不变，后续同类工具静默放行。
- Turn denial：当前 Turn 内同类工具静默拒绝，避免模型换一个工具名再次申请。
- 下一 Turn：旧 denial 不再生效，可以重新弹出审批。
- 应用重启：内存 grant 自然失效，不把临时授权变成长期账户权限。

## 为什么不能只在 UI 隐藏弹窗

“不再显示审批卡片”不等于“权限状态正确”。真正的授权状态必须在执行入口前的权威注册表中判断：

1. Settings 或策略硬拒绝先执行。
2. 已有 Session grant 则直接允许，不产生 pending request。
3. 当前 Turn 已拒绝则直接拒绝，不产生第二张卡片。
4. 只有两者都没有时，才创建审批请求并暂停工具。

如果只在 Renderer 去重，Agent Core 仍然会等待一个用户永远看不到的审批请求，表现就是任务卡住。

## 上下文必须随请求固化

审批请求应携带创建时的 `sessionId` 和 `turnId`，不能在用户点击按钮时再读取“当前活动会话”。用户等待审批时可能已经切换侧边栏，或者另一个会话同时发起工具调用。

因此审批注册表使用请求自身的上下文作为事实来源，活动会话只能作为旧调用方的兼容 fallback。

## 常见陷阱

- 按工具名缓存允许，导致 60 多个同能力工具仍需逐个审批。
- 把拒绝缓存到 Session，用户下一轮无法重新授权。
- 拒绝后仍允许同一 Turn 换一个 Browser 工具重新弹窗。
- 只保存布尔值，不保存 scope，无法区分一次性审批和能力租约。
- UI 负责权限真相，主进程或调度器没有静默决策路径。
- 审批事件缺少 Session/Turn，切换会话后卡片或结果路由错误。

## 自检

1. 用户允许一次后，同一 Session 的下一 Turn 是否完全不产生审批请求？
2. 用户拒绝后，同一 Turn 的第二个同类工具是否静默拒绝？
3. 下一 Turn 是否能重新申请，而不是继承上一次拒绝？
4. 用户在审批期间切换会话，决定是否仍作用于原始请求？
