# 插槽式系统提示词设计：让用户改人格而不弄坏 Agent

> 提炼自：`docs/histories/2026-07/20260704-1020-kairos-soul-slot-and-settings-section.md`
> 相关设计：`docs/design-docs/agent-kairos-prompt-design.md`

## 是什么

长期运行的 Agent 想开放「用户自定义系统提示词」时，有两条路：**全量覆盖**（用户文本直接替换内置模板）和**插槽注入**（模板留出固定占位符，用户只填其中一块）。插槽式的核心：把提示词按「谁有权改」分层——人格/语气归用户（`{soul}` 插槽 → soul.md），执行机制归代码（例程、场景应对、工具契约硬编码在模板里）。

## 为什么全量覆盖是坑

Agent 的系统提示词里藏着大量**与宿主代码强耦合的契约**，表面上只是自然语言：

- Kairos 每个 tick 必须以 `sleep` 工具收尾——scheduler 靠它推进循环；
- 读写授权边界的描述必须与工具守卫（guard）的真实行为一致；
- 「观测增量不含数据源 Skill」这类语义约定，决定模型会不会主动读文件。

用户全量覆盖时不可能知道哪句话是「装饰」哪句话是「承重墙」。删掉一句，Agent 可能不睡、越权、或者干脆瘫痪，而且用户看到的只是「它变笨了」，完全无从自查。**提示词不是配置文件，是接口实现的一部分。**

## 参考实现：Hermes 的同款结论

分析 hermes-agent 源码验证了这个思路是业界收敛的模式：

- `system_prompt.py` 三层组装（stable / context / volatile），用户可改的只有 `SOUL.md`，读不到时 fallback 到内置 `DEFAULT_SOUL_MD`；
- `/personality pirate` 命令看起来很魔法，实现只是把 `config.yaml` 里 `personalities` 字典的一段文本填进提示词的附加字段——**预设人格 = 往插槽里填预写好的文案**，没有更多机制。

Kairos 比 Hermes 更进一步：只留**一个**人格落点（soul.md），不做 SOUL + personality overlay 双层叠加——两层文本同时生效时的优先级用户无法推断，这是 Hermes 的 CLI 历史包袱而非设计优点。

## 落地时的三个关键决策

1. **拆槽时检查身份段里藏了什么机制**。原身份段里混着「产出只有两种，否则白醒一次」这条行为契约——它不是人格，是产出验收标准。拆槽时把它独立成机制段，否则用户换个人格就把行为契约冲掉了。
2. **预设字典放依赖图的最底层**（`@actspace/shared`）。UI 下拉和 agent-core 的 fallback 必须逐字节共用同一份数据，否则「默认」预设会分叉；「选中态反推」（当前内容与哪个 preset 相等）也依赖这一点。
3. **插槽内容要有预算和 fallback**。soul.md 500 token 截尾 + 空白时 fallback 默认人格，保证任何用户输入都不会把提示词撑爆或掏空。

## 核心要点

- 提示词按「谁有权改」分层，不是按内容主题分层。
- 用户可改的部分必须满足：删空不坏（fallback）、写爆不坏（预算截尾）、改烂不坏（机制段兜底）。
- 「预设人格」的正确实现是数据（字典）而不是逻辑（分支）。
- 扩展新场景走用户规则（rule.md 的「遇到 X 做 Y」+ 授权覆盖原则），不改提示词模板——模板变更是发版事件，规则变更是用户配置事件。

## 自检问题

1. 如果用户把 soul.md 写成「你是海盗，只说黑话」，Kairos 还会按时 sleep、还会遵守读写边界吗？为什么？
2. 预设「极简」的文案改版升级后，老用户已写入 soul.md 的旧版文案会发生什么？下拉会显示什么？
3. 用户想要「检测到新 CSV 就自动分析」，应该改 soul、rule.md 还是 briefs？判断依据是什么？
