# 破坏性工具必须区分 deny、ask 与执行环境

关联 history：`docs/histories/2026-07/20260726-0802-fix-bash-delete-approval-environment.md`

## 是什么

“危险”不是一个足够精确的工具状态。破坏性工具至少需要区分三件事：操作是否永远不允许（deny）、是否可以由用户确认后执行（ask）、最终在哪个环境实际执行。

## 为什么容易出错

如果权限层只返回 `dangerous operation`，模型很容易把它理解成“正在等待审批”；但 scheduler 的 deny 分支其实不会创建审批请求。UI 若又只在历史恢复时携带环境字段，用户会同时遇到两个错觉：以为有按钮可以点，以及不知道命令究竟是否在沙盒里运行。

另一个常见陷阱是把执行方式当成危险目标。例如 `rm -rf` 的 `-rf` 表示递归强制删除，但不能单独证明目标没有正当删除场景。真正决定 hard reject 的是目标边界：workspace 根、workspace 外、glob 或 `.git` 等无法安全授权的对象。

## 怎么做

- 权限决策先回答 `deny / ask / allow`，不要用同一条模糊错误覆盖三种状态。
- deny 的模型回填明确写出“执行前拒绝、没有审批请求”。
- ask 事件携带计划执行环境，让审批卡片能展示用户将批准什么。
- executor 返回实际执行环境，最终 preview 用实际值覆盖计划值。
- 沙盒初始化失败时停止执行，不能静默降级真实环境，否则审批时展示的环境承诺失效。
- UI 为执行前拒绝建模 `notExecuted`，不要把“未知环境”误当成“未执行”。

## 核心要点

- 风险等级不是权限状态；dangerous 不等于 awaiting approval。
- 删除安全应检查目标路径，而不是只检查 `-rf` 等 flag。
- 计划环境属于审批契约，实际环境属于执行事实，两者都要可见。
- 安全基础设施失败应该 fail closed，不能静默降低保护等级。
