# 会话 Fork 是结构化快照，不是目录复制

会话型应用里的 Fork 看起来像 `cp -R`，但真正的目标是创建一份“拥有独立身份、保留共同历史、可以继续演化”的状态快照。只复制目录会把新分支里的 `sessionId`、绝对路径和 sidecar 继续指向源会话，之后的恢复、附件读取或子 Agent 追踪就可能串线。

## 建模方式

一次可靠的 Fork 可以拆成三个阶段：

1. **冻结边界**：只允许复制稳定的持久化 head。运行中或等待审批时拒绝 Fork，避免得到半截事件流。
2. **复制事实**：复制主事件流、可变 Context 状态、附件和所有会话级 sidecar，而不是只复制聊天气泡。
3. **重建身份**：生成新的 session ID，并对结构化 JSON / JSONL 做键感知重写；历史 event / turn ID 可以保留，因为它们表达分叉前的共同祖先。

## 为什么要“键感知重写”

全局字符串替换很危险：用户消息或工具输出里可能正好包含源 session ID 或目录路径，这些属于历史内容，不该被篡改。更稳妥的策略是只重写有身份语义的字段，例如 `sessionId`，以及明确承载内部文件引用的 `sessionPath`、`outputPath`、`attachmentsDir` 等字段。

这是一种通用模式：复制任何带内部引用的工作单元时，都应该区分“内容数据”和“身份/定位数据”。Git worktree、任务模板实例化、项目克隆和工作流重跑都有类似边界。

## 常见陷阱

- 只改 `meta.json`，忘记事件流和 Context sidecar 里的旧 ID。
- 只复制 `session.jsonl`，丢掉附件或子任务 transcript，导致历史看似存在但无法完整恢复。
- renderer 禁用按钮，却不在写入边界再次校验 active 状态，留下竞态窗口。
- 把所有字符串都替换，悄悄修改用户原始对话和工具结果。
- 为新分支重新生成所有历史事件 ID，反而丢失“共同祖先”的可追踪性。

## 自检问题

- 新分支删除或继续写入后，源分支是否完全不受影响？
- 新分支中的内部路径是否都落到新目录，而用户历史文本是否保持原样？
- Fork 请求与下一次事件 append 同时发生时，系统在哪一层保证一致性？
