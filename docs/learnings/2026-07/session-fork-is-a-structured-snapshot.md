# 会话 Fork 是结构化快照：复制事实、重建身份、同步资源所有权

合并自：会话 Fork 是结构化快照不是目录复制、Fork 的文件所有权（复制消息还不够）。

来源：`docs/histories/2026-07/20260726-1104-session-fork-copy.md`

Fork 看起来像 `cp -R`，真正目标是创建“拥有独立身份、保留共同历史、可继续演化”的快照。只复制目录会让新分支里的 `sessionId`、绝对路径、sidecar 仍指向源会话，之后恢复、附件读取、子 Agent 追踪就会串线。

## 1. 三个阶段

1. **冻结边界**：只允许复制稳定的持久化 head；运行中或等待审批时拒绝，避免半截事件流。renderer 禁用按钮不够，写入边界要再校验 active 状态，否则留竞态窗口。
2. **复制事实**：主事件流、可变 Context 状态、附件、所有会话级 sidecar（含子任务 transcript），不只是聊天气泡。
3. **重建身份**：新 session ID；对结构化 JSON/JSONL 做键感知重写。历史 event/turn ID 保留——它们表达分叉前的共同祖先，全部重生成会丢失可追踪性。

## 2. 键感知重写，不做全局字符串替换

用户消息或工具输出里可能恰好包含源 session ID 或目录路径，属于历史内容，不能改。只重写有身份语义的字段：`sessionId`，以及明确承载内部文件引用的 `sessionPath`、`outputPath`、`attachmentsDir`。通用模式：复制任何带内部引用的工作单元（worktree、任务模板实例化、项目克隆、工作流重跑）时都要区分“内容数据”与“身份/定位数据”。

## 3. 资源要一起继承：图片文件 ID 的所有权

历史里的图片通常只是文件 ID。复制历史后页面仍能显示文字，模型再次读图却可能失败：文件仍属于父会话，子会话没有读取权。所以继承的是边界前的消息加这些消息引用的资源：先复制资源得到新 ID，再把子历史的结构化引用同步替换，最后发布子历史。用旧 ID → 新 ID 映射去重，同一图片在消息、工具结果、请求快照中的多次引用仍指向同一副本。

独立副本多占空间，但删除父文件不影响子会话，再次 fork 规则一致；共享文件需要另外定义引用计数、回收、跨会话读取权限，不能只放宽 owner 校验。不要在全文中替换 ID，依据文件引用结构替换。

回滚只能删除本次独占创建的目录与文件；目标会话早已存在时创建必须失败，不能把它当本次残留清理。可捕获异常时的清理不是断电事务：要崩溃一致性需另设计 staging、提交标记和恢复扫描，try/catch 不能承担。

## 常见陷阱

- 只改 `meta.json`，忘了事件流和 Context sidecar 里的旧 ID。
- 只复制 `session.jsonl`，丢附件或子任务 transcript，历史看似存在却无法完整恢复。
- 全字符串替换悄悄改写用户原始对话。

## 自检

1. 新分支删除或继续写入后，源分支完全不受影响吗（含附件文件）？
2. 新分支内部路径都落到新目录，而用户历史文本原样保留吗？
3. Fork 请求与下一次事件 append 同时发生时，哪一层保证一致性？
4. 子会话里模型再次读取历史图片会成功吗？
