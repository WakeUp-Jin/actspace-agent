# 断言类名不等于断言行为：单测全绿也能全坏

关联 history：`docs/histories/2026-07/20260730-1200-right-panel-file-view-optimization.md`

## 是什么

这轮给文件视图加了行号、软换行开关和文件内查找，单测覆盖到了每个功能，全绿。真机跑起来之后四个功能里坏了三个 —— **而且每一个都有对应的、通过了的断言**。

它们共享同一个失效模式：断言检查的是「我写的那行代码在不在」，而不是「用户看到的结果对不对」。

```tsx
// 断言长这样，永远会绿 —— 它检查的是我刚写下的那个字符串
expect(codeEl).toHaveClass("whitespace-pre-wrap");
```

`whitespace-pre-wrap` 确实在。但它没生效，因为父级 grid 挂着 `w-max`：宽度取 max-content，代码列那个 `1fr` 就等于「最长行的宽度」，于是**永远没有需要折行的机会**。开关看着生效、实际是空操作。

## jsdom 系测试的三类结构性盲区

`jsdom` 不实现布局、不实现真实时序、也不会给你真实规模。这三件事各对应一类查不出来的 bug：

### 一、布局：类名有了，几何没生效

上面的 wrap 是一例。另一例是行号 gutter 在滚动容器内是 `position: static`，横向滚动一下就被带走 —— 恰好是长行最需要行号的时候。jsdom 里 `scrollLeft`、`offsetWidth`、`getBoundingClientRect()` 全是 0 或常量，这类问题在单测里不可见。

**能做的改进：把断言从「有没有这个类」改成「两种状态是否互斥」。**

```tsx
// 弱：只证明我写了这个类
expect(grid).toHaveClass("w-max");

// 强：证明宽度策略随开关切换，空操作会被抓住
expect(grid).toHaveClass("w-max");
expect(grid).not.toHaveClass("w-full");
await user.click(wrapToggle);
expect(grid).toHaveClass("w-full");
expect(grid).not.toHaveClass("w-max");
```

仍然是在测类名，但测的是**关系**而不是存在。真几何只能靠真浏览器 —— 本轮最后是用 CDP 直接量 `rowsForLongest`（最长行占几行）和滚动后 gutter 的位置才确认修好。

### 二、时序：构造状态再断言，测不出竞态

「打开查找框后第一个字符被吃掉」这个 bug 是**测试撞出来的**，但不是靠断言撞出来的，是靠**操作顺序**：

```tsx
await user.click(searchButton);
await user.type(searchInput, "alpha");
expect(searchInput).toHaveValue("alpha");   // 实际拿到 "lpha"
```

原因是 `openSearch` 把 `select()` 放进了 `requestAnimationFrame`，那一帧落在用户已经开始打字之后：刚输入的 `a` 被选中，下一个键位直接替换掉它。改成用 ref callback 在挂载时同步聚焦。

**教训是关于怎么写测试的**：`render(<C searchOpen />)` 然后断言，永远撞不到这个 bug —— 状态是我摆好的，中间没有时间流过。**像真人一样按顺序操作**（点开 → 打字 → 断言）才会让异步补偿逻辑暴露在真实时序里。这条比具体的 rAF 陷阱更值钱。

### 三、规模：测试数据太小，退化看不见

行号是这么实现的：一个逻辑行 = 一个 grid row = **两个 DOM 节点**（行号 + 代码）。单测里那些十几行的 fixture 完全正常。

真机上 2MB 日志有 19 万行 = 38 万个节点，5 万行的文件实测要 **13.5 秒**才打开。而且这是**引入的回归**，不是继承的：旧实现是单个 `<pre>`（一个文本节点），行数再多都不受影响。为了行号和逐行搜索定位，把 DOM 节点数从 O(1) 变成了 O(行数)。

两处修：

- `LineRow` 加 `memo`。分块高亮每推进一批就 `setState` 换掉整个数组，没有 memo 的话每批都会重渲染**全部**行 —— 5 万行 × 50 批。这里 memo 不是优化点缀，是让分块高亮这个设计能成立的前提。
- `MAX_RENDERED_LINES = 20000` 上限，工具栏明示还有多少行没显示。

**上限这件事值得单独说**：它是「按行渲染」这个选择的必然配套。一旦渲染成本从 O(1) 变成 O(n)，就必须自己给 n 设上限，否则等于拿大文件的可用性换小文件的行号。同一个仓库里 `CsvRenderView` 的 2000 行上限是同一套取舍 —— 看到这种取舍出现第二次，说明它是模式而不是临时妥协。

## 那单测还值得写吗

值得，但要知道它在证明什么。类名断言的真实价值是**防回归**：它锁住「这里必须有个宽度策略」，将来有人删掉时会红。它不能证明「用户能看到折行」。

所以分层：

- **单测**：结构、分支、状态机、互斥关系。快、稳、覆盖广。
- **真浏览器 / CDP 取值**：几何、滚动、主题翻转下的实际颜色、大输入下的耗时。慢，但**只有它能证明看得见的行为**。

判断标准很简单：**如果这个功能的正确性依赖布局、时序或规模，就必须去真环境量一次。**「量」的意思是取到数字（占几行、滚动后位置、几毫秒），不是截个图看着像对的 —— 本轮的 wrap 空操作在静态截图里完全看不出问题。

## 核心要点

- `toHaveClass("...")` 常常只是在断言「我刚才写的字符串还在」。
- jsdom 有三类结构性盲区：布局几何、真实时序、真实规模。
- 把断言从「存在」改成「状态间互斥」，能抓住空操作。
- 测试里按真人顺序操作，比构造好状态再断言更容易撞出竞态。
- 把渲染成本从 O(1) 改成 O(n) 时，必须同时给 n 设上限。
- 依赖布局 / 时序 / 规模的功能，去真环境取数字确认，别只看截图。
