# 文档目录重组必须是一次原子迁移（含扁平前缀方案的演进）

合并自：文档目录重组必须是一次原子迁移、扁平前缀索引适合 Agent 读的设计文档。

整理文档目录看起来只是移动文件，实际更接近一次 Schema migration：目录结构是知识库的地址协议，设计文档、源码注释、检查脚本、执行计划和历史记录都是这个协议的消费者。

## 核心问题

文档持续增长后，常见的两个极端都不好：

- 完全平铺：文件名承担全部分类信息，同一专题的入口、设计、实现说明和原型分散在长列表中。
- 无限嵌套：目录看似精确，但读者需要反复进入 `agent/tools/browser/runtime/...` 才能找到事实来源。

一个实用折中是限制为：

```text
docs/design-docs/
├── 跨专题入口或独立文档.md
└── 强关联专题/
    ├── 设计文档.md
    ├── 实现说明.md
    └── 原型.html
```

专题目录内禁止继续创建目录。目录只回答“这些文件是否需要一起阅读和维护”，不试图完整复制代码架构。

## 什么叫强关联

建立专题目录前，可以用三个问题判断：

1. 这些文档是否服务于同一个稳定能力边界？
2. 修改其中一份时，是否经常需要检查另外几份？
3. 新读者是否通常需要把它们连续读完，才能理解完整机制？

三者大体成立时适合放在一起。只有语言、文件前缀或“都属于 Agent”相同，并不足以形成专题。

例如 Browser Bridge、Browser 集成设计和命令面需要共享职责边界，适合放在同一目录；Agent 测试策略与效果评估虽然都包含“测试”，但一个验证内部行为，一个衡量产品能力，不应该仅按词汇相似度合并。

## 为什么必须原子迁移

如果只移动文件、不更新消费者，会出现几类隐蔽问题：

- Markdown 相对链接随目录深度变化后失效。
- 源码注释仍指向旧事实来源，新 Agent 会读取不存在的路径。
- 检查脚本硬编码旧路径，CI 在下一次无关改动中才失败。
- HTML 原型和图片被移动后，入口页能打开但图片全部丢失。
- 已修改但未提交的文档在复制、删除过程中被旧版本覆盖。

因此迁移顺序应该是：

1. 固定旧路径到新路径的一对一映射。
2. 记录工作区状态，明确哪些文件已有用户改动。
3. 移动文件，不回退或覆盖内容。
4. 更新完整仓库路径、Markdown 相对链接和脚本硬编码。
5. 处理重复文档，但只合并稳定且不冲突的事实。
6. 同一轮执行结构、链接、脚本和仓库卫生检查。

## 资产为什么直接跟随专题

在只允许一层目录时，不应该重新创建 `frontend/assets/` 或 `kairos/mockups/`。图片和原型本身也是设计证据，应直接放在所属专题目录：

```text
frontend/
├── README.md
├── front-聊天输入框规范.md
├── composer-final.png
└── compact-command-states.html
```

这种结构牺牲了一点文件类型上的整齐，但减少了读者在“文档目录”和“资产目录”之间来回跳转，也让相对引用更稳定。

## 常见陷阱

- **按组织架构建目录**：组织和代码模块会变化，专题应围绕稳定产品能力。
- **目录和文件名前缀同时大改**：两类变化叠加后 diff 难审查，最好分阶段进行。
- **把概览全文复制到 README**：入口只保留导航和稳定原则，具体规范仍应一题一文。
- **机械合并相似文档**：标题相似不代表语义一致，先检查事实是否冲突或属于不同生命周期。
- **只检查当前目录**：路径消费者往往藏在源码注释、测试脚本、历史计划和插件文档里。

## 前身：扁平前缀方案（2026-06，已被一层专题目录取代）

关联 history：`docs/histories/2026-06/20260601-2350-flatten-design-docs.md`

多层专题目录曾被收敛成一层：正式 `.md` 用文件名前缀表达领域（`agent-*`、`front-*`、`lab-*`、`core-*`、`fix-*`），图片、HTML prototype、截图等非正式文档放唯一资产目录 `public/`，每个领域保留一个 `*-index.md`。动机：目录分层让 Agent 定位知识要先判断目录、再读索引、再进文件，旧目录名（`agent-core/`、`frontend-ui/`、`lab/versions/`）还同时承载领域、包名和阶段状态；扁平前缀把“找文件”变成线性动作（`rg --files docs/design-docs`），文件名暴露主题，入口索引承担渐进披露。

陷阱（对任何目录方案都成立）：只移动文件不重写索引（目录变扁了入口还在讲旧目录）；资产也全部摊平会淹没正式文档，资产需要一个例外目录；机械替换路径时重复加前缀，迁移后必须做路径存在性检查；历史记录里的旧路径有两类——作为历史事实可保留，作为当前导航必须更新，不要无差别改成现在时。2026-07 的单层专题目录（上文）是对它的修正：前缀只靠文件名分类，强关联文档（设计、实现说明、原型）仍分散在长列表里。

## 自检问题

1. 新专题目录是否表达稳定能力，而不是临时项目阶段或文件类型？
2. 删除任一专题目录后，是否能明确说出哪些共同事实来源会一起丢失？
3. 是否验证了目录深度、Markdown 链接、硬编码路径和机器检查，而不只是看 `git status`？
