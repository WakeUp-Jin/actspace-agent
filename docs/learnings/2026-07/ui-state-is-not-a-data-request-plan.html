UI 展开状态不是后台请求计划

当列表、树或 Diff 页面很大时，用户看到什么、数据加载什么、DOM 挂载什么，是三个不同的问题。把它们绑在一个 expandedIds 上，会把一次普通点击放大成不可控的 I/O 和渲染风暴。

反直觉的失败模式

“Expand all”看起来只是展示动作。旧实现却把每个展开 ID 直接变成一次请求，因此复杂度沿链路逐层放大。

展示状态
N 个文件被标记为展开
→
后台副作用
N 次 IPC、N 个 Git child、N 份 patch、N 组 DOM

即使画面只显示当前文件，只要 store 仍保留全部 expanded ID，系统就是“视觉 capped、后台 uncapped”。这类 bug 很难从截图判断，必须看 producer 到 consumer 的完整调用链。

把三个集合分开

集合回答的问题应该由谁决定
displayedIds当前界面有哪些 section？load policy + selection + filter
requestedIds后台现在允许读取哪些数据？snapshot load policy
mountedRows此刻 DOM 中保留哪些行？virtualizer visible range
 
// 错误：交互状态隐式决定 I/O
useEffect(() => {
  expandedIds.forEach(loadFileDiff)
}, [expandedIds])

// 正确：策略显式决定唯一请求集合
const requestedIds = loadPolicy.mode === "single-file"
  ? [selectedFileId]
  : snapshot.textFileIds

loadFileDiffs(requestedIds)

为什么只加并发限制还不够

Semaphore 能把 100 个并发压成 8 个，但不能消除 100 次重复的 repository 解析、Git 启动和 patch 组装。它降低峰值，却保留总工作量与长尾。

更有效的顺序是：先缩小请求集合，再把同基线、同参数的 tracked files 合成批量命令，最后才对无法批处理的 untracked/file reads 使用有界并发。

Generation 是取消边界

scope、workspace、whitespace 语义或 Git 状态变化后，旧请求即使最终成功，也不再属于当前界面。每个 generation 应有自己的 AbortController、pending cache 和 prepared context。

invalidate(workspaceId) {
  state.abortController.abort()
  state.abortController = new AbortController()
  state.generation += 1
  state.pending.clear()
  state.prepared.clear()
}

取消 child process 解决资源浪费；snapshot/generation guard 解决迟到结果污染。两者缺一不可。

虚拟化解决的是 DOM，不是数据

虚拟列表只限制挂载行。如果后台仍加载全部完整文件，内存和 Git I/O 依然会爆。反过来，只做 capped 数据加载但把 9,000 行一次挂进 DOM，滚动与 React commit 仍会卡。

Data policy
Standard 批量 patch；capped 当前文件；full content 仅可见附近
+
Render policy
扁平稳定 row key；可变高度测量；有限 overscan

常见陷阱

  • 失败 Promise 留在 cache，Retry 永远拿到同一个失败结果。
  • 只取消网络/child，不做 generation guard，迟到结果覆盖新 selection。
  • full-file 开关复用 patch 请求，导致关掉显示选项时重新执行全部 Git。
  • 虚拟列表用 DOM ID 跳转，目标行未挂载时定位失效；应使用 virtual index。
  • jsdom 没有真实布局，尺寸观察得到 0；测试保底视口必须在真实尺寸出现后让位。
自检问题
  1. 一次 Expand all 最终会产生几次 IPC、几条 Git 命令和多少 live DOM row？
  2. 切换 scope 后，旧 child 是否被取消？旧结果是否还能写入新 state？
  3. 关闭 full content 时，patch 是否无需重取且仍可阅读？
