# 计量按最细粒度的模型调用记录：不按渲染消息，也不依赖业务解析成功

合并自：渲染出来的一条消息不一定是计费边界、请求计量为什么要先于业务解析落盘。

关联：[`20260725-2106-turn-usage-cost-visibility.md`](../../histories/2026-07/20260725-2106-turn-usage-cost-visibility.md)、[BUG-045 工程修复](../../exec-runs/20261021-actspace-full-acceptance/execution-summary.md#bug-045)

## 1. 事实按 LLM call 细分，视图后聚合

用户看到的一条最终回复，不对应供应商的一次模型调用：

```text
LLM call 1 -> thinking + tool call ; tool result
LLM call 2 -> tool call           ; tool result
LLM call 3 -> final reply
```

尾栏若读 final reply 自带的 usage 就只剩 call 3，前两次已付费的 token 和费用消失；可重试错误更隐蔽：失败正文通常不持久化，供应商仍已计费。模式：每次调用落一条不可变 `llm_usage` 事实，带 `turnId`，必要时带 `relatedEventIds` 说明它产生了哪些消息/工具事件；产品视图（消息尾栏按 turn、Usage 表按 turn/day、总览按时间窗口）从事实聚合，最终消息只是展示锚点不是数据来源。请求耗时、缓存命中、服务端工具次数、失败重试统计同理。

陷阱：把 Assistant message 数量当 LLM call 数量；失败重试没正文就丢 usage；各页面各写一遍汇率换算导致口径漂移；为方便 UI 把完整价格快照复制进每条消息。

## 2. 计量先于业务解析落盘

一次请求有两个结果：供应商是否执行并产生用量；应用是否理解并接受回答。审核模型已返回 30 Token 但 JSON 格式错误，不代表这次请求免费。计量若放在 `parseReview(await complete())` 成功之后，解析异常会跳过计量；把未知 usage 补成 0 也错——0 是明确无消耗，未知是没取得供应商数据。

顺序：持久化请求开始事实 → 派发请求 → 消费流时累计供应商实际返回的 usage → 流结束/失败/取消后持久化结束事实 → 才解析业务结果。持久化异常必须可见，不能把没记下来的请求当正常成功；取消也可能已有部分计费。

归属反映真实执行结构：标题生成属于会话，不能伪造一次 Agent Run；工具自动审核绑定实际工具的 Run/Turn/Step/call。统计请求、Token、费用时两者都保留，统计 Run 时只算真实 Run，这条规则要同时用于实时触发器、批量写入、删除和时间范围查询。审核自身写入的计量事实不应使审核并发校验失败（其他并发变化仍须拒绝）；派生数据库改了汇总规则后，必须连同行与游标一起失效重建，不能只升级查询代码。
