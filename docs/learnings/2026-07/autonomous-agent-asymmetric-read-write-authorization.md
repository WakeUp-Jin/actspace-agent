# 后台自治 Agent 的读写授权非对称设计

> 提炼自 `docs/histories/2026-07/20260703-2300-kairos-prompt-rewrite-watch-retirement.md`。

## 是什么

给后台自治 Agent（Kairos）的工具守卫做两层授权：

- `allowedRoots`：显式配置的路径列表（paths.json），**可读可写**。
- `readOnlyRoots`：从其它用户动作推导出来的路径（已启用 Skill 的目录、文件监听插件正在监听的目录），**只读**。

守卫按工具的 `isReadOnly` 标志分流：读工具放行 `allowedRoots ∪ readOnlyRoots`，写工具仅限 `allowedRoots`。

## 为什么这样设计

对称授权（读写同一份白名单）看起来简单，但会制造一个荒谬的用户体验：用户在设置页把 `~/Documents/notes` 加入文件监听，Agent 能"看到"这个目录有文件变化了，却因为该目录不在 paths.json 里而无权读取内容——功能等于半残。让用户在两个地方重复授权同一个目录，是把实现细节泄漏给了用户。

关键洞察是：**读和写的风险量级不同，授权信号的来源也可以不同**。

- 写操作有破坏性，必须要求用户**显式**授权（paths.json 手动添加）。
- 读操作风险低，可以从用户的**间接意图**推导——"把目录加入文件监听"这个动作本身就表达了"我希望 Agent 关注这里"，自然蕴含读权限。

## 实现要点

1. **授权分类挂在工具定义上，不挂在守卫里**。每个工具声明 `isReadOnly: true/false`，守卫只做通用分流。新增工具时授权语义自动正确，不需要改守卫代码。
2. **推导出的授权要跟着来源实时同步**。fs-watch 监听目录变化或开关切换时，main 进程重建 KairosController 以刷新 `readOnlyRoots`——否则会出现"用户已移除监听但 Agent 仍可读"的授权残留。
3. **错误信息区分两种拒绝**。"路径不在可读范围"和"路径只读、写入被拒"是不同的用户问题，报错要能区分，否则排障时会误以为授权配置坏了。

## 附带的取舍：提示词 vs 数据注入

同一轮还有一个可迁移的决策：Agent 对持续数据源（fs-watch 日志）不够主动时，**不要**把数据直接注入 Agent 的输入（tick 观测增量），而是改提示词引导它主动去读。理由：

- 注入会让"Skill 作为消费接口"的抽象失去意义——所有数据源最终都会挤进主输入，上下文预算失控。
- 提示词层做**通用**引导（"持续更新的数据源类 Skill 每次唤醒应主动查看"），数据源自己的 SKILL.md 把 description 写得 pushy，两层配合且互不硬编码。
- 保留回退路径：若实际运行仍经常漏看，再补机制层注入——先用便宜的手段，观察后再加码。

## 自检问题

1. 如果第二个插件（比如剪贴板监听）也要给 Kairos 授权只读输出目录，需要改守卫代码吗？（不需要，把目录并入 `readOnlyRoots` 即可。）
2. 为什么 `readOnlyRoots` 的刷新要走 controller 重建而不是让守卫每次现查配置？（守卫在热路径上，每次工具调用现查文件会引入 IO 与竞态；controller 重建把"配置变更"收敛为单一同步点。）
