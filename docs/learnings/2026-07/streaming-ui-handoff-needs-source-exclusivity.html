流式 UI 交接需要单一数据源

模型完成时的“闪一下”经常不是浏览器刷新，而是同一条消息先被渲染两次，再以另一组 React key 重新挂载。解决它需要同时控制数据源和展示身份。

典型故障时间线

Streaming用户消息、Thinking、工具和回复都在内存中持续更新。
→
重叠帧SessionRecord 已包含当前 turn，但 streaming blocks 尚未清空。
→
Persisted流式块被移除，持久化块以随机 event id 重新挂载。

重叠帧让页面高度突然增加；随后旧节点卸载、新节点播放入场动画，视觉上就像整个消息区闪动。

两个必须同时成立的不变量

  1. 数据源互斥：同一个 turnId 在任何渲染帧中只能来自 streaming 或 persisted。
  2. 展示身份稳定：同一个逻辑消息在两个阶段必须拥有相同 React key。
持久化身份：event id用于日志、消息操作、缓存和数据引用。它可以随机生成，但不能承担 UI 交接身份。
展示身份：render key由 turnId + 语义槽位派生，例如 turn:T1:assistant:0。

Before / After

状态直接相加

messages = [
  ...persistedMessages,
  ...streamingBlocks,
]

setSessionRecord(restored)
await refreshSidebar()
setStreamingBlocks([])

当前 turn 会在等待辅助刷新期间出现两份。

按 turn 互斥并同步交接

persistedVisible = persisted.filter(
  event => event.turnId !== streamingTurnId
)

setSessionRecord(restored)
finishStreamingTurn()
await refreshSidebar()

辅助请求不会再把消息交接拆成两个可见阶段。

回归测试如何抓住竞态

普通 happy path 很难观察短暂重叠。测试应故意让最终的会话列表刷新保持 pending，然后在这个窗口断言：

  • 用户消息和最终回复各只有一个。
  • 流式阶段与持久化阶段的 turn DOM 是同一个节点。
  • Assistant、Thinking 和工具块没有因 event id 改变而 remount。
  • 完成、失败、Abort 和 Session 切换使用相同交接规则。

常见陷阱

  • 只把多个 setState 放在一起，却没有定义“当前 turn 只能有一个来源”的渲染不变量。
  • 直接把持久化 event id 改成展示 key，破坏消息缓存、可视化和日志引用。
  • 只移除动画类，隐藏了 remount 症状，却仍然丢失组件内部展开状态。
  • 把 Session 列表、Review、统计刷新夹在消息区交接中间，重新制造异步渲染窗口。
