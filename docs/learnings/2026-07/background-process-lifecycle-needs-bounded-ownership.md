# 后台进程需要有界生命周期与稳定身份

## 核心问题

Agent 启动 dev server、watcher 或长时间构建后，工具调用会先返回，进程则继续跨 turn 运行。这种异步能力如果只有 `start` 和 `kill`，很容易出现三个问题：进程被遗忘、同一命令重复启动、模型在新一轮对话里不知道已有任务。

关键不是把任务分成许多类型，而是让所有后台任务共享一组机械约束：

1. **时间有界**：从进程真正启动时开始计时，超过统一上限自动终止。
2. **数量有界**：按所有者（例如 session）限制并发后台任务数量。
3. **身份稳定**：用规范化 `cwd + command` 作为运行中任务身份，相同任务返回原句柄而不是重复 spawn。
4. **上下文可见**：新用户 turn 首次调用模型前注入一次运行清单，内部工具循环不重复注入。

## 为什么仅靠超时不够

最大运行时间只能清理“最终会过期”的进程，不能阻止模型在一分钟内连续启动多个相同服务。数量上限也只能限制损害规模，无法阻止上限以内的重复任务。因此时间、数量和去重需要同时存在：

```text
时间上限 → 防止遗忘
数量上限 → 防止资源爆炸
身份去重 → 防止重复工作
turn 清单 → 防止模型失忆
```

## 容易踩的坑

### 从转后台时才开始计时

如果命令已经在前台运行了几分钟，转后台后重新开始计时，实际总运行时间会超过声明上限。正确做法是记录 spawn 时间，注册后台任务时只安排剩余时长。

### 每次内部 LLM 调用都注入运行清单

Agent 的一个用户 turn 内可能包含几十次模型调用。每次都注入相同清单会污染上下文。应使用每次 Agent run 独立的闭包状态：首次调用注入清单，后续只注入新事件。

### 只在任务产生新事件时注入清单

安静运行的 dev server 可能长时间没有输出。如果运行清单依赖 notification 才出现，新 turn 中的模型会看不到它，从而重复启动。

### 先 spawn，再做重复检查

重复检查最好在 spawn 前完成；对于前台等待后才转后台的命令，还需要在注册前再次检查，覆盖等待期间出现的新任务。

## 自检问题

- 任务的最大运行时间是从 spawn 还是从后台注册开始计算？
- 新用户 turn 能否看到安静运行、没有新日志的后台任务？
- 相同命令重复调用时，系统返回原任务还是生成第二个进程？
- 达到会话上限时，尚未注册的新进程是否会被可靠回收？
