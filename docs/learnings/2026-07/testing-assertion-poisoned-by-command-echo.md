# 测试断言被「命令回显」假阳性满足的陷阱

> 提炼自：`docs/histories/2026-07/20260703-1745-bash-background-verification-fixes.md`

## 是什么

当被测输出**同时包含命令文本和命令的执行结果**（bash 工具头部、任务通知、日志行等几乎都会回显命令），用 `toContain("关键字")` 断言执行结果时，如果关键字恰好是命令文本的子串，断言会被命令回显满足——执行结果根本没产生，测试也全绿。

本仓的真实案例：`bash_output` 返回 `Task xx (printf first-chunk; sleep 30) status=running\n<文件内容>`。测试断言 `toContain("first-chunk")`，而落盘管道有一个「转后台后文件停止增长」的严重 bug，文件其实是空的——但头部回显的命令里就有 `first-chunk`，13 个测试全部通过，bug 直到手工验收才暴露。

## 为什么容易踩

- 写测试时自然会用命令里的字面量当断言关键字（`printf hello` → 断言 `hello`），子串关系是隐式的，review 时不显眼。
- 假阳性测试比没有测试更糟：它给了「这条链路已覆盖」的错误信心，掩盖的恰恰是它声称要守护的路径。

## 怎么防

1. **让输出不是命令的子串**。最便宜的手法是 printf 格式串拼接：`printf 'chunk-%s' one` 输出 `chunk-one`，命令文本里只有 `chunk-%s` 和 `one`，断言 `chunk-one` 只能被真实输出满足。算术（`echo $((6*7))` → `42`）同理。
2. **新链路先写一个「必失败」验证**。对刚实现的输出管道，先手工把管道弄断（或直接断言文件精确等于全量内容 `toBe(...)` 而非 `toContain`），确认测试真的会红，再恢复。
3. **警惕一切「回显 + 结果」混合输出的断言**：CLI 帮助文本、错误消息带原始输入、日志行带请求参数，都是同类风险面。

## 自检问题

1. 你的 `toContain` 关键字，是不是被测命令/输入文本的子串？
2. 如果被测功能完全不工作（输出为空），这条测试会红吗？
3. 断言能不能升级为对纯结果段的精确匹配（`toBe`），绕开混合输出？
