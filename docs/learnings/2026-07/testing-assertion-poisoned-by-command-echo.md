# 让验证能失败：回显假阳性、故障注入未生效、搬家式重构的变异检查

合并自：测试断言被“命令回显”假阳性满足的陷阱、故障注入也需要证明自己真的生效、搬家式重构先用变异测试看看测试守住了什么。

关联：`docs/histories/2026-07/20260703-1745-bash-background-verification-fixes.md`、`docs/histories/2026-10/20261006-1930-desktop-fe-09-composer.md`、[Context / SQLite 联合实现](../../histories/2026-10/20261011-2059-context-sqlite-joint-plan.md)

共同问题：**一条验证即便被测功能完全坏了也会是绿的**，它给的是“这条链路已覆盖”的错误信心，比没有测试更糟。每次写验证都问：被测功能完全不工作时，这条验证会红吗？

## 1. 断言被输出里回显的输入满足

被测输出同时含命令文本和执行结果（bash 工具头部、任务通知、日志行、CLI 帮助、带原始输入的错误消息）时，`toContain("关键字")` 若关键字恰是命令文本子串，就被回显满足。真实案例：`bash_output` 返回 `Task xx (printf first-chunk; sleep 30) status=running\n<文件内容>`，测试断言 `toContain("first-chunk")`，而落盘管道有“转后台后文件停止增长”的严重 bug、文件其实为空——头部回显的命令里就有 `first-chunk`，13 个测试全绿，bug 直到手工验收才暴露。

防法：
1. 让输出不是命令的子串：`printf 'chunk-%s' one` 输出 `chunk-one`，命令文本里只有 `chunk-%s` 和 `one`；算术（`echo $((6*7))` → `42`）同理。
2. 新链路先写“必失败”验证：手工弄断管道，或直接对纯结果段做 `toBe(...)` 精确断言，确认会红再恢复。
3. 警惕一切“回显 + 结果”混合输出的断言。

## 2. 故障注入要证明自己生效，还要有正向对照

开启“模拟失败”后操作成功，并不说明产品正确处理了错误，也可能是测试装置没识别到请求、根本没制造故障。压缩验收实例：产品已换压缩提示词，测试服务仍用旧句子识别压缩请求，开关返回成功，实际请求被当普通聊天，界面自然显示压缩成功。分别验证三件事：
1. 触发条件被识别（真实请求被标记为要注入故障的那类，别只看开关返回值）；
2. 故障确实发生（错误状态码、请求日志、持久化失败事件）；
3. 产品正确恢复（界面显示失败，解除后重试成功，失败不误计入成功次数）。

装置的回归用例要用产品当前真实请求契约（直接读取压缩提示词，而不是复制一份旧的）：开启错误→压缩返回 400、普通请求仍成功→解除后摘要成功。还要保留正向对照：只有“禁止时失败”排除不了环境本来就坏，只有“允许时成功”也证明不了禁止生效；状态切换、权限、取消、缓存失效同理。

## 3. 搬家式重构：先变异，再信“全量通过”

拆大组件时“剪到新文件、全量绿、提交”默认被搬逻辑原本有测试覆盖，这个前提通常不成立。Composer.tsx 拆分（1810 → 496 行）每步故意改坏刚搬的关键判断再跑全量：

| 步骤 | 变异数 | 改坏后仍全过 |
| --- | --- | --- |
| 附件 | 3 | 3（去重、运行中不收拖放、远端选文件带 `remote: true`） |
| 斜杠菜单 | 11 | 9 |
| 工具栏 | 7 | 3 |
| 根组件收尾 | 27 | 9 |

做法：搬之前列变异清单（每个 `if`、提前 `return`、阈值、“只在 X 时才 Y”，重点是去掉也不会崩的判断）；每次只改一处、跑全量、恢复，用脚本做并断言模式唯一（`assert orig.count(before) == 1`）、`try/finally` 恢复、结束后与备份 diff；有变异活下来就补用例并再跑该变异，新用例优先测抽出来的纯函数/hook（`renderHook`，更快更准；如 `composerSendOptions`、`contextUsageDisplay`）；把“改坏后 0 条失败”写进执行记录。

搬家特别需要：看似无风险没人细看；闭包可能取到另一作用域的同名变量，diff 难发现；拆分改变执行顺序（三个 `useEffect` 移进 `use-composer-draft` 后相对时机变了）。陷阱：变异是等价代码（应说明等价或删掉多余判断）；`replace` 不唯一；忘了恢复；只看有无失败不看是哪条失败（补用例要让断言直接描述该行为）。

## 自检

1. `toContain` 的关键字是不是被测命令/输入文本的子串？被测功能完全不工作时这条测试会红吗？
2. “模拟失败”真的触发了吗？有没有成对的正向对照？
3. 纯搬迁的 PR 全量绿、diff 逐行对得上，还有什么没被发现？“改坏后 0 失败”集中在哪类判断上（“锁定时不做 X”“超阈值才做 Y”）？
