# 公开 Changelog 的内容模型应该匹配阅读顺序

关联 history：`docs/histories/2026-07/20260728-2005-redesign-updates-changelog.md`

## 是什么

公开 Changelog 的内容契约不只是存储格式，它会直接决定页面的信息层级、编辑成本和读者的理解路径。

如果读者希望依次看到“时间、这次发布的主题、具体变化”，源文件也应该按相同顺序表达：

```md
## 2026-07

### 2026-07-28 — 发布标题

#### 新功能

- 用户可观察到的变化。

#### 改进

- 已有体验的提升。

#### 问题修复

- 已解决的问题。
```

这个结构可以直接映射为时间线与连续正文，不需要额外的展示字段来重新解释内容。

## 为什么“用户价值 + 技术摘要”容易变复杂

“用户价值”适合做产品规划中的决策依据，“技术摘要”适合做工程 history，但它们不一定适合成为公开 Changelog 的一级字段。

当源文件按功能域维护表格时，页面为了恢复时间顺序，通常还要额外解决：

- 一个日期对应多个表格行，标题和日期被重复展示。
- 同一事实同时出现在用户价值、摘要和详情中，维护者需要反复改写。
- 技术内容过长，只能增加折叠面板、标签或卡片来降低视觉噪音。
- 读者需要先理解页面的数据模型，才能知道这次到底更新了什么。

复杂 UI 往往不是视觉问题，而是内容模型与阅读任务不一致的结果。

## 怎么设计内容契约

### 1. 先确定读者的主问题

对公开更新页，主问题通常是：

1. 什么时候发布？
2. 这次发布的主题是什么？
3. 新增、改善或修复了什么？

字段应服务这三个问题。内部动机、实现路径、测试证据可以留在 history、design doc 或 pull request 中。

### 2. 用稳定事实做标识

标题会随着文案优化而变化，不适合做永久链接。日期适合生成稳定锚点，例如 `release-2026-07-28`。

如果项目没有正式版本号，就不要为了模仿别人的页面伪造 `v0.x.y`。发布日期本身已经足够承担排序和定位职责。

### 3. 分类必须互斥且可省略

- 新功能：此前不存在的新能力。
- 改进：已有能力、性能或交互的提升。
- 问题修复：明确消除的错误或异常行为。

没有内容的分类直接省略。强行补齐三个分类会诱导编辑者重复内容或把内部工作包装成用户更新。

### 4. 解析器要保护写作契约

构建期解析应尽早拒绝含糊或不可展示的结构：

- 非法日期或日期不属于当前月份。
- 同一天重复发布。
- 未知分类或同一分类重复出现。
- 分类下没有列表项。
- 嵌套列表、复杂块级内容或不安全链接。

严格解析不是为了限制 Markdown，而是为了让编辑错误在构建阶段暴露，而不是以破碎布局进入线上页面。

## 如何从工程历史补齐公开记录

History 与 Git Log 是证据，不是可直接发布的文案。整理时可以按以下顺序：

1. 按日期列出可能影响用户的提交与 history。
2. 合并同一天围绕同一体验的多条工程记录。
3. 删除纯重构、测试数量、文件路径和协议字段等内部噪音。
4. 把剩余事实改写成用户能观察或操作的结果。
5. 根据变化性质放入新功能、改进或问题修复。
6. 对无法从证据确认的能力宁可省略，不做推测。

自动从 Git 提交生成 Changelog 可以帮助发现候选项，但不应替代这一步人工编辑。提交的粒度和措辞服务开发过程，公开发布记录服务产品理解，两者目的不同。

## 页面实现上的对应关系

当内容契约已经按阅读顺序组织，页面可以保持简单：

- 左侧时间线只负责定位日期。
- 右侧正文按日期连续阅读。
- 分类标题和灰色项目列表直接来自源文件。
- JavaScript 只增强滚动高亮与 hash，同一份静态 HTML 在禁用脚本时仍可阅读。

这类页面不需要为每条更新包一层卡片。时间线、留白、字号和文字明度已经足以建立层级。

## 常见陷阱

- 为了视觉丰富增加与内容无关的标签，随后又被迫维护更多字段。
- 用标题生成锚点，改文案后破坏旧链接。
- 把同一天拆成多个 release，导致时间线重复且正文碎片化。
- 直接复制提交信息，让公开页面充满实现名词和仓库路径。
- 只校验最终 HTML，不校验源 Markdown 的结构，导致错误难以定位。
- 依赖滚动脚本隐藏或加载正文，使无 JavaScript 页面不完整。

## 核心要点

- 内容模型应匹配读者的阅读顺序，而不是内部团队的工作分工。
- 公开 Changelog 与工程 history 分工不同，但前者可以从后者取证。
- 稳定日期锚点比可变标题和虚构版本号更可靠。
- 严格的构建期解析能换来简单、稳定的展示层。
- 当数据结构正确时，好的时间线页面主要依赖排版，不依赖复杂组件。
