# 单实例锁 vs 遗言心跳：一个文件同时承载两种语义时的自锁陷阱

> 提炼自 `docs/histories/2026-07/20260703-1800-plugins-fs-watch-integration.md` 的后续迭代（fs-watch 插件单实例锁误报）。

## 是什么

fs-watch 插件用 `state.json` 里的 `lastHeartbeatAt` 做两件事：

1. **消费方存活判定**：Agent 读事件日志前检查心跳是否新鲜（< 90s），判断数据是否还在更新。
2. **单实例锁**：新实例启动时若发现心跳新鲜就拒绝启动（exit 2），防止两个进程往同一个日志目录双写。

同时插件在**优雅退出时会写最后一次心跳**——这对语义 1 是必要的（告诉消费方"数据截止到这个时间点"），但对语义 2 是毒药：进程刚退出，心跳反而是最新鲜的，接下来 90 秒内的任何重启都会被自己的"遗言"挡住。actspace 里改配置自动重启、快速关开开关必现"检测到另一个实例正在运行"的误报。

## 为什么会踩坑

三个各自合理的设计叠加出了 bug：

- 遗言心跳：合理，消费方需要知道数据截止时间。
- 心跳新鲜度当锁：合理，比 pid 文件更能防"进程崩了锁没释放"。
- 停止后立即重启：合理，配置变更就该即时生效。

单看每一条都对，组合起来就是"进程用自己的死亡证明证明自己还活着"。这类 bug 在代码评审里很难被发现，因为它不在任何一个模块内部，而在模块间的时序里。

## 修复思路

锁的判定从「心跳新鲜」收紧为「心跳新鲜 **且** state.json 里的 pid 仍存活」：

```rust
// kill(pid, 0) 不发信号只探活：0 = 存活；EPERM = 存活但无权限；ESRCH = 已退出
fn pid_alive(pid: u32) -> bool {
    let ret = unsafe { libc::kill(pid as libc::pid_t, 0) };
    ret == 0 || std::io::Error::last_os_error().raw_os_error() == Some(libc::EPERM)
}
```

关键权衡：**消费方契约保持不变**（仍然只看心跳，不许 pid 探活）。因为两种场景的误判成本不同：

| 场景 | 判定依据 | 为什么 |
| --- | --- | --- |
| 消费方（Agent 读日志） | 只看心跳 | pid 可能被系统复用给无关进程，误判"还活着"会让 Agent 信任过期数据；心跳窗口自带时效，安全 |
| 插件自身的锁 | 心跳 + pid | 误判窗口只有 90s，远短于 pid 复用周期；且锁误报的代价（拒绝启动）用户直接可见 |

同一个文件、两个读者、两套判定标准——这不是不一致，是按误判成本各自选择。

## 宿主侧的配套：孤儿接管

修了锁之后还有一类真孤儿：dev 热重启把 Electron 主进程直接杀掉，来不及给子进程发 SIGTERM，旧 fs-watch 继续跑、继续心跳。此时新 app 启动的实例会被锁正确地挡住（心跳新鲜且 pid 真的存活）——锁没错，但用户体验是"开关打不开"。

宿主的解法是**接管而不是报错**：`start()` 前读 state.json，发现心跳新鲜且 pid 存活就先 SIGTERM（超时 SIGKILL）再 spawn。前提是输出目录由宿主独占管理，所以任何往这里写心跳的进程都是自己以前 spawn 的，杀掉是安全的。这个前提不成立时（多宿主共享输出目录）不能这么做。

## 核心要点

- 一个状态文件被两种读者用于两种判定时，警惕"对 A 必要的写入对 B 是毒药"，尤其是**退出路径上的写入**。
- 进程锁不要只依赖时间窗口（心跳/mtime），要叠加身份验证（pid 探活）；反过来，跨进程的存活判定不要只依赖 pid（复用误判），要叠加时间窗口。两者互补。
- `kill(pid, 0)` 是 Unix 探活的标准姿势，注意 EPERM 也算存活。
- 守护进程的宿主对"锁被占"有两种响应：报错（占用者身份不明时）和接管（确定占用者是自己的孤儿时）；能接管就不要把问题抛给用户。

## 自检问题

1. 为什么不干脆去掉优雅退出时的最后一次心跳？（答：消费方需要它标记数据截止时间；砍掉语义 1 来修语义 2 是拆东墙补西墙。）
2. 为什么消费方不能用 pid 探活，插件的锁却可以？（答：误判窗口不同——锁只关心 90s 内，pid 复用周期远长于此；消费方场景没有时间上限，复用误判概率不可忽略。）
