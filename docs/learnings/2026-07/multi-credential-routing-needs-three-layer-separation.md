# 多凭据模型路由要拆开秘密、引用与计费

关联 history：`docs/histories/2026-07/20260727-2321-duckcoding-multi-key-model-catalog.md`

## 是什么

同一个模型服务商拥有多把 API Key 时，不要把“Key 明文”“模型选哪把 Key”和“这把 Key 的价格策略”塞进同一个模型配置。更稳妥的结构是三层：安全存储保存秘密，模型只保存稳定凭据引用，运行时解析引用后生成本次调用的密钥与有效价格快照。

## 为什么需要

这三类数据的生命周期不同：

- Key 明文需要加密、不可回显，并可能单独失效。
- 模型绑定需要可序列化、可检查引用，但不应复制秘密。
- 倍率会调整，而历史 Usage 成本不能随最新倍率重新计算。

如果模型直接保存 Key，renderer、settings 和导出数据都容易泄密；如果模型复制倍率，修改 Key 分组价格时会产生大量漂移；如果缺失绑定自动回退默认 Key，又可能把请求送到错误账户并产生意外费用。

## 怎么做

1. provider 默认 Key 保持原有兼容路径；额外 Key 由 main 生成不含秘密的 `credentialId`。
2. 普通 settings 只保存 `credentialId / label / pricingMultiplier / status`，密文单独保存。
3. 模型只保存可选 `credentialId`；缺省表示默认 Key。
4. runtime 同时校验 provider 与 credential，解析目标密钥和倍率；缺失、解密失败或明确不可用时直接失败。
5. 把模型基础价乘倍率，生成仅属于本次调用的 pricing snapshot，并在写 Usage 时计算成本。
6. 删除 credential 前反查模型引用；仍被使用时阻止删除，而不是制造悬空引用。

模型基础价本身也应有单一事实来源。对版本化的内置模型目录，可以在生成模型读取快照时按稳定的精确模型名补齐目录价格，而不把价格复制进每个用户持久化模型。这样目录更新后旧安装模型能立即获得新元数据，同时用户覆盖的上下文、显示名和凭据绑定不会被迁移代码改写。

## 常见陷阱

- 把 provider 的 `hasApiKey` 当成“整个 provider 是否可用”。默认 Key 缺失时，健康的额外 Key 仍可能让绑定模型可用。
- 绑定额外 Key 前先检查默认 Key，导致多 Key 路径被默认账户状态错误阻塞。
- 找不到绑定时静默使用默认 Key。技术上请求可能成功，业务上却跨了账户、额度和价格边界。
- 查询历史 Usage 时再乘当前倍率。这样修改倍率会篡改历史账目。
- 供应商卡片只按默认 Key 决定是否显示，默认 Key 移除后会让额外 Key 失去管理入口。
- 为补齐价格直接重写旧的持久化模型。价格属于可更新的目录元数据，回写会把“用户配置”和“当前派生视图”混在一起，也容易覆盖用户自定义字段。
- 把上游公共目录价格显示成转发供应商的官方结算价。公共价格适合做估算基线，最终仍要以目标供应商实际账单为准。

## 核心要点

- 秘密用安全存储，业务对象只持有稳定引用。
- 倍率属于凭据，不属于模型；有效价格属于单次调用。
- 多凭据路由必须 fail closed，不能用“看起来能工作”的默认回退掩盖错误。
- UI 的“已配置”与“默认 Key 存在”也是两个不同状态。
- 版本化目录负责基础价，凭据负责倍率，读取快照负责组合；持久化层只保存真正属于用户的配置。
