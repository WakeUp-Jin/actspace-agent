# 搬家式重构：先用变异测试看看测试到底守住了什么

> 来自 Desktop 前端重构 09（输入框优化）的 P6：把 1810 行的 `Composer.tsx` 拆到 496 行。history：`docs/histories/2026-10/20261006-1930-desktop-fe-09-composer.md`。

## 问题：「全量测试通过」说明不了搬对了

拆大组件时，一般的做法是：把一段逻辑剪到新文件，跑一遍测试，全绿就提交。

这里有个默认的前提：**被搬的逻辑原本就有测试覆盖**。搬错了，测试会红。

可这个前提通常不成立。`Composer.tsx` 有上千条相关用例，看起来很安全。但 P6 每一步都做了同一件事：故意把刚搬过去的关键判断改坏，再跑全量。结果是：

| 步骤 | 变异数 | 改坏后用例仍然全过 |
| --- | --- | --- |
| T27 附件 | 3 | 3（去重、运行中不收拖放、远端选文件带 `remote: true`） |
| T28 斜杠菜单 | 11 | 9（锁定时也开菜单、Esc、悬停高亮、Skills 缓存 / 过滤 / 失败重拉……） |
| T29 工具栏 | 7 | 3 |
| T30 根组件收尾 | 27 | 9 |

也就是说，这些分支在搬之前就没被任何用例守着。搬的时候写错一个字符，测试照样全绿，问题要等到有人在真实界面里碰巧点到才会暴露。

## 做法

每次搬一块逻辑：

1. **搬之前列变异清单**。每个 `if`、每个提前 `return`、每个阈值、每个「只在 X 时才 Y」都是一条。重点是那些「去掉也不会崩、只是行为悄悄变了」的判断。
2. **每次只改一处，跑全量，再恢复**。用脚本做，别手改：

   ```python
   for name, file, before, after in MUTATIONS:
       orig = read(file)
       assert orig.count(before) == 1      # 模式必须唯一，否则改错地方
       write(file, orig.replace(before, after))
       try:
           run("vitest run")               # 只记失败数
       finally:
           write(file, orig)               # 无论如何都要恢复
   ```

   跑完再对一遍源文件和备份，确认确实恢复了。
3. **有变异活下来，就补用例，再跑一次这个变异**，确认它现在会被抓到。新用例尽量测抽出来的纯函数或 hook（`renderHook`），比通过整个组件去测快得多，也更准。
4. **把「改坏后 0 条失败」写进执行记录**。这是对既有测试质量的真实评价，比「全量通过」有用得多。

## 为什么搬家式重构特别需要这样做

- **搬家看起来无风险，于是没人细看。** 改功能时，大家会盯着改动的地方测；搬代码时，大家默认「逻辑没变」，复核也只看 diff 是不是对得上。可一旦搬错一个变量名，或者闭包取到了另一个作用域的同名变量，diff 上很难看出来。
- **拆分会改变执行顺序。** 例如 T30 把三个 `useEffect` 移进了 `use-composer-draft`，它们相对其他 effect 的执行时机就变了。这种差别只有用例能抓到。
- **抽出来的东西往往更好测。** 原来深埋在 1800 行组件里的判断，拆出来后变成 `composerSendOptions`、`contextUsageDisplay` 这样的纯函数。顺手补测试的成本是最低的。

## 常见陷阱

- **变异写成了等价代码。** 比如去掉的那个判断其实在上游已经保证过了，改了也不会有差别。这时不要硬补用例，应该说明它是等价的，或者干脆把多余的判断删掉（P3 T14 就删过一处）。
- **替换的模式不唯一。** `replace` 会把同一个文件里的多处一起改掉，脚本必须先断言只出现一次。
- **忘了恢复。** 一定要用 `try/finally`，结束后再和备份 diff 一次。脚本中途被打断时，这一步能救命。
- **只看「有没有失败」，不看是哪条失败。** 有时失败的是一条碰巧相关的用例，换个写法的变异就又活下来了。补用例时要让断言直接描述那条行为。

## 自检问题

1. 一次纯搬迁的 PR，全量测试通过、diff 也逐行对得上，还可能有什么问题没被发现？
2. 为什么「改坏后 0 条失败」的变异，往往集中在「锁定时不做 X」「超过阈值才做 Y」这类判断上？
3. 把三个 `useEffect` 从组件移进一个自定义 hook，可能带来什么可观察的差别？什么情况下没有差别？
