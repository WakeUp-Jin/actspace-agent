# 工具 Schema 合法，不代表供应商会接受

JSON Schema 的语法能力大于某个模型 API 支持的子集。一个在本地校验器里合法的 `allOf`，放到工具定义顶层后，仍可能在上游请求验证阶段被拒绝。此时模型尚未生成内容，修改用户问题或盲目重试不会解决结构不兼容。

## 两层校验各自负责什么

工具 schema 告诉模型如何填写参数，也参与供应商请求验证；工具执行器负责实际执行前的约束检查。两者不能互相替代。

例如一个 `web` 工具支持 `search` 和 `open`：

- 使用普通 object、action 枚举和参数描述表达输入，避免已确认不兼容的顶层组合关键字。
- 描述明确说明 search 需要 query、open 需要 url。
- 执行器仍然拒绝缺失 query/url 的调用，且必须在发送网络请求之前拒绝。模型没有遵守文字说明时，也不能突破这一层约束。

不要在通用适配器中无差别删除所有组合关键字；其他工具可能依赖这些约束。先确定哪份工具定义导致拒绝，再决定简化结构还是做有明确语义的供应商转换。

## 如何证明是这一处问题

保持模型、消息、推理设置和网络路径不变，只改变可疑 schema 条件。原请求返回 400、修改后的请求成功，才构成有力的因果证据。直接用另一个模型测试成功，并不能证明原模型兼容。

聚合供应商可能将具体拒绝原因包装在 metadata 内，顶层只剩通用错误。诊断时应提取允许公开的 message/code，脱敏后保留，而不是把整个响应存入会话；无法解析的原始内容应当安全降级。

测试应覆盖三件事：供应商能接受工具定义、无效工具参数仍被执行器拒绝、上游错误经过 SDK 和适配器后仍可诊断。一次真实请求验证与本地回归测试各有作用，不能互相冒充。

自检：去掉 schema 中的条件约束后，真正的参数校验还在哪里？如果供应商只返回通用错误，排障证据是否会在适配器里丢失？
