# 有思考用量，为什么没有思考文字？

LLM 响应中的思考正文、签名和用量有不同职责，不能用其中一个替代另外两个。

| 事实 | 用途 | 能否作为正文展示 |
| --- | --- | --- |
| thinking / reasoning text | 返回给调用方的可读思考或摘要 | 只有非空白正文才能展示 |
| signature / replay envelope | 后续请求的协议回传状态 | 不能把不透明签名当正文 |
| reasoning / thinking tokens | 供应商报告的用量 | 非零只说明有用量，不证明有可读正文 |

供应商可以返回非零思考 token、非空签名，同时让 thinking text 为空。仅看到 UI 空行时，先检查原始响应，再检查解析、Journal、投影和组件，才能区分供应商没有返回正文与客户端漏读。查看原始响应时使用最小测试输入，避免复制用户完整上下文；凭据不放入日志或命令行参数。

## 流式与历史为什么会表现不同？

历史投影通常把完整正文拼接后判断 `text.trim()`。流式路径却可能在第一个 delta 到达时就创建段：即使 delta 为 `""`，也出现标题、箭头和空的展开区域。两条路径必须遵守相同的可见性规则。

安全的处理方式是：

1. 空字符串没有内容变化，不创建新段。
2. 纯空白可以累积在状态中，渲染前用 `trim()` 判断是否含可见内容。
3. 后续非空白正文到达后，展示原始字符串，保留缩进和换行。
4. 隐藏正文为空的 UI 时，保留供应商签名与用量。

不要对每个 delta 直接 `trim()` 再拼接：`"hello"`、`" "`、`"world"` 会变成 `"helloworld"`。判断可见性与修改原始内容是两件不同的操作。

## 回归测试应包含正向案例

只断言“没有 Thinking”会允许把所有思考一律隐藏的错误实现通过。应先输入空内容，确认没有行且等待状态正常；再输入非空内容，确认行出现、原始文字保留；最后在正文或工具之后输入空片段，确认没有额外行或错误的运行状态。

这组案例同时覆盖了空内容准入、流式累积与已有消息之间的边界。
