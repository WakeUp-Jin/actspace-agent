# 增量计算首先要说清楚依赖

假设会话新增一条工具结果：对话需要改变，规则文本通常没变；如果这个工具读了文件，路径导航也可能改变。把事件强行分给一个模块会漏更新，重算全部模块又会浪费工作。判断依据应该是每个模块依赖的输入有没有变。

## 用依赖键换取可复用的输出

来源声明一个键：`key = f(当前依赖)`。当来源身份和键都与上次一致，就复用输出；否则重新计算。键里要包含真正影响结果的内容，例如模型、模式、技能选择；不要只用“最后一条事件编号”代替所有配置变化。没有明确依赖契约的扩展，应先继续重算，不能默认永久缓存。

这个约定的代价是：遗漏依赖会返回旧内容；包含过多依赖会多算一些。因此先保证完整，再收窄粒度。例如规则文件沿用按 Turn 重载时，Turn 就是依赖；这并不意味着可以把文件热更新承诺到每个 Step。

## 复用贡献，仍按顺序组装

缓存整个 Context 会把其他模块的旧内容带回来。更稳妥的做法是只缓存该来源拥有的贡献，复用时继续校验来源身份、可写字段和合并次序。一个变化可以让多个来源失效，不需要规定一个事件只能更新一个模块。

复用对象还要求输出不可变。`Object.freeze(parent)` 只冻结外层，子对象仍可能被改。第一次接收时应校验并复制整个新切片，再递归冻结；之后只信任自己产生的快照，不能仅凭调用者说“已经 frozen”就跳过检查。

## 缓存不等于零成本

如果每次为了比较键都序列化整段对话，仍然存在扫描。即使来源回调少了，Token 估算、最终快照或版本摘要也可能继续占用时间。正确的性能结论需要分别测量这些阶段，不能把“缓存命中”直接换算成整体加速倍数。

最后，缓存应有容量和身份边界：不同会话、逻辑 Agent 和插件代际不能误用彼此的输出；注销来源要失效，失败不能发布半成品。缓存丢失只应增加计算，不应改变业务含义。

自检：新增依赖时，哪里让旧值失效？若一个工具同时改变对话和导航，两者能否独立刷新？把缓存全部清掉，得到的业务结果是否相同？
