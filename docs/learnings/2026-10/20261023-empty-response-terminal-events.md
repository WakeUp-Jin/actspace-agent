# 空结果也需要完成事件

事件驱动系统中，结果载荷和操作是否完成是两个维度。模型成功返回空字符串，仍然完成了一次请求；如果只在结果非空时记录消息，就可能留下永远没有终态的请求。

例如，请求按下面的关系推进：

```text
request/header → assistant/message → step/end → turn/end
```

这里的 `assistant/message` 同时承载内容和请求终态。即使 `content=[]`，它仍须保留 request 身份、真实结束原因和用量。否则下一步结束时，校验器看到的仍是 open request。

错误的判断是把“有内容”当成“需要结束请求”的条件：

```ts
if (output.content.length > 0) {
  await appendAssistantMessage(output);
}
await endStep();
```

正确做法是让生命周期由请求完成决定，让内容照实为空。不要补造一段文字，也不要关闭关系校验来掩盖缺失的终态。

## 怎么验证

回归应同时检查空值和关系：正常完成、终态恰好一次、结束原因及用量准确、终态先于 Step 结束，以及下一轮仍能写入。再从持久事件冷重放，确认关系闭合，而不是只看调用返回成功。

父任务退出成功也不足以证明子任务成功：父任务可能接到失败工具结果后继续完成。需要分别检查子任务终态、父工具状态和最终父任务结果。

另一个容易误判的地方是消费制品。领域包测试及构建通过后，生产入口可能仍加载 Runtime 中预先打包的旧实现。真实复验前必须确认实际加载路径及消费构建；测试绿、源码新和运行中的实现新是三份不同证据。

本例来自 [BUG-049 修复记录](../../histories/2026-10/20261022-0746-acceptance-small-fixes.md)。这一原则同样适用于空查询、零行导出、无改动操作等有明确生命周期的任务。
