# 重试不是让失败的请求继续运行

一次任务可以包含多次模型请求尝试。第一次请求失败后重试成功，任务最终成功，但第一次请求已经结束。若事件日志只记“准备重试”，恢复器却仍认为原请求在运行，就会在重启时补写一个多余的终态，或者拒绝之后的 Task 结算。

可以把身份分成三层：Task 表示用户的工作，Run 表示固定执行组合下的一次运行，requestId 表示一次实际模型调用。重试保留 Task/Run，但下一次尝试使用新的 requestId。

```text
Task A / Run B
  request 1: start -> retry（本次失败，已结束）
  request 2: start -> finish（成功，已结束）
  Run B: finish
  Task A: settled
```

关键不是事件名字，而是事件对状态机的含义。如果 `retry` 已声明本次尝试失败，在线校验与冷启动恢复必须一致地把它视为该 request 的终态。不能一处关闭、另一处保留 pending，也不能为了接受后续事件而放松重复终态检查。

验证时同时检查三条路径：重试后成功、重试耗尽、等待重试时取消。每条路径都应重新打开持久会话，确认旧请求不被再次结算、旧任务不自动重跑、writer 能重新取得。只断言“HTTP 被调用两次”会漏掉这些恢复问题。

这也解释了为什么确定性 HTTP fixture 有价值：它保留真实 Loop、错误分类、事件写入和进程退出，只控制外部响应。相比替换整个执行器，更容易暴露在线执行与持久恢复之间的语义漂移。

自检：一个事件同时表示“这一层失败”和“上一层还会继续”时，你的在线状态机、投影和恢复扫描是否给出了相同解释？
