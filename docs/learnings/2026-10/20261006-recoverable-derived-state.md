# 为什么摘要成功后，不该因为索引失败再压缩一次

压缩会改变模型能直接看到的历史；睡眠索引只是这些历史的导航。两者一起运行，却没有共同的磁盘事务：Journal 可以已写完，artifact 仍可能失败。

若遇错就从头重试，会生成第二份摘要，甚至把读取计数清零两次。更稳妥的方式是把“决定”和“派生结果”分开记录：

```text
保存候选引用并 flush
  → 保存摘要与 Surface 替换并 flush
  → 生成索引，保存已应用标记并 flush
```

三步使用同一个 compactionId。恢复时，只有候选而没有有效压缩完成记录，就不调整状态；压缩已经完成而没有已应用标记，就补索引和状态；标记已存在，就跳过。这不需要改造原有 Session 事务。

这里的 flush 是必要边界：内存接纳事件，不等于文件已经持久化。测试应分别在每个边界截断日志，验证恢复后的状态；不能只让整个函数抛一次异常，就声称覆盖所有崩溃点。

另一个陷阱是把索引路径当成普通资料。它会让导航再次引用导航，持续膨胀。应保留索引的类型化 artifact 身份，识别新旧索引并排除热度计数；路径只在展示时解析。

这种做法也适用于“订单已提交但搜索索引未更新”“任务结果已保存但报告未生成”。核心是让重试补齐缺失步骤，而不重做已经成功的业务操作。

自检：如果进程在索引文件生成后、引用保存前退出，应重做哪一步？如果摘要事务只写了前三条事件，能清零读取计数吗？
