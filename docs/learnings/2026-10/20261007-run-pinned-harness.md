# 为什么插件更新应当切换版本引用

热更新时最容易混淆两个对象：系统为未来任务选择的版本，以及当前任务已经取得的版本。把它们合成一个可变全局指针，会让一次任务先看到旧工具 schema，调用时却执行新实现。

解决方法是让每个 Run 在开始时取得一个版本租约。模型的多轮请求、工具调用和子任务都沿用该租约。用户修改工具时，先产生独立固定产物和候选实例，提交只改变后续 Run 的选择。旧实例等最后一个租约结束再释放。这个模式同样适用于配置切换、规则引擎和服务部署。

还有一个容易遗漏的边界：子任务即使在更新后启动，也应继承父任务的版本，否则父任务根据旧能力安排的工作会突然执行新语义。只传会话 ID 不够，必须沿父 Scope 或明确 generation 取得仍有效的租约。

选择与会话绑定如果分开持久化，会出现“选择已提交、绑定尚未写入”的中间状态。先写提交意图，再提交选择，最后补齐绑定；新任务的准入与这条提交链共用闸门。恢复看到已提交选择就完成绑定，看到未提交意图就保留旧绑定。停止操作不能抹掉已经发生的提交事实。

三个自检问题：

- 能否说清本次 Run 在每次模型请求和工具调用中使用哪个确定版本？
- 更新时，父任务尚未结束，它新建的子任务会拿到哪个版本？
- 如果磁盘写入在选择与绑定之间中断，新任务能否读到半完成状态？
