# 运行结束不等于提示结束

流式状态通常随一次请求创建和销毁，但错误提示需要持续到用户理解或处理错误。把两者放进同一个容器，会导致“执行已正常结束，失败信息也消失了”。这在后台任务、上传、自动保存中同样常见。

## 按消费者决定生命周期

正在生成的文本和进度属于 Run；需要用户重试的失败提示属于会话展示状态。Run 存活时展示 live block，Run 结束后展示会话保留块，可以避免同时显示两份错误。

同步时应复用已经归并的错误块，而不是再写一套事件解释规则。成功、跳过、再次开始或新用户输入都可能让旧提示失效，需要明确清理时机。切换会话只切换读取对象，不应清除另一个会话的错误。

## 两个容易漏掉的边界

- 延迟事件必须检查 Run 身份和终态，避免旧失败覆盖新运行的结果。
- 会话本地状态仍不等于持久化事实。需要跨重启保留时，必须另行设计事实记录和恢复规则，不能因为运行结束后仍显示就宣称可重启恢复。

回归测试应先看到运行中的真实失败，再结束 Run，确认错误和重试按钮仍存在，最后重试并确认旧提示清除。只断言“结束后没有错误”可能永远通过，因为测试根本没产生错误。
