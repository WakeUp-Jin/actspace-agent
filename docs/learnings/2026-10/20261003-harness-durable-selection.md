# 为什么“写入成功”和“切换成功”必须共用一道门

想象旧 Agent 正在执行工具，此时准备好了一个新 Loop。最容易写出的代码是：先把 current 指向新 Loop，再保存配置。但如果保存失败，当前进程会运行新版，重启却恢复旧版；用户收到的“启用成功”也不可信。

反过来先保存再切换同样需要小心：保存过程中一个新任务取得旧 Loop，保存后立刻退出，重启又选择新 Loop。要让执行身份和选择顺序可解释，需要明确：哪一刻算启用完成，哪一批任务受这次启用影响。

## 一条可复用的提交规则

准备和授权可以很慢，所以它们放在门外。最终提交时短暂关门，只让以下动作按顺序完成：检查基线及授权 → 写完整选择记录并 fsync → 同步更新内存 current → 开门。

获取新租约也经过这道门。已有租约不经过，因此旧任务继续执行；新任务只会获得完整的旧组合或新组合。取消等待只退出等待者，不撤销其他人的提交，也不泄漏稍后才获取到的引用。

## 崩溃后以什么为准

持久选择日志是事实源。落盘前退出，恢复旧记录；落盘后即使没有发出成功回执，也恢复新记录。调用方用稳定 activationId 查询或重试，不能用“没收到回复”推断“没执行”。这与支付、发布配置和任务接纳的幂等问题相同。

如果写入报错，不能立即宣布旧选择安全：磁盘上可能留下部分新记录。此时阻断新的执行，让恢复流程判断。末尾半行可以保留证据后截断；完整记录校验失败应停止，不能猜测并跳过。

## 两个容易混淆的生命周期

选择已经成功，不代表旧实例已清理完。旧实例要等最后一个租约释放；清理失败属于资源诊断，不应撤销成功选择。否则一次清理异常会把用户已经使用的新组合又偷偷换回去。

实例释放也不等于代码文件可以删除。重启恢复和显式回退仍需要旧产物，Node 的 ESM 缓存也不保证随实例释放卸载。引用计数管理活对象，保留策略管理历史文件，不能合并成一个计数器。

自检：在 fsync 后、current 更新前强制退出会恢复什么？批准等待时是否应阻塞普通任务？旧插件 dispose 抛错能否推翻成功回执？如果答案分别是“新记录”“不应该”“不能”，就抓住了这次设计的三个边界。
