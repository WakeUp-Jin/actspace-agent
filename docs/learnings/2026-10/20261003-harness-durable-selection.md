# 插件/Harness 热更新：版本租约、选择与清理三件事分开

合并自四篇：写入成功和切换成功必须共用一道门、切换成功和旧实例清理成功要分开、插件更新应当切换版本引用（Run 固定版本）、原地更新不等于保留旧版本（Cordis）。

对应实践：[V1 实现说明](../../design-docs/自进化的方案设计/10-V1实现与使用说明.md)、[Cordis 可行性报告](../../exec-runs/20261003-agent-harness-host-refactor/phase-5-cordis-feasibility.md)。这里的并存与恢复不构成代码隔离沙箱：同一 ESM 文件的模块全局变量仍共享，实例状态要放进实例生命周期。

热更新要同时分清三件事：**未来任务选哪个版本（选择）、当前任务已拿到哪个版本（租约）、旧实例何时清理（回收）**。把它们合成一个可变全局指针，会让一次任务先看到旧工具 schema、调用时却执行新实现。

## 1. Run 开始时取得版本租约

每个 Run 开始时取得一个版本租约，模型多轮请求、工具调用、子任务都沿用它。用户修改工具时先产生独立固定产物和候选实例，提交只改变后续 Run 的选择；旧实例等最后一个租约结束再释放。子任务即使在更新后启动，也要继承父任务的版本（父任务按旧能力安排的工作不能突然执行新语义），只传会话 ID 不够，要沿父 Scope 或明确 generation 取得仍有效的租约。配置切换、规则引擎、服务部署同理。

原地更新不等于保留旧版本：Run A 持有工具实例 X，Loader 把 X 替换成 Y 时先释放 X 再让依赖者连接 Y，A 的变量仍指向 X，但 X 内部连接可能已关闭——保留对象引用不等于保留资源可用性。Y 启动失败时 Loader 重建的 X′ 只是恢复旧实现，不是原来的 X，也没有恢复运行状态；“配置回滚成功”和“旧任务未受影响”要分别验证。要让新旧并存，X 与 Y 需暂时同时存在，由明确使用者决定何时释放 X：Cordis 管实例资源，应用管任务持有关系；服务命名域解决“找哪个实例”，不替应用计算任务是否结束。复用未变化的实例也有同样陷阱：工具注册表代码没变，但新插件会向它注册内容，共享会让旧任务看到新工具——判断可复用要问“谁会写入这个实例”。

## 2. 选择：写入成功和切换成功共用一道门

先把 current 指向新 Loop 再存配置，保存失败时进程运行新版、重启恢复旧版，“启用成功”不可信；先保存再切换，保存期间新任务取得旧 Loop、保存后立刻退出，重启又选新 Loop。要明确哪一刻算启用完成、哪一批任务受影响。

准备与授权可以很慢，放在门外；最终提交短暂关门，按顺序：检查基线与授权 → 写完整选择记录并 fsync → 同步更新内存 current → 开门。获取新租约也过这道门；已有租约不过，旧任务继续；新任务只会获得完整的旧组合或新组合；取消等待只退出等待者，不撤销他人提交，也不泄漏稍后才获取到的引用。选择与会话绑定若分开持久化，会出现“选择已提交、绑定未写入”的中间状态：先写提交意图 → 提交选择 → 补齐绑定，新任务准入与这条链共用闸门；恢复看到已提交选择就完成绑定，看到未提交意图就保留旧绑定；停止操作不能抹掉已发生的提交事实。

**三种身份**：内容摘要（是什么代码）、实例 ID（哪次装配）、选择 revision（当前选择变了几次）。A→B→A 内容相同，revision 仍须增加，否则基于第一次 A 准备的过期候选会误以为基线没变。提交与获取引用都不跨 await，每个持有者拿到完整的 A 或 B。

**崩溃后以持久选择日志为准**：落盘前退出恢复旧记录；落盘后即使没发出成功回执也恢复新记录；调用方用稳定 activationId 查询/重试，不能用“没收到回复”推断“没执行”（支付、发布配置、任务接纳同理）。写入报错不能立即宣布旧选择安全（磁盘可能留部分新记录），要阻断新执行交给恢复流程；末尾半行保留证据后截断，完整记录校验失败应停止，不猜测跳过。

## 3. 回收：切换成功与旧实例清理成功要分开

旧组合 A 还有两个任务，新组合 B 已准备好：启用 B 只改变下一次任务的选择，A 继续服务旧任务；“销毁 A 再创建 B”会中断旧任务，B 创建失败时还丢失可用实现。拆成三个动作：准备完整候选、同步提交当前选择、最后一个持有者释放后回收旧实例。

清理失败不能撤销成功的选择：B 已对新任务可见，销毁 A 失败时报告“B 已启用，A 清理失败”，保留诊断、等待显式处理；不自动重试 disposer（可能已完成部分不可逆副作用）。实例释放也不等于代码文件可删：重启恢复和显式回退仍需旧产物，Node ESM 缓存不保证随实例释放卸载；引用计数管活对象，保留策略管历史文件，不要合并成一个计数器。当前组合没有任务时通常保留以便复用；管理器关闭不能强制减少引用，应让实际持有者结束工作后归还。

## 自检

1. 本次 Run 在每次模型请求和工具调用中使用哪个确定版本？更新时父任务未结束，新建的子任务拿哪个版本？
2. fsync 后、current 更新前强制退出会恢复什么（新记录）？批准等待时是否阻塞普通任务（不应）？旧插件 dispose 抛错能否推翻成功回执（不能）？
3. 磁盘写入在选择与绑定之间中断，新任务会读到半完成状态吗？
4. 新实现失败后，旧任务持有的对象仍可用，还是只重建了同名对象？两个组合共用实例时谁最终释放？
