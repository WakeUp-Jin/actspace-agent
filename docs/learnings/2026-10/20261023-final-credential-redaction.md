# 错误脱敏为什么要靠近实际出站请求

一个请求经过 resolver、模型路由、适配器和 SDK 后才发出去。resolver 返回的凭据不一定就是最终凭据：Host 可能在选择 Provider 后才绑定 Key。如果早期凭据为空，即使脱敏函数本身正确，也只能依赖格式猜测，漏掉自定义格式的 Key。

## 从绑定时间判断边界

沿请求链标出两件事：凭据在哪一步成为最终值，错误在哪一步可能进入业务事件或持久化。脱敏器应位于这两个位置之间。它需要同时接住创建流时的异常、迭代时的异常和流中的 error/aborted 终止事件；只在 `await dispatch()` 外写一个 catch，接不到稍后迭代发生的错误。

在当前实现中，PreparedLlmCall 保留早期防护，共用 PiAiAdapter 再用实际出站 credential 包裹直接 SDK 与 legacy 引擎。两层职责取决于各自掌握的事实，不能用“已经脱敏过”代替检查凭据是否完整。

## 请求作用域比全局密钥表更合适

让脱敏器只持有一次请求的凭据，能避免长期保留已轮换密钥，也不会让请求 A 意外改写请求 B 的诊断。错误采用白名单复制字段；把 message 替换后仍挂着原始 cause、stack 或 headers，会留下旁路泄露。正常回复则保持原样，避免把用户内容误当成错误诊断处理。

## 怎样证明边界生效

使用随机无效凭据，让回环服务先确认实际鉴权，再故意在错误中回显原值和 URL 编码值。测试应同时证明：诊断和 HTTP 状态保留、两种值消失、正常回复不变。最后检查真实进程的实时事件、读取投影、Journal 与输出文件。一个单元测试无法证明 Host 的后续绑定路径也经过了同一防护。

这次 CLI 全部通过而 Host 仍泄露，正说明不同入口可能有不同的绑定时间。验收矩阵应按真实入口划分，再复用公共组件测试。

自检：凭据是否还会在下游被替换？流迭代异常是否被捕获？错误对象是否仍保留原始 Provider 属性？
