# 断线后重试，为什么要保留同一个提交标识？

客户端没有收到回复，并不等于服务器没有执行。这是远端任务最容易误判的一种状态。

例如，Desktop 发送消息，Host 把任务写进日志，随后连接断开。任务已经被接纳，但成功回执没有到达 Desktop。此时如果 Desktop 用新的标识重发，Host 看见的是第二个合法任务，两次执行都会发生。

## 两个标识，各自解决一个问题

- RPC request id：关联这次网络请求与应答。重连后的请求可以有新的 request id。
- submissionId：标识用户这一次发送意图。同一次发送在查询和重试时必须保持不变，并绑定相同内容。

服务端在持久任务日志中按会话和 submissionId 去重：相同内容返回原任务，不同内容拒绝冲突。客户端则保存已经尝试发送的标识与正文，在恢复连接后先查证，再决定是否重试。

这也解释了为什么仅把标识放在组件状态或 sessionStorage 中不够：应用重启会丢掉查证入口。持久化正文却没有保存或恢复提交标识，同样无法正确重试。文件上传还需要保存 uploadId 和服务端确认的偏移，否则每次重试都可能产生另一套附件引用。

## 接纳、执行和显示是三个不同的时刻

任务落盘决定是否接纳；Run 决定什么时候执行；客户端快照和事件决定用户看到了什么。一次网络连接只拥有自己的订阅，不拥有 Run 的生命周期。关闭窗口可以释放连接，却不能顺便取消已接纳的远端任务。

有三种状态需要明确区分：

| 客户端知道什么 | 正确处理 |
| --- | --- |
| 服务器明确拒绝接纳 | 显示错误，保留可编辑草稿 |
| 服务器明确返回原任务 | 使用原任务继续显示，不能再创建一个 |
| 回执丢失，是否接纳未知 | 保留原标识查证，不能当成普通失败重新发送 |

“保留待确认提交”并不代表“允许离线发送队列”。前者是在恢复一次已尝试的操作；后者是离线时接纳新的发送意图，需要另外设计产品行为。

## 自检

1. 服务端落盘之后、返回回执之前崩溃，重启后能否查到同一任务？
2. Desktop 重启以后，是否仍知道该用哪个 submissionId 查询？
3. 重试时正文或附件变了，是否会明确冲突，而不是悄悄替换已接纳内容？
