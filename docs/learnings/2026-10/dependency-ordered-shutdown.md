# 释放资源也需要依赖顺序

插件框架能够回收监听器和服务，但“全部 dispose 了”不代表关闭过程正确。若 Session 关闭时还要写入最后一条事件，而 storage 已经被另一个清理回调关闭，正常退出也会丢失最后的状态。

## 如何判断顺序

不要仅根据插件注册顺序猜测释放顺序。先问：**谁在关闭期间仍会调用谁？** 如果 A 关闭时仍需调用 B，就必须先完成 A 的关闭，再释放 B。

以 Agent 为例，正常关闭顺序是：停止接纳和排空执行 → Session 最后写入与 flush → 释放存储与插件树。Cordis 的作用域回收继续负责局部副作用，但跨服务的先后关系由拥有这些服务的 Host 明确编排。

## 失败时仍要向前释放

一个 Session flush 失败，不能阻止其他 Session 释放写锁。把错误收集起来，逐项尝试关闭，最后统一报告。关闭操作还应允许重复调用：并发调用共用进行中的 Promise；实际失败后可重试，而不是永久缓存一个 rejected Promise。

## 怎样测试

只断言每个 dispose 被调用，发现不了先后问题。让底层资源在 close 后拒绝读写，检查上层最后一次持久化确实发生在底层关闭前；再在其中一步制造失败，确认后面的释放仍发生。补充一个真实进程退出、重新启动读取末尾状态的用例，可以验证实际装配没有绕过这条顺序。
