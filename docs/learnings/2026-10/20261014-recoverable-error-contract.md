# 错误码也是调度协议

异步任务系统中的异常不只给人看，也会决定调度器下一步做什么。恢复阻塞意味着「保留任务，暂停执行，修复环境后允许继续」；未知异常通常意味着执行器内部失败。两者都没有创建 Run，但恢复策略不同。

本次队列卡住的链路是：持久化的 Harness 与当前 Host 契约不兼容 → 控制层拒绝获取租约 → HMR 包装为普通 Error → 调度器识别不到可恢复错误码 → 任务仍 pending，队列却没有进入暂停状态。界面只知道它尚未开始，无法从一句错误文本恢复调度语义。

跨层转换异常时，应先决定下一层该执行哪一种恢复动作，再选择稳定的错误类型或错误码。保留 `RECOVERY_BLOCKED` 能复用已有的暂停/恢复协议；给异常换一句更清楚的文字不能替代这个契约。

验证时至少覆盖两个边界：上游确实输出带码异常；下游确实把它转换成可恢复状态。另用一条真实的跨层运行检查，确认没有中间适配器再次丢掉信息。不要只断言日志出现了某段文字，也不要把「没有 Run」直接归因为模型服务慢。

自检：若 UI 显示排队，任务账本是 pending，应该先检查是否拿到了执行租约、队列是否 paused，再检查网络请求。任务接纳成功只证明输入已持久化，不能证明执行已经开始。
