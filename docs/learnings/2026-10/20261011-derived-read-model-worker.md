# 事实源与派生读模型：性能边界、水位失效与降级口径

合并自：事实源与派生读模型的性能边界、修正过滤条件后为什么旧数据仍不回来。

来源：[使用统计 SQLite 读模型与 Worker history](../../histories/2026-10/20261011-usage-sqlite-read-model.md)、[使用统计历史恢复修复](../../histories/2026-10/20261019-2215-usage-history-recovery.md)

用户可读的事件日志适合做事实源，SQLite 适合做可删除、可重建的查询投影。不必每次 Agent 写入同步双写；查询开始时比较事实源 revision 与索引水位，落后才把变化送进单一 Worker。

## 1. 性能边界

- Worker 隔离 SQLite 与聚合计算，但不应绕过 Runtime/Provider 直接解析 Session 文件，否则存储格式与通用运行时边界重新耦合。
- 分页只限制返回量，不限制计算量；要控内存必须让 SQL 做过滤、计数、分组、排序，主线程和 Worker 都不能先把全库行 materialize 成数组。
- 冷重建与热查询是两个问题：Worker 保护 Main event loop，却不降低首次 FTS 导入的写放大；百万行场景需要后台可见进度、分批事务和 rollup。100k/1m 基准显示这一点。
- SQL 移进 Worker 不代表页面不卡：侧栏为任务徽标恢复所有历史 Session、启动校验重复重放全量日志，都可能绕开新入口。要在真实 Electron 里追踪所有触发链，给显示层轻量提示，同时保留执行与恢复的事实校验；不能为性能把派生索引升级成执行权限或恢复真源。
- 看 CPU 分类，区分 SQL 计算与临时文件开销：逐行触发器 1000 条写入的 CPU 大部分在 system，默认临时存储约 550–610ms，改用内存临时数据约 33–39ms（同样触发器、同样事务）；增大普通页缓存没有同样效果，两者控制对象不同。不能把整个连接永久设为 MEMORY（聚合与大排序可能需要庞大临时空间）：按操作切换——有界追加用内存临时表，查询与批量替换允许落盘；切换会销毁 TEMP 表，相应查询缓存必须失效，回归测试专门验证“没有任何行修改但 TEMP 表被切换删除”。见 [SQLite 临时文件说明](https://www.sqlite.org/tempfiles.html)。

## 2. 降级保持查询语义，预算覆盖派生数据

回退到文件读取不意味着换一套搜索规则：正常路径 FTS+游标、降级用字符串包含+数组分页，同条件结果就不同。小规模回退在请求级内存 SQLite 中复用查询逻辑，变的只是数据来源与库寿命；临时库不能依赖已损坏的磁盘索引，结束时释放。输入有上限还不够：关联投影可能把长身份字段复制进许多派生事件，内存预算要统计展开后的数据；超预算整笔事务回滚，活动、关联、水位一起退回旧状态，下次查询才能安全重试。

## 3. 修正过滤规则后，旧水位让旧数据回不来

索引已读到日志第 100 条，但写入时错误过滤了前 90 条；删掉过滤条件后再打开页面，索引仍只有后 10 条。增量系统依据“处理到哪里”决定是否继续读，水位 100 只证明旧规则处理过这段日志，不证明新规则处理过；日志没新增游标就不动，没有机会补回。

应同时修：计算规则（取消错误过滤）；派生状态（使旧索引及游标失效、从完整事实重建，只清结果表而留游标会得到永久空表）；兼容入口（降级查询与旧缓存遵守同一规则）。版本号不只表示表结构：SQL 列没变而“这张表应包含哪些事实”变了，也需要投影版本或派生库版本。

优先在查询时筛选时间：“最近一天/全部”只是展示范围，就保存完整可重建历史，写入时按首次访问时间删历史会把界面筛选变成永久数据缺口；价格未知只影响费用可信度，不应连带丢请求和 Token。整库版本升级实现简单但共享该库的目录、搜索和其他投影也会重建，规模大时评估成本；只失效某个投影更精细，但必须处理它的水位、暂存表和聚合表。

回归测试先构造“日志不变、游标已到末尾、结果被截断”的旧状态，验证升级补回数据；再重启服务确认恢复后的索引可复用、不每次全量重建。只在空目录里测试新规则证明不了旧用户会恢复。

## 自检

1. 查询的所有触发链（侧栏徽标、启动校验）都走新入口吗？
2. 降级路径与正常路径对同一条件返回相同结果吗？预算统计的是展开后的数据吗？
3. 投影规则变了，水位与派生库版本跟着失效了吗？旧用户的恢复测过吗？
