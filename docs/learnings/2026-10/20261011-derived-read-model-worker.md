# 事实源与派生读模型的性能边界

这次使用统计改造验证了一个可迁移的模式：用户可读的事件日志适合做事实源，SQLite 适合做可删除、可重建的查询投影。两者不需要在每次 Agent 写入时同步双写；查询开始时比较事实源 revision 和索引水位，只有落后时才把变化送进单一 Worker。

关键边界有两个。第一，Worker 可以隔离 SQLite 和聚合计算，却不应该绕过 Runtime/Provider 直接解析 Session 文件，否则会把存储格式和通用运行时边界重新耦合。第二，分页只限制返回量，不自动限制计算量；要真正控制内存，必须让 SQL 做过滤、计数、分组和排序，主线程和 Worker 都不能先把全库行 materialize 成数组。

本次 100k/1m 基准还暴露了冷重建和热查询是两个不同问题：Worker 能保护 Main event loop，但不能凭空降低首次 FTS 导入的写放大。百万行场景需要后台可见进度、分批事务和 rollup，才能同时满足可恢复性、内存峰值和交互等待时间。

真实应用还揭示了另一个陷阱：SQL 已经移入 Worker，不代表整个页面不会卡。侧栏为了任务徽标恢复所有历史 Session、启动校验重复重放全量日志，都可能绕开新查询入口。必须在实际 Electron 中追踪所有触发链，给显示层轻量提示，同时保留执行和恢复的 Session 事实校验；不能为了性能把派生索引升级成执行权限或恢复真源。

### 看CPU分类，区分SQL计算与临时文件开销

逐行触发器慢，不一定是表达式计算慢。本轮1000条写入的CPU大部分花在system，默认临时存储约550–610ms；在同样触发器、同样事务条件下改用内存临时数据约33–39ms。增大普通页缓存没有相同效果，因为两者控制的对象不同。

不能因此把整个查询连接永久设为MEMORY：任意标题聚合和大排序可能需要庞大临时空间。最终按操作切换：有界追加使用内存临时表，查询和批量替换允许落盘；切换会销毁TEMP表，相应查询缓存也必须失效。新增回归专门验证“没有任何行修改，但TEMP表被切换删除”的情况。参见[SQLite临时文件说明](https://www.sqlite.org/tempfiles.html)。

### 降级时保持查询语义，预算覆盖派生数据

回退到文件读取并不意味着可以换一套搜索规则。若正常路径使用 FTS 和游标、降级路径改用字符串包含和数组分页，同一条件会返回不同结果。本次让小规模回退在请求级内存 SQLite 中复用查询逻辑；改变的是数据来源与数据库寿命，搜索和聚合口径保持一致。临时库不能依赖已经损坏的磁盘索引，结束时也必须释放。

输入有上限还不够：关联投影可能把一个很长的身份字段复制到许多派生事件里。内存预算要统计展开后的数据，不能只统计原始 Journal。超预算时整笔事务回滚，活动、关联和水位一起退回旧状态，下一次查询才能安全重试。
