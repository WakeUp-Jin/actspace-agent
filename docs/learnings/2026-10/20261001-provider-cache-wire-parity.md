# SDK 支持缓存，为什么请求仍不命中？

缓存能力要沿实际发送路径追踪，不能只看安装了哪个 SDK。一个统一适配器可能为了代理、账单或特殊附件走另一套 backend；主 SDK 的能力不会自动出现在兼容 backend 上。

排查时分三层：

1. **策略**：业务决定缓存寿命，例如交互式 Chat 选择 1 小时，连续 Agent 工作选择 5 分钟；连接显式关闭优先。把结果绑定到单次请求，避免重试时读取变化后的设置。
2. **序列化**：检查发送给 SDK 的 body，还要用真实 SDK 配合本地假 fetch 检查最终 body。仅断言传入 `cacheRetention: long`，无法证明网络请求包含 `ttl: 1h`。
3. **服务商结果**：检查 cache write 与 cache read。没有写入就不能期待下一轮读取；有写入也可能因长度、前缀变化、过期或路由变化而不命中。

为每条 backend 路线准备同一组正反例：短缓存、长缓存、关闭、非目标模型。关闭测试必须与有标记的正例配对，否则一个永远不发送缓存参数的实现也会通过。

不要把两种比例混为一谈：Context 占用率是当前上下文除以容量，缓存命中率是复用输入占比。0.42% 的 Context 若要整数展示，应显示 `<1%`，而不是先 floor 成 0 再解释。
