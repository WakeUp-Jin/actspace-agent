# 长生命周期工具端口为什么会拿到过期配置

一次工具调用读取的是“现在的设置”，还是端口创建时留下的设置，取决于读取发生的位置。端口可以跨多轮对话复用；设置里的凭据则可能在同一会话中被断开、重连或更换。这两个生命周期不一致时，UI显示删除成功，并不能证明后续请求停止使用旧凭据。

## 从读取时间判断问题

下面的端口把凭据对象保留在闭包中。即使设置服务随后换成新的对象，闭包仍持有旧对象。

```ts
const credentials = settings.readCredentials();
const port = createSearchPort({ credentials });
```

如果底层端口每次搜索都会访问`options.credentials`，可以通过getter在调用时读取：

```ts
const port = createSearchPort({
  get credentials() { return settings.readCredentials(); },
});
```

另一种设计是显式传入`getCredentials()`回调。选哪一种取决于现有端口契约；关键不是语法，而是确认底层没有再次解构并缓存该值。缓存网页结果等可复用资源可以保留，凭据则应按请求读取。

## 回归应该观察什么

测试应复用同一端口，按“已连接→断开→重连并换Key→全部断开”连续调用，检查实际请求目的地和鉴权头。只断言设置对象或页面文字会漏掉闭包里的旧值。测试使用合成凭据；真实验证记录provider名称即可，不记录Key。

已经开始的请求通常仍持有开始时的凭据。按调用读取保证的是后续请求生效；若产品还要求中断在途请求，需要独立的取消语义，不能把它当成getter自动提供的能力。

## 自检

- 每个请求实际在哪一行读取凭据？该值是否又被另一个长期对象缓存？
- 重建整个Runtime是否只是掩盖了生命周期问题，并额外丢掉可复用状态？
- 测试是否检查了外发请求，而非仅检查配置变化？
