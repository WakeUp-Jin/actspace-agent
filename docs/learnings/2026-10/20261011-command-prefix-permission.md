# 命令前缀授权为什么不能用 startsWith

一次批准回答“这次能运行吗”；会话授权回答“未来哪些调用可以不再询问”。后者需要把用户意图变成可重复验证的边界。

`pnpm` 的字符串前缀会同时命中 `pnpmx`、`pnpm test && other`。即使用空格分割，引号、变量、重定向也会改变 shell 的解释。可靠做法是仅识别自己能完整理解的简单语法，得到 argv 和授权前缀；未知语法回到审批，不猜测它等价于什么。

分工也很关键：工具理解命令政策，Runtime 理解授权身份和生命周期。工具给出“这次调用可按 pnpm 授权”；Runtime 验证它属于同一会话、Agent、工作区和政策版本。这样既不用让通用 Runtime 内置 npm 特例，也不会只相信界面按钮。

授权命中仍不等于可以立刻执行。等待期间目录符号链接、权限模式或授权本身可能变化；执行前要重算资源并复验，持久化检查之后也不能忽略撤销。审计记录的是授权准入，实际执行是否成功要看工具结果。

最容易混淆的一点：限制 cwd 不是文件系统隔离，允许 pnpm 也不是允许只读操作。项目脚本可以做很多事情。前缀授权减少交互，沙箱限制进程能力；这是两种独立机制。

自检：允许 `git status` 是否也允许 `git show`？不允许，它们是不同的两 token 前缀。相同 pnpm 授权能否给另一个 Agent 用？不能，因为身份也是授权边界。
