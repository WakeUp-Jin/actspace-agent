# 只能“授权”的沙箱，为什么挖不出只读子目录

工具沙箱的要求看起来很普通：工作区可写，但 `.git/hooks` 和 `.git/config` 不能写，否则沙箱里的命令可以植入一个 hook，等你下次在沙箱外执行 `git commit` 时运行。macOS 的 Seatbelt 一行就能表达；换到 Linux 的 Landlock，却怎么也写不出来。原因不在 nono，而在两种机制的模型不同。

## 两种模型

- **允许 + 拒绝（Seatbelt）**：规则可以叠加，后面的 `deny` 能覆盖前面的 `allow`。

  ```scheme
  (allow file-write* (subpath "/repo"))
  (deny file-write* (subpath "/repo/.git/hooks") (literal "/repo/.git/config"))
  ```

- **只能允许（Landlock）**：每条规则只能在某个目录层级上“加”权限，子目录自动继承上级的权限。没有“减”的操作。

只能允许的模型下，“`/repo` 可写，`/repo/.git/hooks` 只读”无法直接写出。能想到的绕法是不授权 `/repo` 本身，而是把它拆开，逐个授权除了 `.git/hooks` 以外的子项。但这样 `/repo` 根目录与 `/repo/.git` 根目录本身就不可写了：新建文件要求对所在目录有写权限，`git` 每次操作都要创建 `.git/index.lock`。拆开之后，沙箱是“安全”了，却连 `git status` 都跑不了。

反过来，“全部可读、减去 `~/.ssh`”在只能允许的模型下是可以做到的：从 `/` 往下，不是排除路径上级的目录整体授权，是上级的就展开子项继续递归，排除路径本身跳过。读取不需要上级目录的写权限，所以拆分不会误伤。**同样是“减去一块”，读可以用拆分表达，写不行。**

## 陷阱：写了 `deny` 不等于生效

nono 的权限清单里有 `deny` 字段，看起来正好解决问题。实测 0.80.0 的清单模式会直接丢弃它（源码把 `deny_paths` 写死为空），沙箱内照样能写 `.git/config`。`~/.ssh` 读不到，只是因为它本来就没被授权，并不是 `deny` 在起作用。

所以安全规则必须做反向测试：不只验证“允许的能做”，还要验证“禁止的确实被拦”，并检查文件是否真的没被写出来。只看命令返回码，可能把“命令自己失败了”误当成“沙箱拦住了”。

## 做法：把差异变成能力，而不是近似

遇到后端表达不了的要求，有两种处理：近似（Linux 上干脆不保护 `.git`），或者如实报告。ActSpace 选了后者：

- 能力表里有一项 `filesystem.write-deny`，`tool` 模板把它列为必需；
- Linux 上 nono 后端报告 `unsupported`，管理器判定 `tool` 沙箱不可用；
- bash 于是走“沙箱外执行”的审批，审批卡显示“真实环境”。

这样用户看到的是一个诚实的边界：要么真的有完整保护，要么明确知道自己在真实环境里执行，不存在“以为有沙箱、其实缺了一块”的中间态。

## 自检

- Linux 上把 `.git` 挂成只读的 bind mount 能不能解决？可以，但那需要 mount namespace，不再是 Landlock 能力，属于另一种后端，应当作为新后端注册，而不是在 nono 后端里偷偷补。
- 为什么 macOS 上 nono 的禁止读取不也用拆分覆盖？拆到 `~/Library` 下十几个路径会生成上千条授权，nono 启动约 900ms；Seatbelt 能写 `deny`，就直接用规则。可选的时候，选模型原生支持的表达方式。
- “允许的能做、禁止的被拦”之外，还应测什么？经别名路径访问（如 macOS 的 `/System/Volumes/Data/...`）是否同样被拦。
