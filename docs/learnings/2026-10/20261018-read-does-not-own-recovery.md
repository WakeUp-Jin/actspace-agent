# 读取状态不等于接管恢复

`getOrCreate` 很方便，但当“创建”会执行恢复时，它就不再适合作为通用读取入口。

设想一个子任务已经由 Provider 持有状态机。界面为了显示进度调用 snapshot；若 snapshot 找不到自己的缓存，就重新 open Ledger，恢复逻辑会把未完成任务视为上次进程遗留，将它改成 interrupted。任务本身仍在运行，因此工具成功，但最后提交 completed 被拒绝。外层如果统一包装为持久化错误，表面上看起来像磁盘出了问题。

解决时先分清三个权限：谁能观察、谁能调度、谁能恢复。当前所有者可以向查询服务登记已确认的状态；查询不另造状态机，其他调度器不得接管。所有者释放后，才允许正常的重新打开与恢复。

最有价值的测试不是“工具能成功”，而是：**任务运行中读取状态，不增加日志事件，不改变任务状态；随后完成仍成功。** 再检查其他入口是否共用这条观察路径，就能同时保护界面轮询和远程 RPC。

自检：你的 snapshot 是否会启动恢复或写事件？一个正在运行的任务是否可能被两个状态机分别持有？
