# 事件折叠与视图生成为什么要分开

一个流式回答可以包含数千个 chunk，但历史恢复通常只需要最终可展示状态。如果每个 chunk 后都重新估算上下文 token、生成预览和深拷贝视图，成本会变成“事件数 × 历史内容大小”。减少 DOM 节点并不能修复主进程里的这类开销。

恢复应先依次运行 reducer，最后再生成视图。checkpoint 尾部还需带上 pending 事务：压缩开始到结束必须整体可见。先验证连续序号并在全部 reducer 成功后提交，可以避免部分恢复污染已提交状态。

不要直接删除 chunk。首 token 时间、usage、未完成回答和中断恢复可能依赖它；优化的是无用的派生计算。语义输入引用稳定时可复用昂贵计算，但水位、活动回合和时间的语义仍要逐项保留。冷重放与逐事件输入的结果等价，是比“变快了”更重要的回归测试。

监控也有观察成本。默认关闭、低频请求、局部状态、清理生命周期能控制成本；开启组恰好 CPU 更低只说明测量有噪声，不证明监控没有开销。
