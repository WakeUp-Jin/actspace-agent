# 长寿命端口如何读取可变配置

配置对象会更新，并不代表使用它的闭包也会更新。关键是比较两个生命周期：如果工具端口比设置版本活得更久，在创建端口时解析出的模型就会一直被旧闭包持有。界面显示新配置、主请求使用新模型，都不能证明辅助工具读到了新值。

## 在调用入口取值

不可变的依赖（artifact reader、记录器、固定凭据引用）可以在创建时注入。允许用户实时修改的绑定，应在每次工具调用开始时从设置服务解析，再创建本次调用使用的 inspector。这样下一次调用观察最新配置；已经准备好的请求保留自己的模型和凭据身份，避免执行到一半切换身份。

```ts
// 端口可复用；配置快照属于一次调用。
return {
  inspectImage: (input, context) => {
    const model = settings.resolveVisionModel();
    return createInspector(model).inspect(input, context);
  },
};
```

另一种做法是在设置变化时销毁全部端口并重建，但它扩大了失效范围，还要协调运行中的任务。只有其他依赖也必须重建时，才值得采用这条路线。

## 三个方向检验失效边界

只测试“初始配置正确”发现不了这种问题。固定同一个端口实例，连续验证未配置→首次配置、模型A→模型B、可用→不可用→恢复。不可用时还要断言没有读取图片和发送辅助请求，避免旧能力仍然可调用。新会话使用旧端口也应覆盖，因为重开会话不一定重建底层服务。

清空显式绑定与禁用能力的含义需要分开。如果解析器允许回退到其他可用模型，选择“跟随”仍能看图是合法行为；测试应控制全部候选配置，而非只清空一个字段。
