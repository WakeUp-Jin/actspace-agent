# 长寿命端口读可变配置：在调用入口取值，并区分失败阶段

合并自三篇：长寿命端口如何读取可变配置（图片 inspector）、长生命周期工具端口拿到过期凭据（搜索端口）、配置快照与分阶段错误（生图）。与之互补的“请求开始后冻结配置”见 [LLM 请求配置冻结与 Retry Lease](../2026-09/20260922-request-bound-llm-preparation.md)。

## 1. 比较两个生命周期：端口 vs 设置版本

配置对象更新，不代表使用它的闭包也更新。依赖注入时读 Settings 并交给闭包，得到的是那一刻的快照；工具端口比设置版本活得更久（跨多轮对话复用，而凭据可能在同一会话中被断开、重连、更换）时，界面显示新值、主请求用了新模型，都不能证明辅助工具读到了新值——UI 显示“删除成功”也不证明后续请求停止使用旧凭据。

```ts
// 反例：创建端口时读出凭据，闭包永远持有旧对象
const credentials = settings.readCredentials();
const port = createSearchPort({ credentials });
// 做法 A：getter，调用时读取
const port = createSearchPort({ get credentials() { return settings.readCredentials(); } });
// 做法 B：显式传 getCredentials() 回调；关键是确认底层没有再次解构并缓存该值
```

做法：不可变依赖（artifact reader、记录器、固定凭据引用）创建时注入；允许用户实时修改的绑定（视觉模型、搜索凭据），**每次工具调用开始时**从设置服务解析，再创建本次调用用的 inspector：

```ts
return { inspectImage: (input, context) => createInspector(settings.resolveVisionModel()).inspect(input, context) };
```

下一次调用观察最新配置；已准备好的请求保留自己的模型和凭据身份，避免执行到一半切换身份。另一路线是设置变化时销毁并重建全部端口——失效范围更大且要协调运行中的任务，仅当其他依赖也必须重建时才值得；重建整个 Runtime 也可能只是掩盖生命周期问题并丢掉可复用状态。缓存网页结果等可复用资源可保留，凭据应按请求读取。无状态请求端口按调用读取通常比重启 Runtime 简单；请求开始后保持同一份快照，避免“一半旧地址、一半新凭据”。

按调用读取保证的是**后续**请求生效；已开始的请求仍持有开始时的凭据，若产品要求中断在途请求，需要独立的取消语义，不是 getter 自带的能力。

## 2. 回归测试：固定同一个端口实例

不能只测“改配置后创建新实例”。创建一次端口，依次验证：未配置 → 首次配置、模型 A → 模型 B、可用 → 不可用 → 恢复；搜索凭据：已连接 → 断开 → 重连并换 Key → 全部断开。检查**实际外发请求的目的地与鉴权头**，不只是设置对象或页面文字。不可用时断言没有读取图片、没有发送辅助请求；新会话使用旧端口也要覆盖（重开会话不一定重建底层服务）。清空显式绑定与禁用能力含义不同：解析器允许回退到其他可用模型时，“跟随”仍能看图是合法的，测试要控制全部候选配置而不是只清一个字段。测试使用合成凭据，真实验证只记录 provider 名称不记录 Key。实例：[BUG-038](../../exec-runs/20261021-actspace-full-acceptance/execution-summary.md#bug-038)、[Desktop 三项缺陷修复过程](../../exec-runs/20261007-desktop-acceptance-b03-b08-b12/execution-process.md)。

## 3. 生图有两个以上外部阶段

生成 API 返回图片 URL ≠ 图片已下载 ≠ 本地会话产物已保存。把所有失败都叫“无效响应”，会让用户反复更换原本可用的生成服务。分清请求、下载、解码、保存，才知道该检查哪一段。错误诊断保留**允许列表内的系统码**，不要打印整个 error/cause（可能含签名 URL、Token、本地路径）。

下载失败后重新调用整个生成工具会再生成一张收费图片：没有独立下载恢复协议时不能简单把这类错误标为可重试；保留部分成功产物、明确失败阶段，比无限重试可靠。

## 自检

1. 配置是在启动时还是调用时读取？每个请求实际在哪一行读取凭据，该值是否又被别的长期对象缓存？
2. 失败发生在付费操作之前还是之后？诊断是否含敏感信息？一次 UI 成功是否被误当成长期稳定性证明？
3. 测试是否检查了外发请求，而非仅配置变化？
