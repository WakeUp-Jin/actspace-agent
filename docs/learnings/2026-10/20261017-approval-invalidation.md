# 权限变化是重新判断，不是批准旧请求

用户在等待审批时切换权限，改变的是判断命令是否可执行的条件。旧审批请求记录的仍是旧条件，因此不能直接把它变成“用户已批准”。

一个可靠的流程是：关闭旧请求、记录关闭原因、用新权限重新提取资源并执行策略判断，再开始命令。这样，即使新模式更宽松，硬拒绝与资源检查也不会被绕过。权限变化只需要一个短生命周期的通知订阅，没必要轮询。

异步流程的陷阱在于“用户拒绝”与“权限变化”可能同时到达。Promise.race 只选择最先完成的 Promise，并不理解哪个动作更有业务权威。先收到的拒绝必须保留；取消旧请求后还要检查 Host 已经决定的结果，不能把已拒绝命令重新放行。回归测试要主动安排这个顺序，而不只测正常点击。

取消也要有准确范围。重新评估一个请求，只能取消这个 requestId；取消整个 run 会连带关闭其他工具的审批。相应订阅、超时计时器和 AbortSignal 监听都应在 finally 释放。

最后，检查权限或取消状态的位置很重要：异步路径解析、沙箱准备和持久化屏障都可能让之前的检查过期。进程创建前要再次检查取消状态，执行体调用前要确认权限仍与准入时一致。已经运行的命令则属于另一个生命周期，不能把权限变更混同于进程终止。

自检：能否说明日志里的“取消”是谁触发的？能否在两个审批同时存在时只关闭一个？能否证明拒绝与模式切换同时发生时不会执行命令？这三类测试比只验证一次“运行成功”更能约束审批系统。

真实界面还揭示了分层测试的盲区：工具层已能响应新策略，Host 入口却先把所有请求标记超时，导致重新评估永远到不了。界面显示“任务完成”也不代表每条工具成功；必须检查单条工具结果和 Journal 时间，区分自然过期与代码主动失效。对应回归应落在产生错误决策的 Host 入口，而不是只补更多工具层 mock。
