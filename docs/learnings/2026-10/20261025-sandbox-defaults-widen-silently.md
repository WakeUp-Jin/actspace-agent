# 沙箱的默认值会悄悄放宽边界

> 来自沙箱第二期 T6（[history](../../histories/2026-10/20261025-1517-sandbox-v2-evaluation-sandbox.md)）。单元测试全部通过之后，第一次用真实 nono 跑真实候选，才发现评估沙箱的两条边界并不成立。

## 发生了什么

评估沙箱的设计是：候选只能写本次评估的临时根目录，网络只放行模型服务。我们生成的 nono profile 在字面上完全符合这个设计：`allow` 只有临时根目录，`allow_domain` 只有模型域名。但真实执行时：

1. **候选写进了原工作区。** nono 的 profile 默认带“系统写入组”：macOS 的 `system_write_macos` 放行 `/tmp`、`/private/tmp`、`$TMPDIR` 和整个 `/private/var/folders`（本用户所有应用的临时目录），Linux 的 `system_write_linux` 放行 `/tmp`。测试里的原工作区恰好在 `$TMPDIR` 下面，于是可写。
2. **只放行本机端口时，网络完全放开。** 模型服务在 `127.0.0.1` 上，域名白名单为空，只有 `open_port`。nono 对空的 `allow_domain` 的理解是“不过滤”：不启动代理，所有域名都允许。

两处都不是 bug，是 nono 为了“大多数命令能直接跑”而选的默认值。问题在于我们的 profile 没有写出来的部分，也在起作用。

## 为什么容易漏

- **配置是“加法”写的，默认值是“隐式”加上的。** 读我们生成的 JSON 看不出 `/private/var/folders` 可写；要用 `nono why --path <路径> --op write` 才能看到 `group:system_write_macos`。
- **“空列表”有两种含义。** 对我们来说 `domains: []` 是“一个域名都不放行”；对 nono 来说是“没有配置域名过滤”。这类歧义在 allowlist 风格的接口里很常见。
- **单元测试只能验证我们写出了什么，验证不了它生效后是什么。** 后端测试断言 profile 的内容，全部通过；边界是否成立只能靠在沙箱里真的去写、真的去连。

## 怎么做

- **边界用探针证明，不用配置推断。** 集成测试里让候选执行 `probe.mjs`：写原工作区、写 HOME、写别的临时目录、连白名单外的域名，每一项都断言失败。“应该失败”的用例比“应该成功”的更重要。
- **探针的位置要贴近危险区。** 这次能发现系统写入组，正是因为原工作区放在了系统临时目录下。真实用户的仓库不在那里，但别的应用的临时文件在。
- **对“空”做显式分支。** 只有本机端口时写成 `block: true` 加 `open_port`，不把空列表交给后端去解释。
- **按用途收紧，不顺手改别处。** 评估沙箱排除了系统写入组；工具沙箱也受同样的默认值影响，但改它会让一些工具失败，这是另一个决定，单独交给用户。

## 自检

1. 一个 allowlist 接口收到空列表，你的代码和底层工具对它的理解一致吗？怎么确认？
2. 你的沙箱配置里没写的那部分，由谁决定？有没有工具能把“最终生效的规则”打印出来？
3. 如果只能加一个集成测试用例，你会选“该成功的能成功”还是“该失败的会失败”？为什么？
