# 把继承钩子改成通知时，谁负责释放副作用？

业务服务调用 `onPreparing()` 很容易扩展成许多子类钩子。把可选行为移成插件后，通知只说明“发生了什么”；插件仍必须拥有它启动的请求、计时器和退出等待。

以自动标题为例：主任务发出准备通知，标题插件启动独立请求。生成失败不应阻断主任务，但用户手动命名必须胜过迟到的生成结果。因此命名通知的监听器要在同步部分取消旧请求；结果写入前再检查取消状态与当前标题。`emit` 不等待异步完成，并不意味着所有行为可以不考虑顺序。

插件销毁时应取消全部请求并等待收尾；切换组合前的 idle 检查也要看到后台任务。仅移除事件监听器无法收回已经发出的网络请求，更无法撤销已经写入文件的事实。Cordis 的作用域帮助管理释放流程，业务仍需定义可取消范围。

自检：谁持有 AbortController？谁等待完成？用户操作与迟到结果冲突时谁胜出？如果这三个问题没有答案，把钩子改成事件只是搬动代码。
