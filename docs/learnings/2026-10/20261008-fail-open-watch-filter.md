# 文件监听降噪：在事件源头按 Git 语义过滤，拿不准就放行

> 来自 Review 资源优化。history：`docs/histories/2026-10/20261008-2337-review-cpu-optimization.md`；数据见 `docs/exec-runs/20261008-review-resource-test/optimization-results.md`。

## 问题：监听本身不贵，贵的是每个事件引发的下游工作

Review 递归监听整个工作区。资源测试发现，监听器本身几乎不占内存和 CPU。真正的开销在后面：每 150ms 窗口一次完整的 Git 快照查询（约 5 条 Git 命令），再加上 renderer 刷新。

触发这些查询的，大多是对 Review 毫无意义的事件：往被 `.gitignore` 忽略的 `dist/` 里写构建产物。`git status` 根本看不到这些文件，查完结果和上次一模一样。

所以优化的方向不是「让查询更快」，而是**不让无意义的事件进入下游**。

## 为什么不按目录名排除

最直接的想法是写死忽略 `node_modules`、`dist`、`build`。这样做有两个问题：

1. **已跟踪的文件也可能在这些目录里。** 有的仓库会用 `git add -f` 提交 `dist/` 下的产物，按目录名排除就会漏掉它们的真实改动。
2. **忽略规则是活的。** 用户改 `.gitignore`、`.git/info/exclude` 或全局 `core.excludesFile` 后，写死的列表就和 Git 的判断不一致了。

规则应该和「Review 显示什么」用同一个事实源，也就是 Git 自己。

## 做法：窗口内攒路径，一次问 Git

```text
watch 事件 ──► 分类
              ├─ Git 元数据 / .gitignore / 没有文件名 ──► 标记「必须刷新」
              └─ 工作区文件 ──► 记下相对路径
窗口结束 ──► 有「必须刷新」？ ──是──► 失效
                 │否
                 ▼
        git check-ignore -z --stdin（整批路径一次）
                 │
        有任何一条没被忽略？ ──是──► 失效
                 │否
                 ▼
               丢弃
```

几个关键点：

- **`git check-ignore` 默认会查 index。** 已跟踪的文件即使匹配忽略规则，也不会被报成 ignored。上面第 1 个问题因此自然消失，不需要自己写判断。用 `--no-index` 反而会出错。
- **复用已有的合并窗口。** 一个窗口里同一个文件可能被写几十次，先去重再批量交给 Git，每个窗口最多一个 Git 进程。实测 375 次/秒的写入只换来 2 次/秒的 `check-ignore`。
- **`.gitignore` 本身的变化必须放行。** 它改变的是规则，过滤器没法用旧规则判断新规则。

## 核心原则：fail-open

过滤器的两种错误代价不同：

| 错误 | 后果 |
|---|---|
| 把无关事件当成变化（多放行） | 多做一次查询，CPU 稍高 |
| 把真实变化当成噪声（误拦截） | Review 显示过期内容，用户可能基于旧 diff 去 stage 或 commit |

所以所有拿不准的情况都按「有变化」处理：非仓库、子模块路径、Git 超时或报错、输出被截断、单个窗口路径太多。性能优化可以有漏网之鱼，正确性不行。

这也是这类过滤器容易写错的地方：把 `catch` 写成 `return false`，看起来「失败就跳过」很合理，实际上是把失败变成了静默漏刷新。

## 常见陷阱：确认你测的是新代码

第一次跑前后对照时，「改后」组的 CPU 降了一半，看起来很成功。但计数器显示 `check-ignore` 被调用了 **0 次**。原因是 dev 模式的增量编译只更新了部分文件，watcher 还是旧版本，不传路径。降下来的那一半其实全来自另一项改动（窗口从 150ms 改成 500ms）。

经验：给每项优化都配一个**直接计数**（这里是过滤器调用次数、被丢弃的窗口数），不要只看总 CPU。总数下降不能说明是哪项改动起的作用，甚至不能说明新代码真的跑了。
