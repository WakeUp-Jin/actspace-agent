# 为什么停止任务也需要返回结果

一个 Run 可以成功、失败，也可以被用户取消。取消通常通过 AbortSignal 中断正在等待的请求，因此底层常用异常跳出执行；但“中断机制”和“任务最终结果”属于不同层次。

如果 Loop 已经将 aborted 终态写入日志，却继续把取消异常抛给上层，调度器可能只记录 cancelled 状态而没有结果。客户端适配层如果要求每个结束的 Run 都有结果，就会把用户正常停止误报成失败。界面的消息显示“已停止”，侧栏却显示“失败”，两处都忠实反映了不同层收到的信息。

正确的收尾顺序是：中断当前请求，关闭未结算的 step/turn，持久化 checkpoint，再返回包含 Run 身份和 `reason: "aborted"` 的结构化结果。上层据此持久化 cancelled，并向客户端返回停止状态。结果可以没有完整文本，但不应缺少结束原因。

这里有一个重要例外：如果写入终态或 checkpoint 失败，就不能把它包装成正常停止。应继续抛出持久化错误，阻止调度器基于未可靠保存的状态继续执行。已经进入 durability blocked 的会话同样不能报告收尾成功。

验证时至少覆盖三条路径：正常停止有结果且不发错误通知；取消遇到结算失败仍抛错；真实客户端停止后不用刷新也能显示正确状态。只断言 AbortSignal 已触发，无法验证这条完整契约。

这个约定还必须贯穿调度层：如果执行器已经把正常取消转换成返回值，那么调度器不能在 catch 中仅看 `signal.aborted` 就吞掉所有异常。取消与故障可以同时发生，异常可能是 checkpoint 或清理失败。执行前的信号中断与执行开始后的故障需要区分；前者可以取消接纳，后者应保留失败事实。

取消的身份同样重要。一次调用绑定一个 task/run；调用返回延迟时，会话可能已经执行下一任务。处理旧调用的取消信号，应查询原任务对应的 Run，而不是“会话当前活跃的 Run”。测试需要明确构造原任务已完成、后续 Run 活跃而旧调用仍未返回的时序。
