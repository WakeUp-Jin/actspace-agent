# 监控页 UI：事实列表负责定位，详情区负责解释

关联 history：[docs/histories/2026-05/20260528-0042-kairos-monitor-page-redesign.md](../../histories/2026-05/20260528-0042-kairos-monitor-page-redesign.md)

## 一句话

事件流型监控页不要把所有事实都塞进一张“万能表”。更稳的结构是：轨迹给状态密度，列表给定位，详情区给解释。

## 场景

Kairos 的原始事实来自 `SessionEvent[]`，里面既有 `kairos_tick_injected`、`tool_call`、`tool_result`，也有 `assistant_message` 和 sleep 生命周期事件。

如果直接做成“原始事件表 + JSON 详情”，用户能看到全部事实，但很难回答三个真正重要的问题：

- Kairos 现在是否正常，是否在睡眠或异常？
- 最近一次最终回复是什么？
- 某一行工具调用到底输入了什么、输出了什么？

这次页面改造成：

- 顶部 header：只保留当前运行状态和控制按钮。
- 运行轨迹：只表达回复、睡眠、异常、其他四类状态密度。
- 执行列表：按折叠后的 `KairosEventRow` 做定位，不展示原始 JSON。
- 右侧统计：放少量当前窗口最重要的计数。
- 右侧详情：默认最终回复，选中工具行后切到工具结果。

## 为什么这样更稳

监控页里的信息有不同职责：

| 层级 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| 轨迹 | 看趋势、密度、异常尖峰 | 阅读完整内容 |
| 列表 | 找到某个事件行 | 展开所有细节 |
| 详情 | 解释当前选中事实 | 同时展示所有事实 |

这能避免一个常见错误：把“可追溯”误解成“所有字段都默认可见”。可追溯应该由事件 id、relatedEventIds、debug 能力保证；默认 UI 应该服务用户的判断路径。

## 通用模式

面向事实流的产品监控页可以按这个顺序设计：

1. 先定义用户最常问的 3 个问题。
2. 把事实流折叠成面向问题的 row，而不是直接渲染 raw event。
3. 颜色只给真正需要警觉的语义，不给每种类型都分配颜色。
4. 详情区同一时间解释一个主题，避免“最终结果”和“过程输出”并排争抢。
5. 真实窗口验证表格和轨迹，不只靠单测。

## 这次踩到的布局陷阱

真实 Electron 窗口里暴露了两个单测看不到的问题：

- 表格默认布局会把“工具执行”“最终回复”压成竖排，因为摘要列内容更长，会挤占类型列。
- 运行轨迹用 `repeat(auto-fit, minmax(18px, 1fr))` 时，事件很少会把每个块拉成大横条，不再像低密度状态轨迹。

修法：

```css
.kairos-events__table {
  table-layout: fixed;
}

.kairos-events__table th:nth-child(2),
.kairos-events__table td:nth-child(2) {
  width: 104px;
}

.kairos-events__kind {
  white-space: nowrap;
}

.kairos-trace__blocks {
  display: flex;
}

.kairos-trace__block {
  flex: 1 1 18px;
  max-width: 34px;
}
```

经验是：**表格列宽和轨迹块宽是监控台的稳定尺寸，不应该完全交给内容自适应。**

## 自检问题

1. 这个监控页的“默认详情”应该展示最终结果、原始 JSON，还是最近选中行？为什么？
2. 如果某种事件很多，应该新增一种颜色，还是先问它是否真的需要警觉语义？
3. 表格在单测里通过，但真实窗口中文字竖排，说明缺少哪类验证？
