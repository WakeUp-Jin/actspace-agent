# 附加诊断信息不应成为主架构

UI 需求同时包含"主目标"和"附加目标"时，**附加目标只能作为元数据依附在主目标上，不能反过来切割主目标的承载结构**。这条 takeaway 来自 Kairos 上下文 Sheet 三次迭代——v1.1/v1.2 错把"段落溯源"提升成了"按段切 6 张卡片"的主架构，结果主目标（完整阅读 prompt）被破坏；v1.3 才把这个错位掉头。

## 为什么需要

很多设计需求看起来是平铺的，但拆开看一定有主次：

> "**系统提示词展示**，并且**有一些段落用户可以知道来自于哪一个文件**"

字面平铺，但语义上：
- **主目标**：完整展示系统提示词——让用户看到模型实际看到的内容。
- **附加目标**：能溯源——用于"看到不对劲想改"的诊断。

v1.1 设计时的直觉路径：
1. 需求两件事 → 实现两件事。
2. "段能溯源" → 按段切。
3. "段卡片各自有边框 / 独立背景 / 独立展开按钮"——附加目标的承载结构成了主体。

结果：
- 模型看到的是**一篇连贯文档**，用户看到的是**6 张独立卡片**——视角不一致。
- 卡片边框 / 6 个独立"展开全部"按钮 / 渐隐遮罩——这些**全是为承载溯源信息而生的副产物**，反过来切割了主体阅读流。
- 写代码时还得维护"6 段每段的展开状态"——一个为伪需求而生的复杂度。

v1.3 把方向掉头：
- 主体是一份连贯文档。
- 溯源信息**只在段头条作为元数据出现**（短色条 + 段名 + 源文件徽章占一行）。
- 段与段之间用 1px 分隔线分界——分隔线是文档章节的视觉语言，**不是切割信号**。

## 怎么用：Before / After 对照

### Before（v1.1/v1.2）：附加目标承担了主架构

```tsx
{segments.map(segment => (
  <li className="rounded-act-md border border-[#e6e8ef] bg-surface shadow-...">
    <header>
      <span>{segment.label}</span>
      <SourceFileBadge file={segment.sourceFile} />  {/* ← 附加信息 */}
    </header>
    <PreviewWithFold text={segment.text} />  {/* ← 为卡片化服务的折叠 */}
    <button>展开全部 / 折叠</button>  {/* ← 状态复杂度 */}
  </li>
))}
```

- DOM 层级：6 个独立 `<li>` 卡片
- 主体阅读流：被 6 张卡片切割
- 附加信息住在哪儿：卡片头部
- 状态复杂度：6 个独立 `expanded` 状态

### After（v1.3）：附加目标只是章节元数据

```tsx
{segments.map((segment, idx) => (
  <article className={idx === 0 ? "pt-1" : "border-t border-[#eef1f6] pt-4"}>
    <header className="mb-2 flex items-center gap-2">
      <span className="h-[14px] w-[3px] bg-gradient-..." />  {/* 章节标题前缀 */}
      <span className="font-semibold">{segment.label}</span>
      <SourceFileBadge file={segment.sourceFile} className="ml-auto" />  {/* 附加信息 */}
    </header>
    <div className="whitespace-pre-wrap">{segment.text}</div>  {/* 完整段正文 */}
  </article>
))}
```

- DOM 层级：6 个 `<article>` 章节，并排在一个连续文档里
- 主体阅读流：完整、连贯，按章节自然滚动
- 附加信息住在哪儿：章节标题元数据行
- 状态复杂度：零（没有任何展开/折叠状态）

## 核心要点

1. **拆需求时强制区分主-附层级**。"展示 + 溯源"看似平铺，本质是"主体 + 元数据"。如果识别不出主附，就先问自己："如果只能保留一个，留哪个？"——能留下的就是主目标。
2. **附加信息的归宿是元数据位置**（标题行 / 侧栏 / 角标 / tooltip / 状态条），不是主体容器。元数据位置的视觉语言是"轻量、依附、可忽略"；主体容器的视觉语言是"分量、独立、必看"——错位即视觉混乱。
3. **附加信息不应该引入主目标的状态分支**。v1.1 的"按段折叠"是典型反例——它给主目标（阅读 prompt）增加了 6 个独立的局部状态，但这些状态根本不是阅读需要的。
4. **模型视角 = 用户视角**（在诊断场景里）。如果一个 UI 的目标是让用户"看到模型看到的"，那 UI 的信息结构应该跟模型实际接收的结构同构——LLM 接收的是一段连贯文本，UI 也应该是一份连贯文档。
5. **可以"牺牲"附加目标的展示密度来保住主目标的连贯**。v1.3 没有给每段加边框，溯源徽章视觉重量更轻，但溯源功能完整保留——这是值得的取舍。

## 常见陷阱

### 陷阱 1：把"信息齐全"误认为"信息架构对"

v1.1 的设计师（也就是我自己）当时认为"6 段都标了源文件、每段都能独立预览/展开"是"信息很齐全"。但信息齐全和信息架构对是两码事——信息可以全部都在里面，但承载方式错了，用户读起来还是吃力。

### 陷阱 2：把"未来可能扩展"提前做成切割

v1.0 时给每个工具加了 JSON Schema 展开按钮，理由是"未来工具多了，用户会想看 schema"。但当下只有 1 个 Kairos 工具，加了反而成噪声。v1.1 走查时撤销了。**为想象中的未来扩展提前切结构，是另一种形式的"附加目标驱动主架构"**——只不过这次驱动它的不是已有的附加目标，是想象的附加目标。

### 陷阱 3：用卡片做"分类"

卡片是一个非常贵的视觉元素——它有边框、背景、间距、独立的状态空间。一旦用卡片来承载"这几个是一类、那几个是另一类"的分类信息，主体就被卡片切割了。**分类信息更便宜的承载方式**：色条 / 标签 / 章节标题 / 灰度分组 / 不同的字号——这些都是元数据级别的视觉语言。

### 陷阱 4：状态机膨胀

"每段独立折叠"听起来灵活，实际维护成本是 N 个布尔 state（v1.1 是 6 个），每个状态都得有展开/折叠两种渲染分支。当方向回到"章节流"后，这 6 个状态全部消失——这是一个信号：**如果某个特性产生了一堆独立局部状态，先问问这个特性是不是必要的**。

## 自检问题

1. 我的这个 UI 需求里，**主目标和附加目标分别是什么**？如果它们看起来同样重要，问自己"删掉一个，留哪个"——留下来的就是主目标。
2. 当前实现里，**承载附加目标的结构**（容器边框、独立背景、局部状态、独立交互按钮）**是否在切割主目标**的连续性？
3. 如果把附加目标完全删掉，主目标的呈现会**更清晰还是更模糊**？如果删掉后变得更清晰，说明附加目标当前的承载方式是错的——它在拖累主目标。
4. 我的 UI 视角和"模型视角 / 数据视角"**是否同构**？特别在诊断 / 调试 / 监控类面板里，UI 结构与底层数据结构的不一致会让用户产生认知摩擦。
