# Runtime 空态和测试 Fixture 要分边界

关联 history：`docs/histories/2026-05/20260528-0032-foundation-bug-usability.md`

## 是什么

产品运行时的数据源必须来自真实事实；没有事实时展示空态。测试 fixture 可以继续存在，但只能在测试、Story 或显式开发验证边界内使用，不能被生产组件当作 fallback。

## 为什么需要

Usage 页面以前在没有真实 `UsageStatisticsSnapshot` 时回退到 `mockUsageStatistics`。这让用户看到趋势、成本、模型占比和热力图，却不知道它们不是自己的数据。对统计、账单、审计、历史记录这类界面来说，假业务数据比空态更危险。

## 怎么想

可以用这条规则判断：

- **运行时 fallback**：只允许 fallback 到空态、错误态或“需要先产生数据”的说明。
- **测试 fixture**：允许构造完整样例，用来验证布局、计算和交互。
- **开发 mock bridge**：如果保留，也必须让用户看得出它不是事实数据，不能悄悄注入业务图表。

## 常见陷阱

- 为了让页面“看起来完整”而把 fixture import 到生产组件里。
- 在加载失败时展示旧 mock 数据，掩盖真实 IPC 或聚合错误。
- 把“浏览器 mock 验证”误解成“产品可以展示 mock 业务数据”。

## 自检问题

1. 用户看到这组数据时，会不会以为它来自自己的真实会话？
2. 如果真实数据加载失败，页面是在暴露失败，还是用假数据掩盖失败？
3. fixture 是否只被测试文件、Story 或显式开发入口引用？
