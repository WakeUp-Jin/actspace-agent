# Design Tokens Before Component Polish

这次 `actspace` 前端样式调整暴露了一个可迁移的 UI 工程模式：在做大范围视觉调整前，先把品牌语言收敛成全局 design tokens，再进入组件细节。

## 为什么

如果直接逐个组件改颜色、字号和圆角，很快会出现三个问题：

- 同一种语义出现多个相近颜色，例如三种蓝色都在表达“可操作”。
- 文本颜色和品牌色混用，导致阅读层级不稳定。
- 后续 Agent 或开发者继续改 UI 时，不知道该复用哪个值，只能继续散写。

全局 token 的价值不是“少写几个 hex”，而是把设计判断变成代码约束。

## 这次采用的分层

`actspace` 的规则被拆成三层：

```css
--color-brand: #2f6fff;
--color-text: #202124;
--color-sidebar: #f3f5f7;

--accent: var(--color-brand);
--text: var(--color-text);
--surface: var(--color-surface);
```

第一层是明确的品牌和基础色，第二层保留旧变量兼容现有 CSS。这样可以先让界面方向统一，再逐步清理历史变量，不需要一次性重写所有组件。

## 关键取舍

品牌色不应该承担所有层级表达。

这次把规则定成：

- 黑色负责阅读。
- 灰白负责承载。
- 蓝色负责行动和品牌记忆。

这比“把所有文字都改成品牌蓝”更适合长期使用的桌面工具。用户每天看的正文、导航和消息回复应该稳定、清晰；蓝色只在发送按钮、选中状态、focus 和可执行入口出现，才会保持信号价值。

## 常见陷阱

- **token 太多**：刚开始就定义几十个组件专用 token，会让系统变得难记。先定义基础色、语义色、字号、圆角、阴影和动效即可。
- **只写文档不落 CSS**：规范如果没有映射到 `:root`，后续实现仍然会散写。
- **把品牌色当默认文本色**：短截图可能好看，长时间阅读会疲劳，也会削弱真正重点操作的辨识度。
- **一次性重构全部 CSS**：视觉系统可以先兼容旧变量，再逐步替换硬编码。

## 自检问题

1. 新组件里的颜色是否来自语义 token，而不是临时 hex？
2. 蓝色出现的位置是否真的表示动作、状态或重点？
3. 默认正文颜色是否适合长时间阅读，而不是只在截图里显得有品牌感？
