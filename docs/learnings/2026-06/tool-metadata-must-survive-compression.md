# 工具元数据要穿过压缩链路

来源：`docs/histories/2026-06/20260614-1245-glob-size-mtime-output.md`

## 核心结论

给模型看的工具输出不只是一段展示文本，它也是上下文工程的一部分。像文件大小、修改时间这类元数据，如果是为了帮助模型判断复杂度和相关性，就必须同时进入正常输出格式和压缩摘要规则。

## 为什么

Agent 工具通常有两条输出路径：

- 小输出：原样回填给模型。
- 大输出：先经过摘要器或截断器，再回填给模型。

如果只在 executor 里追加元数据，却没有告诉摘要器“这些字段必须保留”，长输出一旦触发压缩，模型拿到的可能又退回成普通路径列表。结果就是工具在小仓库里看起来变聪明，在大仓库或大结果集里突然丢掉关键信号。

## 判断方法

新增工具输出字段时，顺手检查三处：

- executor 或 renderer：原始输出是否真的包含新字段。
- truncator / summarizer prompt：压缩后是否要求保留新字段。
- 测试：是否覆盖字段存在，以及字段参与排序、筛选或决策的行为。

## 常见陷阱

不要把“排序使用了某字段”等同于“模型看到了某字段”。排序只能表达相对顺序，不能表达信号强度。例如 `glob` 按 mtime 倒序排列能暗示最近修改，但模型不知道两个文件差 1 分钟还是 3 个月。

## 自检

- 这个字段是 UI 装饰，还是模型决策信号？
- 大输出触发压缩后，这个字段还会保留吗？
- 测试有没有锁住“字段存在”和“字段语义”两件事？
