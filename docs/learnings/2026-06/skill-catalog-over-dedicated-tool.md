# Skill Catalog 优先于专用读取工具

来源：`docs/histories/2026-06/20260603-2358-agent-skill-loading-implementation.md`

## 核心结论

当 Agent 已经拥有通用文件读取能力时，Skill 系统不一定需要再做一个专用的 `load_skill` 工具。更轻的方案是：把 Skill 的 `name`、`description` 和 `SKILL.md` 绝对路径注入系统上下文，让模型在任务匹配时用已有 `read_file` 读取正文。

## 为什么这样更好

专用工具看起来更清晰，但它会增加一条新的工具协议、注册路径、测试矩阵和前端预览语义。若它只是“按名字找到路径再读文件”，本质上是在重复 `read_file` 已经具备的能力。

Catalog 的职责应该是帮助模型发现能力和定位入口；正文读取、目录查看、引用搜索这些动作，则可以继续由 `read_file`、`list_directory`、`grep`、`glob` 这些通用工具承担。

## 判断方法

适合复用通用工具的情况：

- 新能力只是把已有资源暴露给模型，而不是提供新的执行语义。
- 已有工具已经有权限、裁剪、预览、日志和测试覆盖。
- 专用工具的输入输出只是现有工具的薄包装。

适合新增专用工具的情况：

- 需要新的权限边界或审批语义。
- 需要结构化输出，且通用工具输出会让模型难以稳定使用。
- 需要跨多个底层动作做不可分割的事务。

## 常见陷阱

`tsc` 默认不会删除已经不存在的源码对应的旧 `dist` 文件。删除专用工具源码后，`dist/tools/tools/load-skill/` 这类旧产物可能仍然留在本地。

短期排查时，要看公开导出和注册链路，而不是只看 `dist` 目录里有没有旧文件。长期工程卫生上，正式 build 应该先清输出目录再重建，避免打包或跨包消费拿到陈旧产物。

## 自检

- 这个能力是不是只是“让模型知道路径，并读取文件”？
- 是否已经有通用工具具备同样的权限、裁剪和展示能力？
- 新增专用工具会不会让模型在两个等价入口之间犹豫？
