# 增量观测的游标：计算与提交分离（at-least-once）

> 提炼自 `docs/histories/2026-06/20260610-1030-kairos-prompt-cache-optimization.md`

## 是什么

把"观测到了什么"做成增量（只报新东西）时，必须维护游标（已读水位）。
关键设计：**计算增量（只读游标）和提交游标（写盘）必须是两个独立动作**，
且提交只发生在"消费方确认处理完成"之后——也就是消息队列里经典的 at-least-once 语义。

## 为什么需要

Kairos 原实现在 `diff()` / `refresh()` 内部"算完顺手就把游标写盘"。两类 bug 由此而来：

1. **失败丢增量**：tick 算出了增量、注入了 prompt，但 LLM 调用失败——游标已推进，
   这批"新文件 / 新消息"永远不会再出现。增量被"展示过"但从未被"处理过"。
2. **旁路偷吃增量**：上下文快照（用户打开 Sheet 预览"下次 tick 会看到什么"）复用同一条
   计算路径，预览一次就把 watch manifest 和 sessions 游标推进了——看一眼，观测就没了。

只要"读"和"确认"耦合在一起，任何额外的读取方都会变成隐性消费者。

## 怎么做

```
computeDiff(root)  → { entry, scannedEntries }   // 只读，可被任何人调用
commitManifest(root, scannedEntries)             // 只在 tick 正常闭合后调用

refresh() → result（含 result.cursor）           // 只读
commitCursor(result.cursor)                      // 同上
```

- 提交必须用**计算时捕获的快照**（`scannedEntries`），不能提交时重扫——否则 tick 执行
  期间新出现的变化会被"标记已读但从未展示"。
- 失败路径不提交 → 下个 tick 重见同一批增量（at-least-once：宁可重复，不可丢失）。
- 无法定位游标的内容（如手工编辑、无时间戳的 inbox 文本）宁可重复展示也不丢弃。

## 核心要点

1. "算出增量"和"承认已消费"是两个事务边界，合并它们等于把读取者全部变成消费者。
2. 提交内容 = 计算时的快照，不是提交时的现状。
3. 失败语义先想清楚：增量场景几乎总是要 at-least-once（重复无害、丢失有害）。
4. 只读旁路（预览、快照、调试）天然安全——因为它们拿不到 commit 权。

## 自检问题

- 你的 `refresh()` / `poll()` 是否有副作用？把它给只读调用方用安全吗？
- 处理失败后重试，还能看到同一批数据吗？
- commit 的参数来自计算时捕获的值，还是 commit 时重新读取的值？
