# 读类工具缓存要有失效和逃生口

关联 history：`docs/histories/2026-06/20260604-2023-read-file-range-dedup.md`

## 是什么

Agent 的读文件工具不只是文件系统 API，它也是上下文入口。一次 `read_file` 返回的源码会变成后续模型输入的一部分，所以重复读取同一段未变化的代码会同时浪费上下文、拉低 prefix cache 稳定性，并把真正新的信息挤出去。

一个实用模式是：对“同一文件、同一 offset、同一 limit”的读取做短期 unchanged cache。如果文件元数据没有变化，重复读取只返回一个短提示，让模型复用先前已经看过的行号内容。

## 为什么需要

分段读取通常是代码 Agent 的最优动作：先读小范围定位，再用 `offset/limit` 翻页。相比把大段源码摘要掉，分段读取保留了精确行号、符号和局部上下文。

但分段读取也容易带来另一个问题：模型会反复读刚看过的 range，尤其在多轮工具调用、压缩前后或不确定自己是否看过某段时。没有 dedup 时，这些重复输出会被当作新消息继续进入上下文。

## 怎么做

缓存键应包含读取语义，而不是只包含文件路径：

```ts
const cacheKey = `${resolvedPath}\0${offset}\0${limit}`;
```

失效信号至少包含：

```ts
{
  size: fileStat.size,
  mtimeMs: fileStat.mtimeMs,
}
```

缓存最好挂在工具管理器或会话级 runtime 上，而不是 executor 的模块全局变量。这样同一个 Agent 运行空间内可以 dedup，但测试、不同会话和不同工具管理器不会被隐藏状态互相污染。

## 常见陷阱

- 不能只按 path dedup。不同 `offset/limit` 是不同知识片段。
- 不能没有逃生口。上下文压缩后，模型可能真的需要重复拿到原文，所以需要 `force=true`。
- 不要把源码大输出优先交给摘要。摘要会丢行号和局部细节，代码任务更适合精确 range。
- 元数据失效不是强一致内容哈希。它便宜、足够实用，但对极端“同 size 且 mtime 未变”的改写不敏感。

## 自检问题

- 这个工具输出是否会直接进入 LLM 上下文？
- 重复调用时，模型得到的是新信息，还是同一段内容的第二份拷贝？
- 当缓存返回短提示后，模型是否仍有办法按需恢复完整原文？
