# 阈值判定必须用「未截断的全量」，不能复用「已截断的加载结果」

> 提炼自 `docs/histories/2026-06/20260610-1100-kairos-compression-trigger-wiring.md`

## 是什么

当一个系统同时存在「加载预算」和「压缩/清理阈值」两个比例参数时，阈值判定的输入
必须是**资源的真实全量**，而不能图省事复用加载阶段的产出——因为加载产出已经被预算
截断过了。

## 为什么需要

Kairos 短期记忆有两个参数：

- `loadBudgetRatio = 0.75`：`load()` 最多把 contextWindow 的 75% 装进上下文；
- `compressionThreshold = 0.85`：磁盘记忆达到 85% 时触发压缩。

原来的 `estimateTokens()` 直接 `load()` 然后返回 `loadedTokenEstimate`。这个值被
budget 截断，**数学上恒 ≤ 75% < 85%**——压缩阈值永远不可能触发。这类 bug 极隐蔽：

- 类型对、单测过（函数本身行为"正确"）、运行时无报错；
- 唯一症状是"压缩从来没发生过"，而压缩本来就是低频事件，很难被注意到。

## 怎么想

两个量的语义完全不同，哪怕计算路径高度相似：

| | 回答的问题 | 截断 | 数据源 |
| --- | --- | --- | --- |
| `load()` | 这次能给 LLM 装多少？ | 受 budget 截断 | 当日最新段（`loadDaily`） |
| `estimateDiskTokens()` | 磁盘上一共积压了多少？ | 不截断 | 全部段（`loadDailyAll`，含 reset 切出的段）|

判定"要不要清理"的输入是后者。一个快速自检：**如果阈值 > 预算，用预算截断值判定
就是恒假；如果阈值 < 预算，则会在不该触发时早触发**——无论哪种都错。

## 顺带的第二个坑：分区覆盖判定的边界

压缩产物（week summary）落在「首日所在月目录」，而加载时的覆盖判定只查「日期自己
所在月目录」。如果一个压缩批次跨月（如 05-30 ~ 06-02），6 月的日期永远查不到那份
落在 5 月目录的 summary → 原文与摘要被同时加载。修复方式不是改查找逻辑，而是给
**写入侧**加约束：候选批次截断在同一自然月内。当读取侧的查找规则不易改动时，让写
入侧遵守读取侧的分区假设，往往是更小的改动面。

## 核心要点

1. 「能装多少」和「一共有多少」是两个量，别用前者判定后者。
2. 阈值参数之间的大小关系（threshold vs budget）值得写进注释——它决定了误用的症状。
3. 永不触发的低频路径（压缩、归档、清理）要有单测直接断言"会触发"，否则上线后无人察觉。
4. 产物的存放分区必须满足读取侧的查找假设；改不动读取侧时就约束写入侧。

## 自检问题

- 你的系统里有没有"复用另一条路径的中间结果"做阈值判定的地方？那个中间结果被截断/过滤过吗？
- 如果把 compressionThreshold 调到 0.6（低于 budget 0.75），旧实现会发生什么？（答：会在
  load 结果 60%~75% 之间"碰巧"触发，行为取决于截断点，依然不正确。）
