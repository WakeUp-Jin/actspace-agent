# Actions 缓存开着不等于用上了：先核对谁存、谁读、存了什么、省不省时间、放久了还在不在

工作流里 `setup-go`、`setup-node`、`actions/cache` 的缓存都开着，日志里也写着命中，但 CI 提速第二轮核对时发现：一处缓存里连着五天都没有那个 job 要的东西，另一处存了 4.4 GB 却没有任何发版运行读得到，还有一处缓存恢复出来了、真正编译的子进程却不读它，再一处读到了也用上了、却不比不用它快，最后一处刚存下时好用、放过 5 天就会在 job 中途被用它的工具自己删掉。结论：缓存是否有用取决于「谁第一个存、存的是什么、读的运行在哪个分支上、干活的进程读不读它、恢复它比重新生成快多少、放了几天之后还在不在」，配置里开没开、日志里有没有命中都说明不了问题。

关联：`docs/histories/2026-11/20261114-0215-ci-speedup-round2.md`、`docs/exec-runs/20261113-ci-speedup-round2/execution-summary.md`。

## 为什么会这样

GitHub Actions 的缓存有两条和直觉相反的规则。

**一个 key 只保存一次。** job 结束时如果这个 key 已经存在，就不再保存；缓存条目不会被更新。几个 job 共用一个 key、往里放的东西又不一样时，谁先跑完，存下来的就是谁的内容，其余 job 之后每次都「命中」一份没有自己产物的缓存。

反例：`ci.yml` 的 `browser-bridge` 和 `build`（以及 `release.yml`）原来给 `setup-go` 传的 `cache-dependency-path` 相同，算出的 key 也相同。`build` 只编本机的浏览器桥 CLI；`browser-bridge` 要跑 `go test`，还要交叉编译 Windows 和 macOS 两个目标。`main` 上存下来的那份只有 14 MB，是本机的编译产物；`browser-bridge` 需要的那些（存全了是 45 MB）五天里一次也没进去过，`go test` 和交叉编译每次都从头编 5 s + 15 s，日志里却显示缓存已恢复。

按快慢，先跑完的本该是 `browser-bridge`：它一分钟，`build` 要五分钟。但这个 key 第一次出现的那次 `main` 运行里，`browser-bridge` 的测试失败了，而失败的 job 不保存缓存；四分钟后 `build` 跑完，存上了自己那份。后来 runner 的 Go 补丁版本升级换了 key，这回 `browser-bridge` 通过了、先存上，存下的是全的。共用 key 时存下什么，取决于换 key 之后第一次运行里谁先成功跑完。

**一次运行只读得到本分支和默认分支存的缓存。** PR 存的缓存，别的 PR 读不到，tag 运行也读不到。

反例：`release.yml` 只在改到打包文件的 PR、`v*` tag 和手动触发时跑，从不在 `main` 上跑。它在 macOS / Windows 上存的 pnpm store 和 Go 缓存只有同一个 PR 的后续推送能读到，tag 发版必然不命中。这些缓存每份近 200 MB，累计 4.4 GB，仓库的缓存总量因此超过 10 GB 上限，GitHub 已经在按最久未访问淘汰。

第三种情况和 Actions 的规则无关：**缓存恢复到了默认位置，干活的进程却用自己的目录。**

反例：`browser-bridge` 这个 job 里有两处自己起 `go` 的地方——`scripts/check-browser-command-registry.mjs` 的 `go run`，和 `browser-bridge/apps/cli` 一条测试里的 `go build`。环境里没有 `GOCACHE` 时，两处都把编译产物放进同一个临时目录，不碰 `setup-go` 恢复出来的那份。原来检查脚本先跑、顺带把临时目录编热，测试里那次构建只要 1 s。第一次修的时候只把检查脚本指回了恢复的缓存，临时目录没人编热了，测试里的构建变成每次从零编整个 CLI（7–12 s）：从零编译一次也没少，只是换了个步骤。等这个 key 终于命中，交叉编译从 11–15 s 降到 1 s，`go test` 那一步反而要 14 s，才看出来。

第四种情况：**缓存读到了，也用上了，但恢复它不比重新生成快。**

反例：`release.yml` 在 macOS / Windows 上的 pnpm store。同一个 PR 的后续推送确实读得到它，可它每份近 200 MB，解开是 700 MB 的几万个小文件，恢复要十几到几十秒，而 pnpm 现下载同一批包本来就是并行的。改动前 13 次发布运行里，命中时「恢复加安装」和没命中时「现下载安装」的中位数：darwin-arm64 29 s 对 28 s，Windows 32 s 对 32 s，darwin-x64 64 s 对 77 s；没命中的那次还要再花 8–54 s 把 store 压缩上传。同一个 job 里的 Go 编译缓存正相反：14 MB，恢复 2–3 s，省下 7–18 s 的编译。

这组数字还差点把结论带反。darwin-x64 上命中的那 8 次，不只安装快 13 s，后面的 desktop 构建也快（136 s 对 209 s），看上去缓存连构建都加速了。其实两组运行不在同一天：命中的集中在周日和周二，现下载的多数在周五下午。在同一台 runner 上交替「还原 store」和「现下载」各做四次，安装是 76 s 对 79.5 s，构建是 237.5 s 对 238.0 s——差别来自 runner，不来自缓存。

第五种情况：**缓存刚存下时好用，放几天之后在 job 中途被用它的工具自己清掉。**

反例：go 每次构建结束时会顺手清理构建缓存——距上次清理超过一天，就删掉修改时间在 5 天以前的条目；条目每被用到一次，修改时间刷新一次。在开发机上这就是「5 天没用过的删掉」。在 CI 上，`setup-go` 的 key 存过一次就不再更新，恢复时文件保留保存那天的修改时间，于是缓存存下 5 天之后，每次恢复出来的条目在 go 看来全都过期了。job 里第一条 go 命令不受影响，它要的条目在清理之前已经读到了；但它一跑完，它没用到的条目就被删掉。`browser-bridge` 先后跑 `go run`、`go test` 和两个交叉编译：把恢复出来的条目的修改时间改到 6 天前，`go run` 跑完，2569 个条目剩 526 个，`go test` 加交叉编译从 3 s 回到 16 s。拿一份真放了 5 天半的缓存核对也一样：第一条 go 命令跑完，941 个条目剩 273 个，接着的构建要 5.5 s，先刷新过时间的是 1.1 s。只跑一条 go 命令的 job（`build`、`release.yml`）碰不到这件事。

这类问题在刚改完的那几天测不出来：前面所有「命中之后只要一两秒」的数字，用的都是存下不到一天的缓存。

## 稳定的做法

- 要缓存的内容不一样，key 就要不一样。`browser-bridge` 的 key 现在多算一个 `browser-bridge/go.work`，有了自己的条目。
- 只有读的运行够得着的缓存才值得开。`release.yml` 的 Linux job 两份缓存都开：那两个 key 由 `ci.yml` 在 `main` 上保存，tag 运行读得到。macOS / Windows job 在 tag 上两份都不开；PR 上同一个 PR 的后续推送读得到，只开 Go 编译缓存。
- 恢复比重新生成便宜得多的才值得存。编译产物小、重新生成贵，存；包管理器的 store 大、从 CDN 并行下载本来就快，先量再决定。Linux 上的 pnpm store 留着，是因为它本来就由 `ci.yml` 存着，多一个工作流读它不多占配额。
- 内容每次都变的缓存（`tsc -b` 的产物）用带 commit SHA 的 key 加 `restore-keys` 前缀回退，见 `.github/actions/setup-workspace/action.yml`。
- 脚本或测试自己起编译器时，在 job 级别把缓存目录统一指到恢复的那一份（`browser-bridge` 是在 `setup-go` 之后把 `go env GOCACHE` 写进 `GITHUB_ENV`），不要一个步骤一个步骤地加：漏掉的那一处会把省下的时间原样吃回去。
- 一个 job 要在同一份恢复出来的缓存上先后跑几条命令，而这个工具按修改时间清理缓存时，恢复之后先把缓存里的文件 `touch` 一遍。`browser-bridge` 在导出 `GOCACHE` 之后加了这一步，两千多个条目用 0.04 s。

## 怎么验证

- 不看「缓存已恢复」那一行，看用缓存的那一步的耗时，而且要拆到步骤里面看：一步里只要有一条测试、一条子命令没用上缓存，整步的时间就不会降。Go 缓存真的用上时，`go test` 的编译和两个目标的交叉编译合计一两秒。
- 用 `gh api repos/<owner>/<repo>/actions/caches --paginate` 把缓存按 key 和 `ref` 列出来：挂在 PR ref 上的大缓存基本是只写不读；`last_accessed_at` 等于 `created_at` 的条目从来没被读过；同一个 key 在不同 ref 上大小差几倍，说明存它的不是同一种 job。
- 本地连续跑两遍同一条命令，第二遍应该几乎不耗时；仍然耗时就是缓存没接上。模拟时进程环境要和 CI 上一样：这次本地的模拟脚本给 `go test` 显式带了 `GOCACHE`，测试里嵌套的构建跟着用上了缓存，两遍都很快；CI 上没有这个变量，问题到缓存第一次命中才暴露。稳妥的办法是把工作流里的 `run` 步骤原样导出来跑，步骤之间只通过 `GITHUB_ENV` 文件传变量，再看有没有出现计划之外的缓存目录。
- 比「有缓存」和「没缓存」，两组样本要出自同一台机器、同一段时间。托管 runner 之间同一步骤能差 1.5–2 倍，把不同日期的运行按命中没命中分组，比出来的可能是 runner。办法是开一个只在临时分支上触发的工作流，在一个 job 里交替两种做法各跑几次，再开一个顺序相反的 job：Intel 的 macOS runner 在同一个 job 里越往后越快，顺序不反过来，这个趋势会被算成其中一种做法的功劳。
- 拿改动前的运行当基线之前，先看基线那几天缓存里装的是什么。`browser-bridge` 的基线正好落在缓存残缺的那五天里；key 换掉、缓存存全之后，没带任何改动的运行自己就从 70 s 降到 50 s 上下，这一截差点被算成改动的效果。要比就和同一时期、没带改动的运行比。
- 缓存的效果要在它放旧之后再量一次。等不了那么多天，就把缓存目录里文件的修改时间往前拨（`find "$GOCACHE" -exec touch -d '6 days ago' {} +`），按 job 里的顺序把命令跑一遍，数每条命令跑完后缓存里还剩多少文件。工具自己记着上次清理时间的话（go 记在缓存目录的 `trim.txt` 里），一并拨回去，否则它一天之内不会再清。

## 自检

- 这个 key 第一次是哪个 job 存的？它存的内容里有我这个 job 要的东西吗？
- 读这份缓存的运行，和存它的运行在同一个分支上，或者存的那次在默认分支上吗？
- 配额里最大的几类缓存，各自最近一次被读是什么时候？
- 这个 job 里有没有自己起编译器的脚本或测试？它们读写的缓存目录，是恢复出来的那一个吗？
- 恢复这份缓存要多久，不用它重新生成要多久，没命中的那次保存又要多久？这三个数是在同一台机器上量的吗？
- 用这份缓存的工具自己会不会清理它？按什么清？恢复出来的文件在它看来是多久以前的？这个 job 里用同一份缓存的命令不止一条吗？
