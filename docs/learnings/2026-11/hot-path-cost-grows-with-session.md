# 高频路径上的工作量，不能跟着会话长度涨

一段代码单独看是对的，测试也全过；可它放在「每次请求」「每个流式片段」「每秒一次的轮询」上，工作量又跟着会话长度增长，长会话一跑就是好几 GB 的分配。短会话、单元测试里根本看不出来。

## 为什么会这样

成本是两个因子相乘：**一次会话里跑多少次 × 每次跑多少**。

| 写法 | 跑多少次 | 每次跑多少 | run 实测 |
|---|---|---|---|
| 每个流式片段深拷贝一次约 0.9 MB 的请求上下文 | 每个片段 | 随上下文长度增长 | run1 一次运行主进程分配 11.5 GB，58% 来自这里 |
| 自动审查时 `[...journal.iterateEvents()]` | 每次审批 | 整份会话 | run8 约 1.3 GB |
| 每次请求对每个 surface 条目 `readEvents(seq, seq + 1)` | 每次请求 | 随条目数增长 | run8 约 480 MB |
| 子 Agent 面板每秒 `inspectSessionEvents` | 每秒 | 整份会话 | run8 约 340 MB |
| 每个工具参数片段都把已收到的参数整段重新 JSON 修复解析 | 每个片段 | 随参数长度增长（O(n²)） | run8 约 1.9 GB |

这里有两个容易忽视的放大器：

1. **内存窗口。** 日志只在内存里留最近 512 条或 4 MB，更早的事件读一次就要从文件 `JSON.parse` 一次，再深拷贝一次。所以「整份读」在短会话里只是遍历数组；会话一长，就变成整份解析文件。
2. **「只读一条」也可能是全量。** `readEvents(seq, seq + 1)` 看上去很便宜，但放在 `entries.flatMap` 里，就等于把整份对话逐条从文件读一遍。

## 稳定的做法

- **增量读：** 记住上次读到的 `seq`，下次只读 `eventsAfter(seq)`。
- **追加时顺手维护：** 要「某类事件的列表」，就在 append 和加载时维护一份小索引。不要等到用的时候再扫描。
- **用已有的视图：** 对话内容用 `journal.surface`，不要读原始事件再推一遍。
- **刚解析出来的对象不再拷贝：** 只冻结。深拷贝只在信任边界做一次。
- **流式片段只转发增量，** 不要每片都把累计结果重算一遍。

完整规则见 [性能与内存约定](../../coding-standards/perf-memory-conventions.md)。

## 怎么验证

**计时测试不可靠，要数读了多少：**
- 用 `@actspace/session-journal/testing` 的 `syntheticJournal(1_000)` 和 `syntheticJournal(10_000)` 各跑一次同一个操作；
- 比较 `history.eventsRead`，应该相等或者只差常数；
- 修 bug 时先让这个测试在旧代码上失败，再去修。

**实机按函数看分配：**
- 用 [内存采样工具](../../tools/heap-monitor/README.md) 录一轮，`analyze.mjs top` 看谁分配多，`callers` 查是谁调的；
- 两轮工作量不同时（时长、请求数、审批次数），不比合计，只比具体函数。

`pnpm check:hot-path-reads` 会拦住新增的整份读写法。但它只认得出写法，认不出「这段代码在高频路径上」，后者还要靠评审。

## 自检

1. 会话长 10 倍时，这段代码的工作量会不会也变成 10 倍？
2. 它一次会话会跑多少次？是每次请求、每个片段、每秒一次，还是只在打开会话时跑一次？
3. 循环里的 `readEvents` 读的是内存里的事件，还是要从文件解析？
