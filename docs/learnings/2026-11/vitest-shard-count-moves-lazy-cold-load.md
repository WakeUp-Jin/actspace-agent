# 改 vitest 的分片数，会换掉每一片里替懒加载页面付冷转译的那条用例

桌面端测试从两片加到三片后，`host-feedback.test.tsx` 里一条从没失败过的用例在 CI 上超时：点「连接远端机器…」之后用 `findByRole` 等设置页的标题，1 秒内没等到。本地把三片各跑几遍全是绿的。结论：一次 vitest 运行里，每个 `React.lazy` 页面的整棵模块树只冷转译一次，这笔时间落在这次运行里第一个打开它的用例的那一次 `findBy*` 等待里；谁是第一个由分片决定，片数一改就换人。本地复现不了，是因为 vitest 记着上一次的结果，文件顺序和 CI 不一样。

关联：`docs/histories/2026-11/20261114-0215-ci-speedup-round2.md`、`docs/exec-runs/20261113-ci-speedup-round2/execution-summary.md`。

## 为什么会这样

三件事叠在一起。

**转译一次运行只做一次，求值每个测试文件都做。** vitest 给每个测试文件一个隔离的 worker，模块要重新求值；但 vite 的转译结果缓存在主进程里，一次运行内所有 worker 共用。一个页面的模块树第一次被加载时要逐个文件转译，之后别的测试文件再加载它只需要求值。

**懒加载把这笔时间从收集阶段挪进了用例。** 静态 import 的模块在收集测试时转译，不占用例的时间。`lazy-pages.tsx` 里 `React.lazy` 后面的页面（设置、轨迹视图、扩展等）要到用例里点开时才 import，冷转译正好落在点开之后那一次 `findBy*` 里，而 testing-library 的 `findBy*` 默认只等 1 秒。

同一条用例里等设置页标题的那一次 `findByRole`，实测：

| 这条用例在它那一片里 | 本地 4 核 | 本地限到 2 核 |
|---|---|---|
| 不是第一个打开设置的 | 122 ms | 217 ms |
| 是第一个打开设置的 | 534 ms | 843 ms |

CI 的 runner 比本地 4 核慢 1.4–2.5 倍，同一次运行里不同 runner 之间还能差出一倍，「是第一个」的那一行很容易越过 1 秒。

**谁是第一个，由分片和文件顺序决定。** `--shard` 按文件路径的哈希分配，片数一变，每个文件同片的邻居全换；片内的顺序在没有结果缓存时按文件大小从大到小。两片时 `host-feedback.test.tsx` 排在它那一片的第 66 个开始，前面已经有别的文件打开过设置；三片时它是 2/3 片里第一个打开设置的。

那条用例在 CI 上的耗时：

```text
两片              324 / 384 / 411 ms
三片              794 ms            通过
三片              1282 ms           慢 runner，等待超过 1 s，失败
三片，放宽等待后  1141 / 1283 ms    通过
```

同一次改片数还让另外两条等轨迹视图的用例变成了「第一个」（其中一条从 500–746 ms 涨到 1116–1315 ms，只是还没失败），原来付这笔时间的用例则变快了（647 → 323 ms）。

这不是第一次。上一轮把桌面端测试从一个 job 拆成两片时，`workbench-responsive.test.tsx` 里打开设置的等待就超时过，当时把那一处改成 10 秒并写了注释，但没有记下「再改片数还会换一条」，这一轮又踩了一次。

## 稳定的做法

- 跨 `React.lazy` 边界的等待显式给上限，旁边注明等的是哪个懒加载页面：

  ```ts
  // SettingsPage 是 React.lazy：……
  await screen.findByRole("heading", { name: "Agent 服务器" }, { timeout: 10_000 });
  ```

  断言没有变，只是不再把「转译这棵树要多久」算进 1 秒里。同一个文件里多处等同一个页面时抽一个 helper（`workbench-responsive.test.tsx` 的 `findSettingsBackButton`、`findTrajectoryView`），不依赖文件内用例的先后。
- 改片数之后按下一节的办法找一遍新的「第一个」。会改变文件归属或先后的其它改动同理：加 project、换 sequencer、大批增删测试文件。
- 没有采用全局调大 `asyncUtilTimeout`：它会改变两千多条 renderer 用例每一次等待的上限，真失败时每条都要多等。

## 怎么验证

- **先删掉 vitest 的结果缓存**（`apps/desktop` 下的 `node_modules/.vite/vitest`），而且每跑一轮都要再删一次。有这份缓存时，vitest 把上次失败的文件排在最前、其余按上次耗时从长到短；CI 上没有它，按文件大小排。两种顺序下「第一个」不是同一个文件，带着缓存跑出来的全绿说明不了 CI。
- 新旧片数各把全部分片跑一遍，带 `--reporter=json --outputFile.json=<文件>`，逐条比较用例耗时（各跑两轮取较小值去噪）。变慢 150 ms 以上的就是新的「第一个」：这次 2966 条共有用例里正好三条，同时能看到原来的「第一个」变快。
- 用 `taskset -c 0,1` 把 vitest 限到两个核、`--maxWorkers=3` 保持和 CI 一样的 worker 数，模拟慢 runner。放宽之前那条用例三轮里有一轮超时（963 / 1165 / 996 ms）；放宽之后三轮是 977 / 990 / 1248 ms，都通过。
- `vitest list --shard=…` 不按分片过滤，查某个文件落在哪一片要看 json 报告里的文件清单。

## 自检

- 这条用例等的元素在不在 `React.lazy` 或别的动态 import 后面？在的话，那次等待有没有显式上限？
- 改了片数、project 或文件顺序之后，有没有在删掉结果缓存的前提下比过新旧每条用例的耗时？
- CI 上一条 `findBy*` 超时而本地复现不了时，本地跑之前删过 vitest 的结果缓存吗？
