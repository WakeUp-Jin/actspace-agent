# runner 镜像换版的几天里新旧并存：CI 的红绿或耗时变了，先按镜像版本分组再归因

CI 提速第二轮的六次推送里，`包测试` 有两次红在同一条用例上：`packages/shell/tool-shell/src/test/node-ports.test.ts` 里一条 400 ms 时限的用例。先怀疑这一轮自己改的分片和排法，再怀疑同期合入的另一个 PR，都不对。把手头的日志按 runner 镜像版本分组后，旧镜像上 15 次全过，新镜像上 7 次失败 5 次。结论：`ubuntu-latest` 不是一个固定的环境，镜像换版的几天里新旧版本同时在发，连同一次运行的几个 job 都会分到不同版本；这几天里做的「改动前后」对比混着「镜像前后」，要先按镜像版本分组，再谈是谁的改动。

关联：`docs/histories/2026-11/20261114-0215-ci-speedup-round2.md`、`docs/exec-runs/20261113-ci-speedup-round2/execution-process.md`（步骤 7、16）。

## 为什么会这样

GitHub 托管 runner 的标签指向的是一个镜像系列。镜像定期出新版，新版是分批铺开的，铺开期间同一个标签既发旧版也发新版，哪个 job 拿到哪一版，仓库这边控制不了。

这次看到的经过（`ubuntu-latest` 指向 `ubuntu-26.04`）：

```text
11-11、11-12   148 个 job 全是 20261101.186.1
11-13          176 个 job：20261101.186.1 59 个，20261111.196.1 103 个，20261111.82.6 14 个
11-14 凌晨     26 个 job：20261101.186.1 2 个，20261111.196.1 22 个，20261111.82.6 2 个
```

同一次运行里也是混的：这个 PR 六轮 `ci.yml` 各十个 job，分到旧版的分别是 4、4、4、0、5、1 个。

新旧镜像之间变了两样和这个仓库有关的东西，各引出一个问题。

**预装的工具版本变了。** `go.mod` 只写到 `1.26` 时，`setup-go` 用镜像里预装的那一版 Go，并把补丁版本算进缓存 key。旧镜像是 1.26.10，新镜像是 1.26.11。Browser Bridge 的 Go 缓存第一轮在新镜像上存了一份，第二轮分到旧镜像，key 不同，又冷跑了一次；之后四轮都分到新镜像才连续命中。

**起子进程变慢了。** `tool-shell` 的测试会打印它跑的每条命令的耗时，同一组三条命令的中位数从 168 / 135 / 132 ms 变成 216 / 218 / 219 ms。那条用例要求 `sleep 0.2; printf finished` 在 400 ms 内跑完，它的耗时大致是起命令的开销加 0.2 s 的 sleep：旧镜像上 340–370 ms，新镜像上 420–470 ms。余量本来只有三十到六十毫秒，换一版镜像就没了。

第二个问题被归错了两次因，因为每一步看上去都说得通：

- 第二轮红了，当成既有的偶发竞态，推测是分片之后同一台机器上争抢更多，把那一片同时跑的包数降到 2。
- 第三到第五轮是绿的，第六轮又红在同一条用例上。先怀疑这一轮改的排法让它失去了独占机器的那一段，再怀疑同期合入的一个改了子智能体的 PR。

按镜像版本排出来是这样（第 2 片，时间上限用例）：

| 轮次 | 分到的镜像 | 结果 |
|---|---|---|
| 第二轮 | `20261111.196.1` | 失败 |
| 第三轮 | `20261101.186.1` | 通过，728 ms |
| 第四轮 | `20261111.82.6` | 通过，790 ms |
| 第五轮 | `20261101.186.1` | 通过，805 ms |
| 第六轮 | `20261111.196.1` | 失败 |

中间绿的三轮没有一轮分到 `20261111.196.1`。镜像是随机分的，所以失败看上去也是随机的，很自然就归到了「偶发」上；而「偶发」这个解释一旦接受，就不会再去找它为什么恰好从这两天开始。

其实第二轮已经有线索：Browser Bridge 的缓存 key 里 Go 的补丁版本在两轮之间变了，当时记了一句「镜像在滚动更新」，没有想到同一次运行里的测试 job 也在新旧镜像之间跳。

## 稳定的做法

- CI 上某条用例开始随机失败、某一步的耗时变了、某个缓存不命中了，先从 job 日志里取出镜像版本，把手头的样本按它分组。分组之后一边全过、一边多数失败，就不用再查自己的改动。
- 样本不要只取自己的 PR。同期 `main` 和别的分支的运行没有带你的改动，是现成的对照组。这次起决定作用的一条证据是：`main` 最新提交自己的运行，在新镜像上红在同一条用例。
- 分组用两个维度的表：行是镜像版本，列是有没有带自己的改动。失败跟着行走是镜像，跟着列走才是改动。

  | 镜像版本 | 改动前的排法 | 这个 PR 的排法 |
  |---|---|---|
  | `20261101.186.1` | 13 次都通过 | 2 次都通过 |
  | `20261111.196.1` | 4 次失败 3 次 | 2 次都失败 |

- key 或行为跟着镜像预装软件走的地方，换版期间会在两个值之间来回跳。要么接受每个值各冷跑一次，要么把版本固定到补丁号、以后自己跟着升。这个仓库选的是前者，写在 `docs/CICD.md` 的 Browser Bridge 一段。

## 怎么验证

- 镜像版本在每个 job 日志的开头。有两行 `Version:`，要的是 `Runner Image` 分组里的那一行；上面 `Runner Image Provisioner` 分组里的是另一个组件的版本，这次它分不开 `20261111.196.1` 和 `20261111.82.6`。

  ```text
  ##[group]Runner Image Provisioner
  Hosted Compute Agent
  Version: 20261103.629
  …
  ##[group]Runner Image
  Image: ubuntu-26.04
  Version: 20261111.196.1
  ```

- 日志用 `gh api repos/<owner>/<repo>/actions/jobs/<job id>/logs` 拉，只看开头二十行就够。job id 从 `gh run view <run id> --json jobs` 里取。
- 看时间敏感的用例时，比通过与否更细的读数是用例自己的耗时：这条用例通过时在旧镜像上是 694–805 ms，新镜像上是 790–800 ms，带了修复之后分别是 722 ms 和 798–838 ms。同一条用例在两版镜像上差出一截，说明变的是环境。

## 自检

- 这条失败或这个耗时变化，在同期没有带我的改动的运行里有没有出现？
- 手头的样本各是哪个镜像版本？按版本分组之后，结论还成立吗？
- 这一步用到的工具版本和缓存 key，是仓库里固定的，还是跟着镜像预装的走？
