## 原因与已经排除的解释

- **U-06 已定位**：`usage-rollups.ts/searchMetricsSource` 对命中标题的活动明细重新排序、聚合。现有全局rollup没有Session维度，无法直接回答任意标题选中的Session集合。索引只缩小候选集；命中巨型Session时，聚合成本仍与其全部历史成正比。
- **U-01 尚未完全归因**：35,000新增事件要经过Provider解析、Runtime校验、跨线程传输、SQL关联与多表写入。原生采样同时看到序列化/SQL执行/WAL写入；目前不能声称传输、投影或checkpoint中的某一个解释了全部耗时。后续须完成互不重叠的阶段计时。
- **发布限制已确认**：`read-model-sync.ts/publish` 仍在一个Session事务内复制、重算汇总和清理。C-09修复重复扫描，但每256行yield只是发送存活心跳；Worker串行消息链仍不能让另一查询插入该事务，不等于批次公平调度已全部实现。
- C-11只让有界普通追加使用MEMORY临时空间；重建/metadata/查询仍FILE。C-12移除私有building表的七个页面索引，保留Session/身份索引和发布表查询索引。这两项不改变统计语义；77条后端回归通过，但U-01未达标。

原型只使用独立测试库，不修改Session格式、不让SQLite进入Agent Loop或授权路径，不替换当前应用生产读路径。

1. **标题聚合原型**：增加按Session、时间桶和统计维度维护的派生汇总；标题搜索先选Session，再对汇总求和，部分时间边界仍回读精确明细。必须验证null费用、多币种、混合维度、重试替换、删除、reset边界与当前结果完全等价，并同时量测额外写入/磁盘成本。若追加性能反而失守，不接入生产。
2. **追加链路原型**：先把读取/codec校验/传输/投影/提交分别计时；比较有界批量投影和减少重复事件传输的方案。任何Provider/Runtime查询端口变化另写明确契约，继续保证codec校验、来源替换检测、取消、背压与内存上限。不能把未经验证的直接读文件绕行作为优化。
3. **发布原型**：比较预构建完整派生代后以短事务切换可见代、旧代在无读者后分批回收的方式，消除当前巨型复制发布事务。汇总、FTS、run去重必须随同一代切换，不能只切明细表。

三个原型分别给出正确性、20次延迟分布、峰值内存/磁盘和退出恢复证据。只有选择结果明确后，再把表/索引、schema迁移与文件修改范围写入正式设计和执行计划。不能预先承诺三个方向都需要实施或一定能达到250ms。
