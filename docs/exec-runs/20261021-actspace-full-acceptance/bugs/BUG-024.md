## 复现与实际结果

1. 在隔离 profile 放入自己验收产生的真实 explore 父子 Journal 副本；一个子保留原 ID，另一个仅重映射 session ID。不是在用户原数据上操作。
2. 通过公开 `sessions.archive({ sessionId, archived: true })` 归档两个 delegation 子及两个普通会话。
3. 真实 UI 进入设置 → 归档会话，显示两条 `New chat / 1 次运行 / 恢复`，同页下方显示两条 `F4PARENT` 普通会话。
4. 对账 `sessions.list({ archived: true })`：前两条 ID 分别是 `32fd99f3-82ea-4527-8c49-aab465e51f6e` 和 `e52ae2a2-c12f-4dd0-b9cb-9bb27f7a9c86`，均 `isChildSession=true`；后两条为普通会话。

预期依据：[本轮计划 F4-01](../../../exec-plans/active/20261021-actspace-full-acceptance.md)明确普通侧栏、分页、搜索、归档筛选和快速打开不混入只读子会话。实际普通分页可排除这两个子，归档入口却将它们作为普通可恢复会话展示。

这是一轮受控归档状态下两个子项的观察，未证明用户通过正常 UI 自然归档子会话的完整触发路线，也未点击“恢复”验证后续行为。公开 API 返回的 `accessState=read-write` 不能消除它们的 delegation 身份；不据该字段扩大为可写子会话缺陷。

## 当前推荐方案（仅记录）

建议先明确普通可恢复会话的共享分类，再统一归档列表与普通分页/搜索的过滤。区分 delegation、普通 fork 和 side-chat，保留来源事实；不要笼统过滤所有非空 lineage，否则会延续 BUG-022 的普通分叉不可见问题。检查服务端列表语义与各客户端消费者后确定过滤归属，避免只在一个设置组件临时隐藏。

回归：有/无已归档子会话、普通会话归档/恢复、普通 fork、侧边对话、旧派生索引重建、本地/远端返回值和归档数量。原生归档触发路线及恢复子项行为尚未验证，作为后续定位范围，不写成既有影响。
