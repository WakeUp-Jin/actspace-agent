## 复现步骤与预期

1. 启动受控持续运行任务 `FIXTURE_HOLD QUEUE_ANCHOR`。
2. 真实 UI 连续排入 `QM FIRST`、`QM SECOND`、`QM THIRD`，顺序为 FIRST → SECOND → THIRD。
3. 对第二条点“引导”：SECOND 显示在顶部，绿色呼吸点与“下一步读取 / 撤回”可见。
4. 在模型读取前点“撤回”，等待 DOM 稳定。
5. 停止当前运行，点“继续发送”，对账实际请求顺序。

预期：[中间消息区规范](../../../design-docs/frontend/front-中间消息区规范.md)“撤回或回合结束时还没被读到的引导，回到队首”，所以撤回后应为 SECOND → FIRST → THIRD。

实际：DOM 恢复 FIRST → SECOND → THIRD；实际 HTTP 请求也依次 FIRST、SECOND、THIRD，各一次。绿点、下一步读取、停止后暂停和显式继续在这条路线通过，不能因此签收队首要求。本记录确认一次完整三项队列实验，不称所有状态或重启后均已复现。

## 当前推荐方案（仅记录）

建议由 Host TaskLedger 将“撤回尚未领取的引导并放到普通队首”定义为原子持久化语义，保证 UI 排序、下一次领取与重放结果一致。沿用当前 revision/串行化约束，核对旧 Journal 兼容及多个引导项的相对顺序。不要只在 renderer prepend：那会与真实调度顺序不一致，也无法覆盖 Web、重启和其他客户端。

需要后续核对人工撤回、Run 结束退回及引导拒绝是否应共用同一语义；这些是方案的待验证范围，不是已经证实的多个缺陷。回归至少包含中间/首尾项、多个引导、领取竞争、停止/失败/暂停、显式继续、重启重放、过期 revision 和 Desktop/Web 的顺序对账。
