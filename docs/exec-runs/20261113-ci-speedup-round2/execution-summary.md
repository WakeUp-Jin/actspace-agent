读这张表要注意七点：

- 同一步骤在不同 runner 上能差 1.5–2 倍（基线里没改过的 Typecheck 是 25–53 s）。八轮的数字是范围，不是定值；`Lint 与类型检查`、`官网` 这类没怎么改的 job 忽高忽低就是这个原因。

- PR 的全部检查什么时候跑完，由 CodeQL 的 JS 分析（98–144 s）和 `ci.yml` 最慢的 job（103–133 s）共同决定。
- 第七轮的 142 s 是排队排出来的：另一条 PR 早 71 s 推送，两边加起来超过了账户同时能跑的 20 个 job，最后跑完的那个 job 先等了 46 s。那一轮最慢的 job 是 112 s，不排队的话整次运行约 114 s。
- 第八轮的 107 s 不受那一片失败的影响：最后跑完的是通过了的 `桌面端测试 (2/3)`（103 s），失败的那一片在第 72 s 就结束了。受影响的只有十个 job 的时长之和。

## 人工验证指引

### 必须验证

1. **合并后第一次 `main` 运行里的 `构建`**
   - 验证方式：Actions 页打开那次 `CI` 运行的 `构建` job。
   - 预期结果：`Build` 被跳过；`actions/setup-go`、`Package desktop (smoke)`、`Build CLI and Web` 三步都执行并通过。job 时长应明显短于改动前的 253–305 s。

2. **只改文档的 PR 不触发 `ci.yml`，也不卡合并**
   - 验证方式：开一个只改 `docs/` 下某个普通文档的 PR。
   - 预期结果：只有 `仓库基础检查` 运行，没有处于 pending / Expected 的检查，审批后可以合并。再改一下 `docs/roadmap.md`，`CI` 应该被触发（官网读它）。

3. **`main` 上只改文档的 push 不触发 `ci.yml`**
   - 验证方式：上面那个 PR 合并后看 Actions 页。
   - 预期结果：这个提交只有 `仓库基础检查` 的运行（CodeQL 原来就不被纯文档提交触发）。

### 建议验证

1. **Browser Bridge 的缓存在 `main` 上保存并被 PR 读到**
   - 验证方式：合并后第二次 `main` 运行、以及之后任意一个 PR 里，看 `Browser Bridge` job 三个步骤的耗时。
   - 预期结果：`Browser Bridge Go tests` 和 `Browser Bridge cross-compile` 各 1–5 s；`Browser Bridge contract checks` 几秒到十几秒，看这台 runner 第一次从磁盘读 Go 工具链的快慢。runner 镜像升级 Go 补丁版本的那几天会有一两次三步合计回到三四十秒，属于正常。

2. **11-18 之后 `Browser Bridge` 的缓存还管用**
   - 验证方式：2026-11-18 之后任意一个 PR 或 `main` 运行里，看 `Browser Bridge` 的 `Browser Bridge Go tests` 和 `Browser Bridge cross-compile` 两步。前提是那时用的还是 11-13 存的缓存：`setup-go` 那一步日志里是 `Cache hit`，Go 的版本和 `browser-bridge` 下的 `go.work`、两个 `go.mod` 都没变过。
   - 预期结果：两步仍然各 1–5 s。如果回到 5 s 和 10 s 以上，说明 `Keep restored Go cache entries from being trimmed` 那一步没起作用。

3. **下一次发版**
   - 验证方式：打 `v*` tag 后看 `发布` 工作流四个平台。
   - 预期结果：Linux 命中 pnpm 和 Go 缓存；macOS / Windows 不恢复也不保存缓存；darwin-x64 的第一步 `关闭 Spotlight 索引` 输出三行 `Indexing disabled.`（这一步即使失败也不会让 job 失败，要点开看）；各平台时长在以前的范围内。

4. **缓存占用回落**
   - 验证方式：`gh api repos/WakeUp-Jin/actspace-agent/actions/cache/usage`，或 Actions › Caches 页。
   - 预期结果：现在是 10.5 GB，其中约 4.6 GB 是各个 PR 以前在 macOS / Windows 上存的 pnpm store 和 Go 缓存；它们 7 天没人读就会被清掉。之后这三个平台只有改到打包文件的 PR 会各存一份 14 MB 的 Go 缓存。

## 已知风险和遗留事项

- **`包测试` 在 #83 合入前会随机变红，而且会越来越常见。** 八轮里第一、二、六、八轮的 `包测试 (2/2)` 是红的。三种失败都不是本计划引入的，#83 都在修，本计划没有改这些用例，避免和它冲突：
  - `packages/shell/tool-shell` 的 `node-ports.test.ts` 里一条 400 ms 时限的用例（第二、六、八轮）。它和 runner 镜像有关：`ubuntu-26.04` 的镜像 11-13 起在换版本，新旧同时在发。旧镜像上 15 次都通过；新镜像上 10 次失败 6 次，改动前的排法在新镜像上也是 5 次失败 3 次，包括 `main` 最新提交自己的运行。新镜像上起一条 bash 命令多 50–130 ms，时限没有余量。分片、排法、并发都不是原因，CI 这一侧没有可调的。
  - `packages/subagent` 的 `external.test.ts`（第一轮）和 `SessionHandle is closed` 的未处理错误：#90 合入后才出现的竞态，和镜像无关。第 2 片同时只跑 2 个包之后的七轮里它们没有再出现（同期默认并发的 9 次里出现 5 次；本地 22 轮对比是 5 次对 0 次），但七轮里有三轮在上面那条用例上提前停了，不能当成已经消掉。
  - #90 合入后、没带 #83 修复的 `包测试`，`main` 和别的分支 8 次里红了 7 次。11-14 手头的 26 个 `ubuntu-26.04` job 里 22 个已经是新镜像。
- **账户同时只能跑 20 个 job，本计划让一次全部触发从 18 个变成 21 个。** GitHub 的 Free 计划同时最多 20 个 job（其中 macOS 5 个），所有仓库和工作流共享。一般的代码 PR 是 13–15 个 job（改动前 11–12 个），碰不到上限；同时改到打包脚本和依赖清单的 PR（本 PR 就是）会有一个 job 多等十几秒，八轮里除第七轮外每轮一个，等了 10–17 s。两个 PR 在一两分钟内先后推送时后一个要排队：第七轮 7 个 job 各等了 17–50 s，整次运行因此从约 114 s 变成 142 s。没有为此减 job，理由见计划的决策记录「不为并发上限减 job」。
- **`Browser Bridge` 的提速有一半不是本计划换来的。** 基线的 70 s 里 `go test` 和交叉编译每次从头编：它和 `build` 共用的缓存 key 上，那五天存着的是 `build` 的 14 MB。11-13 runner 镜像换了 Go 的补丁版本，key 跟着换，这回存下的是全的，没带本计划改动的运行也降到 40–58 s（6 次，中位 52 s）。本计划实际换来的是四件事：
  - 这个 job 有自己的 key，不会再被别的 job 存的那份占住。
  - registry 检查的 `go run` 用上了缓存：改动前 6–15 s（中位 11.5 s），之后 0.2–12 s（五次，中位 1.3 s）。job 里第一条 go 命令要付从磁盘读 Go 工具链的时间，慢的 runner 上这部分省不下来，第八轮就是 12 s。
  - locator fixture 少等 10 s。
  - 缓存放过 5 天之后不会被 go 清掉，见下一条。
- **刷新 Go 缓存时间的那一步还没有在 CI 上真正起过作用。** go 每次构建结束时会删掉 5 天没用过的缓存条目，而恢复出来的条目带着保存那天的修改时间。现有的缓存是 11-13 存的，11-18 之前刷不刷新没有差别。依据是对照实验（执行过程步骤 19）：条目放旧之后 `go test` 和交叉编译合计多 13 s，刷新之后和新缓存一样。`build` 和发布工作流每个 job 只跑一条 go 命令，不受影响，没有加。
- **再改桌面端测试的片数要重新找「第一个」。** 每一片里第一个打开懒加载页面的用例要替整棵模块树付冷转译，片数一改就换一条。办法见 `docs/learnings/2026-11/vitest-shard-count-moves-lazy-cold-load.md`。
- **与 #83 有文本冲突。** 冲突在 `ci.yml` 的 `on:` 块、job 的 `name:` 行和 `docs/CICD.md`。#83 先合的话：本 PR 的 `ci.yml` 去掉 `pull_request.paths`，把收窄后的规则搬进它的 `变更范围` job，`push.paths` 保留；本 PR 先合的话反过来由 #83 处理。两边都没有改 job id。
- **`main` 上只改文档的提交没有 `ci.yml` 的运行。** 要看它的代码是否通过，看它前面最近一个有运行的提交。一次改动超过 300 个文件、排在前面的又全是文档时工作流不会触发，要手动运行。
- **Browser Bridge 的缓存 key 带 Go 的补丁版本。** `go.mod` 只写到 `1.26`，runner 镜像滚动升级的几天里新旧两版并存，各要冷跑一次。把版本固定到补丁号可以避免，但之后要有人跟着升，没有做。
- **发布工作流的时长仍然主要看分到哪台 macOS runner。** 八轮里 darwin-x64 是 358–790 s，其中 desktop 构建 126–271 s，另有两轮各排了五分钟的队才拿到 runner。本计划对它的三处改动都小于这个波动：
  - pnpm store 不恢复没有代价：同机对照里「还原加安装」76 s，「现下载安装」79.5 s。
  - Go 缓存在 PR 上命中一次省 7–18 s（改动前 13 次运行按命中与否分组的中位数；第六轮三个平台实测省了 18 / 5 / 11 s）。命中也不保证快：第八轮 Windows 命中了，那一段却用了 28 s。发版的 tag 运行读不到它，Go 组件和以前一样从头编。
  - 关 Spotlight 在 Intel 上估计省几十秒，给不出更准的数。实验前定的标准是两个 job 都平均快 10% 以上，实际是 7% 和 17%，有一个没达到。加了这一步之后的三轮 darwin-x64 是 443 / 358 / 430 s，之前五轮是 536–790 s；但没加这一步的 darwin-arm64 这三轮也比之前快（中位 252 s 对 325 s），而且这三轮都在周六凌晨（UTC）、前五轮在周五下午到晚上，只能算旁证。
- **Agent CLI 的进程级测试只在 PR 上跑。** 这个工作流原来就没有 `push: main` 触发，本计划没有改。
- **逐包构建还在。** `构建`、`pnpm package:agent-cli` 和发布的每个平台都要逐包 `clean` 加 `tsc`，CI 上 39–60 s。换成 `tsc -b` 要动发布链，登记在 `docs/exec-plans/tech-debt-tracker.md`。
