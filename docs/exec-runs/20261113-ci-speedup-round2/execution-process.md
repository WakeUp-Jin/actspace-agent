# CI 提速第二轮 — 执行过程

## 基本信息

- **关联计划**：`docs/exec-plans/completed/20261113-ci-speedup-round2.md`
- **执行模式**：夜间（云端 Agent 自主执行，用户不在线）
- **开始时间**：2026-11-13 12:30（UTC，下同）
- **结束时间**：2026-11-14 02:30（执行中途停过一次，11-14 00:47 用户让继续后接着做完）

## 执行时间线

### 步骤 1：基线

- **操作**：用 `gh` 拉仓库最近 50 次工作流运行（2026-11-11 至 11-13）的 job 和步骤时间，共 174 个已完成 job。每个 job 拆成三段：排队（job 创建到开始）、环境准备（checkout、装 pnpm / Node / Go / ripgrep、`pnpm install`、恢复缓存、`build:deps`、CodeQL 初始化）、实际工作（其余步骤）。
- **结果**：各 job 的中位数和从中看出的规律写在计划的「背景」一节。排队中位 2 s；环境准备占 31%、实际工作占 68%；浪费集中在重复构建、串行的脚本测试和两组最长的测试上，不在环境准备上。
- **顺带核对**：
  - 没有任何工作流现场编译工具：ripgrep 是下载预编译包并校验 sha256，其余工具来自 `pnpm install`。
  - 全仓库只有 `release.yml` 用 macOS（每次 2 个 job）和 Windows（1 个）runner，都是产物必须在对应系统上打；lint、依赖审计之类已经全在 Ubuntu 上。
  - 剩下的 `needs` 只有 `release.yml` 的汇总 job 和 `site-pages.yml` 的部署 job，都要下载上游的 artifact；`ci.yml` 各 job 互不 `needs`。
  - 基线里 `包测试` 15 次运行失败 5 次：3 次是 apt 装 ripgrep 时 DNS 失败（已由预编译包那次改动解决），2 次是时间敏感用例偶发失败（`subagent` 的 `external.test.ts`、`tool-shell` 的 `node-ports.test.ts`）。

### 步骤 2：本地连续构建两次

- **操作**：4 核机器、Node 22，对 `pnpm build:deps`、`pnpm build`、Browser Bridge 的三个步骤各连续跑两次并分段计时。
- **结果**：见计划「背景」。`build:deps` 的增量是生效的（第二次里 `tsc -b` 不到 1 s）；`pnpm build` 按设计每次全量，但同一次构建里把同一批包编了两遍；Browser Bridge 的三段 Go 编译都进不了缓存。
- **决定**：不给发布路径加增量（每个包 `build` 先 `clean` 是有意的），只去掉重复的那一遍。

### 步骤 3：触发条件、并发、必需检查、缓存

- **并发**：`ci.yml`、`base-checks.yml` 已经是 PR 上取消旧运行、`main` 上按提交分组不取消。`codeql.yml` 在 `main` 上按分支分组：不取消正在跑的，但同一组只允许一个排队，连续推送时中间那次会被顶掉。
- **路径过滤**：`ci.yml` 只有 `pull_request` 带 `paths-ignore`（`docs/**`、`**/*.md`），`main` 上的 push 不带；`**/*.md` 把 51 个被 CI 读取的 Markdown 也忽略了。
- **必需检查**：读 `main` 的 ruleset，必需检查只有 `仓库基础检查`，它不带路径过滤；所以用工作流级 `paths` 跳过 `ci.yml` 不会留下 pending 的必需检查。
- **缓存**：10.49 GB / 168 条，超过 10 GB 上限。Linux 的 pnpm store 约 5.1 GB（lockfile 每变一次存一份，约 190 MB）；发布工作流在 Windows / macOS 上存的 pnpm store 和 Go 缓存 4.4 GB，只有同一个 PR 的后续推送读得到；CodeQL 的 TRAP 缓存 0.6 GB；`tsc -b` 产物 0.17 GB。

  - `包测试 (2/2)` 失败：`packages/subagent` 的 `external.test.ts` 断言 `expected [] to deeply equal [ 'root' ]`，就是基线里出现过的那个偶发失败。它和第二轮的那条失败是什么时候开始出现的，见步骤 16。

### 步骤 6：第二轮改造

按第一轮的数据试了三件事，两件采用、一件否决：

- **包测试的并发**（`37ae7ecf`，采用）。第一轮 `包测试 (2/2)` 的失败是既有的偶发失败，但分片加 `--no-sort` 之后同一台 runner 上始终有 4 个包在跑，每个包的 vitest 还要开最多 3 个 worker。本地把第 2 片在 pnpm 默认并发和 `--workspace-concurrency=2` 下穿插着各跑 22 次：默认并发有 5 次出现偶发失败（`external.test.ts` 3 次、未处理错误 2 次），并发 2 是 0 次；`tool-shell` 测试自己打印的子进程耗时 p90 从 560 ms 降到 219 ms。本地的代价是第 2 片 35.6 s → 39.6 s、第 1 片 34.1 s → 35.7 s，于是两片都加了。另一个候选 `VITEST_MAX_WORKERS=1` 让第 1 片涨到 47 s，否决。
- **桌面端测试加 worker**（否决）。vitest 默认开「核数 − 1」个 worker。本地给三片加 `--maxWorkers=100%` 各跑两轮，快 2–20%、多数在 10% 上下；刚在包测试上看到把核占满会放大偶发失败，桌面端又有大量依赖定时器和渲染时序的用例，不采用。
- **desktop 的两个 vitest project 各用各的 setup 文件**（`56033b66`，采用）。第一轮日志里 vitest 自报的 setup 时间比 environment 还长。`setupFiles` 写在配置的根上，main 的 98 个 node 环境测试文件每个都加载 renderer 的 setup（jest-dom、React、Radix 的 Tooltip），实际只用得到隔离 git 配置的那几行。拆开后单跑 main project 20.0 s → 12.2 s，通过的文件数和用例数不变（97 个文件通过、1 个跳过；753 个用例通过、4 个跳过）；三片各跑两轮，每片省 2–3 s，合计仍是 309 个文件、2978 个用例。
- **验证**：`pnpm --filter @actspace/desktop typecheck`、`pnpm lint`、`actionlint`、`./scripts/ci.sh` 通过。

### 步骤 8：三片分法引出的等待超时

- **现象**：失败的那条用例在基线（两片）里的耗时是 324 / 384 / 411 ms，第一轮（三片）794 ms，第二轮 1282 ms。两轮都落在 2/3 片，第二轮那台 runner 更慢。
- **定位**：
  - 设置页是 `React.lazy`。vite 的转译结果在一次 vitest 运行里由主进程缓存、各 worker 共用，所以整棵设置模块树的冷转译只由这一片里第一个打开设置的用例承担，而且落在它那一次 `findByRole` 等待里。三片时 `host-feedback.test.tsx` 是 2/3 片里第一个打开设置的文件，两片时它前面已经有别的文件打开过。
  - 第一次在本地对比两片和三片时没有复现：本地留着 vitest 的结果缓存，文件按上次耗时排序；CI 上没有这份缓存，按文件大小排序。删掉缓存、每轮都删，把两片和三片的每一片各跑两轮、带 json reporter 逐条用例比耗时：2966 条共有用例里变慢 150 ms 以上的正好三条——这一条（193 ms → 533 ms），和两条等轨迹视图的（`workbench-responsive` 337 ms → 642 ms、`conversation-view-tooltip` 110 ms → 304 ms）。轨迹视图也是 `React.lazy`。
  - 临时在三处等待前后加计时确认时间确实花在等待上：不是第一个时 52–122 ms，是第一个时 315–534 ms；限到 2 核是 76–217 ms 对 500–843 ms。计时代码看完就还原了。
  - 另外两条在 CI 上还没失败，但 `workbench-responsive` 那条两轮是 1315 ms 和 1116 ms（基线 500–746 ms），里面只有一部分是那次等待，同样在逼近上限。
- **决定**：保留三片，把三条用例里等懒加载页面的等待放宽到 10 s（`c3006e45`），断言不变。上一轮从一个 job 拆成两片时，`workbench-responsive` 里等设置页的那一处就是这样处理的，这次沿用它的写法和数值。没有选的做法和理由在计划的决策记录里。
- **验证**：限到 2 核、3 个 worker、不带结果缓存跑 2/3 和 3/3 片。放宽前三轮里 2/3 片有一轮失败（那条用例 963 / 1165 / 996 ms）；放宽后三轮都通过（977 / 990 / 1248 ms）。限到 1 核、2 个 worker 各跑一轮，三条用例是 1353 / 1012 / 1263 ms，都通过。不限核把三片各跑一轮：309 个文件、2978 个用例，2970 通过、8 跳过，和改动前一样。`pnpm --filter @actspace/desktop typecheck`、`pnpm lint` 通过。

### 步骤 9：包测试第 1 片改回默认并发

- **现象**：写文档时回头核对第二轮的数据，发现「降到 2 个每片只多几秒」这句话和 CI 对不上：`包测试 (1/2)` 的 Test 步骤从 50 s 涨到 74 s，而这句话已经写进了 `ci.yml` 的注释、`docs/CICD.md` 和计划。
- **定位**：从两轮的日志里取每个包 vitest 自报的耗时和结束时刻。第 1 片在并发 2 下各包耗时之和只从 144.1 s 降到 116.5 s；两条队各自的长度已经接近 60 s，再加上 `packages/core/runtime`（24 s）按目录名排在最后、第 49 s 才开始，整步是 74 s。同一个 job 的环境准备这一轮是 36 s，上一轮 48 s，不是这台 runner 慢。第 2 片各包快了一倍多，同一批包跑完的时间基本不变。
- **本地复核**：第 1 片用两种并发交替各跑 8 轮，默认并发 33.1–33.6 s、并发 2 是 34.5–35.0 s，都没有偶发失败。本地各包在并发 2 下快了 1.7 倍（各包耗时之和 93.6 s → 54.8 s），刚好抵消排队；CI 上只快了 1.2 倍。这个差别在本地测不出来。
- **决定**：`--workspace-concurrency=2` 只留在第 2 片（`8c8c6c91`），三处文字改成和实测一致。已知的时间敏感用例都在第 2 片的包里；第 1 片回到的是第一轮在 CI 上跑过的配置。
- **验证**：从 `ci.yml` 里取出这一步的脚本，在本地对两片各跑一遍：第 1 片启动 22 个包、第 2 片 50 个，合起来还是 72 个。`actionlint`、`./scripts/check-action-pinning.sh` 通过。

### 步骤 10：第三轮观察

### 步骤 15：在同一台 macOS runner 上做对照

步骤 13 留下的问题只看历史数据分不清，要在同一台 runner 上比。做法是开一条临时分支，上面只多一个工作流文件，`on.push.branches` 只写这条分支：推送只触发它自己，不进 PR，也不进 `main`。做完后分支已删除，三次运行的记录留在 Actions 页（`gh` 只读，删不了）。

**实验一：pnpm store 是恢复的还是现下载的，影不影响后面的构建。** 每个 job 先现下载安装一遍，把 store 打成 tar（720 MB）；然后做四轮，每轮清掉工作区和 store，「恢复」的那轮先解 tar 还原 store，「现下载」的那轮不还原，再安装依赖、构建 desktop。两个 `macos-15-intel` 的 job 顺序相反，另有一个 `macos-latest` 的 job。还原用的是本地解 tar，不含从 Actions 缓存下载的时间，是真实恢复的下限。

| job | 第 1 轮 | 第 2 轮 | 第 3 轮 | 第 4 轮 |
|---|---|---|---|---|
| macos-15-intel（先恢复） | 恢复：还原 55 s + 安装 44 s，构建 311 s | 现下载：安装 100 s，构建 291 s | 恢复：34 s + 39 s，构建 243 s | 现下载：77 s，构建 223 s |
| macos-15-intel（先现下载） | 现下载：71 s，构建 236 s | 恢复：38 s + 36 s，构建 222 s | 现下载：70 s，构建 202 s | 恢复：29 s + 28 s，构建 174 s |
| macos-latest（先现下载） | 现下载：23 s，构建 77 s | 恢复：11 s + 12 s，构建 104 s | 现下载：25 s，构建 84 s | 恢复：11 s + 13 s，构建 86 s |

- x64 上构建的平均值：恢复 237.5 s，现下载 238.0 s。store 怎么来的不影响构建；步骤 13 里 136 s 对 209 s 的差别来自日期和 runner。arm64 上各两次，恢复 95 s、现下载 80.5 s，差在一次 104 s 上，看不出规律。
- 「还原加安装」对「现下载安装」：x64 上 76 s 对 79.5 s，arm64 上 23.5 s 对 24 s。恢复 pnpm store 在 macOS 上不省时间，关掉它没有代价。步骤 13 里 darwin-x64 那 13 s 的差别也来自日期。
- 意外的发现：两个 x64 的 job 里，构建都是一轮比一轮快（311 → 291 → 243 → 223 s，236 → 222 → 202 → 174 s），安装和解 tar 也一样；arm64 上没有这个趋势。发布 job 的 desktop 构建在 job 开始后两分钟左右，正落在最慢的那一段。

**实验二：job 开头那几分钟是谁在占 CPU。** 两个 `macos-15-intel` 的 job，各自安装依赖后连续构建四次（不清工作区），后台每 20 s 用 `top` 记一次最占 CPU 的 25 个进程；其中一个 job 一开始先执行 `sudo mdutil -a -i off` 关掉 Spotlight 索引。

- 两台 runner 都是刚开机的虚拟机：job 开始时分别开机 7 分钟和 3.5 分钟，一分钟负载 5.1 和 20.7（4 核）。三个卷的 Spotlight 索引都开着，job 开始那一刻 `mds`、`mds_stores` 和几个 `mdworker_shared` 合计占 118% 和 253% 的 CPU。
- 不关索引的 job：安装 65 s，四次构建 144 / 149 / 138 / 122 s。安装期间 Spotlight 的进程占 49–149%，构建期间 0–115%、平均约 27%；`mds` 和 `mds_stores` 这十分钟里累计多用了 90 s 的 CPU 时间，另有 150 个先后出现的 `mdworker` 进程。
- 关掉索引的 job：安装 53 s，四次构建 122 / 112 / 113 / 107 s。执行 `mdutil` 之后 `mds_stores` 不再出现，Spotlight 的进程在之后的采样里多数不到 1%，最高 18%。
- 同样是装完依赖后的第一次构建，实验一（前一天 18:45 UTC 前后）是 311 s 和 236 s，这里（00:54 UTC）不关索引也只要 144 s：Intel 的 macOS runner 在不同时段、不同机器上能差一倍，比 Spotlight 的影响大得多。
- 关掉索引的那个 job 每一段都快 12–25%，但这是两台不同的 runner 各一个样本，还不能算数，所以做了实验三。

**实验三：同一台 runner 上交替开、关索引。** 四个 job：`macos-15-intel` 两个、`macos-latest`（arm64，3 核）两个。每个 job 装完依赖后连续构建六次，每次构建前用 `mdutil -a -i on` 或 `off` 切一次索引，同一种 runner 的两个 job 顺序相反；另外记下每次构建期间 `mds` 和 `mds_stores` 两个常驻进程多用了多少 CPU 时间。安装依赖那一段四个 job 都没动索引，是 runner 的自然状态。

|---|---|---|---|---|---|---|---|
| macos-15-intel（先关） | 60 s | 关 110 s | 开 146 s | 关 126 s | 开 106 s | 关 94 s | 开 101 s |
| macos-15-intel（先开） | 67 s | 开 163 s | 关 122 s | 开 153 s | 关 111 s | 开 103 s | 关 116 s |
| macos-latest（先关） | 30 s | 关 79 s | 开 104 s | 关 89 s | 开 82 s | 关 86 s | 开 90 s |
| macos-latest（先开） | 29 s | 开 93 s | 关 95 s | 开 97 s | 关 108 s | 开 109 s | 关 97 s |

- Intel 上按平均值算，两个 job 里关掉索引分别快 7%（110.0 s 对 117.7 s）和 17%（116.3 s 对 139.7 s）。差别不是均匀的，集中在 job 的前几分钟：六次「开」的构建里，`mds` 和 `mds_stores` 多用了 10 s 以上 CPU 的有三次（163 / 146 / 153 s，分别多用 73 / 12 / 10 s），每一次都比同一台 runner 上相邻的「关」慢 20–42 s；另外三次（106 / 101 / 103 s，多用 1–3 s）和相邻的「关」比有快有慢（快 20 s 到慢 12 s）。也就是索引有活干的时候构建才慢，追平之后开着也不碍事。
- 自然状态下它正好有活干：`pnpm install` 刚往磁盘上写了约 6 万个文件的 `node_modules`，store 里还有一份。安装依赖期间 Spotlight 的进程在三台 Intel runner 上平均占 0.7–1.1 个核（实验二那台 99%，这里两台 110% 和 67%，一共 4 个核）；紧接着的第一次构建里，没有先关索引的两台是 0.5 和 0.6 个核。其中一台 job 开始时已经开机 14 分钟、负载只有 2.5，照样如此——活是这个 job 自己带来的，不只是开机后的扫尾。
- 把两个实验里干净的样本放在一起（都在 00:54–01:13 UTC，四台不同的 Intel runner）：自然状态下装完依赖后的第一次构建是 144 s 和 163 s，先关掉索引是 122 s 和 110 s；安装依赖自然状态 60–67 s（三台），关掉索引 53 s（一台）。
- 这个实验有一处不干净：索引关过再打开，Spotlight 会起 `mdsync` 和 `mdworker` 重新扫一遍，之后「开」的时候它们合计占 0.4 个核，再关掉 `mdworker` 也还留着 0.2 个核。所以第 4 次以后的「开」和「关」都不是纯粹的状态；它们之间没有差别，说明这种轻量的扫描不拖慢构建，拖慢构建的是 `mds_stores` 和 `mdworker_shared` 在给新文件建索引的那几分钟。
- arm64 上看不出差别：一个 job 是 99.7 s 对 100.0 s，另一个 92.0 s 对 84.7 s（差在一次 104 s 上）；每次构建期间 `mds` 和 `mds_stores` 只多用 0–5 s 的 CPU，安装依赖期间 Spotlight 的进程占 0.2 个核。
- 实验前定的判断标准是：Intel 的两个 job 里关掉索引都平均快 10% 以上，而且不是靠某一次离群值。按平均值算，先关的那个 job 只有 7%，没有达到。仍然采用的依据是上面两条：差别集中在索引确实有活干的那三次，每一次都慢 20–42 s；自然状态下装完依赖后的第一次构建正是这种情况。它能省多少，这里给不出比「几十秒」更准的数。
- **决定**（`5c40e79a`）：发布工作流在 Intel 的 macOS job 最前面加一步 `sudo mdutil -a -i off`，arm64 不加。这一步只是为了快，设成允许失败、限时 1 分钟，失败或卡住都不挡打包。打包脚本只用 `ditto`、`codesign`、`hdiutil create`、`notarytool`，都不依赖 Spotlight；脚本里 `hdiutil` 的重试循环没有动。按上面的数字估算，darwin-x64 的 job 在安装依赖上少约 10 s、desktop 构建上少 20–40 s；组装那一段也是成批地写文件，有没有同样的效果没有测。实际效果见步骤 16。
- 这是本轮最后一个对照实验。Windows runner 上有没有类似的后台扫描（比如 Defender）没有测。

## 遇到的问题

- **问题**：六轮里有三轮 PR 的 CI 是红的：第一轮 `包测试 (2/2)`，第二轮 `包测试 (2/2)` 和 `桌面端测试 (2/3)`，第六轮 `包测试 (2/2)`。
  - **原因**：`包测试` 的三次都是改动前就有的失败（步骤 16）；`桌面端测试` 那次是三片分法引出的（步骤 8）。
  - **应对**：后者修了；前者不在本 PR 里修，由 #83 负责。`gh` 在这个环境里只读，失败的 job 不能重跑，每一轮的红绿只有一次机会。
- **问题**：`host-feedback` 那条用例在 CI 上超时，本地第一次对比两片和三片时没有复现。
  - **原因**：本地留着 vitest 的结果缓存，文件按上次耗时排序；CI 上没有这份缓存，按文件大小排序，哪条用例第一个打开懒加载页面因此不同。
  - **应对**：每轮先删缓存，带 json reporter 逐条用例比耗时（步骤 8）。
- **问题**：两处改动本地验证通过，到 CI 上表现不同：包测试第 1 片的并发 2（步骤 9）和 Browser Bridge 的 `GOCACHE`（步骤 11）。
  - **原因**：前者是本地 4 核机器上各包快了 1.7 倍、刚好抵消排队，CI 上只快 1.2 倍；后者是本地模拟脚本给 `go test` 多带了一个 CI 上没有的环境变量。
  - **应对**：并发这类调整以 CI 的步骤时间为准；验证工作流改动时把 `run` 步骤原样导出来跑，步骤之间只通过 `GITHUB_ENV` 文件传变量。
- **问题**：发布工作流缓存的结论改了两次（`79b7e98a` → `f07401cc` → `7e3142a0`）。
  - **原因**：第一次只拿三次历史运行做对比，恰好都是缓存命中的；补全到十三次后又发现命中与否和日期混在一起，分不开。
  - **应对**：先把历史运行补全并按命中与否分组（步骤 13），再在同一台 runner 上做交替对照（步骤 15）。
- **问题**：分析第六轮的失败时先后归错了两次因：先归到分片和 `--no-sort` 让 `tool-shell` 多了争抢，再归到 #90。
  - **原因**：只拿本 PR 的六轮和基线比，没有想到同一个 `ubuntu-latest` 下镜像在换版本。第二轮 Browser Bridge 的缓存 key 因为 Go 补丁版本不同而没命中时，其实已经碰到过一次，当时没有往下追。
  - **应对**：把同期 `main` 和别的分支的 `包测试` 日志都拉下来，逐个标上镜像版本和是否带 #83 修复，再分组（步骤 16）。镜像版本取 job 日志开头 `Runner Image` 分组里的 `Version:`；它上面 `Runner Image Provisioner` 分组里也有一行 `Version:`，那是另一个组件的版本，分析脚本第一次取错成了它。
- **问题**：本机上 `packages/core/tool-runtime` 有三条用例、`packages/session/session-persistence-jsonl` 有一条用例失败。
  - **原因**：前者是 `docs/exec-plans/tech-debt-tracker.md` 里登记过的环境问题（机器上真有 `/workspace` 目录）；后者偶发，改动前的检出上同样出现。
  - **应对**：本地只用来核对每一片启动了哪些包、量各包的耗时（带 `--no-bail`），红绿以 CI 为准。
- **问题**：`vitest list --shard=N/3` 列出的是全部文件，不能用来核对分片。
  - **原因**：`list` 子命令不按分片过滤。
  - **应对**：改用 `vitest run --shard=N/3` 加 json reporter，从结果里取每一片实际跑了的文件。
- **问题**：分析脚本把 job 最后一个步骤结束到标记完成之间的空档算进了「环境准备」，第三、四轮里几个 job 的准备时间看起来多了 9–14 s。
  - **原因**：脚本把「job 时长减去各步骤时长」的余量并进了准备。
  - **应对**：把这段空档单独列出来（步骤 12）。
- **问题**：macOS 的 job 有两次排了五分钟的队才拿到 runner（第二轮 darwin-arm64 306 s、第四轮 darwin-x64 310 s）。
  - **原因**：GitHub 那边 macOS runner 的供给，改动前 11-09 也有过一次 321 s。全仓库只有发布工作流用 macOS，每次 2 个 job，没有碰到 5 个并发的上限。
  - **应对**：仓库这边没有可调的，只记录。

## 跳过或推迟的事项

- 发布链和 `构建` 换成 `tsc -b`：要动发布用的构建路径；两种产物的差异已比对并登记在 `docs/exec-plans/tech-debt-tracker.md`，不在这一轮做。
- 把 Go 固定到补丁版本，让缓存 key 不随 runner 镜像变：固定之后要有人跟着升版本，镜像换版时多冷跑一两次的代价更小。
- 桌面端测试加到四片、给每片加 worker、换 vitest 的 pool：前两项测过，收益抵不上多出来的 job 和偶发失败的风险；后一项会改变用例之间的隔离方式。
- 全局调大 testing-library 的 `asyncUtilTimeout`：会让所有真失败的等待都多等，只放宽了确认受影响的三条。
- CodeQL：不换查询集就没有可砍的，增量分析要用还没公开的开关。
- Agent CLI 的 `process tests` 复用 `tsc -b` 缓存：六轮里它都比打包那个 job 短 11–30 s，不在关键路径上。
- macOS arm64 上关 Spotlight：对照里测不出差别。Windows runner 上有没有类似的后台扫描没有测。
- 在本 PR 里修 `包测试` 的三种随机失败：#83 已经在修。
- 为 `--no-sort` 对时间敏感用例的影响再做一次 CI 对照：没有哪个决定取决于它。
