# Execution Plan 使用说明

execution plan 适合用在那些超出单轮聊天上下文、需要多次推进或风险较高的任务上。

## 什么时候该建 plan

- 任务会跨多个 commit 或多轮工作推进。
- 这次改动会影响架构、协议、数据迁移或其他高风险区域。
- 完成任务依赖阶段性验证、回滚策略或关键决策留痕。
- 可能会有多个人或多个 Agent 在一段时间内共同推进。

## 存放位置

- 进行中的 plan 放在 `docs/exec-plans/active/`
- 完成的 plan 直接删除，不归档；已失效、被取代或明确不再执行的 plan 经确认后同样删除。需要时查 git 历史，办法见 `docs/exec-plans/README.md`。
- 复用模板在 `docs/exec-plans/templates/execution-plan.md`
- 暂不处理但值得保留的债务放到 `docs/exec-plans/tech-debt-tracker.md`

## 维护要求

- 写清目标、范围、约束、风险和验证方式。
- 推进过程和关键决定记在 plan 的「进度记录」「决策记录」里，不要只存在聊天记录里。
- 状态变化要同步更新。
- `active/` 每个一级入口必须出现在 `docs/exec-plans/README.md`，并具有可执行的下一步。
- plan 是临时文件。设计文档、learnings、包 README 和代码注释不把 plan 或执行记录当内容来源：要长期成立的规则写进设计文档，出处写 history。

## 计划完成时

实现做完就在同一轮收尾，只剩人工验收的 plan 也一样，不为了等验收留在 `active/`。夜间模式例外：执行摘要要先交给人看，人看过之后再收尾。收尾做三件事：

1. plan 里定下、今后还要遵守的规则和约束，确认已经写进设计文档或包 README；没有就先补上。
2. 没验证的范围和没做完的事写进 history 的「未验证与遗留」和 PR 描述。需要后续处理的登记到 `docs/exec-plans/tech-debt-tracker.md`，性能类登记到 `docs/exec-plans/perf-backlog.md`。
3. 删除 plan 和 `docs/exec-runs/<plan-slug>/`，去掉 `docs/exec-plans/README.md` 里对应的一行，以及其他文档里指向它们的链接。

`pnpm check:docs` 会拦住设计文档、learnings、计划目录和 `docs/` 顶层文档里指向已删文件的链接；包 README、代码注释和脚本里的它查不到，删之前按 plan 的文件名搜一遍。现有 histories 保持原样。

## 执行模式

plan 执行时，根据任务性质选择执行模式：

### 交互模式

人在线，Agent 操作需逐步审批。适合：

- 架构变更、协议修改等高风险改动。
- 探索性任务，方向还不确定。
- 首次执行某类任务，需要观察 Agent 的行为。

### 夜间模式

人离线，Agent 在 nono 沙箱内获得 full-access 自主执行。适合：

- 边界明确的实施任务（plan 已经写清楚了范围和步骤）。
- 重复性工作。
- 低风险改动。

夜间模式使用 [nono](https://github.com/nolabs-ai/nono) 作为内核级沙箱，Codex 自身沙箱关闭，隔离完全交给 nono。profile 和启动方式见 `docs/nono-profiles/README.md`。

## 执行文档

交互模式不另写执行文档：人全程在场，进度和决定记在 plan 里，要人验证什么写在 PR 描述和 history 里。

夜间模式要在 `docs/exec-runs/<plan-slug>/` 下创建两份文档，它们是人了解执行全貌的唯一途径：

- **执行过程**（`execution-process.md`）：执行过程中持续更新的时间线记录，包含关键步骤、关键决定和遇到的问题。
- **执行摘要**（`execution-summary.md`）：执行完成后填写，核心部分是人工验证指引——告诉接手的人要验证什么、怎么验证。

模板在 `docs/exec-runs/templates/`，详细说明见 `docs/exec-runs/README.md`。这两份文档留到人看过执行摘要，随 plan 一起删除。

## 从设计文档生成 plan

复杂任务应该先有设计文档，再从设计文档拆 execution plan。

- 设计文档回答：为什么做、做成什么样、模块边界是什么、哪些方案被排除。
- execution plan 回答：谁改哪些文件、按什么顺序改、每步如何验证、失败时怎么回退。
- 如果一个设计文档覆盖多个独立子系统，不要写成一份大而全的 plan，应拆成多个可独立执行的 plan。
- 拆分后如果多个 plan 共享类型、协议或数据格式，应先写一个全局契约或数据地基 plan。

## plan 就绪检查

开始执行前，先检查 plan 是否已经足够具体。

- 是否写清必读文档，尤其是新会话或子 Agent 需要先读的文件。
- 是否写清相关代码路径，而不是只写模块名。
- 是否写清输入、输出、契约和依赖关系。
- 是否写清不做什么，避免执行时扩大范围。
- 是否写清验证命令和预期结果。
- 是否写清失败场景和最小回退策略。
- 是否没有 `TBD`、`TODO`、`之后补充`、`适当处理` 这类占位语。

## 可并行 plan 要求

如果 plan 预计交给多个 Agent 或多个会话并行执行，每份 plan 都必须能独立启动。

- 写清该 plan 依赖哪些其他 plan，哪些只是可选参考。
- 写清本 plan 的产物会被哪些后续 plan 消费。
- 写清允许修改的文件范围，减少并行冲突。
- 写清共享契约以哪个文件为准，不允许各个会话各自发明类型。
- 给子 Agent 的执行提示中必须要求先读 `AGENTS.md`。
- 不要让子 Agent 只靠聊天上下文，应把必要上下文沉淀到 plan 文件里。

## 任务粒度

实施型 plan 应尽量拆成小而可验证的任务。

- 每个任务最好能在短时间内完成，并产生一个清晰的可检查结果。
- 每个任务应写明准确文件路径、修改目的和验证方式。
- 涉及测试的任务应优先写清失败用例、通过命令和预期结果。
- 不要写“增加错误处理”“完善测试”这类空任务，要说明具体错误、具体测试和具体期望。
- 如果任务之间强依赖，明确标出顺序；如果可以并行，明确标出并行边界。

## plan 自审

写完 plan 后，先自审再执行。

- 对照设计文档逐项确认：每个关键设计是否都有对应任务。
- 扫描占位语和模糊词，发现就改成具体动作。
- 检查类型名、函数名、文件路径在全文是否一致。
- 检查验收是否能由命令、截图、fixture 或本地文件结果证明。
- 如果自审发现 plan 仍像“大纲”，先补 plan，不要急着写代码。
