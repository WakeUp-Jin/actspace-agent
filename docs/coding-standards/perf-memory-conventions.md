# 性能与内存约定

这份约定来自 2026-11 的内存排查。运行一次 Agent，主进程短时间内分配了好几 GB，面板内存冲到 2～3 GB。逐处看，每段代码都是「功能正确」的；问题出在一类写法：**工作量跟着会话长度增长，又放在每次请求、每个流式片段、每帧这样的高频路径上反复执行**。会话短的时候测不出来，会话一长就成倍放大。

排查过程和数字见 [性能待办](../exec-plans/perf-backlog.md) 的「已完成」一节。工具见 [内存采样工具](../tools/heap-monitor/README.md)。

## 1. 先认出高频路径

写代码前先问：这段代码一次会话里跑多少次？下面这些路径按「会跑很多次」对待：

| 路径 | 频率 | 典型位置 |
|---|---|---|
| 每次模型请求 | 一轮几次到几十次 | agent-loop `contextInput` / `resolve`、context-engine、请求记录 |
| 每个流式片段 | 每秒几十次 | live 通道、`assistant` 增量、渲染进程 `applyLiveEvent` |
| 每帧渲染 | 每秒 60 次 | 聊天区 Markdown、平滑输出、轨迹投影 |
| IPC 轮询 | 每秒一次起 | 子 Agent 面板、后台任务、状态栏 |
| 每次审批 / 每次工具调用 | 一轮几次到几十次 | 自动审查、权限、工具结果投影 |
| 每次追加事件 | 每轮几十到几百次 | journal `append`、projection 注册表、校验器 |

在这些路径上新增或修改的函数，在注释或 PR 说明里写一句：**它的工作量和什么成正比**，例如「和本次新增事件数成正比」或「和整份会话长度成正比」。答案是后者时，按第 2 条改。

## 2. 高频路径的工作量不随会话长度增长

**禁止的写法**（高频路径上）：

- 整份读日志：`journal.iterateEvents()` 遍历全部事件、`journal.readEvents()` 不带范围或者范围很大、`registry.inspectSessionEvents(sessionId)`、`journal.events`。
- 为了找几条事件逐条读：`entries.flatMap(entry => journal.readEvents(seq, seq + 1))`。内存窗口（默认 512 条 / 4 MB）之外的事件每读一条都要从文件解析。
- 每次都从头重算整份投影，再从结果里取一小块。

**应该的写法：**

- **增量读：** 记住上次读到的 `seq`，下次只读之后的事件（`journal.eventsAfter(seq)`）。
- **追加时顺手维护：** 需要「某类事件的列表」时，在事件追加和加载的地方维护一份小索引。按类型取最新一条已经有 `latestSessionEvent`。
- **用已有的视图：** 对话内容用 `journal.surface`（内存里的、已信任的视图），不要回头读原始事件再推一遍。
- **有界扫描：** 必须往回找时，从末尾倒着按页读，找到就停，并写明上限。

只在低频路径上（打开会话、导出、恢复、用户点击一次的操作）允许整份读。写的时候在调用处注释说明为什么允许，静态检查（第 8 条）会要求这条注释。

## 3. 只读数据不复制

- 已冻结的对象，或者刚 `JSON.parse` 出来、还没有别人引用的对象，不要再做 `snapshotSessionJson`、`structuredClone` 或 `JSON.parse(JSON.stringify(x))`。需要防改的，`Object.freeze` 就够了。
- 深拷贝只在**信任边界**做一次：IPC 入口、写盘前、插件交回的数据。之后在进程内传引用。
- 已信任的视图（日志交出的 surface 视图）直接引用，用版本号判断变没变，不要序列化后再比较。参考 [上下文引擎直接用日志视图](../design-docs/agent-plugin-runtime/agent-spec-context-trusted-surface.md)。

## 4. 同一份内容只存一份

- 对话内容在日志里只存一次。其他结构存引用（`seq`、`messageId`），用的时候推出来，不存副本。参考 [对话内容只存一份](../design-docs/agent-plugin-runtime/agent-spec-surface-derived.md)。
- 高频、可丢的数据（流式增量）不写进持久日志，只走实时通道。
- 每次请求都差不多的大块内容（请求记录的上下文）只在变化时写完整内容，没变化就写引用。

## 5. 缓存要有键、有上限

- 缓存键用版本号（例如 `gen:count:lastSeq`、`throughJournalSeq`），不要用整份内容算哈希或 `JSON.stringify`。
- 每个缓存写明上限和淘汰方式；按会话存的缓存在会话关闭时释放。
- 已经结束、不会再变的结果（子 Agent 结束后的模型、用量）可以记住，不再重读。

## 6. 轮询有下限，没变化就不重算

- 能推送就不轮询。
- 必须轮询时：间隔不低于 1 秒；先比较版本号，没变化就直接返回上次的结果。
- 轮询处理函数也是高频路径，第 2 条同样适用。

## 7. 渲染进程

- 流式路径上，每帧的工作量和已经输出的长度无关：已经定稿的块 memo 住；只有最后一块重新解析，而且降频（参考 [流式 Markdown 解析降频](../design-docs/frontend/front-流式Markdown解析降频规范.md)）。
- 渲染函数里不新建解析器、处理器、高亮器等重对象，统一做成模块级常驻。
- 实时事件到达时只更新受影响的那部分，不重算整份会话投影。
- 一个状态更新触发多次 `setState` 时，合并到同一帧。

## 8. 怎么验证

| 手段 | 什么时候用 | 命令 |
|---|---|---|
| 静态检查 | 每次提交。扫描整份读日志和深拷贝的写法；超出基线的文件报错，不在高频路径上的要写注释说明 | `pnpm check:hot-path-reads` |
| 规模测试 | 改了第 1 条里的任何路径。合成 1k 条和 10k 条事件的会话，断言读日志的条数、解析行数、拷贝次数不随规模增长。只计数，不计时 | 随 `pnpm test` 运行；写法见 [测试约定](#规模测试的写法) |
| 覆盖检查 | 每次提交。核对 `scripts/scale-test-coverage.json`：高频入口都登记了对应的 `*.scale.test.ts`，每个规模测试都比较 1k 与 10k、用读取计数、不计时；静态检查基线里仍整份读日志的文件要么有规模测试，要么列在 `pending` 并写明原因 | `pnpm check:scale-tests` |
| 实机采样 | 大改动之后，或者用户反馈卡顿、内存高的时候。按函数统计分配了多少 MB，和上一轮对比 | [内存采样工具](../tools/heap-monitor/README.md) |

### 规模测试的写法

- 用 `@actspace/session-journal/testing` 的 `syntheticSessionEvents(count)` 生成会话，用 `countingHistory(events)` 包住归档历史，统计读了多少行。
- 同一个操作在 1k 条和 10k 条事件上各跑一次，断言两次的读取行数相同（或者只差常数）。**不要断言毫秒数**：计时在不同机器上波动大，测试会偶尔失败。
- 修 bug 时先写规模测试，确认它在旧代码上失败，再修。
- 文件名以 `.scale.test.ts` 结尾，并登记到 `scripts/scale-test-coverage.json` 的 `entries`（入口文件 → 测试）。`pnpm check:scale-tests` 会核对登记、写法，以及静态检查基线里仍整份读日志的文件是否都有规模测试或 `pending` 理由；`pending` 只能变短。

## 自检

提交前对自己改过的高频路径问三个问题：

1. 会话长 10 倍时，这段代码的工作量会变成 10 倍吗？
2. 这段代码有没有复制一份已经冻结或者刚解析出来的数据？
3. 一个流式片段、一次 IPC 轮询，会不会触发整份重算？
