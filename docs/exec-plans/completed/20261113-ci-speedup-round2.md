# CI 提速第二轮：去掉重复工作、测试再分片、路径过滤与缓存收敛

## 目标

在不删减任何测试和检查的前提下缩短 GitHub Actions 的反馈时间，并让仓库 10 GB 的 Actions 缓存只存用得到的东西：

- PR 上 `ci.yml` 从约 185 s 降到 130 s 左右；PR 的全部检查跑完的时间降到 CodeQL 的时长（约 140 s）。
- Agent CLI 工作流从约 163 s 降到 100 s 左右。
- `main` 上的 `构建` job 不再把 desktop 构建两遍。
- 只改文档的提交在 PR 和 `main` 上都不触发 `ci.yml`，同时没有任何必需检查会因此卡在 pending。

## 范围

- 包含：
  - `.github/workflows/ci.yml`：路径过滤、`test-packages` 分片、`test-desktop` 加到三片、`build` 的 PR / `main` 分流、`site` 去重、`browser-bridge` 的 Go 缓存（自己的 key、`GOCACHE` 导出到整个 job、恢复后刷新缓存条目的修改时间）。
  - `.github/workflows/agent-cli-binaries.yml`：拆成两个并行 job，补全触发路径。
  - `.github/workflows/codeql.yml`：`main` 上按提交分组，issue 模板不触发。
  - `.github/workflows/release.yml`：macOS / Windows 上不再存 pnpm store，Go 编译缓存只在 PR 上开；Linux 照旧。Intel 的 macOS job 开头先关掉 Spotlight 索引。
  - 根 `package.json` 的 `build`、`build:cli-web`（新增）、`test:scripts`，新增 `scripts/run-script-tests.mjs`。
  - `apps/desktop/vitest.config.ts` 和两个 setup 文件：`main`、`renderer` 两个 project 各用各的 setup，main 进程测试不再加载 renderer 那份。
  - `apps/desktop/src/renderer/test/` 下三个测试文件里等懒加载页面出现的等待上限（从 testing-library 默认的 1 s 放宽到 10 s，断言不变）：三片分法让这三条用例成了各自分片里第一个加载懒加载页面的用例。
  - `scripts/test-browser-locator-runtime.mjs`：一条期望报歧义的断言补上 `timeoutMs`，不再等满默认的 10 s，断言不变。
  - `docs/CICD.md` 同步；把上一轮 `20261109-ci-speedup` 剩下的两项（记录各 job 时长、移到 `completed/`）一并收尾。
- 不包含：
  - 测试用例的断言和 vitest 的 `pool` / `isolate` 配置。改它们会改变测了什么、怎么隔离；对用例的改动只有上面三处等待上限和 locator fixture 那一个 `timeoutMs`。包测试里的三种偶发失败由 #83 修。
  - 发布链的构建方式（desktop `build` 的 `clean` + 逐包 `tsc -p`）。
  - CodeQL 的查询集和语言矩阵、`supply-chain-security.yml`、`base-checks.yml`、`site-pages.yml`、两个 composite action。
  - 仓库设置（ruleset、必需检查）。

## 背景

- 相关文档：`docs/CICD.md`、`docs/exec-plans/completed/20261109-ci-speedup.md`（上一轮：拆四个并行 job + `tsc -b` 缓存）、`docs/exec-plans/completed/20261108-ci-pipelines.md`。
- 相关代码路径：`.github/workflows/*.yml`、`.github/actions/setup-workspace/action.yml`、根 `package.json`、`apps/desktop/package.json`（`build`、`build:deps`、`build:deps:dev`）、`scripts/release-package.sh`、`scripts/check-browser-command-registry.mjs`、`scripts/test/*.test.mjs`。
- 基线：2026-11-11 至 11-13 仓库最近 50 次工作流运行、174 个已完成 job，每个 job 按 排队（创建到开始）/ 环境准备（checkout、装工具、装依赖、恢复缓存、`build:deps`）/ 实际工作 拆开，取中位数（秒）：

  | 工作流 / job | 排队 | 准备 | 工作 | 合计 | p90 |
  |---|---|---|---|---|---|
  | Agent CLI / managed ESM package | 2 | 28 | 132 | 160 | 166 |
  | CI / 构建 | 2 | 24 | 157 | 182 | 305 |
  | CI / 桌面端测试（每片） | 2 | 36 | 104 | 138 | 166 |
  | CI / 包测试 | 2 | 35 | 102 | 131 | 188 |
  | CI / 仓库脚本与进程级测试 | 2 | 35 | 86 | 119 | 130 |
  | CI / Lint 与类型检查 | 2 | 23 | 46 | 69 | 73 |
  | CI / Browser Bridge | 2 | 24 | 48 | 69 | 81 |
  | CI / 官网 | 2 | 20 | 21 | 41 | 48 |
  | CodeQL / javascript-typescript | 2 | 26 | 122 | 147 | 184 |
  | CodeQL / actions | 2 | 24 | 23 | 49 | 52 |
  | 仓库基础检查 | 2 | 7 | 6 | 14 | 87 |

  整次运行从创建到最后一个 job 结束（成功运行的中位数）：`ci.yml` PR 上 185 s、`main` 上 279 s；CodeQL PR 上 130 s、`main` 上 162 s；Agent CLI 163 s；仓库基础检查 17 s；供应链安全 18 s。
- 从基线看出的规律：
  - 排队不是问题：中位 2 s，最大 5 s。
  - 环境准备占全部 job 时间的 31%，每个 job 20–36 s。pnpm store 缓存、`tsc -b` 产物缓存、预编译的 ripgrep 都已经在用，剩下的是下载解压和 `pnpm install` 建链接，没有成块的浪费。
  - 实际工作占 68%，浪费集中在重复和串行：`pnpm build` 把基本相同的一批包构建两遍，`main` 上打包冒烟再构建一遍 desktop；`test:scripts` 的 24 条子命令串行，两个各带 31 s 固定等待的进程级测试排着队；`官网` 重跑别的 job 已经跑过的检查和测试；Browser Bridge 的 Go 编译产物进不了缓存；Agent CLI 的打包（79 s）和进程级测试（46 s）串行，而后者并不读打出来的包。
  - 最长的两段是包测试（Test 步骤 118 s）和桌面端测试（每片 Test 步骤 105 s）。
  - 缓存占用 10.49 GB，超过 10 GB 上限、已经在淘汰；其中 4.4 GB 是发布工作流在 macOS / Windows 上存的 pnpm store 和 Go 缓存，只有同一个 PR 的后续推送读得到，发版时读不到。
- 本地连续构建两次（4 核，Node 22）：
  - `pnpm build:deps`（七个 job 都跑的 `tsc -b` 链）第一次 11.1 s，第二次 5.3 s。第二次里 `tsc -b` 不到 1 s，其余是链上八次 `pnpm` 启动和每次都重做的 esbuild 打包、默认 Harness 组装，增量本身是生效的。
  - `pnpm build`（发布路径）第一次 83.7 s，紧接着第二次 83.1 s：每个包的 `build` 都先 `clean`，按设计不做增量。真正的问题是同一次构建里把同一批包编了两遍——先 `agent-cli...` 的依赖闭包 29.8 s，desktop 的 `build` 接着 `clean` 再把 runtime 的依赖闭包逐包重编 30.1 s。
  - Browser Bridge：`check-browser-command-registry.mjs` 在没有 `GOCACHE` 时把 `go run` 的产物放进临时目录，每次从头编 4.4 s；`go test` 和交叉编译的产物因为和别的 job 共用缓存 key、被先保存的那份占住，也每次从头编 2.1 s + 8.4 s。这一步当时漏看了一处：`apps/cli` 的测试里还有一次嵌套的 `go build`，用的是同一个临时目录，第三轮才从 CI 的步骤耗时里发现，见决策记录「Browser Bridge 测试里嵌套的构建」。
- 已知约束：
  - `main` 的 ruleset 只要求 `仓库基础检查`（不带路径过滤），PR 需要 1 个审批。
  - `pull_request` 的路径过滤看整个 PR 相对目标分支的 diff；`push` 看这次推送前后的 diff；两者都只取前 300 个文件。
  - 一次运行只能读本分支和默认分支存的缓存；同一个 key 只在第一次没命中时保存一次。
  - `gh` 在本次执行里只读，不能手动触发工作流、不能重跑失败的 job；`main` 上的路径和 `workflow_dispatch` 只能本地模拟。
  - GitHub 托管 runner 快慢不均：同一次运行里不同 runner 上的同一步骤可以差 1.5–2 倍，macOS runner 波动更大。
  - `ubuntu-latest` 的镜像换版本时新旧同时在发，同一次运行的 job 会分到不同版本。11-13 起正在换，第六轮才注意到，见决策记录「第六轮 `包测试 (2/2)` 的失败」。
  - GitHub 托管 runner 有账户级的并发上限：Free 计划同时最多 20 个 job、其中 macOS 最多 5 个，所有仓库和工作流共享。改动前一次全部触发是 18 个 job，基线里看不到它；第七轮才从排队数据里注意到，见决策记录「不为并发上限减 job」。
  - Go 按文件的修改时间清理构建缓存：每次构建结束时删掉 5 天没用过的条目。Actions 恢复缓存时文件保留保存那天的修改时间。`ci.yml` 是 11-08 才建的，基线和前七轮里的缓存都没放到 5 天；第八轮读 Go 的清理规则时才注意到，见决策记录「恢复出来的 Go 缓存 5 天后被清掉」。

## 风险

- 风险：路径过滤漏掉某个被构建或检查读取的文档，只改它的提交不再跑 CI。缓解：新规则忽略的已跟踪文件（1888 个）是旧规则（1939 个）的子集，少掉的 51 个正是被 CI 读取的文件；`docs/` 下被读取的 4 个文件逐个加回，登记方式写进 `ci.yml` 注释和 `docs/CICD.md`。
- 风险：分片时漏掉或重复某些测试。缓解：包测试两片的 `--filter` 由同一份目录清单一正一反生成，本地核对两片正好是原来的 72 个包（22 + 50）；桌面端三片合计 309 个测试文件、2978 个用例，与分片前一致；`test:scripts` 新旧都是 28 个测试文件加同样 5 条 `check:*`。
- 风险：桌面端测试改片数后，每个文件同片的邻居和先后都变了，原来不超时的等待可能超时。第二轮里实际发生了：`桌面端测试 (2/3)` 的一条用例成了那一片里第一个打开设置页的，冷转译落进默认 1 s 的等待。缓解：删掉本地 vitest 结果缓存、按 CI 的文件顺序把两片和三片逐条用例对比，找出全部三条受影响的用例并放宽它们的等待，见决策记录「三片分法引出的等待超时」。
- 风险：`pnpm build` 改变构建顺序后产物不同。缓解：干净检出下新旧两种顺序各构建一次，2600 个产物文件除每次构建都会变的 `apps/web/dist/sw.js` 外哈希全部相同。
- 风险：包测试分片后同一台 runner 上并发更密，放大既有的时间敏感用例的偶发失败。缓解：已知的时间敏感用例都在第 2 片，这一片同时跑的包数降到 2 个，见决策记录「包测试的并发」；根因由 #83 修。
- 风险：`main` 上 `构建` 的新路径（打包冒烟后接 `build:cli-web`）和手动触发在 PR 上跑不到。缓解：本地按 `main` 的步骤顺序跑通（82.4 s + 6.3 s），产物与单跑 `pnpm build` 一致；合并后的第一次 `main` 运行需要人看一眼。
- 风险：与 #83（给 `ci.yml` 加 `变更范围` / `CI 汇总` 两个 job）在 `ci.yml` 的 `on:` 块和 `docs/CICD.md` 上有文本冲突。缓解：本计划没有改任何 job id，冲突只在文本层面；合并办法写在执行摘要里。

## 里程碑

1. 基线：拉最近 50 次运行，按 排队 / 环境准备 / 实际工作 拆分，找规律。
2. 本地连续构建两次，定位第二次仍然耗时的环节。
3. 第一轮改造：去重复、并行、分片、路径过滤、缓存收敛，每项本地验证后单独提交。
4. 推送，观察第一轮实际耗时。
5. 第二轮：按第一轮的数据补漏，再推送观察。
6. 第三轮：修第二轮暴露的问题（三片分法引出的等待超时、包测试第 1 片的并发），再推送观察。
7. 第四轮：修第三轮暴露的问题（Browser Bridge 的缓存命中了，测试里嵌套的 Go 构建却没用上），再推送观察。
8. 第五轮：重新核对发布工作流的缓存，把 macOS / Windows 的 Go 编译缓存在 PR 上开回来，再推送观察。
9. 第六轮：在同一台 macOS runner 上做对照实验（pnpm store 怎么来的影不影响构建、Spotlight 索引拖不拖慢构建），按结果改发布工作流，再推送观察。
10. 文档同步，给出前后对比。
11. 第七轮：文档推送之后再看一遍实际运行，拿同一时刻没带本计划改动的运行核对前后对比。
12. 第八轮：修第七轮顺带发现的 locator fixture 等待，再推送观察。
13. 第九轮：核对 Go 缓存放过 5 天之后还管不管用，给 `Browser Bridge` 补上刷新缓存条目时间的一步，连同文档一起推送。

## 验证方式

- 命令：
  - `./scripts/ci.sh`、`pnpm lint`、`pnpm check:docs`、`npx -y markdownlint-cli2@0.20.0 "**/*.md"`、`./scripts/check-action-pinning.sh`、`actionlint`（1.7.12，认识 YAML 锚点）。
  - `pnpm test:scripts`：新旧各跑一遍，比对测试文件清单、用例数（131 个，126 通过、5 跳过）和耗时。
  - 干净检出下 `pnpm build`：新旧各一次，比对全部产物文件的哈希。
  - 包测试两片各跑一遍，核对两片的包清单合起来等于不分片时的清单。
  - `pnpm --filter @actspace/desktop exec vitest run --shard=N/3`，N = 1、2、3，核对文件数和用例数之和；拆 setup 文件前后各跑两轮，再单跑 `--project main` 比对通过的文件数和用例数。
  - 懒加载等待：每轮先删 `apps/desktop` 下的 `node_modules/.vite/vitest`（本地的结果缓存会改变文件顺序，CI 上没有它），两片和三片的每一片各跑两轮，带 `--reporter=json` 逐条用例比耗时；再用 `taskset -c 0,1` 加 `--maxWorkers=3` 模拟慢 runner，放宽等待前后各把 2/3、3/3 片跑三轮。
  - 用脚本按 GitHub 的有序 `paths` 语义对全部已跟踪文件求值，比对新旧规则忽略的文件集合。
  - `main` 路径：本地依次跑 `./scripts/release-package.sh`、`pnpm build:cli-web`。
  - Browser Bridge：把 `ci.yml` 里这个 job 的 `run` 步骤导出来原样跑两遍，步骤之间用一个 `GITHUB_ENV` 文件传环境变量，进程环境里不预先设 `GOCACHE`；第一遍缓存目录是空的，第二遍先 `touch` 全部 `.go` 文件模拟新的检出。看 `apps/cli` 的测试耗时，以及临时目录 `abb-go-cache` 有没有出现。
  - `pnpm check:browser`：给 locator fixture 的断言补 `timeoutMs` 前后各计时一次；再去掉制造歧义的那一行，确认断言失败。
  - Go 缓存放久之后：本地把缓存条目的修改时间和 `trim.txt` 改到 6 天前，按 job 里的顺序跑 `go run`、`go test`、两个交叉编译，看每条命令跑完后剩下的条目数和耗时；再把刷新时间那一步的脚本从工作流里原样导出来，插在前面重跑一遍。
- 手工检查：合并后看第一次 `main` 运行里 `构建` 的三个步骤（Go、打包冒烟、`Build CLI and Web`）都执行并通过；开一个只改 `docs/` 的 PR，确认只有 `仓库基础检查` 触发。
- 观测检查：PR 每次推送后，用 `gh` 拉各工作流的 job 和步骤耗时，与基线逐项对比。
- 对照实验：发布工作流里只看历史运行分不清的两个问题（pnpm store 是恢复的还是现下载的、Spotlight 索引开着还是关着），在一条只带一个临时工作流的分支上，让同一台 macOS runner 交替两种状态各构建几次再比；顺序相反的 job 成对跑，做完删分支。Go 缓存放久之后的表现用同样的办法在 CI 上核对：对同一份恢复出来的缓存做「原样 / 条目改到 6 天前 / 改旧之后再刷新」三个对照，再用一份真的放了 5 天的缓存做一组。

## 决策记录

- 2026-11-13：必需检查沿用现状——工作流级 `paths` 过滤，只有不带过滤的 `仓库基础检查` 是必需检查。纯文档 PR 不会产生任何 `ci.yml` 的 check，也就没有会卡在 pending 的必需检查。#83 是另一种做法（去掉 `pull_request` 的过滤，改成 job 级跳过，再加一个可以设为必需的 `CI 汇总`）；两者不冲突，#83 合入后把本计划收窄过的规则搬进它的 `变更范围` job 即可，`push` 上的 `paths` 保留。
- 2026-11-13：路径过滤从 `paths-ignore` 改成有序 `paths`。`paths-ignore: '**/*.md'` 把官网内容、内置 skill、prompt、测试夹具和 4 个被 CI 读取的 `docs/` 文件也忽略了，只改它们的 PR 原来不跑 CI；有序 `paths` 能先整体排除再逐个加回。`main` 上的 push 用同一份规则：只改文档的提交和它前一个提交的代码相同，不需要再跑一遍。
- 2026-11-13：`main` 上不取消运行，并且按提交分组而不是按分支分组。`ci.yml` 和 `base-checks.yml` 原本就是这样；`codeql.yml` 原来按分支分组，连续推送时排队中的那次会被后一次顶掉，这次改掉。
- 2026-11-13：`pnpm build` 改成先构建 desktop，再用 `build:cli-web` 只补 desktop 没构建过的包，而不是让 desktop 复用前一步的产物：desktop 的 `build` 以 `clean` 开头，是发布路径，不动它。

- 2026-11-14：locator fixture 的 10 s——给一条断言补上 `timeoutMs`。上一条把契约检查拆开看的时候，`scripts/test-browser-locator-runtime.mjs` 在 19 次运行里都是 10.9–11.2 s，和 runner 快慢无关；本地跑也是 11.2 s，其中 CPU 时间不到 1 s。原因是一条断言：它期望 `point` 在选择器有歧义时报 `selector_ambiguous`，而这个错误只在等待超时的时候才报，断言没传 `timeoutMs`，每次都等满默认的 10 s。同一个文件里后来加的同类断言传的是 `timeoutMs: 100`，这里照做。脚本从 11.2 s 降到 1.2 s，`pnpm check:browser` 本地和 CI 上各少等 10 s。断言没有变弱：去掉制造歧义的那一行，它仍然以 `Missing expected rejection` 失败。顺着同一个特征（时长不随机器快慢变）把第七轮的日志过了一遍，另外只有 `scripts/test/` 下两个进程级测试各等的 31 s，那是有意按生产环境的过期租约规则等的，不动。第八轮 CI 上这一段是 1.0 s。
- 2026-11-14：不为并发上限减 job。第七轮本 PR 有 7 个 job 排了 17–50 s 的队：另一条分支早 71 s 推送，它的 11 个 job 还有 7 个在跑，本 PR 的 21 个 job 到达时只剩 13 个名额，每个排队的 job 都是在别的 job 结束后 1–3 s 内开始的。GitHub 的文档写明 Free 计划同时最多 20 个 job、所有仓库共享。回头看前六轮，每轮也恰好有一个 job 排了 10–17 s：一次全部触发是 21 个 job，比上限多一个，等的是十几秒就跑完的供应链安全或基础检查；第五轮排队的是 `构建`，那一轮 `ci.yml` 的 130 s 里有 12 s 是它。本计划把全部触发时的 job 数从 18 个加到了 21 个（`ci.yml` 8 → 10，Agent CLI 1 → 2）。没有为此减 job，理由有三。其一，21 个只出现在同时改到打包脚本和依赖清单的 PR 上（本 PR 就是）；一般的代码 PR 是 13–15 个（改动前 11–12 个），单独一个 PR 碰不到上限。其二，多个 PR 同时推送时哪种排法都要排队，排多久取决于各 job 的时长之和，本计划没有增加它（`ci.yml` 七轮是 763–927 s，同期改动前的排法成功的 6 次是 785–964 s）。其三，能减的只有把 `官网` 并进别的 job，省一个名额和约 20 s 的环境准备；但 #83 的 `CI 汇总` 在 `needs` 里列了 `site`，这边删掉这个 job 之后，合并时 `needs` 那一行不会报冲突，漏改的话合出来的 `ci.yml` 是无效的，为全部触发时的十几秒不值得冒这个险。这个上限也是桌面端测试停在三片的又一个理由：四片时全部触发是 22 个。上限和各工作流的 job 数已写进 `docs/CICD.md`。
- 2026-11-14：恢复出来的 Go 缓存 5 天后被清掉——`Browser Bridge` 恢复缓存之后先把条目的修改时间刷新一遍。Go 每次构建结束时，如果距上次清理超过一天，就删掉修改时间在 5 天以前的缓存条目，条目每被用到一次刷新一次时间。`setup-go` 的 key 存过一次就不再更新，恢复时 `tar` 保留保存那天的修改时间，所以缓存存下 5 天之后，每次恢复出来的条目在 go 看来都过期了：job 里第一条 go 命令（registry 检查的 `go run`）用到的条目还在，它一跑完，`go test` 的测试产物和两个交叉编译目标的条目就被删掉。本地把条目改到 6 天前：`go run` 跑完，2580 个条目剩 656 个，`go test` 0.07 s → 3.1 s，两个交叉编译 0.5 s → 10 s。CI 上对同一份恢复出来的缓存做三个对照：原样时 `go test` 1.7 s、交叉编译 1.2 s；条目改到 6 天前是 5.7 s 和 10.6 s，第一条命令跑完 2569 个条目剩 526 个；改旧之后再刷新是 1.9 s 和 1.5 s，条目不减。第一条命令自己在三个对照里一样快（4.1 / 4.1 / 3.6 s）。再用 `main` 上真放了 5 天半的那份缓存核对：恢复出来的条目修改时间确实是 11-08，一条只用到小部分缓存的命令跑完，941 个条目剩 273 个，随后的 CLI 构建 5.5 s；先刷新时间的对照是 1.1 s。刷新两千多个条目用 0.04 s。只改 `Browser Bridge`：`构建` 和发布工作流每个 job 只跑一条 `go build`，命中发生在清理之前，不受影响（第七轮发布的 linux-x64 恢复的就是那份 5 天半的缓存，编浏览器桥组件 5.0 s，改动前命中的 12 次是 1.5–4.9 s，没命中的一次 10.1 s）。没有选的做法：把缓存目录里的 `trim.txt` 写成当前时间，让 go 一天内不清理，本地验证同样有效，但它依赖这个文件的名字和格式；给 key 加日期让缓存定期重存，要绕开 `setup-go` 自带的缓存改用 `actions/cache`，每个周期的第一次运行仍然是冷的。这一步的效果要到 11-18 之后才看得出来：现有的两份缓存都是 11-13 存的，在那之前刷不刷新没有差别。
