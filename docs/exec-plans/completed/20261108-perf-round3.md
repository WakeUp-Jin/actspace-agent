# 性能第三轮：高频路径不再整份读日志

## 目标

去掉 run8 测出的四个主进程热点（[性能待办](../perf-backlog.md) P1–P4）。做完后，每次审批、每次模型请求、每次子 Agent 面板轮询，工作量都不再随会话长度增长；从文件读旧事件也不再多一份深拷贝。

## 状态

2026-11-09 R1–R4 已实现并提交（`45b675b1`、`1a300840`、`12810fea`、`8f1e6d4b`），每项都有「旧败新过」的规模测试；配套新增 `pnpm check:scale-tests` 覆盖检查（`d8fe2499`）并收紧 hot-path-reads 基线（`24910abc`）。R1 没有按方案 A 改用 surface 视图：开工前核对发现审查刻意要「压缩后仍交原始消息」，所以保留语义、改成按会话的增量投影，理由见[执行过程](../../exec-runs/20261108-perf-round3/execution-process.md)。实机采样对比未做，验收指引见[执行摘要](../../exec-runs/20261108-perf-round3/execution-summary.md)。

方案拍板于 2026-11-07（用户：「按照你的建议来」）。以下为原计划正文。

## 范围

**包含：** R1–R4，每项都配规模测试（[性能与内存约定](../../coding-standards/perf-memory-conventions.md) §8）。

**不包含：**
- P5–P9 待查项：等这一轮做完、重跑采样后再看；
- 日志格式变更；
- 渲染进程。

## 背景

- **基线：** `tmp/heap/run8`（不进仓库）。数字见 [性能待办](../perf-backlog.md)。
- **分析命令：** 见 [内存采样工具](../../tools/heap-monitor/README.md)。
- **日志内存窗口：** 默认 512 条或 4 MB（`SessionJournal` 的 `retainedEvents` / `retainedBytes`）。窗口外的事件由 `JsonlEventHistory.readEvents` 从文件读出来，每行 `JSON.parse` 一次，再做一次 `snapshotSessionJson`。所以「整份读」在长会话里就是「整份解析文件」。
- **测试基础件**（本轮之前已加）：
  - `@actspace/session-journal/testing` 的 `syntheticSessionEvents`、`countingHistory`；
  - 静态检查 `pnpm check:hot-path-reads` 及其基线。

## 任务

### R1 自动审查不再整份读日志（P1，约 1.3 GB）

**现状：** `packages/core/runtime/src/harness/review-session-action.ts` 做了两件事：

1. `[...session.journal.iterateEvents()]` 复制出全部事件，倒着找当前的 `tool/call`，交给 `reviewConversation(events)`（`packages/approval/auto-review/src/context.ts`）；
2. 审查结束后再 `iterateEvents()` 一遍，检查审查期间有没有混进别的事件。

**方案 A（已选）：** 对话部分改用内存里的 surface 视图（主模型看到的那份），其余只读需要的事件。

- **对话消息：** 从 `journal.surface.entries` 取 `user` / `assistant` 节点。内容和 `reviewConversation` 现在从 `surfaceNode(event)` 推出的一样。
- **最近的工具调用和人工决定**（最多 24 条）：从末尾倒着按页读，够 24 条或者到达本轮开头就停。
- **当前 `tool/call`：** 倒着读到为止。或者在日志里按 `callId` 记一份索引，开工时看哪个简单。
- **审查后的检查：** 改成 `journal.eventsAfter(revision)`，只读审查期间新增的事件。

**开工前核对：**
- `reviewConversation` 现在拿到的是**全部**事件，其中包括被压缩替换掉的旧消息；surface 视图里这些是压缩摘要。审查要的是哪一种，先确认它的语义（压缩之后，「原始用户授权」可能只剩摘要里有），必要时问用户。
- 「`users` 为 0 就报错」这条规则在 surface 视图下是否还成立。

**规模测试：** 合成 1k / 10k 条事件的会话，归档历史用 `countingHistory` 包住，断言一次审查从文件读的行数不随规模增长，比如都 ≤ 256。

### R2 每次请求不再逐条读压缩摘要（P2，约 480 MB）

**现状：** `packages/core/agent-loop/src/loop.ts` 的 `contextInput` 对 `surface.entries` 里的**每个**条目调一次 `journal.readEvents(seq, seq + 1)`，只为了找出 `surface/replaced` 事件的 `compactionId`。

**方案 A（已选）：** `SessionSurface.apply` 处理 replace 事件时，顺手把 `compactionId` 记到条目上，或者 surface 自己维护一份 `messageId → compactionId` 的小表。
- 加载会话时 surface 本来就会 apply 全部事件，重启后也不用回头读。
- `loop.ts` 改成直接从 surface 取。
- 先确认 `SessionSurfaceEntry` 加字段会不会影响已信任视图的版本号（`surface-trust.ts`）和等价测试的 golden。

**规模测试：** 1k / 10k 条事件、多次压缩的会话，断言 `contextInput` 一次请求的历史读取行数为 0。

### R3 子 Agent 面板不再每秒整份读日志（P3，约 340 MB）

**现状：** `apps/desktop/src/main/runtime-v2/fixed-renderer-ipc.ts` 有三处整份读：
- `getSubagents` 每次 `inspectSessionEvents(sessionId)` 后 `projectSubagentItems(journal, …)`，面板运行时每秒轮询一次；
- `revealSubagentRecord`、`getSubAgentTranscript` 也整份读，频率低。

**方案 A（已选）：** 主进程按会话在内存里维护子 Agent 列表的折叠状态。
- 第一次读全量折叠一次，记下 `throughSeq`；之后每次只折叠 `eventsAfter(throughSeq)`。
- 会话关闭时释放。
- 先确认 `projectSubagentItems` / `foldSubagentTree` 能拆成「状态 + 逐条折叠」，不能拆的话就把它们改成可增量的形式。
- `revealSubagentRecord` 共用同一份状态。`getSubAgentTranscript` 读的是子会话自己的日志，先看频率再定。

**规模测试：** 父会话 1k / 10k 条事件，连续调 10 次 `getSubagents`，断言第 2 次以后不再读历史。

### R4 从文件读旧事件不再深拷贝（P4，约 860 MB，和 R1–R3 有重叠）

**现状：** `packages/session/session-persistence-jsonl/src/event-history.ts` 的 `readEvents` 对每一行 `JSON.parse` 之后再调一次 `snapshotSessionJson`。

**方案（已选）：** 刚解析出来的对象没有别人引用，改成只做深冻结，不拷贝。
- `snapshotSessionJson`（`session-journal/src/event-envelope.ts`）做三件事：`validateJsonValue`、序列化后检查 1 MiB 上限、`JSON.parse` 一份再 `deepFreeze`。同一文件已经有只检查不拷贝的 `validateSessionJson`。
- 读历史时改成 `validateSessionJson(event)` 加 `deepFreeze(event)`，`deepFreeze` 需要导出或者换个地方放。
- 这些检查写盘时已经做过，读回来要不要再做，按[单条记录的限制](../../learnings/2026-10/20261006-record-limits-and-projections.md)的思路确认；默认保留，因为文件可能被外部改过。

**规模测试：** 读 10k 条事件时 `snapshotSessionJson` 调用次数为 0，或者用分配计数器断言。

## 验证方式

- **命令：**
  - `pnpm -r typecheck`；
  - 各相关包的 `test`；
  - 根目录 `pnpm test`、`pnpm check:docs`、`pnpm check:hot-path-reads`。
  - 改过的整份读调用点从基线里删掉，基线只减不增。
- **等价：** 审查输入、模型请求、子 Agent 列表的结果和改前一致。现有 golden 测试必须全部通过，R1 再补一份审查输入的 golden。
- **实机：** 用户按 [内存采样工具](../../tools/heap-monitor/README.md) 跑一轮，尽量复现 run8 的工作量（多会话、开自动审查、有子 Agent），然后对比：
  - `reviewSessionAction`、`contextInput`/`resolve`、`getSubagents` 处理函数、`readEvents`/`snapshotSessionJson` 各自的分配；
  - 各进程的堆和 RSS 峰值。

## 风险

- **R1 改了审查看到的内容：** 压缩前后语义可能不同。缓解：开工前核对，加 golden 测试，语义有变化先问用户。
- **R2 改了 surface 结构：** 可能影响已信任视图和等价测试。缓解：先跑 `context-trusted-equivalence`、`surface-derived-equivalence`。
- **R3 增量状态和整份重算不一致：** 缓解：测试里对随机事件序列比较增量结果和全量结果。
