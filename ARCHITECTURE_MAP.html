ACTSPACE 全局模块地图

一个 Agent-first 的本地桌面工作台：主 Agent 负责对话式协作，Kairos 自治 Agent 在后台常驻巡航。 本图纸覆盖三包结构、两条业务主线、八大子系统与全部核心模块，供手绘架构图时逐层参考。

Electron + React + TS + Vite 3 packages 单仓 DeepSeek 1M / Kimi 256K JSONL 事件溯源 本地优先 · 密钥不出主进程
00 /

鸟瞰：仓库即三层蛋糕

整个仓库只有一个不可违背的依赖方向：desktop → agent-core → shared。 上层通过包名（@actspace/agent-core、@actspace/shared）消费下层的 dist/ 产物，禁止反向引用、禁止直接相对引用 sibling 的 src/。

packages/desktop
Electron 桌面端：main / preload / renderer
─▶
packages/agent-core
Agent 运行层：引擎 / LLM / 工具 / 上下文 / Kairos
─▶
packages/shared
纯类型契约：IPC / SessionEvent / 模型注册表
包一句话定位关键约束
packages/desktopElectron 应用壳：窗口、IPC 路由、依赖装配、持久化编排、全部 UIrenderer 不碰文件系统、不碰密钥、不 import agent-core
packages/agent-core可独立测试的纯 Node Agent 运行层：执行循环、模型接入、工具系统、上下文管道、Kairos 自治内核完全不知道 Electron 存在；不处理 IPC 协议
packages/shared跨进程契约唯一来源：事件 schema、IPC 类型、模型注册表、Kairos 契约与聚合纯函数不依赖任何兄弟包；改契约 = 改宪法，须三端同步
docs/ · scripts/ · infra/仓库知识库（设计文档/执行计划/history/learnings）、自动化脚本、部署定义docs 是本地规则正式来源，代码变更须同轮同步文档
画图建议：先画这三层蛋糕和一个磁盘圆柱（userData/），再在旁边标注"依赖方向永远向下"。后面每一节都是对某一层的放大。

主线一：一次对话 Turn 的四层数据流

项目最重要的动态主线（事实来源：docs/design-docs/agent-turn-layers.md）。 四层各司其职，数据格式在层间逐级翻译，每层只认自己的协议。

Sequence · 从输入到落盘
① Renderer
Composer 收集 {userInput, model, thinkingEnabled}→ 先把 Workspace 选择写入 session meta→ IPC: agent:run-turn(RunTurnInput)
② Main Process
readMeta → workspaceRoot→ buildAgentConfig() 前端参数 + env/settings → AgentConfig→ createAgentForSession() 构造期一次性恢复会话历史 → AgentDeps→ runTurnWithAgent(deps)
③ Bridge
new Agent(deps).run(userInput)→ AgentEvent → RuntimeStreamEvent 实时翻译→ 按 previewKind 聚合 ToolUiPreview→ 汇总 AgentTurnResult
④ Agent Loop
每次调 LLM 前 maybeCompact()（超阈值压缩历史）→ llm.stream(context)→ thinking / text / tool_call→ ToolManager.execute（权限三态）→ 结果回填 context，循环直到无工具调用
⑤ 回程
Bridge 流式回调 onStreamEvent→ Main webContents.send 推给 Renderer 实时渲染→ Main 持久化 session.jsonl + meta.json（含 subagents transcript）

七个全局设计思想

画图时建议把这些作为"图例注释"写在边上——它们解释了为什么模块长成这个形状。

01

事件溯源（Event Sourcing）

一切真相都是 SessionEvent 的 append-only JSONL 流。UI 状态、LLM 上下文、用量统计、Kairos 记忆全部从事件流重建；坏行容错跳过，永不让一行垃圾炸掉整个会话。

02

协议翻译链，每层只认自己的协议

AgentEvent →（Bridge）→ RuntimeStreamEvent →（IPC）→ React 状态。引擎不知道 IPC，渲染层不知道引擎；改任何一层协议只动翻译器，不渗透。

03

静态前缀 + 动态尾部

上下文中越靠前的内容变化频率必须越低。主 Agent 用 CACHE_STABILITY 档位排序，Kairos 用纯静态 system prompt + tick 尾部消息——同一原则，两处落地，为 DeepSeek 64-token 块前缀缓存服务。

04

内核复用，外壳分叉

主 Agent 与 Kairos 共享 LLMService / ToolManager / runAgentLoop 内核；差异全部留在外壳（bridge 推聊天区 vs eventSink 写短期记忆），新增第三种 Agent 形态时内核零改动。

05

计算 / 提交分离 + 非关键路径异步化

观测游标只在 tick 成功闭合后提交（at-least-once，失败不丢增量）；压缩、摘要、审计全部后台跑、失败可跳过，绝不阻塞主循环。"看一眼"（快照预览）不消耗状态。

06

密钥与权限的硬边界

API Key 只活在 main 进程的 env 层；写类工具严格不越界、读类放宽但显式标注；Kairos 工具调用再加白名单 + blocklist 双校验；删除文件强制一次性审批。权限是分层叠加的，不是单点开关。

07

懒加载上下文，只注入"目录卡片"

Skill 只把名字 + 描述 + 绝对路径注入 system prompt，正文由 Agent 匹配任务后自己 read_file；工具大输出落盘留 ref 而非塞回上下文。上下文是稀缺资源，按需取用。

08

发送 = 落盘 = 重放

发给 LLM 的字符串与持久化的事件、与重放重建的消息必须逐字节一致（thinking 块连 signature 都要存）——否则跨 tick/turn 缓存在分歧处断裂。用序列化层 deepEqual 测试锁死。
