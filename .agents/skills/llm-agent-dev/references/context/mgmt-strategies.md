# 上下文管理核心设计

## 上下文失控的四种模式

在 Agent 开发中，上下文管理的重点不是"获取更多信息"，而是防止以下四种失控：

### 上下文污染

幻觉或错误信息进入上下文后被反复引用。典型场景：工具错误信息不精确，LLM 基于错误上下文反复重试；用户记忆整理时的误解持续影响后续交互。

应对：工具错误输出必须准确反映真实原因；记忆模块需要更新和精简机制，避免"过时记忆"长期存在。

### 上下文干扰

上下文过长时，模型过度关注累积的历史内容，忽视训练期间学到的策略。模型输出变得"固化"，创造性下降。

应对：上下文修剪（移除无关历史）、上下文总结（将长对话浓缩为摘要）。核心思想是"极致压缩"——用最少的 token 传递最多的信号，让模型内部发生"信息爆炸"。

### 上下文混淆

不相关的信息（如无关的工具定义）被放入上下文，模型把这些都纳入考虑范围，导致决策质量下降。

应对：工具定义清晰有边界；工具超过 30 个时使用 RAG 检索相关工具子集。DeepSeek-v3 团队验证：工具超过 100 个时模型几乎必然选错，RAG 筛选到 30 个以内可将准确率提升 3 倍。

### 上下文冲突

多智能体架构中，不同 Agent 产生的结果相互矛盾，合并后输入给主 Agent 导致输出质量下降。

应对：上下文隔离策略——将大任务拆分为独立子任务，每个子 Agent 拥有专属上下文空间。Anthropic 内部评估显示，多智能体研究系统比单智能体表现高出 90.2%，关键在于隔离减少了路径依赖。

## 管理策略

### RAG 筛选

选择性添加相关信息。无论上下文窗口多大，RAG 都有价值——"如果你把上下文当作杂货抽屉，垃圾就会影响回复"。

### 上下文隔离

将上下文隔离到各自专用线程中。适用场景：多方向探索、大任务分解、需要不同工具集的子任务。每个子 Agent 专注自己的上下文，最终将压缩后的结论汇报给主 Agent。

### 上下文修剪

从上下文中移除无关信息。实施方式：Token 压缩策略（根据模型特性决定压缩哪部分）、优先级标记（高优先级消息不参与裁剪）。

### 上下文总结

将累积对话浓缩为摘要。关键设计：总结后保留历史文件引用，当 Agent 发现摘要信息不够时，可以搜索完整历史找回细节（Cursor 的做法）。

## 上下文管理容器的设计流程

1. 消息添加：接收消息 → 格式验证 → 存储到后端 → 更新 Token 计数
2. 上下文构建：获取系统提示词 → 获取会话历史 → Token 检查是否需要压缩 → 格式化为 LLM API 格式
3. 压缩流程：判断是否超过阈值 → 执行压缩 → 保留压缩历史
4. 格式化：将内部消息格式统一转换为具体 LLM 提供商的 API 格式

参考代码: `examples/context-manager.ts`

## 注意事项

- 压缩触发条件建议设为上下文窗口的 80%-90%，而非固定轮次。过早压缩丢失决策信息，过晚导致 API 报错
- 系统提示词、用户记忆、Skill 加载的上下文不能被压缩，只有会话历史和工具输出可以压缩
- 消息格式化必须处理不同 LLM 提供商的差异（OpenAI / Anthropic / 其他），建议通过提供商专属的格式化方法实现
