# 会话历史记录上下文

## 什么是会话历史记录上下文

会话历史记录是上下文的七种类型之一，负责保存完整的多轮对话流——用户输入、助手回复、工具调用与结果。它是 LLM 理解对话连续性的基础，也是支撑跨会话恢复的关键数据。

### 与短期记忆的区别

短期记忆（ShortTermMemoryContext）和会话历史记录关注点不同，存储复杂度差异很大：

**短期记忆**：管理当前会话内的对话流。存储方式可以非常简单——以日期为维度的 `.jsonl` 文件，按 Token 预算从新到旧加载，超出预算时通过多层压缩（日→周→月→年摘要）释放空间。不需要 Redis、不需要多后端架构，一个文件系统就够了。

**会话历史记录**：需要跨会话持久化完整记录，支持用户随时恢复之前的对话。这对存储的可靠性（不能丢数据）、一致性（多端同步）、性能（快速加载历史）有更高要求，因此需要下文的 Redis 缓存、WAL、多后端降级等复杂架构。

### 并非所有 Agent 都需要

如果 Agent 只维持当前会话的上下文（如命令行工具型 Agent），短期记忆的简单存储就足够。只有需要跨会话恢复、多用户并发、高可用保障的场景，才需要下文的复杂存储设计。

## 存储设计

### Redis 缓存后端架构

最基础也最实用的方案：Redis 作为缓存层 + 一个持久化数据库作为兜底。架构清晰、开发难度小，适合大多数场景。

### 工作原理

**写穿模式（Write-Through）**：写入时先写持久化数据库（唯一真相源），成功后再写 Redis 缓存。保证数据一致性，代价是写入延迟略高。选择写穿而非写回（Write-Back）的原因：Agent 对话数据不能丢失，写回模式在缓存崩溃时会丢数据。

**读穿模式（Read-Through）**：读取时先查 Redis，未命中则从数据库加载并异步回填缓存。对调用方透明——无论数据在缓存还是数据库，接口一致。

### 统一存储接口

定义 CacheBackend 和 PersistentBackend 两个抽象接口，通过 UnifiedStorage 统一服务将二者编排在一起。上层业务只与 UnifiedStorage 交互，不关心具体后端实现。

用工厂模式（StorageFactory）根据配置创建具体的后端实例——Redis/Memory 作为缓存后端，MySQL/MongoDB/Memory 作为持久化后端。更换存储后端不影响上层业务逻辑。

配置通过 Schema 验证（如 Zod），核心配置项：

- `cache.type`：缓存后端类型（redis / memory）
- `persistent.type`：持久化后端类型（mysql / mongodb / memory）
- `defaultTtl`：缓存默认过期时间
- `enableWriteThrough` / `enableReadThrough`：读穿写穿模式开关

参考代码: examples/session-storage.ts

## 多后端 WAL 架构

当高可用是硬性需求时，在 Redis 缓存方案基础上引入主备架构和预写日志（WAL），确保即使后端故障也不丢失任何消息。

### 三层组件

- **主存储（Primary）**：快速的主数据库用于读写（Redis、PostgreSQL）
- **备份存储（Backup）**：持久的次级数据库用于冗余（SQLite、云数据库）
- **WAL（预写日志）**：内存或持久化的日志，确保写入持久性并支持异步备份

### 工作原理

**写入流程**：

- 主数据库可用时：写入主数据库 → 写入 WAL → WAL 定期异步刷新到备份数据库
- 主数据库不可用时：先查询备份防止重复写入 → 写入备份数据库 → 写入 WAL

**读取流程**：优先从主数据库读取，失败时从备份数据库读取。

**WAL 刷新**：后台工程线程按间隔运行（默认 5 秒），将待处理的 WAL 条目刷新到备份数据库。

### 主备同步

主数据库故障期间，备份数据库自动接管成为"主力"。由于 WAL 的存在，备份数据基本完整。主数据库恢复后，同步脚本定时检查两个数据库的数据差异，补充故障期间缺失的数据。

## 三层架构分层

复杂存储系统的代码组织建议分为三层：

**基础层**：定义 CacheBackend 和 DatabaseBackend 抽象接口，各后端（Redis、PostgreSQL、SQLite、Memory）分别实现。同时由 Manager 统一管理后端的创建和连接生命周期，支持 lazy loading 和 fallback 降级。

**策略层**：将读写行为抽象为可插拔的策略。通过策略工厂（StrategyFactory）创建读策略（主存储优先/缓存增强/故障转移）、写策略（幂等写入/WAL 优先/双写）、健康管理器（熔断器模式）和 WAL 管理器。策略之间有依赖关系——读写策略依赖健康管理器来判断后端是否可用。

**应用层**：StrategicStorageManager 协调多个 StorageManager 实例，注入策略，提供统一的高级接口（get/set/mget/mset/delete）。业务代码只与应用层交互。

这种分层的价值在于：切换存储策略（如从读穿模式改为旁路缓存）不需要修改基础层代码，只需替换策略层的实现。

## 降级策略

当某个存储后端不可用时，系统应该优雅降级而非完全不可用：

- Redis 不可用 → 直接读写数据库（性能下降但功能正常）
- 数据库不可用 → Redis 暂存 + WAL 记录，后续补写（需要恢复机制）
- 全部不可用 → 内存暂存当前会话，警告用户数据可能丢失

Manager 层自动处理降级——连接失败时 fallback 到内存后端，并记录 fallback 状态供监控使用。

## 优化模式

### 旁路缓存（Cache-Aside）

标准的读穿写穿在高并发写入时可能出现缓存与数据库不一致。旁路缓存的核心变化：写入时先写数据库，然后**删除**缓存（而非更新）。下次读取时缓存未命中，自动从数据库加载最新数据。

这样即使删除缓存失败，最多是暂时读到旧数据，TTL 会让它最终过期。避免了并发写入导致的缓存数据覆盖问题。

### 同进程去重（Single-Flight）

防止缓存击穿——热点 key 过期瞬间大量请求同时打到数据库。核心思路：同一时间对同一个 key 只允许一个数据库查询，其他请求复用这个查询的结果。

实现方式：维护一个 `Map<string, Promise>`，新请求先检查是否已有相同 key 的请求在执行，有则复用，无则创建。请求完成后清理 Map 条目。

其他防击穿方案：互斥锁（只允许一个请求加载数据）、提前刷新（TTL 低于阈值时主动刷新）。

## 会话生命周期管理

- **创建**：用户发起首条消息时创建会话
- **活跃**：每次交互更新 last_active 时间戳
- **归档**：超过一定时间不活跃的会话从热存储迁移到冷存储
- **恢复**：用户重新访问已归档会话时，从冷存储加载回热存储

## 注意事项

- Redis 内存有限，设置 TTL 自动清理不活跃会话的缓存
- 消息存储的序列化格式要向前兼容——Agent 的消息结构可能随版本演进
- 记忆存储支持增量更新，避免全量覆写导致并发冲突
- 存储层不应包含业务逻辑，只负责数据的 CRUD 操作
- 生产环境使用持久化 WAL（而非内存 WAL）以实现最大持久性
- 主数据库选择低延迟的（Redis、PostgreSQL），备份选择高耐久的（SQLite、S3、云数据库）
