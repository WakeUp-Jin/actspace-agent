# 压缩策略

上下文压缩分为两个阶段：压缩调度（决定压缩什么、何时触发）和压缩指令（告诉 LLM 如何压缩、保留什么）。

## 压缩调度

压缩调度解决的问题：在将上下文输入给 LLM 之前，判断哪些部分需要压缩。

### 两层压缩机制

**第一层：前置处理——工具输出裁剪**

工具输出是 Token 占比最大的部分。每次工具执行完毕后立即裁剪，而非等到上下文溢出再处理。

裁剪策略按优先级：
- 限制工具最大输出字符数（建议 2000 字符）
- 超过阈值时使用快速模型生成摘要
- 读取工具对大文件采用分层读取：头部 + 中间采样 + 尾部
- 渐进式读取：先读文件前 50 行和摘要，深度需要时再完整加载

对于读取类工具，还有一层极限保护：输出超过 100000 字符时强制截断，防止单个工具调用撑爆后续的摘要模型。

**第二层：兜底处理——会话历史压缩**

当工具输出已经裁剪到健康状态，上下文仍超过阈值时，对会话历史进行压缩。

压缩策略：
- 使用 LLM 进行摘要 + 保留最近 30% 的完整记录
- 如果历史中存在工具调用消息，优先裁剪前 70% 历史中的工具消息（Token 占比最高）
- 压缩后提供历史文件引用，Agent 需要细节时可以搜索回溯

### 触发条件

上下文 Token 使用率达到模型最大窗口的 80%-95% 时触发。具体阈值取决于模型——窗口越大的模型可以设得越宽松。

### 不可压缩的上下文

以下内容永远不参与压缩：系统提示词、用户记忆、Skill 加载的上下文。只有会话历史和工具输出是压缩的操作对象。

## 压缩指令

压缩指令是给执行压缩的 LLM 的提示词，决定压缩质量。

### 设计要点

- 不同模型可能需要不同的压缩指令。Claude 和 Gemini 的压缩指令风格差异较大
- 压缩指令需要明确告诉模型保留什么：关键决策、文件路径、未完成的任务状态、重要的错误信息
- 总结输出需要严格控制长度，否则"摘要"变成"扩写"就本末倒置了
- 压缩结果中应包含足够的上下文锚点，让 Agent 读到摘要后能快速定位到之前的工作进度

### ClaudeCode 的 8 节结构化摘要

ClaudeCode 使用模型生成结构化摘要，将历史消息传递给 LLM，通过 8 个维度提取关键信息：

1. **主要请求和意图**：用户所有明确的请求和意图
2. **关键技术概念**：讨论的技术、框架和方法
3. **文件和代码部分**：检查、修改或创建的文件，包含关键代码片段和修改原因
4. **错误和修复**：遇到的错误及解决方法，特别是用户反馈要求改变做法的情况
5. **问题解决**：已解决的问题和正在进行的排查
6. **所有用户消息**：非工具结果的用户消息（理解反馈和意图变化）
7. **待处理任务**：被明确要求处理但尚未完成的任务
8. **当前工作**：摘要请求前正在进行的具体工作，包含文件名和代码片段

压缩后使用开篇语引导新上下文："上下文已使用结构化 8 节算法压缩。所有必要信息已保留，可无缝继续对话。"

### Gemini 的 5 点 scratchpad 方式

Gemini-cli 使用 scratchpad（草稿本）链式思考来增强提取能力，生成 XML 格式的状态快照。保留 5 个维度：

1. **Overall Goal（总体目标）**：用户的高层目标
2. **Key Knowledge（关键知识）**：必须记住的关键事实、约定和约束
3. **File System State（文件系统状态）**：已创建、读取、修改或删除的文件及其状态
4. **Recent Actions（最近操作）**：最近几次重要操作及其结果
5. **Current Plan（当前计划）**：分步计划，标记已完成的步骤

区别在于：ClaudeCode 侧重完整性（8 个维度），Gemini 侧重密度（5 个维度 + scratchpad 推理增强）。

### 工具消息裁剪

区别于前置的工具输出限制（控制单次工具输出大小），工具消息裁剪是在历史记录中清理过时的工具调用和结果。Claude 团队验证：在接近 Token 限制时自动清除过时工具调用，移除过时内容但保留对话流程，可以有效延长 Agent 运行时间。

实现思路：从历史记录中筛选出工具的输入和输出，判断是全部删除还是保留最近 N 次工具调用，保留系统消息和非工具相关的对话消息不受影响。

### 压缩质量验证

压缩后的摘要应能让一个"新的 Agent"仅凭摘要就理解：当前在做什么任务、已经完成了哪些步骤、下一步应该做什么、有哪些已知的约束或问题。

参考代码: `examples/context-compressor.ts`

## 注意事项

- 不要在固定轮次触发压缩——对话长度差异很大，应基于 Token 使用率动态判断
- 工具输出裁剪是"预防"，历史压缩是"治疗"。预防比治疗更重要
- 压缩过程本身消耗 Token，使用快速低成本模型执行压缩任务
- 保留压缩历史记录到数据库，方便调试和回溯
- Token 压缩的具体执行策略（中间移除、最旧移除、混合策略）见 `mgmt-token-strategies.md`
