# 结构化输出设计

当需要 LLM 按特定格式输出时（JSON、固定字段），有三种方法可以实现，各有适用场景和成本差异。

## 三种实现方法

### 方法一：工具调用辅助

定义一个"假的工具"——不执行任何操作，只利用 function calling 的参数 schema 来约束输出格式。通过 `tool_choice` 强制模型调用该工具，模型输出的参数就是结构化结果。

优势：schema 约束严格，格式可靠性最高，不需要额外解析逻辑。
适用：需要强格式保证的场景，如数据提取、分类标注。

### 方法二：提示词控制 + 结果解析

在提示词中明确要求输出格式（提供 JSON 模板），然后对模型输出进行 JSON.parse 解析。

优势：简单直接，不依赖 function calling 能力。
风险：模型可能输出格式不完全符合预期，需要容错解析。
适用：格式简单、容错度高的场景。

### 方法三：API 级 JSON Mode

部分模型提供 `response_format: { type: "json_object" }` 参数，强制输出合法 JSON。

优势：API 级保证，无需额外工具定义。
限制：不是所有模型都支持；只保证是合法 JSON，不保证 schema 匹配。

## 成本考量

JSON 格式比纯文本格式消耗更多 Token——大量的花括号、引号、key 名称都是"格式税"。在高频调用场景中，考虑是否真的需要 JSON 输出，或者 TSV / 纯文本 + 正则解析是否足够。

经验数据：同样的信息内容，JSON 格式比 TSV 格式 Token 成本高 30-50%。

## 设计建议

- 需要强格式保证时，优先使用方法一（工具调用辅助）。它同时解决了格式约束和字段类型验证
- 方法一的"假工具"可以复用——定义一组通用的输出格式工具（如 `output_json`、`output_list`），在不同场景中切换
- 结构化输出的 schema 定义尽量精简，字段描述清晰，减少模型的"猜测成本"
- 对于分类任务，使用 enum 约束字段取值范围比在 description 中列举更可靠

参考代码: `examples/structured-output.ts`

## 注意事项

- 不要在高频内部调用（如压缩、摘要）中使用 JSON 输出——纯文本摘要更省 Token
- 工具调用辅助法中，tool_choice 设为具体工具名可以强制使用，设为 "auto" 则模型可能跳过
- 解析失败时的降级策略很重要：重试一次、正则提取关键字段、返回原始文本让上层处理
