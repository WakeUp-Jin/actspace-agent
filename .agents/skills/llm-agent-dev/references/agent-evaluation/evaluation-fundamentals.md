# 评估基础

评估是 Agent 开发中最容易被忽视但最关键的环节。没有评估体系，提示词优化就变成了凭感觉的艺术而非可量化的工程——你无法判断一次改动到底是改进还是退化。

## 为什么评估值得投入

Agent 的输出具有不确定性，同样的输入可能产生不同的执行路径和结果。评估将这种不确定性纳入可衡量的框架，带来四个核心收益：

1. **迭代式优化有据可依**：V2 版本的提示词是否真的比 V1 更好？不再依赖主观感受
2. **变更回归检测**：最新的提示词更新是否导致了性能下降？在上线前发现问题
3. **模型切换决策**：更换为更高级/更低成本的模型时，是否能维持当前性能？
4. **边界能力探索**：准确的评估帮助团队发现模型的能力边界，为释放模型潜力提供方向

## 评估的四个组成部分

一个完整的评估方案由四个要素构成：

| 要素 | 说明 | 关键要求 |
|------|------|----------|
| 示例输入 | 给模型的指令或问题 | 准确代表实际使用中遇到的各类场景 |
| 标准答案 | 正确的或理想的回答 | 需要领域专家参与编写，确保准确性 |
| 模型输出 | LLM 基于输入实际生成的回答 | 这是与标准答案对比的评估对象 |
| 分数 | 定量或定性的表现评价 | 评分方法根据任务性质选择 |

准备至少 100 组示例输入和标准答案，低于这个数量评估结果的参考价值有限。编写标准答案的人工成本虽高但是一次性的，编写好的数据集可以长期复用。

## 评估流程

评估不是跑一次就结束的动作，而是一个带有过拟合检测的迭代闭环：

1. 准备测试用例（示例输入 + 标准答案）
2. 将用例拆分为两组——80% 作为**开发集**，20% 作为**留存集**
3. 在开发集上测试当前提示词/Agent，根据结果迭代优化
4. 开发集表现达标后，用留存集验证泛化能力
5. 留存集与开发集的准确率差距控制在 10% 以内——超过说明提示词对开发集过拟合，需回到步骤 3 重新调整

拆分为开发集和留存集的目的是防止"在训练数据上表现完美、在新数据上一塌糊涂"的情况。这个思路来自机器学习中的训练集/验证集划分。

除准确率外，还可以关注两个辅助指标：

- **边缘案例覆盖**：极端输入下模型的表现
- **响应延迟**：模型的响应时间是否满足产品需求

## 三种评分方法

优先选择代码评分和模型评分，人工评分成本高、周期长，作为最后手段。

### 代码评分

适用于有明确客观标准的任务。一旦设置完成，可以快速、一致地处理大规模评估。

常见形式：
- **精确字符串匹配**：模型输出必须与标准答案完全一致
- **关键词存在性检查**：输出是否包含特定关键词或短语
- **正则表达式匹配**：检查复杂的文本模式

参考代码: examples/evaluation-scoring.ts

### 人工评分

适用于需要主观判断的任务（语气、创造力、复杂推理）。在评估开放式任务或依赖微妙语境的场景中不可替代，但耗时且成本高，在不同评分者之间可能存在一致性问题。

常见形式：
- **专家评审**：领域专家评估准确性和深度（如律师审查合同条款、医生评估诊疗建议）
- **用户体验小组**：评估输出的清晰度、帮助性和参与度

### 模型评分

用另一个 LLM 来评估输出质量，介于代码评分和人工评分之间——比代码评分能处理更复杂的评估标准，比人工评分更快且更具可扩展性。

为评估模型编写提示词时，包含四个要素：
- 原始提示或问题
- 要评估的模型输出
- 一套评估标准或指南
- 如何评分的具体说明

常见的评估标准示例：
- 回应在事实上是否准确？
- 回复是否恰当地回答了问题？
- 输出与品牌/风格指南的契合度如何？
- 回应是否过度道歉或过度引用自身上下文？

注意评估模型的定位：多数 LLM 默认是友好的，倾向于给高分。在评估提示词中明确要求"客观中立，不道歉，不使用道歉语言"，否则评分偏见会系统性地拉高结果。

## 评估驱动开发

将评估融入日常开发流程，形成类似 TDD 的工作方式：

1. 修改 Agent 的上下文/工具/提示词
2. 运行评估集
3. 对比改动前后的分数
4. 确认是改进后再合并

## 注意事项

- 不要追求 100% 通过率——Agent 输出有随机性，目标是"显著优于基线"
- 评估集初期 10-20 个用例起步，逐步扩展到 100+ 组
- 评估运行的持续成本需要控制——使用模型评分会产生 API 调用费用，尽量构建快速且经济的评估体系
- 评估指标要和实际用户体验挂钩，避免"指标很好但用户不满意"
