# 评估器实现

本文指导如何构建一个 Agent 评估器——不是理论上"评估什么"，而是工程上"怎么评估"。核心思路：通过事件系统采集 Agent 的实际执行行为，与预定义的期望行为对比，产出结构化的评估结果。

## 评估器架构

评估器由四个模块组成，各司其职：

1. **测试数据集**：定义"喂给 Agent 什么输入"和"期望 Agent 怎么做"
2. **事件系统**：在 Agent 执行过程中采集行为数据（调用了哪些子 Agent、使用了哪些工具）
3. **评估函数**：将采集到的实际行为与期望行为对比，产出评估结果
4. **运行器**：串联以上三者——遍历测试用例、重置采集器、调用 Agent、收集结果、运行评估

参考代码: examples/evaluation-system.ts

## 测试数据集设计

每个测试用例包含四个字段：

| 字段 | 作用 |
|------|------|
| `id` | 唯一标识，便于定位失败用例 |
| `description` | 可读的用例描述 |
| `input` | 用户输入，直接喂给 Agent |
| `expected` | 期望行为——Agent 应调用哪些子 Agent、每个子 Agent 应使用哪些工具 |

### 期望行为的粒度

对于单 Agent 系统，期望行为主要是工具调用列表——Agent 是否选择了正确的工具。

对于多 Agent 系统，还需要验证主 Agent 是否正确协调了子 Agent：

- `expected.agents`：期望调用的子 Agent 列表
- `expected.tools`：每个子 Agent 期望调用的工具映射

这种设计的原因是：多 Agent 架构下，"调度正确的子 Agent"和"子 Agent 使用正确的工具"是两个独立的失败点，需要分别评估。

### 测试用例覆盖策略

设计测试用例时覆盖以下维度：

- **单工具场景**：验证基础的工具选择能力
- **多工具组合**：验证复杂任务下的工具编排
- **跨 Agent 协作**：验证主 Agent 的调度决策
- **边缘情况**：模糊输入、工具间有重叠能力的场景

## 事件系统

为什么需要事件系统而非让 Agent 函数直接返回执行情况？在简单 Agent 中确实可以直接返回。但当 Agent 架构变复杂——大量工具调用、多智能体协作、嵌套调用链——发布-订阅模式的事件系统是更可扩展的方案。

### 核心设计

采用单例 EventBus，合并事件发射和数据收集两个职责：

- **事件类型**：`agent:call`（子 Agent 被调用）、`tool:call`（工具被调用）、`edit:complete`（编辑完成）
- **数据收集**：内部监听所有事件，自动汇总为结构化数据
- **生命周期**：每个测试用例执行前调用 `reset()` 清空状态，执行后调用 `getData()` 提取采集数据

### 在 Agent 中嵌入事件采集

在 Agent 代码的关键节点触发事件：

- Agent 入口处触发 `agent:call`
- 每次工具调用前触发 `tool:call`，携带 Agent 名称和工具名称

这种侵入式采集的好处是精确——你能捕获 Agent 运行时的每一个关键决策点。缺点是需要在 Agent 代码中埋点。对于评估目的，这种权衡是值得的。

## 评估函数

评估函数将采集到的实际数据与期望行为对比，产出结构化的评估结果。

### 对比逻辑

分两个维度独立评估：

1. **Agent 调用对比**：计算遗漏的 Agent（期望调用但未调用）和多余的 Agent（未期望但被调用）
2. **工具调用对比**：对每个 Agent，计算遗漏的工具和多余的工具

两个维度都通过时用例才算通过。这种分离的好处是：当用例失败时，能精确定位是"调度了错误的子 Agent"还是"子 Agent 内部选错了工具"。

### 结果输出

评估结果包含：
- `passed`：是否通过
- `agentMatch` / `toolMatch`：分维度的通过状态
- `details`：每个维度的 expected/actual/missed/extra 明细

## 运行评估

将以上模块串联为完整的评估流程：

1. 遍历测试用例
2. 每个用例执行前重置事件总线
3. 将用例的 `input` 喂给 Agent
4. Agent 执行完毕后，从事件总线提取采集数据
5. 调用评估函数对比实际行为与期望行为
6. 汇总所有用例的结果，计算总体通过率

由于 LLM 输出的随机性，同一用例建议运行 3-5 次取平均或多数投票结果。

## 注意事项

- 事件系统使用单例模式，确保在多 Agent 嵌套调用时所有事件都汇聚到同一个收集器
- 每个测试用例之间必须重置采集状态，避免上一个用例的数据污染下一个
- 评估函数中的工具列表对比需要去重——同一工具被多次调用只计为调用了一次
- 评估器本身的代码也需要测试，尤其是对比逻辑中的边界情况（空列表、未知 Agent 等）
