# 定时任务和KAIROS模式

Agent 运行空间是让 Agent 从"被动响应"变为"主动运行"的基础设施。包括定时任务系统和 KAIROS 后台运行模式。

## 定时任务系统

让 Agent 定时执行任务并推送结果。核心设计：Agent 生产任务，轮询调度器消费任务。

### 三个核心组件

**1. 任务存储**

使用 JSON 文件或数据库存储定时任务。每个任务包含：
- id：唯一标识
- cron：cron 表达式（统一表示一次性和循环任务）
- prompt：要执行的任务指令
- recurring：是否循环执行
- lastFiredAt：上次执行时间

**2. 轮询调度器**

每秒检查任务列表，达到触发条件的任务开始执行。性能优化：每秒读缓存，每 5 秒重新读取存储文件。

**3. 任务管理工具**

提供给 Agent 三个工具：创建任务（cron_create）、查询任务（cron_list）、删除任务（cron_delete）。Agent 通过这些工具自主管理定时任务。

### 任务创建方式

- 自然语言输入：用户说"每天早上 9 点检查邮件"，LLM 解析为 cron 表达式
- 结构化指令：通过 /loop 命令精确指定间隔和任务内容

### /loop 指令解析规则

/loop 指令支持三种匹配方式（按优先级依次匹配）：

1. **前置间隔**：`/loop 5m 检查构建状态` → 每 5 分钟执行一次"检查构建状态"
2. **尾部 every**：`/loop 检查构建状态 every 5m` → 同上，间隔写在末尾
3. **无显式间隔**：`/loop 检查构建状态` → 使用默认间隔（通常为 10 分钟）

解析器将间隔转换为 cron 表达式后调用 cron_create 工具。

## KAIROS 模式

KAIROS（源自古希腊语"恰当的时机"）让 Agent 从交互式转变为常驻后台运行。

### 核心思想

将 Agent 处理的所有任务统一放入队列。Agent 在后台持续消费队列，不打断用户的工作流。在"恰当的时机"主动运行——当用户不活跃时处理积压任务，当有紧急事项时主动通知。

### 事件驱动机制

KAIROS 不是传统的 while 循环，而是事件驱动的。核心触发器是 **tick 消息**——一条格式为 `<tick>2025-01-01 14:20:15</tick>` 的 user 消息，注入到 Agent 的上下文中。Agent 将其视为"你醒了，现在干嘛？"的信号。

tick 消息的设计意义：
- 将"自治循环"的控制权交给基础设施（而非 LLM 自行决定何时运行）
- 每个 tick 携带当前时间戳，让 Agent 能感知时段
- 避免了 while(true) 的死循环风险，每次 tick 都是一次完整的 LLM 调用

### 任务队列设计

所有消息源统一入队，按优先级排序：

| 优先级 | 来源 | 说明 |
|--------|------|------|
| 1 (最高) | user | 用户直接输入 |
| 2 | cron | 定时任务触发 |
| 3 (最低) | tick | KAIROS 自治唤醒 |

队列处理器串行消费——同一时刻只有一个任务在执行，天然互斥，无需加锁。消息分发规则：
- user / cron 消息 → 交给主 Agent（Agent.run()）
- tick 消息 → 交给 KAIROS 专用执行器（KairosRunner.handle_tick()）

### KairosRunner：独立执行器

KairosRunner 与主 Agent 并列，有独立的上下文管理：
- **系统提示词**：替换为 KAIROS 专用提示词（不是追加，而是完全替换）
- **对话历史**：仅保留最近 N 轮 tick 交互（不加载用户的对话历史）
- **长期记忆**：与主 Agent 共享（用户画像、偏好、指令等）
- **工具集**：与主 Agent 共享 + 额外的 Sleep 工具

### Sleep 工具

Sleep 是 KAIROS 模式的核心工具，让模型自主决定何时以及休眠多长时间。

参数：`seconds`（休眠秒数）。模型根据当前任务状态决定调用时机和时长：
- 没有有意义的工作可做 → 必须调用 Sleep（不能只回复"没事做"）
- 等待慢进程 → 多睡一会儿
- 积极迭代中 → 少睡一会儿

Sleep 时长被限制在 `[min_sleep_seconds, max_sleep_seconds]` 范围内。KairosRunner 在处理完 tick 后从 LLM 最近的工具调用记录中提取 Sleep 工具的参数来确定实际休眠时长。如果 LLM 未调用 Sleep，则使用默认值。

Sleep 与定时任务的区别：定时任务的间隔由用户预设（固定 cron），Sleep 的间隔由模型在运行时动态决定——这是 KAIROS 比定时任务更"主动"的关键所在。

### 尾递归调度

KAIROS 的执行流程采用尾递归调度模式——每条消息处理完后，在"尾部"决定是否注入下一个 tick：

```
dequeue → dispatch → tail_dispatch
                        ├── user/cron 完成 → 队列空 → 立即注入 tick（不 sleep）
                        └── tick 完成 → 可中断 sleep → 队列仍空 → 注入 tick
                                          └── sleep 被中断（新消息入队）→ 跳过 tick，回到 dequeue
```

关键规则：
1. user/cron 消息处理完后，如果队列为空，**立即**注入 tick（让 Agent 马上进入后台模式，不需要等待）
2. tick 消息处理完后，先执行可中断的 sleep，sleep 结束且队列仍为空，注入下一个 tick
3. sleep 期间如果有新消息入队（通过 wake_event 信号），中断 sleep，跳过 tick 注入，直接处理新消息
4. 连续 tick 错误超过阈值（如 5 次），触发熔断冷却（如暂停 60 秒）

### 与交互模式的切换

KAIROS 的消息队列天然支持模式切换。用户发起对话时，user 消息以更高优先级入队，打断 sleep 并优先被处理——Agent 自动切换到"交互模式"。对话结束后队列为空，tail_dispatch 注入 tick，Agent 回到"后台模式"继续自治运行。

这种设计让用户获得"Agent 一直在工作"的体验，同时不干扰实时交互。

### KAIROS 系统提示词

KAIROS 系统提示词定义了 Agent 在自治模式下的行为准则，包含 7 个指令段：

**Pacing（节奏控制）**：用 Sleep 工具控制两次行动之间的等待时长。如果某个 tick 上没有有用的事可做，必须调用 Sleep，不能只回复"没事做"。

**First wake-up（首次唤醒）**：新会话的第一次 tick，简短问好并询问用户意图。不主动探索代码库或做修改——等用户给方向。

**Subsequent wake-ups（后续唤醒）**：找有用的事做。面对模糊情况时像好同事一样主动调查、降低风险、建立理解。不重复已问过的问题，不絮叨计划——直接做。如果确实无事可做，立即调用 Sleep。

**Staying responsive（保持响应）**：用户活跃时频繁检查消息，把实时对话当结对编程对待。优先回复用户，而不是继续后台工作。

**Bias toward action（倾向行动）**：凭最佳判断直接行动，不请求确认。读文件、跑测试、做代码修改——全部无需请示。犹豫时选一个方案直接走。

**Be concise（保持简洁）**：文字输出聚焦于需要用户输入的决定、里程碑状态更新、改变计划的错误。不逐步叙述，能一句话说完不用三句。

**Terminal focus（终端焦点）**：根据用户是否在看终端调整自主程度。未聚焦时大胆自主（做决定、提交、推送），聚焦时更协作（抛出选择、大改动前询问）。

## 运行空间的整体视角

Harness Engineering 的目标是为 Agent 搭建完整的运行环境：

- **能力结构**：工具系统定义了 Agent 能做什么
- **协作机制**：多智能体和任务队列定义了 Agent 如何与外部协作
- **反馈闭环**：评估系统和记忆更新确保 Agent 持续改进
- **主动性**：定时任务和 KAIROS 让 Agent 不只是被动等待指令

运行空间随着模型的升级应该逐渐变化——模型越强，运行空间的约束可以越松，给模型更大的自由度。

## 注意事项

- 定时任务的 cron 解析要覆盖常见的自然语言表达，不要只支持标准 cron 格式
- KAIROS 模式下的任务执行结果推送不要太频繁，避免打扰用户。可以批量汇总后定时推送
- 后台任务执行失败时的重试策略要谨慎——避免错误任务反复执行消耗资源
- 任务队列需要持久化，防止进程重启导致任务丢失
- Sleep 工具的时长范围要合理设置——太短浪费 API 调用，太长降低响应速度
- KAIROS 的 tick 错误要有熔断机制，连续失败时冷却而非继续重试
- KairosRunner 的对话历史要控制长度（如最近 10 轮），避免上下文窗口溢出
