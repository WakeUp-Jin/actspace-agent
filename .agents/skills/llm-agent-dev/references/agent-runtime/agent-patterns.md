# Agent 形态

Agent 的"形态"决定了它如何组织执行流程。选择哪种形态取决于任务的复杂度和分解方式。

## 单智能体系统

一个 LLM + 一组工具 + 一套提示词。像一个独立的专业人士，自行收集数据、做出决策、执行行动。

核心执行循环：LLM 流式输出 → 检查是否有 tool_calls → 有则通过 ToolScheduler 调度执行 → 结果回填上下文 → 再次调用 LLM → 循环直到 LLM 不再产生工具调用。

适用场景：任务边界清晰、工具数量可控（<30）、不需要并行探索的场景。

单智能体的核心优势在于上下文的天然连贯性——所有的决策历史、工具调用结果、中间推理都在同一个上下文窗口中，模型可以完整地看到整个执行过程。这在涉及"写入"操作（代码编辑、文件修改等需要理解前后依赖的任务）时尤为关键。

## 多智能体系统

多个独立 Agent 协作处理复杂任务。每个子 Agent 有专属的上下文空间、工具集和提示词。

### 监督者模式（Supervisor）

一个主 Agent 协调多个子 Agent。主 Agent 控制任务分配和结果汇总，子 Agent 执行具体子任务。

适用：任务可以明确分解为独立子任务，且需要统一的决策者。

### 群体模式（Swarm）

多个 Agent 根据各自特长动态交接控制权。系统记住最后活跃的 Agent，确保上下文正常传递。

适用：任务需要不同专业领域的知识，且流转路径不固定。

### 层级化模式（Hierarchical）

监督者模式的扩展——多层管理结构。每个团队有主管，主管向经理汇报。

适用：大型复杂任务，需要多层分解和多团队协作。

### 自定义工作流模式（Custom Workflow）

每个 Agent 只与特定的一部分 Agent 通信，流程部分确定、部分灵活。区别于监督者模式的"中心化调度"，这种模式下各节点间有直接的通信路径。

适用：存在明确的流水线阶段，但每个阶段内部又需要灵活决策的场景（如代码生成 → 审查 → 测试的固定流程，每个阶段由专门的 Agent 负责）。

## 子智能体实现：AgentTool 模式

在监督者模式的实际实现中，最常见的做法是将"启动子智能体"封装为一个工具（AgentTool）。主智能体通过 tool_calls 调用该工具来创建并执行子智能体。

### 工作流程

```
主智能体 LLM → tool_call: Agent(prompt, description, subagent_type)
  → AgentTool 创建子智能体（独立 ID / 上下文 / 工具集 / 系统提示词）
    → 子智能体执行独立的 LLM-Tool 循环
    → 返回结构化结果（text + usage + toolUseCount）
  → 结果作为 tool_result 回填主智能体上下文
主智能体 LLM 继续推理（参考子智能体的结果）
```

### 核心设计要点

**独立上下文**：子智能体有全新的消息序列，不继承主智能体的对话历史。主智能体的任务描述（prompt）作为子智能体的首条 user 消息。

**独立工具集**：子智能体的工具集是主智能体工具集的子集，通过过滤规则（按 agent type 分配、移除不允许的工具）保证子智能体只能访问其职责范围内的能力。

**独立系统提示词**：不同类型的子智能体（explore、general-purpose、plan 等）有不同的系统提示词，专注于各自的任务特征。

**前台/后台切换**：
- 同步模式：主智能体阻塞等待子智能体完成，结果直接作为 tool_result 返回
- 异步模式（`run_in_background=true`）：子智能体在后台执行，主智能体继续处理其他工作。子智能体完成后通过通知消息异步回传结果

**级联取消**：主智能体的 AbortController 创建子级 controller，主智能体被取消时子智能体自动中止。

### 异步通知格式

后台子智能体完成后，通过结构化消息通知主智能体：

```xml
<task_notification>
  <task_id>a1b2c3d4</task_id>
  <output_file>/path/to/transcript</output_file>
  <status>completed</status>
  <summary>Agent "探索代码库结构" completed</summary>
  <result>子智能体的最终回复文本</result>
  <usage>
    <total_tokens>15000</total_tokens>
    <tool_uses>8</tool_uses>
    <duration_ms>45000</duration_ms>
  </usage>
</task_notification>
```

参考代码: `examples/agent-loop.ts`

## 单智能体 vs 多智能体

### 上下文挑战

多智能体最大的问题是上下文中断，具体表现为两类场景：

**主 → 子 中断**：主 Agent 的完整上下文无法全量传递给子 Agent。子 Agent 拿到的是一段精炼的任务描述，但丢失了主 Agent 的推理过程、之前子 Agent 的执行细节、以及用户对话中隐含的约束条件。如果任务描述不够精确，子 Agent 容易偏离预期。

**子 → 子 中断**：子 Agent B 不了解子 Agent A 的执行过程和中间状态。当 A 的输出格式不符合 B 的预期、或 A 做出了影响 B 的隐式假设时，就会出现协作失败。例如：A 修改了文件结构但 B 不知道，A 输出的数据格式与 B 解析逻辑不匹配。

解决策略：
- 主 Agent 向子 Agent 传递精炼且完整的任务描述（包含必要的约束和上下文摘要）
- 子 Agent 返回结构化的执行摘要（而非全部中间步骤）
- 必要时通过共享存储传递关键中间状态
- 使用一致的输出格式约定，减少子 Agent 间的格式不匹配

### 单智能体的优势

- **写入操作更可靠**：代码编辑、文件修改等需要理解前后依赖的操作，在单一上下文中完成更准确，不存在"子 Agent 不了解前序修改"的问题
- **上下文连贯**：所有推理、决策、工具调用结果都在同一个窗口中，无需额外的协调机制
- **开发成本低**：不需要设计子 Agent 间的通信协议、结果汇总策略和错误恢复机制

### 多智能体的优势

- **读取操作可并行化**：研究搜索、代码审查等"只读"任务可以并行分派给多个子 Agent，显著缩短总执行时间
- **解决工具过载问题**：当工具数量超过 30 时，单智能体的工具选择准确率明显下降。多智能体通过为每个子 Agent 分配精简的工具子集来解决这个问题
- **模型分级使用**：协调者使用更强的模型（如 Opus）做全局决策，子智能体使用更快更便宜的模型（如 Sonnet）执行具体任务。这种组合的整体效果可以优于统一使用强模型

### 多智能体改善方法

1. **精确的任务描述**：子 Agent 的提示词要包含充分的上下文、明确的输出格式要求和成功标准
2. **合理的工具分配**：每个子 Agent 只分配其任务所需的工具，避免工具过载。同时工具的输入/输出要有明确的 schema
3. **从宽到窄的探索策略**：先让多个子 Agent 宽泛探索不同方向，再收敛到最优路径深入执行
4. **引导推理过程**：通过提示词引导子 Agent 先规划再执行，减少盲目试错
5. **观察和调试优先**：为每个子 Agent 建立可观测性（日志、执行轨迹、token 消耗），优先解决可观测性问题再优化效果

### 渐进式构建策略

推荐的演进路径：

1. **小模块单智能体**：先将任务拆解为可独立完成的小模块，每个模块用单智能体处理
2. **引入多智能体**：当发现某些模块可以并行化、或工具集过大时，将这些模块拆分为多个子 Agent
3. **收敛为完整单智能体**：随着模型能力提升（更大的上下文窗口、更好的工具选择），逐渐将子 Agent 合并回单智能体

这个路径的核心逻辑：多智能体是当前模型能力限制下的工程妥协，不是目标架构。当模型足够强时，单智能体的上下文连贯性优势会超过多智能体的并行化收益。

## 执行循环设计

执行循环采用纯函数 `runAgentLoop` 实现，不持有任何状态，通过参数接收依赖，通过事件回调通知外部。

核心是双层 while 循环：
- **内层**：处理 tool calls + steering 消息。每轮流式调用 LLM → 有 tool_calls 则通过 ToolScheduler 执行 → 结果回填上下文 → 继续循环。支持 parallel/sequential 两种工具执行模式。
- **外层**：处理 follow-up 消息。内层结束后（agent 本来要停了），检查是否有排队的后续消息，有则注入并重新进入内层。

终止条件：LLM 不再产生 tool_calls 且无 steering/follow-up 消息，或 `shouldStopAfterTurn` 回调返回 true，或 AbortSignal 被触发。无硬编码的最大迭代次数——安全阀通过 `shouldStopAfterTurn` 回调实现（接收 turnIndex，调用者自行决定上限）。

事件系统覆盖四个层级：agent（start/end）、turn（start/end）、message（start/delta/end）、tool（start/end），通过 emit 回调驱动，使构建响应式 UI 成为可能。

Agent 类是极简入口——持有 llm/contextManager/scheduler 的引用，提供 `run(userText)` 和 `abort()`，不做状态管理。子智能体通过独立的 `createSubAgentTool` 工厂函数创建为普通工具。

参考代码: `examples/agent-loop.ts`

## 注意事项

- 单智能体优先——除非明确需要并行探索或任务分解，否则单体 Agent 更简单、调试更容易
- 多智能体的成本是单体的 N 倍（每个子 Agent 都有独立的 LLM 调用），权衡性能收益和成本增加
- 子智能体的工具集要严格控制——不要让只读搜索型 Agent 拥有写入工具
- 异步子智能体的通知消息要包含足够的上下文（状态、摘要、用量），让主 Agent 能基于通知做出正确的后续决策
- 多智能体的可观测性（日志、执行轨迹）是调试的前提，先建立可观测性再优化效果
